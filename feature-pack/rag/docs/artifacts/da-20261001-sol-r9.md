## 발견 결함

### R9-M1 — 짧은 예외 값과 캐시된 stream 버퍼가 값 비노출 경계를 통과한다

- 심각도: **major**. r8의 출력 보호 계약이 완전히 닫히지 않은 잔존 항목이다.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/tick.py:194-210` (_safe_code/_error_fields), `:214-229` (component 출력 폐기·복원), `:268-275` (CLI 호출/오류 전달).

**짧은 예외 값:** 실제 합성 runtime/CLI의 bridge publish만 짧은 대문자·underscore 형태의 합성 메시지로 RuntimeError를 던지게 했다. 각 단어는 24자 이하이고 16자리 hex 연속도 아니다. 관찰은 exit 40, 타입 RuntimeError이며 **메시지 값 자체가 출력 JSON의 code와 tick 로그에 남음**이다. 이 값은 정상 이유 코드의 등록 목록에서 온 것이 아니다. 문자열 형태만으로 알려진 코드와 예외 데이터 값을 구별할 수 없으며, 짧은 원문 값/식별자도 그 형태를 가질 수 있다. 합성 메시지 값은 판정서에 적지 않는다.

**캐시된 stream 버퍼:** 독립 자식에서 context 진입 전 sys.stdout/sys.stderr 객체를 보관한다. 실제 _discard_component_output 안에서 그 기존 객체에 합성 marker를 write하되 즉시 flush하지 않는다. 일반 print와 os.write는 숨겨졌고 FD/stream의 목적지도 정상 복원됐다. 그러나 context가 끝난 뒤 공개 후속 출력·정상 종료로 기존 버퍼가 flush되자 **marker가 stdout/stderr에 나타났다.** 정상 yield와 내부 RuntimeError 예외의 두 경로에서 동일했다. launchd의 파일/pipe 같은 비대화형 stream에서 버퍼링된 출력의 수명이 fd 복원보다 길 수 있다.

- 의미: 저장소 64hex 차단과 즉시 fd 쓰기 차단은 통과하지만, 임의 예외 값을 코드로 신뢰하는 경계와 버퍼의 처리 순서가 아직 값 비노출을 보장하지 않는다. FD 복원이 실패했다고 표현하지 않는다. **복원은 성공했고, 보류된 값이 복원 후 나오므로 문제다.**
- 범위: 실제 운영 bridge나 실제 키/본문의 누출을 관찰한 것은 아니다. 허용된 합성 callback·context 경계의 값과 버퍼 동작을 확인했다. 캐시된 standard stream 객체는 새 파일/다른 임의 fd로 일부러 우회한 경우가 아니다.
- 수정 방향: 코드 형태 휴리스틱 대신 알려진 정적 이유 코드/정제 타입으로 오류 메타데이터를 제한한다. 원래 stdout/stderr 목적지를 복원하기 전 관련 출력 버퍼의 수명·폐기를 처리해야 한다. 두 경로를 함께 닫아야 한다.

### R9-M2 — LOG_DIR_UNSAFE로 거부한 symlink 디렉터리에서 오류 로그 쓰기·prune를 실행한다

- 심각도: **major**.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/tick.py:246-252` (선택 경로 저장·symlink 거부), `:295-299` (거부 후 같은 경로로 append_log), `:135` 및 `:148-152` (파일 쓰기·prune).
- 재현: 선택한 임시 log-dir 자체를 다른 임시 디렉터리로 향하는 symlink로 만든다. 대상에 현재 날짜의 로그와 15일 지난 날짜 로그를 합성 텍스트로 준비한다. valid fixture config와 실제 tick.main을 호출한다.
- 관찰: **exit 20, LOG_DIR_UNSAFE**지만, 거부한 링크를 통해 대상의 현재 로그에 오류 JSON을 append했다. 별도 같은 조건 검증에서 **대상의 오래된 합성 로그도 unlink**했다. key/runtime 락은 생성되지 않아 작업은 거부됐지만, 마지막 오류 로깅만 거부된 경로를 계속 사용했다.
- 원인: path를 거부한 뒤에도 log_dir 변수가 None이 아니며, append_log는 directory 성분의 안전성 판단을 모른다. O_NOFOLLOW는 날짜 파일의 마지막 성분만 보호한다.
- 범위: Nano가 밝힌 상위 ancestor symlink 미검사와 구분한다. **여기서는 선택한 log-dir leaf 자체를 main이 검사하고 UNSAFE로 거부했다.** 그 판단을 오류 처리에서 무시하는 문제다. 외부 대상은 전부 이 테스트가 만든 임시 디렉터리/텍스트 로그였다. 운영 파일을 쓰거나 삭제하지 않았다.
- 수정 방향: 오류 보고는 검증된 로그 자원만 사용해야 한다. 거부된 경로를 tail 로깅에 다시 넘기지 않고, 로그 쓰기·회전·prune를 같은 검증된 디렉터리 경계에 묶어야 한다.

### R9-m1 — 출력 폐기 준비 실패 후 stdout/stderr 복제 fd가 남는다

- 심각도: **minor**.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/tick.py:218-220`.
- 재현: os.dup의 실제 반환 fd를 기록하고, 두 dup 이후 /dev/null의 os.open만 EMFILE OSError로 실패시킨다. 실제 context를 실행한다.
- 관찰: 준비 예외 후 **복제 fd 2개가 여전히 열려 있다.** null open이 try/finally보다 앞이라 saved를 닫는 경계가 아직 시작되지 않았다. 실제 main 경로에서도 exit 50/OSError이며 runtime lock은 정상 해제됐다. stdout/stderr redirection은 시작 전이므로 그 목적지가 바뀐 경우로 주장하지 않는다.
- 의미: standalone 틱 종료 시 OS가 회수하지만, in-process 호출/자원 압박의 실패 경로에서 확보한 fd를 정리하지 않는다.
- 정리: 관찰한 복제 fd만 probe에서 닫았다. 원래 fd 1·2와 외부 프로세스는 건드리지 않았다.
- 수정 방향: 각 자원 확보 단계부터 예외 해제 경계를 적용해야 한다.

### R9-m2 — os.write가 일부 바이트만 써도 로그 성공으로 처리한다

- 심각도: **minor**.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/tick.py:143`.
- 재현: 독립 테스트 자식에만 파일 크기 limit 12바이트를 설정하고 SIGXFSZ를 무시한다. 실제 append_log로 16바이트 JSON 줄(개행 포함)을 임시 일반 파일에 쓴다. disk-full을 실제로 만들지 않았다.
- 관찰: 자식은 exit 0, append_log가 예외 없이 반환했지만 **로그 크기는 12바이트이며 개행이 없다.** 실제 OS의 partial write 반환을 확인한 것이다.
- 원인: os.write의 반환 바이트 수를 검사하거나 남은 바이트를 쓰지 않는다. caller가 사용하는 log_write_failed 경로에도 들어가지 않아 불완전 JSON 줄을 성공 기록처럼 남긴다.
- 의미: best-effort 로그 실패가 비즈니스 exit을 바꾸지 않는 기존 정책은 유지할 수 있지만, 실패/불완전 기록을 감지해야 한다. 실제 runtime 데이터 손상이나 상한 초과를 주장하지 않는다.
- 수정 방향: 전체 바이트 완료를 확인하고 완료 불가 시 안전한 로그 실패 보고 경계로 넘겨야 한다.

## 새 경계·운영 영향 판단

1. **정상 코드 과차단:** consumer source의 _error/예외 constructor에 선언된 이유 코드 literal 중 기존 _CODE 형태인 396개를 _safe_code와 대조해 **추가 차단 0**이었다. 앱의 Error 클래스 11개도 type 검사를 통과했다. 정상 233개 회귀도 통과했다. 동적/외부 코드 전부를 검증한 것은 아니며, 이 정상 통과가 임의 문자열의 값 안전성을 증명하지는 않는다.
2. **정상 파일 열기:** 신규 symlink leaf 거부·일반 로그 생성·회전·0600 파일이 새 테스트를 통과했다. 직접 RDWR로 연 임시 FIFO도 일반 파일 검증에서 즉시 거부돼 대기하지 않았다. 선택한 디렉터리를 거부한 오류 처리의 R9-M2는 별도다.
3. **기존 권한:** 기존 log-dir=0755, tick.lock=0644를 준비한 후 정상 main은 exit 0이고 그 모드는 그대로였다. 0700/0600은 새로 생성하는 대상의 정책이며 기존 권한을 보정하지 않는다. 실제 운영 디렉터리/상위 권한은 금지 범위여서 확인하지 않았다. 상위 ancestor symlink까지 검사하지 않는 알려진 범위도 이번에 해결된 것으로 표현하지 않는다.
4. **fd/락 해제:** 정상·실제 callback 오류·context 내부 예외 이후 FD 1·2가 원래 목적지로 돌아오는 것을 자식 출력으로 확인했다. context 준비 실패 때도 main의 lock finally는 실행돼 다른 fd의 nonblocking flock 획득이 성공했다. stdout 복제 fd 준비 정리는 R9-m1로 남는다. 테스트가 락을 보유한 채 끝나거나 배경 대기로 남지 않았다.
5. **프록시·CA env:** HTTPS_PROXY와 SSL_CERT_FILE을 요구하는 가짜 op는 full fixture env로 직접 호출할 때 유효한 키를 반환(exit 0)하지만, 새 wrapper에서는 그 변수가 빠져 **exit 30/key_error**였다. parent env는 그대로다. 이는 Nano가 설명한 의도된 허용목록 범위이며 값 상속 방어의 실패로 세지 않았다. **운영 판단:** op의 연결이 이런 변수에 의존하는 환경에는 현 정책의 호환성이 보장되지 않고, 다음 틱도 같은 입력/정책이면 자동 복구되지 않는다. 직접 네트워크/시스템 trust store를 쓰는 환경과 구분해야 한다. 실제 op 호출·운영 설정 확인이 금지돼 이 호스트의 필요 여부는 판단하지 않았다. U2 활성화 단계에서 필요한 네트워크 환경과 forwarding 정책을 확정해야 한다.
