## ① R11-m3: 함수 충돌 재현 닫힘·현재 레지스트리 불변

`Bindings`는 모듈별 local[path][name]과 전체 anywhere[name]에 binding 집합을 저장한다. plain name/self/cls는 호출 모듈의 정의를 우선하고, 타 모듈·다른 receiver는 후보가 한 binding으로 합의할 때만 해석한다. 불일치가 None이면 `_kind`가 structural로 넘겨 수기 검토 없이 허용값을 늘리지 않는다.

독립 두 파일에 reason의 `_identifier(value, code)`와 data의 `_identifier(value, field)` 및 `_identifier(v, "PATH")`를 넣고 **구버전 생성기를 메모리에서 대입**했다:

```text
OLD_FUNCTION_PATH_IN_REGISTRY true
OLD_FUNCTION_PATH_KIND declaration/reason
CURRENT_FUNCTION_PATH_IN_REGISTRY false
CURRENT_FUNCTION_PATH_SCAN_KIND structural
CURRENT_AMBIGUOUS_IMPORTED_KIND structural
CURRENT_AMBIGUOUS_IMPORTED_REQUIRES_REVIEW true
CURRENT_FROZEN_COUNT 528
CURRENT_REGEN_VALUE_DIFF_ZERO true
CURRENT_RENDER_FILE_DIFF_ZERO true
CURRENT_UNCLASSIFIED 0
CURRENT_CONTRADICTIONS 0
```

data helper의 literal은 더 이상 선언이 아니며 이 비-whitelist 위치는 수기 data 검토 대상이다. import 충돌도 조용히 union하지 않는다. 새 테스트 5개는 로컬 선언 보존·data literal 제외·import/다른 receiver 충돌의 모호함·타 모듈의 합의된 binding 보존을 검사한다.

현재 `render(current().registry)`와 reason_codes.py 파일의 문자열도 정확히 같다. 실제 재생성 파일을 덮어쓰지 않고 비교했다. 현재 source의 미분류/수기 모순은 0이고 PATH는 frozen 목록 밖이다. 다른 모든 namespace/상속/constructor 의미 해석이 증명된 것은 아니다(R14-m1).

## ③ R12-m1: 키 공급 4변형 반영

`test_a_reference_config_ticks_in_every_key_supply_variant`의 각 fixture는 먼저 합성 runtime을 설치한다. 이후 아래 env/op × profile 키 유지/제거를 실제 tick/component 경로로 실행한다:

| 공급 경로 | profile/reference 상태 | 실제로 고정한 단언 |
|---|---|---|
| env | profile 남김 / reference 없음 | exit 0, stdin=KEYS, child env에 store/reference 없음, profile 존재 |
| env | profile/reference 모두 없음 | exit 0, 같은 3키 stdin, profile도 child env에 없음 |
| synthetic op | profile 남김 / reference 없음 | 위 조건 + op 호출 참조가 정확히 3개 |
| synthetic op | profile/reference 모두 없음 | 위 조건 + op 3개 및 3키 전용 설치 후 환경 |

op 변형은 시작 env에 store 키가 없으며 임시 credentials와 명시 synthetic script를 사용한다. `op_calls`를 3개 references와 정확히 비교하므로 키 공급 단계를 조용히 우회한 성공을 허용하지 않는다. child kwargs의 input equality·store/reference 부재·profile 존재 여부로 변형의 차이를 검증한다. env 변형은 별도 credentials 없이 supplied 키 경로를 실행한다.

`installed=False`라는 내부 파라미터 이름은 “DB 미설치”가 아니라 profile-key-left 변형이다. **4개 모두 설치된 fixture**이며 최초 profile bootstrap 회귀를 새로 수행했다고 확대하지 않는다. R12-m1이 요구한 설치 후 키 공급 변형은 반영됐다. spy는 실제 process를 호출하고 core 데이터 작업은 합성 fixture다.

## Minor — R14-m1: 동명 클래스의 constructor binding은 전역 덮어쓰기 잔여

- 심각도: **minor**, 생성기의 이유 코드 의미/범위. 위치: `tests/_regen_reason_codes.py:113,122-123,154`.
- 함수의 binding 저장은 모듈별로 바뀌었지만 `classes[node.name] = node`는 계속 전역 이름만으로 덮어쓴다. 각 모듈의 클래스에 대해 `class_binding(node.name)`을 부를 때 이미 마지막 모듈의 ClassDef를 사용한다. 실제로 다른 signature여도 local/anywhere에는 같은 잘못된 binding만 들어가므로 lookup의 disagreement 검사까지 도달하지 않는다.
- 독립 합성 두 파일:

```python
# data.py
class Choice:
    def __init__(self, field): pass
Choice("PATH")

# reason.py
class Choice:
    def __init__(self, code): pass
Choice("VALID_CODE")
```

```text
CLASS_COLLISION_DATA_THEN_REASON_PATH_IN_REGISTRY true
CLASS_COLLISION_DATA_THEN_REASON_UNCLASSIFIED 0
CLASS_COLLISION_DATA_THEN_REASON_CONTRADICTIONS 0
CLASS_COLLISION_REASON_THEN_DATA_PATH_IN_REGISTRY false
CLASS_COLLISION_REASON_THEN_DATA_UNCLASSIFIED 2
```

- data→reason 입력 순서에서는 PATH가 **조용히 reason으로 허용**되며 closed-world도 통과한다. 순서를 뒤집으면 두 literal이 structural로 올라간다. 두 클래스의 의미가 파일 순서에 좌우되는 것은 “정의가 불일치하면 모호함→수기 검토” 계약과 맞지 않는다.
- 현재 source의 동명 클래스는 두 `_Parser`뿐이며 현재 frozen PATH는 거부된다. 합성 재현을 현재 비밀/운영 값 유출로 표현하지 않는다. 이 전역 class map은 이전에도 있던 잔여로, 지정 함수 수정의 성공과 구분한다.
- 후속: ClassDef/상속 lookup에도 module/scope identity를 적용하거나 구분 불가능한 constructor는 모호함으로 올린다. 서로 다른 파일의 같은 클래스명 code/field 및 파일 순서 반전 회귀가 필요하다. source 수정은 하지 않았다.

따라서 **R11-m3 지정 함수 재현은 닫힘**이라고 판정하되 callee identity 전체가 닫혔다고 하지는 않는다. R11-m4와 R12-m1은 지정 범위에서 닫힘이다. minor 하나는 공개 source literal의 진단 의미에 관한 것으로 현재 runtime의 값 비노출 major로 확대하지 않는다.
