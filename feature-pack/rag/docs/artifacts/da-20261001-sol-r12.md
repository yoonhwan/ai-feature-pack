## D1/D2 반영 및 테스트가 결함을 잡는지

**D1은 핵심 행렬이 반영됐다.** absent/None/empty, 공백/falsey 비-str, 스토어 3키 각각과 profile 키 재사용, 스토어 키 필수, 초기 profile 필수, 검색 인자 검증의 우선순위가 신규 테스트에 들어갔다. 기존 allowlist/distinct 및 유효 키의 combined search도 보존됐다.

**D2는 코드·alias 회귀·Nano 결과 문구에 반영됐다.** 독립 관찰에서 실제 runtime의 profile_source_db와 reference.source_db를 같은 합성 파일로 두고 reference 키를 제거했다. `init`은 성공했고, 그 경로의 readonly open은 1회, 사용 키는 명시 제공한 profile 키임을 boolean으로 확인했으며 reference snapshot은 0개였다. 무키 복호화나 reference 키 fallback이 아니다. 정본 문구는 R12-m2로 남는다.

새 search 테스트의 mock이 guard 실패를 가리고 있지는 않다. 이전 커밋의 함수만 별도 프로세스 메모리에 읽어 대조했다:

```text

PRE_FIX_LATE_GUARD_SIDE_EFFECT_CALLS ['_lock']
```

후기 guard 구현이면 test spy의 `_lock` 호출로 TypeError가 발생하여 기대 RuntimeError/정적 코드 및 calls=[] 단언이 실패한다. 올바른 조기 guard만 기대값을 만족한다. 추가 low-level 관찰은 runtime 메서드를 바꾸지 않고 os.open/open_ledger/open_encrypted/reference helper에 실패 observer를 둔 것으로, 실제 search가 그 전에 종료됨을 확인했다.

tick의 `spy_component_run`은 실제 subprocess.run을 호출하는 observer다. component 실행을 성공 mock으로 대체하지 않는다. CLI helper도 실제 cli.main과 합성 암호화 DB를 사용하며 embedding 부분만 합성 vectors로 대체한다. 실제 DB/네트워크 운영 성공으로 확대하지 않는다.

## Minor

### R12-m1 — 영구 reference tick 테스트는 키가 이미 주입된 경로만 고정한다

- 심각도: **minor**, 회귀 범위. 위치: `tests/test_tick.py`의 `env_without_reference_key`, `test_a_reference_config_ticks_without_any_reference_key`; 설계 ④ T-tick-reference-config-no-key.
- 새 테스트는 `keyed_env()`에서 reference 값만 제거한다. 스토어 3키는 이미 있고 합성 profile bootstrap 키도 남는다. 설계가 지정한 `base_environment + credentials/stub_op → 3키 채움`의 결합 경로는 영구 새 테스트에 들어가지 않았다.
- 본 DA에서 이 누락 경로를 실제로 실행했다. 시작 시 스토어 3키 모두 없고 합성 op를 3회 호출한 tick이 exit 0/status ok였다. 별도로 reference와 profile bootstrap 키도 모두 제거한 설치 후 환경에서 동일한 3키 공급 경로가 성공했다. 따라서 현재 동작 결함으로 세지 않는다.
- 보정: reference-config 통합 회귀에 credentials/stub_op 변형을 추가하고, 설치 후 profile/reference 키도 없는 3키 전용 환경을 고정한다. 기존 key-loaded 변형은 유지할 수 있다. 프로토콜/보관 위치를 늘리는 변경은 필요 없다.

### R12-m2 — 정본 설계 R6은 아직 profile 경로 예외를 반영하지 않았다

- 심각도: **minor**, 문서 보장의 정합성. 위치: `arch-20261001-item5-refkey-design.md:63`의 R6.
- 정본은 여전히 “reference 키가 없을 때 search_tour_reference·투어 DB 열기·스냅샷 파일 생성은 일어나지 않는다”고 범위를 한정하지 않는다. 반면 승인 설계 DA D2, 구현 결과의 D2, 새 alias 테스트는 별도의 명시 profile 키로 같은 물리 파일을 읽는 profile bootstrap을 허용한다.
- 코드의 암호화 경계 문제는 아니다. 실제 alias probe에서도 profile 키가 사용됐고 reference 키는 None·reference snapshot 0이었다.
- 보정: 정본 R6을 “reference 검색/helper·그 경로의 source DB open/snapshot DB 생성”으로 한정하고, profile bootstrap은 별도 profile 키로 보호된다고 적는다. 새로운 경로 alias 금지나 runtime 수정은 요구하지 않는다.
