# 1. 정정 문장 (r15 → 대체)
## 1.1 m1 — r15 §1.4 의 «순서 병기» 마지막 문장 대체
원문(대체 대상): 「순서 효과를 가를 쌍(Background → 지정 안 함)은 한 번도 측정하지 않았다 — 이 설계는 그 측정을 요구하지 않는다(사전 기준은 r14 §2.2 에서 상한 소진).」
**대체 문장:** 「Background → 지정 안 함 순서는 N4 의 **A1(Background·위치 1) → B(지정 안 함·위치 2)** 로 한 번 있었다. 그러나 A1 의 **P4 가 timeout** 이라 두 호출 모두 P4 success 인 **적격 역순 대조는 얻지 못했다**. 이 설계는 그 때문에 새 측정을 요구하지 않는다. P1 은 **시도 1/2 를 소모**했고, 호출 1 이 A(적격·success/success)라 재시도 자격(H0c)이 없어 **종료**했다(2회 상한을 소진한 것이 아니며, 다음 실행을 열라는 뜻이 아니다).」
(직접 대조: 내 r15 §1.3 표 3행(A1)·4행(B), r14 §2.2 재시도 선택지는 호출 1 이 D 행인 경우뿐.)
## 1.2 m2 — r15 §2.2 «한계(관측)» 문장 대체
원문(대체 대상): 「…운영 plist 의 수정 시각은 10-02 15:22 이므로 … **같은 `ProcessType=Background` 구성에서 ok/degraded 틱과 key_error 틱이 모두 관측됐다.**」
**대체 문장:** 「운영 틱 로그에 ok/degraded 틱과 key_error 틱이 **둘 다** 있다(날짜별 상태 건수는 위와 같다). 운영 plist 는 **현재 파일과 수정 시각(10-02 15:22)으로 보아 그 기간 같은 구성이었을 것으로 추정**하나, **당시 적재된 plist 의 내용·구성 이력은 확인하지 않았다**(파일 수정 시각 외에 연속성을 증명하는 자료가 없다). 같은 구성에서도 실패가 있을 수 있다는 점에서 **`ProcessType` 하나가 운영 틱 실패를 결정한다는 자료는 없고, 이 변경은 효과를 보증하지 않는 가설 검증용 구성 변경**이라는 결론은 그대로다.」
r15 §0-3 의 「그 plist 로 ok/degraded 틱과 key_error 틱이 둘 다 나왔다」·§2.3 (e) 행의 「운영 이력상 ok/degraded 시기 존재」도 같은 한정을 따른다(현재 파일과 mtime 기준 추정).
## 1.3 m3 — r15 §2.4 S3 문장 대체
원문(대체 대상): 「리포 템플릿이 `Background` 인 채면 다음 재설치 때 값이 되돌아갈 수 있다(드리프트).」
**대체 문장:** 「리포 템플릿이 `Background` 인 채면, **나중에 이 템플릿을 재사용해 운영 plist 를 수동으로 재생성하거나 재배치할 때** 값이 `Background` 로 되돌아갈 수 있다(드리프트). **휠(런타임) 재설치는 운영 plist 를 건드리지 않으므로** 휠 재설치 때문에 되돌아가는 것이 아니다 — 이것이 R-2 와 plist 편집이 독립이라는 §2.4 서두와 S3 동기화 필요성이 함께 성립하는 정확한 표현이다.」
## 1.4 고지 표현 — r15 §2.5 오빠 고지 초안 대체
원문의 「작업 종류 지정(Background) **한 줄**을 지웁니다」를 다음으로 바꾼다(실제 XML 의 키·값 줄 수가 아니라 항목 하나라는 뜻):
**대체 고지:** 「운영 consumer 설정 파일에서 작업 종류 지정(`ProcessType`) **항목 하나**를 지웁니다(시스템 기본으로 돌아가며 가벼운 제한은 남습니다). 지금은 꺼져 있고 적재되지 않아 바로 달라지는 것은 없고, **지금과 같은 정지·미적재 상태가 유지되면** 재개할 때 처음 적용됩니다. 원본은 백업해 둡니다. 효과가 있는지는 모르며 재개해도 팝업·지연이 생길 수 있습니다.」
- 「재개 때 처음 적용」은 **집행 직전 미적재·정지 전제가 유지될 때의 설명**이다(note 1). 오빠께 드리는 `! bash /tmp/h<N>` 한 줄 진입로·값 비출력·대화형 프롬프트 0 검증은 그대로 유지하고, **plist 편집 HIL 과 재개 R-4 는 별개의 두 질문**으로 분리한다(한 번에 1개).

# 2. 구현 DA 인수 조건 (집행 스크립트 구현 발주 브리프로 재사용) — note 1
이 절은 **아직 존재하지 않는 코드의 인수 조건**이다. 이 문서·r15·DA r15 PASS 는 운영 편집을 승인하지 않는다. 구현·합성 시험·구현 DA 를 마치기 전에는 어떤 운영 파일도 바꾸지 않는다.
## 2.1 전제 확인 (S2 진입 조건)
1. **직전 전제 확인:** 집행 시작 직후·편집 직전에 「`com.airag.consumer` 가 launchd 에 **적재돼 있지 않고** 정지(disabled) 상태」임을 확인한다. 확인 수단은 launchd 상태를 **읽기만** 하는 방법이며(스크립트 안에서 `launchctl` 을 쓰는 경우 `list`/`print-disabled` 같은 조회에 한정할지, 아예 launchctl 0 으로 하고 파일·프로세스 흔적으로 확인할지는 구현 발주에서 정하되, **적재·해제·재적재 동작은 어떤 경우에도 호출하지 않는다**).
2. **전제를 확인하지 못했거나 상태가 달라졌으면 S2 에 들어가지 않는다**(편집 0, 사유 한 줄 출력, 비정상 종료). 적재돼 있으면 중단하고 **기존 HIL 경로**(HELM·planner → 오빠)로 넘긴다.
3. **launchctl 계약:** 편집 스크립트는 `bootout`·`bootstrap`·`enable`·`disable`·`kickstart`·reload 어느 것도 **자동으로 추가하지 않는다**. 이미 적재된 job 의 되돌림은 별도 기존 HIL 경로다.
## 2.2 편집 입력 한정
4. 편집 대상 입력은 **정상 plist 로서 `ProcessType` 값이 `Background` 이거나 이미 키가 없는 파일**로 한정한다. 이미 키 없음이면 무변경·성공(백업은 남기지 않거나 기존 규칙대로 하되 파일은 바꾸지 않음).
5. **거부 대상(편집 0·비정상 종료·사유 출력):** `ProcessType` 값이 `Background` 가 아닌 다른 값 · 값 형이 문자열이 아님 · **`ProcessType` 키 중복** · plist 루트가 딕셔너리가 아님 · 파싱 실패. **중첩된 딕셔너리 안의 같은 이름 키를 최상위 키로 오인해 제거하지 않는다**(예: `EnvironmentVariables` 안의 이름. 최상위만 대상).
6. 제거는 **최상위 `ProcessType` 항목 하나**뿐이다. 다른 키·값·순서·주석 처리 방식의 변경 0(편집 전후 비교는 아래 §2.3-9).
## 2.3 백업·검증·게시
7. **백업 선행:** 원본을 백업 위치에 **실제로 복사**하고 **복사본과 원본의 sha256 일치**를 확인한 뒤에만 편집 후보를 만든다. 백업 실패·해시 불일치 → 편집 0·중단.
8. **후보 파일에서 검증한 뒤 게시:** 편집은 **운영 경로가 아닌 후보 파일**에 먼저 만든다. 후보 검증 = ① `plutil -lint` 통과 ② 최상위 키 이름 목록이 원본에서 정확히 `ProcessType` 하나만 줄어듦 ③ 나머지 키의 값 해시 불변(`ProgramArguments`·`StartInterval`·`RunAtLoad`·`EnvironmentVariables`·`StandardOutPath`·`StandardErrorPath`, 값은 화면·로그에 출력하지 않음) ④ 하나라도 어긋나면 운영 파일은 건드리지 않고 중단.
9. **원자적 게시:** 검증을 통과한 후보를 **원자적으로**(같은 파일시스템의 rename 방식) 운영 경로에 게시한다. 중단·신호·쓰기 실패 중에도 **잘린(부분 기록된) 운영 파일이 남지 않는다.**
10. **파일 메타데이터 보존·확인:** 게시 후 운영 파일의 권한·소유자가 원본과 같음을 확인한다(백업 쪽도 동일 확인). 확인 결과는 PASS/FAIL 만 출력.
11. **사후 확인·복원:** 게시 후 운영 파일을 다시 읽어 §2.3-8 ②③ 을 재검증한다. 실패하면 **백업으로 복원**(원자적)하고 복원 파일의 해시가 백업과 일치하는지 확인한다. **복원 자체가 실패하면** 그 사실과 백업 위치를 출력하고 비정상 종료(사람 판정).
12. **값 비출력:** 화면·로그·결과 파일에는 키 이름 목록과 PASS/FAIL 만 낸다. 환경·경로·인자 값은 출력하지 않는다.
## 2.4 합성 시험 (fixture 만 사용)
**공통 금지:** 운영 경로(`~/Library/LaunchAgents/…`)·운영 `launchctl`·실제 `op` 를 어떤 시험에서도 쓰지 않는다. 시험 모드/인자로 주입한 fixture 경로만 쓰며, **운영 경로가 지정되면 시험 모드에서 거부**하는 시험을 포함한다.
- 정상 `Background` → 키 하나 제거·나머지 해시 불변·lint 통과·게시·사후 재검증 통과
- 이미 키 없음 → 무변경·성공
- 거부 입력: 다른 `ProcessType` 값 / 형이 문자열 아님 / 키 중복 / 루트가 딕셔너리 아님 / 파싱 불가 → 편집 0·비정상 종료
- 중첩 키 보존: `EnvironmentVariables` 등 안의 `ProcessType` 이름 키가 있는 fixture 에서 최상위만 제거되고 중첩 키는 남음
- 실패 주입: 백업 복사 실패 / 백업 해시 불일치 / lint 실패 / 게시(쓰기) 실패 / 후보 검증 불일치(다른 키 값이 바뀐 후보) → 운영 파일 불변(또는 복원)
- 중단: 후보 작성 중·게시 중 신호(INT/TERM) → 잘린 운영 파일 없음, 백업 보존
- 복원 실패 주입 → 사실·백업 위치 출력·비정상 종료
- 상태 전제 불일치: 적재됨/정지 아님/확인 불가 stub → S2 진입 0·편집 0
- 메타데이터: 권한·소유자 보존(불일치 주입 시 FAIL)
- 값 누출: fixture 에 센티넬 환경 값·경로를 넣고 화면·로그·결과 파일에 센티넬 0
- launchctl 호출 0: 시험용 가짜 `launchctl` 이 **호출 기록 0** 임을 확인(조회 허용 설계라면 허용 목록 밖 호출 0)
## 2.5 인수 경계
- 이 인수 조건을 모두 통과해도 **운영 편집은 오빠 HIL 1건 이후**에만 집행하며 재개(R-4)는 별개 질문이다. 템플릿 동기화(S3)·템플릿 시험 보강(`ProcessType` 키 부재 단언)은 별도 코드 승인 + DA 대상이다.
