## 2.2 C4 대체 — note 1: 귀속 한정
r11 §3.2 C4 의 로그 관련 문장(`kTCCServiceDeveloperTool` 요청 P0 timeout 창 3곳·success 창 0/2, 16:59:13.071 의 `does not allow prompting; returning denied`, 같은 시각 16:59:13.049~056 의 ngrok 서명 평가 로그, A2 구간 Calendar/Reminders 요청)은 **«설계 작성자의 사후 `log show` 조회 보고»** 이다. `result.json` 의 TCC 필드(A1·B `unknown_log_unavailable`, A2 `none_logged_ok`)는 이 계수와 별개의 프로브 자체 관측이며 위 계수를 검증하지 않는다. 독립 재조회로 확인 완료된 값이 **아니고**(DA 도 시스템 로그를 새로 조회하지 않았다), 보존 한계는 r9·r10 에서 수용된 그대로다. **D2 의 필요성·권고는 이 로그 귀속에 의존하지 않는다** — D2 의 근거는 §2.1 의 관측 공백(위치 1 × 지정 안 함 = 0건) 하나뿐이다. ngrok 서명 평가와 같은 시각이라는 사실만으로 해당 TCC 요청을 ngrok 이나 `op` 에 귀속하지 않는다(r11 유지).

## 2.3 §4.2 대체 — M1: D2 판독표 (단일 분기 · 상호 배타 · 완전)
**호출 순서:** 호출 1 = `--process-type unset`(첫 작업, 키 없음), 호출 2 = `--process-type background`. 아래 순서대로 **위에서 처음 해당하는 분기에서 멈춘다.**
### 단계 0 — H0: 기술적 부적격 → 해석 보류 (표보다 먼저)
다음 중 **하나라도** 해당하면 표를 읽지 않는다. 단계별 P4/P0 상태는 «관측 사실»로만 병기한다(라벨 없음).
- 어느 호출이든 종료코드 ≠ 0(§2.4 의 종료 규칙에 따라 둘째 호출이 시작되지 않았을 수 있음) · 신규 결과 폴더가 호출마다 정확히 1개가 아님
- G4 동등 검사 실패(§2.4-⑤ 의 a~g 중 하나라도): 닫힌 스키마·완료·중단·종료 확인·정확한 단계 집합·`profile.json` 스키마·호출 1 키 없음/호출 2 값 Background 대조
- P0 가 `success` 도 «회수 확인된 `timeout`(reaped·child_exited·rc -9)» 도 아님(`spawn_error`·`unsupported`·`observation_unknown`·종료 미확인 timeout·`skipped_*`)
### 단계 1 — H1: 두 호출 중 하나라도 `P4≠success` → 해석 보류 + 관측 병기
`P4` 가 `timeout`·`network_error` 등 success 가 아닌 호출이 하나라도 있으면 **P0 값에 상관없이** 표를 읽지 않는다. 이 경우 «어느 호출(unset/Background)의 P4 가 어떤 상태였고 P0 는 어떤 상태였는지»를 **관측 사실로 나란히 병기**한다. **P4 timeout 을 ProcessType 대조 라벨이나 P0 대조 라벨에 섞지 않는다**(P4 는 `op` 가 아닌 python 자식의 이름 해석·연결·TLS 이고 호출 간 비교에 쓰지 않는다). 이번 A1(P4·P0 timeout)과 같은 모양이 호출 1 에서 반복되는 경우가 여기에 해당한다.
### 단계 2 — 두 호출 모두 `P4=success` 인 **적격 결과**에서만: P0 두 값의 4조합
| 행 | 호출 1 P0(unset·첫 작업) | 호출 2 P0(Background·둘째) | 읽는 법 — 관측과 후보만 (방향 확정 금지) |
|---|---|---|---|
| **R1** | success | success | 이번 1쌍에서 P0 timeout 이 관측되지 않았다. 위치 1 × 지정 안 함 칸에 첫 관측 1건(success)이 생겼다. **재현 안 됨은 해결이 아니다.** 지정·위치의 효과 방향은 확정하지 않는다 |
| **R2** | success | timeout(회수 확인) | 지정 안 함 첫 작업은 기한 안에 끝났고 Background 둘째 작업은 기한을 넘긴 관측. **지정 여부·순서·시간 상태의 후보가 모두 남는다.** 1쌍이라 방향을 확정하지 않는다 |
| **R3** | timeout(회수 확인) | success | **지정하지 않은 첫 작업에서도 기한을 넘긴 관측**이며 둘째 Background 는 끝났다. **순서·시간 상태 후보가 남는 관측**이다. «ProcessType 지정 때문»이라는 설명이 이 쌍에서 필요하지 않았다는 사실만 적고, 첫 작업 효과도 1쌍으로 확정하지 않는다 |
| **R4** | timeout(회수 확인) | timeout(회수 확인) | **지정 안 함·Background 양쪽에서 timeout 이 관측됨.** 이 쌍은 위치 1 특이 패턴이 아니므로 첫 작업 효과 쪽 라벨을 주지 않고, 지정 여부 하나만으로 갈린 모양도 아니다. 관측 사실로 한정한다 |
- 어느 행에서도 **원인 확정·운영 plist 변경·consumer 재개 승인·표본 무효화·기준 없는 반복 요구를 내지 않는다.** 다음 한 걸음(같은 쌍 반복·다른 판별)이 필요한지는 결과를 본 뒤 별도 판단한다.
- 행 사이의 겹침·누락은 부록의 16조합 검산으로 확인했다.

## 2.4 §3.3 D2 대체 — m2: 두 호출을 묶는 h 파일의 실패·중단 계약
`probe.sh` 를 직접 두 번 부르는 h 파일(Master 가 `ft-hil.sh --add` 로 생성)은 아래 계약을 만족해야 한다. 이 계약은 **새 제품 기능·chain 변경을 요구하지 않고** h 파일 안의 분기와 판독 절차만 정한다.
1. **호출:** ① `probe.sh --python <consumer python> --p0-only --process-type unset` → ② 둘째는 `--process-type background`. 두 호출 사이 새로 등록하는 launchd 작업 없음(각 호출이 자기 작업을 등록·정리).
2. **첫 호출 rc ≠ 0 이면 둘째를 시작하지 않는다.** 특히 **rc=4(잔존 — 남은 것 확인 필요)**, **129/130/143(신호)**, 1(결과 불완전)·2(시작 거절)·3(bootstrap 실패)도 같다. h 파일은 **그 코드를 그대로 종료코드로 보존**하고(다른 값으로 바꾸지 않음) 한 줄 사유를 출력한다. 래퍼 자신이 INT/TERM/HUP 을 받으면 둘째를 시작하지 않고 신호 코드(130/143/129)로 끝난다. 이것으로 `probe.sh` 가 이미 하는 자체 정리(`probe.sh:148-151` trap)에 더해 래퍼에서 새 정리 동작을 만들지 않는다.
3. **timeout 관측은 기술적 실패가 아니다.** `probe.sh` 가 rc=0 으로 끝났다면(P0 가 정상 회수된 timeout — `rc -9`·`reaped=true` — 포함) 둘째를 **진행한다.** timeout 자체로 중단하지 않는다(A1 의 h87 도 rc=0 이었다). timeout 의 «회수 확인» 여부는 판독 단계(H0)에서 따진다.
4. **결과 폴더 대응:** 각 호출 전후로 `~/.local/share/airag-probe/` 의 폴더 이름 목록을 비교해 **호출마다 신규 폴더가 정확히 1개**임을 확인하고 호출 1→폴더 1, 호출 2→폴더 2 로 유일하게 대응시킨다. 0개·2개 이상이면(다른 실행이 끼어든 경우 포함) 그 호출은 기술적 부적격이고, 호출 1 직후라면 둘째를 시작하지 않는다(종료 5 — chain 의 G4 실패와 같은 의미의 새 코드 사용을 권고, 이미 쓰는 값과 겹치면 Master 가 구분 가능한 코드로 정한다).
5. **수동 판독도 G4 동등 검사(축약 금지):** `v1 키 존재`·`plist 키 존재` 만으로 줄이지 않는다. 호출마다 Master 가 다음 a~g 를 **전부** 확인한다. 가능하면 `chain.py` 의 `validate_result`·`gate_n4`(`chain.py:232-260`)를 **그대로 호출**해 확인한다(모듈 import 에 부작용이 없는지는 Master 가 확인하고, 불가하면 아래 체크리스트를 동등하게 수작업으로 한다).
   - a. 종료코드 0 · 신규 폴더 정확히 1개
   - b. `result.json` 이 닫힌 스키마(`validate_result` 와 같은 기준)
   - c. `complete=true`·`aborted_class=null`·`timed_out_wait=false`·종료 미확인 0·`descendants_may_hold_pipe` false
   - d. 단계 배열이 **정확히 P4·P0·P2·P1·P1b 각 1회**(순서 포함), P2/P1/P1b 는 `skipped_not_applicable`·`account_type_confirmed` null
   - e. `profile.json` 이 닫힌 키 5개(`profile_version`=1·`profile`="p0only"·`process_type_set` 불리언·`load_before`·`load_after` 길이 3 수치)
   - f. **호출 1: `process_type_set=false` 이며 `job.plist` 에 `ProcessType` 키 없음 / 호출 2: `true` 이며 `job.plist` 에 `ProcessType` 키가 있고 값이 `Background`**(독립 대조, `profile.json` 값만으로 대체 금지)
   - g. P0 ∈ {success, 회수 확인된 timeout}
6. **D2 고지(오빠께, 구현·h 파일 확정 시):** 순서 «**지정 안 함 → Background**», `op --version`·P4 네트워크 확인(my.1password.com 연결) **각 최대 2회**(호출당 1회씩), 서비스 계정 토큰 접촉 0 은 **스크립트가 토큰 파일을 읽지 않고 `op` 에 넘기지 않으며 계정 조회를 하지 않는다**는 범위 한정(`op` 내부의 설정·네트워크·기존 데몬 접촉은 미확인), **호출당 75초 상한**(기존 도구 예산, `probe.sh:4,147`) · 두 호출 합 약 150초+래퍼 오버헤드, **chain 의 240초 감시는 이 실행에 적용되지 않고 새 합계 deadline 도 없다**, 팝업 가능·누르지 말 것·consumer 계속 꺼 둠·Ctrl-C 로 중단 가능.
7. **Master 인수 조건(h 파일 넘기기 전 실측):** ① 경로·전제 파일 `test -f` ② `bash -n` ③ 대화형 프롬프트 0 ④ 위 종료 규칙(rc≠0 → 둘째 미시작·코드 보존, 신호 전파, rc=0 timeout → 진행, 폴더 1:1)을 **`op` 실행 없이**(프로브 호출부를 시험용으로 대체해 rc 0/1/4/130 을 주입하는 식 — 방법은 Master 재량) 확인 ⑤ 위 판독 a~g 절차 준비.

## 2.5 §6 대체 — M2: R-3 증거와 결정의 분리 (R-3 문구는 바꾸지 않는다)
- **R-3 문구(r10 §6 원문 그대로):** «launchd 컨텍스트 `op` 호출이 기한 안에 끝나는 관측 **또는** 오빠의 «막히는 상태로 재개해 위험 관찰» 명시 판정 — P0 한 번 success 는 실제 키 읽기 성공·팝업 방지와 같지 않으므로 위험 관찰 승인과 구분». **이 문구와 충족 기준은 변경하지 않는다.** r11 §6 의 «충족으로 읽지 않는다·미충족 유지»는 **철회한다**(R-3 에 없는 기준을 더한 것이었다).
- **증거(사실):** R-3 앞 가지의 관측이 **확보됐다** — launchd 임시 작업에서 `op --version` 이 기한(7초) 안에 끝난 관측 **2건**(B 581ms · A2 2449ms). 이 표본은 무효화하지 않는다.
- **같은 묶음의 미해결 사항(결정 기준이 아니라 기록):** 같은 N4 묶음에서 A1(P4·P0 모두 7초 초과) 1건이 있었고, 이 관측들이 운영 틱의 조건을 대표하는지·안정한지는 **미해결**이다(성공 2건은 위치 2·3 이고 consumer 의 실제 호출은 5분 간격 틱의 키 읽기 명령 — r11 §6 한계 ①②③ 유지). 이것은 R-3 의 충족 여부 판정에 쓰지 않는다.
- **한계(기존 R-3 문구에 이미 있음):** P0 success 는 서비스 계정 키 읽기 성공·팝업 방지와 같지 않다.
- **결정:** **consumer 재개는 승인하지 않는다 — 이유는 R-3 이 아니라 R-2(설치본 I-1 반영 미충족)와 R-4(오빠 재개 승인 미충족)** 이다. R-1·R-5 는 r10 §6 그대로. 이 설계는 enable/bootstrap/bootout/disable 어느 것도 집행·승인하지 않는다.
- **R-3 을 더 강하게 바꾸는 것은 이 설계의 의도가 아니다.** 바꾸려면 변경임을 명시하고 충족 기준을 **사전에 정의**해 HELM·오빠 판정에 올려야 하며, 사후에 지금의 2건을 무효로 하거나 기준 없이 «더 반복하라»고 하지 않는다.
- **D2 와의 관계:** D2 는 R-3 의 충족 조건이 아니다(R-3 앞 가지는 이미 위 2건으로 증거가 있다). D2 는 §2.1 의 관측 공백(위치 1 × 지정 안 함)을 채워 **원인 판별**에 쓰는 별도 선택지이며, 오빠가 D2 를 하지 않기로 해도 «막히는 상태로 재개해 위험 관찰» 명시 승인 경로는 그대로 열려 있다(그 경우 팝업 고지·범위 한정 고지·중단 후보의 기존 HIL 경로는 r10 §6 R-4·R-5 그대로).
