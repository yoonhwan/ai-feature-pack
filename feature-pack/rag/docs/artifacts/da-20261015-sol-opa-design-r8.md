## 2. 독립 확인과 구현 인수 범위

- 실제 보존 P 결과와 E1 JSON에 설계의 G1/G2를 별도로 모델링해 대입했다. **P0 7038ms timeout·reaped=true·TCC unknown·후속 skipped는 G1 통과**, 실제 터미널 all-fast 결과는 G2 통과했다. 생략 단계의 reaped=false 때문에 정상 관측이 거절되지 않는다.
- 그 사본에 잔존 flag·inconclusive_error·불완전·aborted·timed_out_wait·실행 단계 spawn_error를 단일 변경한 **7개 부정 사례는 모두 중단**됐다. 기존 결과를 수정한 것이 아니라 메모리 사본으로 게이트 표만 확인했다.
- 240초에서 각 단계가 75초, 각 전환이 3초인 모형은 **3단계 모두 시작하여 234초**다. 세 번째 초과 경로의 문서 산술도 156+80+최종 표시 2=238초로 일치한다. 단계 시작 판단·감시·전환/최종화가 실제 남은 시간으로 집행되는지는 구현 DA 항목이다.
- N3의 감시 대상 PID가 taskpolicy 자체에 머무는지 확인하려고 **자체 비제품 Python만** `/usr/sbin/taskpolicy -b`로 실행했다. 출력한 Python PID가 직접 Popen PID와 같아 exec 인계가 확인됐다. 실제 op·운영 프로세스는 실행/변경하지 않았다. 기존 r7의 정책 상속/종료코드 확인도 유지한다.

이 확인은 **설계 표·예산 모델·비제품 exec 경로**에 한정된다. 아직 없는 신규 래퍼의 전체 마감·신호/정리·결과 파일 발견·출력 제어를 시험 통과했다고 주장하지 않는다. 구현 시에는 r8:115–126의 합성 사례, 후보 결과 파일의 유일성/스키마 거부, 신호 때 코드 보존 및 후속 미실행을 실제 wrapper 경계에서 확인한다. 파일 목록 비교는 결과 후보 유형을 먼저 한정해 임시 HOME 폴더를 E1 결과 JSON과 혼동하지 않도록 한다.

## m1 — 후퇴안 A의 150초에는 전환 시간과 시작 조건이 맞지 않는다 (minor, 비차단)

근거: r8:104–109,158.

주 경로는 도구 225초와 전체 240초를 구분했지만, 후퇴안 A는 다시 **2×75=150초를 전체 상한**처럼 적는다. 같은 전환 게이트까지 포함하면 두 단계의 정상 슬롯 합은 **2×(75+3)=156초**다. 전체를 150초로 설정하고 같은 83초 시작 조건을 적용하면 첫 슬롯 78초 뒤에는 72초만 남아 두 번째 단계가 시작되지 않는다.

이는 주 경로의 240초 계약을 깨지 않고, fallback을 고르거나 상한에 가까운 경우의 인수 기준 문제이므로 비차단 minor다. 구현 전에 후퇴안의 전체 한도를 전환/정리 포함 값으로 따로 적거나, 150초를 지키되 두 번째 단계를 예산에 따라 생략할 수 있다고 명시한다. 도구 자체 75초 계약을 단축 시도로 바꿀 필요는 없다.
