## 발견 결함

### R10-M1 — C 표준 출력 버퍼가 Python flush 경계를 넘어 복원 후 stdout으로 나온다

- 심각도: **major**, 값 비노출 경계. HELM의 architect 상향 대상이다.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/tick.py:238-267` (_discard_component_output), 특히 `:242-244`의 Python stream 보관과 `:257-267`의 Python flush·fd 복원. 실제 tick 호출은 `:306-311`.
- 원인: 종료 전에 flush하는 것은 원래 sys.stdout/sys.stderr의 Python 객체다. libc의 stdout FILE 버퍼는 그 객체와 별개다. C printf가 넣어 둔 bytes는 Python flush로 폐기되지 않으며, fd 1을 복원한 뒤 C의 fflush 또는 정상 프로세스 종료가 그 버퍼를 내보낼 수 있다.
- context 재현: 별도 자식에서 실제 _discard_component_output 안에 libc printf로 합성 marker를 출력한다. 일반 Python print와 os.write도 함께 실행한다. 정상 yield/내부 RuntimeError의 두 경우 모두 fd 복원 뒤 libc flush를 수행한다. parent가 자식 stdout/stderr를 캡처해 boolean만 검사한다.
- 관찰: Python print와 직접 fd write는 숨겨졌고 공개 후속 stdout/stderr는 정상 목적지에 나타났다. 하지만 **네이티브 marker는 정상·예외 두 경우 모두 stdout에 남았다.** fd 복원 자체의 실패로 표현하지 않는다.
- 실제 tick 재현: 기존 합성 fixture의 bridge publish만 libc printf를 호출한 뒤 원래 작업을 계속하게 한다. 실제 tick.main을 자식에서 호출하고 정상 종료한다. **exit 0이지만 stdout에 합성 네이티브 marker가 있었다. 이 실제 tick 자식에는 수동 libc flush를 넣지 않았다.** 프로세스 종료의 표준 버퍼 처리를 통해 발생한 것이다.
- 범위: 실제 운영 bridge가 C printf로 본문을 출력했다거나 실제 키/본문이 누출됐다고 주장하지 않는다. 합성 callback과 실제 C 표준 출력 API로 새 보호 경계의 한계를 재현했다. 임의의 다른 파일/비표준 fd로 우회한 경우가 아니다.
- 설계 수준 요청: 보호 대상 출력의 종류와 수명을 architect가 명확히 정하고 검증해야 한다. Python 객체와 native stdio의 서로 다른 버퍼 수명·복원/종료 순서를 포함해야 한다. 이번 DA는 구현 코드를 수정하지 않았다.

### R10-m1 — 소스의 모든 대문자 리터럴을 오류 이유 코드로 인정한다

- 심각도: **minor**.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/tick.py:201-224`, 특히 `:209-215`의 전체 source 정규식 수집.
- 원인: _known_codes는 error constructor/코드 정의가 아니라 따옴표 안의 모든 대문자 문자열을 수집한다. 환경 변수명·일반 상태/상수도 실제 이유 코드 목록에 섞인다.
- 관찰: 현재 목록 **574개**, AST로 대조한 선언된 이유 코드 literal **460개**, 차집합 **114개**였다. OP_SERVICE_ACCOUNT_TOKEN 및 PATH도 허용됐다. 실제 합성 CLI/runtime의 RuntimeError 메시지에 환경 변수명을 넣었을 때 exit 40이고 그 문자열이 code로 전달됐다.
- 의미: 알려진 코드만 보고한다는 진단 계약보다 허용 범위가 넓다. 이 재현의 문자열은 공개 소스의 환경 변수명이며 실제 credential 값이 아니므로, 이를 비밀 값 유출 major로 확대하지 않았다.
- 과소 차단/과차단: 선언된 460개 이유 코드 literal은 모두 허용됐다(추가 차단 0). 미등록 합성 marker는 거부됐다. 동적/외부 오류 코드를 전부 검증한 것은 아니다. 읽을 수 없는 source를 제외하거나 package import가 실패하면 목록이 줄고 RUNTIME_FAILED fallback으로 갈 수 있다.
- 수정 방향: 소프트웨어의 이유 코드 정의와 단순 데이터 리터럴을 구별해야 한다. 소스 내 모든 quoted uppercase 문자열이라는 사실만으로 오류 코드의 의미를 보장할 수 없다.

## 새 경계·운영 판단

1. **flush와 복원:** 캐시된 Python stream은 정상/예외 종료 모두 flush-before-restore가 유지됐다. 준비 실패의 확보된 fd만 복원·close하는 경계도 통과했다. native C stdio는 R10-M1의 별도 버퍼다. 새로운 테스트가 서로 다른 출력 계층을 모두 다룬다고 확대하지 않는다.
2. **검증된 log-dir:** 정상 경로는 새 0700 디렉터리와 로그를 만든다. config 파일이 없더라도 먼저 검증한 로그 디렉터리에는 exit 20의 안전한 오류 기록을 남겼다. symlink로 거부한 디렉터리는 수정/정리하지 않았다. 검증 전 오류는 정적 log_unavailable만 출력한다. 상위 ancestor symlink 미검사·기존 권한 보정 없음은 이전의 알려진 범위이며 이번에 해결된 것으로 표현하지 않는다.
3. **부분 쓰기:** 반복 write는 쓰인 만큼만 진전한다. 0 반환은 성공처럼 지나가지 않는다. 이는 best-effort 로그 실패를 기존 log_write_failed 경계로 전달하며 비즈니스 exit 정책을 바꾸지 않는다. 정상 회전·보존 기존 테스트도 통과했다.
4. **op의 proxy/CA:** OP_ENV_ALLOWLIST와 load_keys는 r9의 네트워크 판단 당시 정책과 동일하다. HTTPS_PROXY·SSL_CERT_*를 뺀다. r9에서 해당 변수를 요구하는 가짜 op는 full fixture env로 직접 호출할 때 exit 0/유효 키, wrapper에서는 exit 30이었고 parent env는 그대로였다. 이 r10에서 동일 스텁 실험을 불필요하게 반복하지 않았다. **운영 판단:** 해당 변수에 의존하는 환경에는 호환성이 보장되지 않으며, 같은 정책의 다음 틱이 자동 복구하지 않는다. 이는 의도된 forwarding 범위이며 새로운 방어 실패로 세지 않았다. 실제 op/운영 설정 확인이 금지돼 이 호스트의 필요 여부는 미판정이다. U2 단계에서 필요한 네트워크 환경과 forwarding 정책을 확정해야 한다.
