# 1. B1 — DB 종류별 읽기 전용 연결·식별 계약 (r17 §6 «여는 방식» 칸 대체)

r17 의 «두 DB 모두 core `open_readonly`» 문장을 삭제한다(`connect.py:206` 은 `db_meta.engine`·core 스키마 버전을 검사하므로 consumer 원장에는 쓸 수 없다).

| DB | 읽기 전용 연결 | 식별 검사(전부 통과해야 `ok` 판정 대상) | 근거 |
|---|---|---|---|
| projection(core 스키마) | core `connect.open_readonly(path, key)` 그대로(`?mode=ro`·키 적용·`query_only=ON`·`busy_timeout=5000`·읽기 검증·암호화 확인·`db_meta.engine`·스키마 버전) | 함수 내부 검사 | `connect.py:194-218` |
| consumer(원장 스키마) | 점검 모듈 안에서 **같은 순서의 범용 SQLCipher 읽기 전용 연결을 새로 구성**: `sqlcipher3.connect(<uri>?mode=ro, uri=True, isolation_level=None)` → `PRAGMA key` → `PRAGMA temp_store=MEMORY` → `PRAGMA query_only=ON` → `PRAGMA cipher_version` 비어 있지 않음 → `SELECT count(*) FROM sqlite_master`(읽기 검증) | `SELECT engine FROM meta` 결과가 `[(ENGINE,)]`(`ENGINE="airag-consumer-ledger-v1"`) · `PRAGMA user_version` 이 `(4,)` | `operations.py:156-168`(범용 ro 연결 형태), `ledger.py:23,314-316`(식별 계약) |

- consumer 연결에서 **하지 않는 것**: `journal_mode`·`synchronous`·`foreign_keys` 같은 쓰기·상태 변경 PRAGMA(`ledger.py:319-320`)와 rw 열기·스키마 생성. `operations.py` 의 `_connect` 는 비공개 함수이므로 import 하지 않고 같은 형태를 점검 모듈에 둔다.
- 결과 enum 을 다섯으로 확장: `ok`·`not_ok`(`quick_check` 반환이 `[("ok",)]` 가 아님)·`deadline`·`open_error`(열기·키·암호화·읽기 검증 실패)·`identity_error`(식별 검사 불일치 — B1 같은 계약 오류를 «손상 의심»과 구분해 남김). DB 이름은 `consumer`·`projection` 두 값.
- 실패 코드: `not_ok`→`DATABASE_INTEGRITY_FAILED`, 나머지 셋→`DATABASE_INTEGRITY_UNAVAILABLE`(type 칸 = DB 이름). 
- 시험 설계(실행 보류): 정상 합성 consumer 원장(`meta`·`user_version=4`)이 `ok`, 다른 engine 값이 `identity_error`, 잘못된 user_version 이 `identity_error`, 정상 합성 projection 이 `ok`, **consumer 에 core opener 를 쓰면 실패한다는 대조 시험**(회귀 방지), 점검 전후 DB 파일 바이트·mtime 불변.

# 2. M1 — 호출 경계를 «어댑터 함수 1회 호출 전체»로 (r17 §4 «후킹 위치»·«응답 read 구간은 미포함» 대체)

r17 의 «`OpenerDirector.open` 래핑»과 «비스트림이라 헤더 도착이 생성 완료 뒤» 전제를 삭제한다(세 어댑터 모두 `open` 반환 다음 줄에서 `read()` — `memory.py:391-392`, `llm_enrichment.py:200-201`, `embeddings.py:305-306`).

- **새 호출 경계**: 호출 줄을 만드는 단위 = 아래 세 함수의 **1회 호출 전체**(연결·헤더·본문 `read()`·응답 파싱·검증 포함). 시작 줄은 함수 진입 직전, 끝 줄은 반환 또는 예외 직후.

| 래핑 대상 | 줄의 `name` | `tok` | 비고 |
|---|---|---|---|
| `llm_enrichment._post_json`(`:193-220`) | `llm` | 첫 위치 인자 `path` 가 `"/tokenize"` 와 같으면 true | chat·tokenize 공통 경로 |
| `embeddings._post_embeddings`(`:290-`) | `embed` | false | 임베딩 POST |
| `OpenAICompatibleMemoryExtractor.__call__`(`memory.py:323-`) | `llm` | false | 기억 추출 chat(클래스 속성 교체 — 인스턴스 호출이 `type(obj).__call__` 로 해석되므로 유효) |

- 래핑은 모듈/클래스 속성 교체이며 URL·포트·본문을 읽지 않는다(`path` 문자열을 상수와 비교해 enum 만 만듦 — `name` 3종 유지). 모듈 내부 호출은 전역 이름 조회라 교체가 반영됨. **래핑 실패 처리**: 대상 이름이 없거나 형태가 다르면 추적을 비활성화하고(예외 아님) 업무는 그대로 — 시작 시 존재 확인 3건.
- **지정 어댑터 밖의 외부 통신은 이 계측이 다루지 않는다**: HF 토크나이저 로드의 간접 통신, vision 정규화 경로(`pipeline.py:150`)가 위 세 함수 밖 호출을 갖는지는 미확인 → 「관측 범위 밖」으로 기록.
- 구간 의미: 줄 `b`~`e` 사이는 «호출 전체»이며, 그 안에서 연결 대기·헤더 대기·본문 수신 중 어디였는지는 이번 단위에서 나누지 않는다(필요하면 후속 단위에서 별도 관측). 이 구간은 파싱·검증 시간을 포함하므로 «서버 응답 시간»과 같은 값이 아니다.
- `e.out` 분류는 예외 객체의 **클래스와 `.code` 문자열 상수 비교만**(`PROVIDER_TIMEOUT`→`timeout`, `PROVIDER_UNREACHABLE`·`PROVIDER_UNAVAILABLE`→`unreachable`, `PROVIDER_HTTP_ERROR`·`PROVIDER_RATE_LIMITED`·`PROVIDER_SERVER_ERROR`·`PROVIDER_REQUEST_ERROR`→`http_error`, 그 외→`error`, 정상→`ok`).

# 3. M2 — trace 파일 계약 (r17 §4 «기록 장소»·«복구 사슬»·«멈춘 호출 판별» 대체)

| 항목 | 계약 |
|---|---|
| 파일 열기 | `O_WRONLY\|O_APPEND\|O_CREAT\|O_NOFOLLOW\|O_NONBLOCK` + `fstat` 정규 파일 확인(`tick.py:344-349` `_open_regular` 와 같은 방식). 추가로 소유자 == 현재 euid·`st_nlink==1` 확인 |
| 기존 파일 권한 | 열린 fd 의 `st_mode & 0o077` 이 0 이 아니면 `fchmod(fd, 0o600)` 1회 시도, 실패하면 추적 비활성화 |
| 초기화·회전 | pass 시작 시 `lstat` 로 대상이 심볼릭 링크가 아님을 확인한 뒤 `os.replace(trace, trace.prev)`. 확인·교체·열기 중 **어느 하나라도 실패하면 그 pass 의 추적 전체를 비활성화**(`x` 줄을 못 쓰면 카운터만 남김). **어떤 경우에도 업무 호출은 그대로 진행** |
| 부분 쓰기 | 줄 하나 = `os.write` 한 번. 반환 길이가 줄 길이보다 짧으면(또는 `OSError`) 추적 비활성화 + `x` 줄 1회 시도(실패해도 무시). 판독 규약: **개행으로 끝나지 않거나 스키마 불일치인 줄은 버린다**(마지막 줄이 잘렸을 수 있음) |
| 동시 쓰기(core 다중 worker `AIRAG_LLM_CONCURRENCY` 1·2·4: `processing.py:104,129`) | 호출 번호 `n` 은 `itertools.count()` 의 `next()` 로 호출 시작에서 부여(`b`·`e` 가 같은 `n`). 줄 수·바이트 예산·`os.write` 는 전용 락 아래에서 수행하되 **`acquire(blocking=False)`** — 획득 실패한 이벤트는 쓰지 않고 지역 `dropped` 만 증가(업무 스레드를 락 대기로 지연시키지 않음). 락 보유 중 업무 호출은 없음 |
| 누락 표지 | `dropped>0` 이면 이후 **성공적으로 쓰인 첫 줄 이후 모든 줄**에 누적값 `d`(int, 1~99,999)를 싣는다. 상한 도달·쓰기 오류·초기화 실패로 멈추면 `x` 줄(사유 `cap_lines`·`cap_bytes`·`write_error`·`init_error`) |
| 줄 크기 | **개행 문자 포함 ≤192바이트**(예산 계산도 개행 포함). 파일 총량 ≤384KiB·줄 ≤2,048 — 둘 다 락 아래에서 확인 |
| 예외 범위 | 추적 코드 호출(`_begin`·`_end`)은 **`Exception` 만** 삼킨다. 래퍼 구조는 `tok=_begin(...)`(내부에서 Exception 삼킴) → `try: result = 원함수(*a, **k)` → `except BaseException as e: _end(tok, 분류); raise`(**업무 예외는 삼키지 않고 같은 객체로 재발생**) → `else: _end(tok,'ok'); return result`. `_end` 의 오류만 삼킨다. 분류 코드는 예외 객체를 변경·출력하지 않는다 |

**필드 조합별 필수·금지(닫힌 스키마, 추가 키 거부)**

| `ph` | 필수 | 금지 | 의미 |
|---|---|---|---|
| `b` | `v`=1, `n`, `name`, `tok`, `t` | `i`, `out`, `rsn` | 호출 시작 |
| `e` | `v`=1, `n`, `name`, `tok`, `t`, `out` | `i`, `rsn` | 호출 끝(`b` 와 같은 `n`) |
| `wb` | `v`=1, `i`, `t` | `n`, `name`, `tok`, `out`, `rsn` | consumer 발행 윈도우 시작 |
| `we` | `v`=1, `i`, `t`, `out`(`ok`·`fail`·`error`) | `n`, `name`, `tok`, `rsn` | 같은 `i` 의 종료(`_publish_window` 반환 딕셔너리의 `ok` 값 읽기·예외면 `error` 후 재발생) |
| `x` | `v`=1, `t`, `rsn` | `n`, `i`, `name`, `tok`, `out` | 추적 중단 |

공통 선택: `d`(누락 누적, 모든 `ph` 허용). 값 범위: `n` 0~99,999 · `i` 0~9,999 · `t` float 0~86,400(소수 3자리) · `name`∈{`llm`,`embed`,`other`} · `d` 1~99,999.

**짝 없는 `b` 의 해석(r17 «멈춘 호출 판별» 문장 삭제)**: 짝 없는 `b` 는 «완료 줄이 없는 호출»일 뿐 **중도 절단 호출을 확정하지 않는다.** 원인 후보 = ①종료 시점에 호출 진행 중 ②`e` 줄 누락(락 경합·예산·쓰기 오류) ③추적 중단. 같은 파일에 `x` 줄 또는 `d` 필드가 하나라도 있으면 «계측 누락 있음 — 원인 미확정». 둘 다 없고 마지막 유효 줄이 짝 없는 `b` 이면 «종료 시점 진행 중 후보»로만 읽는다(후보 단계, 확정은 이후 관측).
**크기 계약 한정**: 위 상한은 추적 파일에만 적용되며 틱 로그 줄·summary·반환 코드에는 영향이 없다.

# 4. M3 — quick_check 마감 범위와 예산 (r17 §6 «시간» 칸 대체)

r17 의 «합계 최악 21초»를 삭제한다. 대체 내용:

- **마감의 시작·종료 범위**: 점검 스레드 시작(= `_pass_child` 가 fd 격리 직후 점검 스레드를 만드는 시점)부터 **게이트 결정이 나는 시점**까지. 범위 안 = 연결·키 적용·읽기 검증·식별 검사·busy 대기·`quick_check` 스캔·연결 종료. 
- **제한 방식(두 겹)**: ①점검 전체를 **데몬 스레드**에서 순차 실행하고, 메인 스레드가 `join(timeout=예산)` 으로 대기 — 만료 시 해당 DB 를 `deadline` 으로 기록하고 `connection.interrupt()` 를 최선 시도로 호출(스레드 안전) ②스레드 안에서는 `set_progress_handler`(시간 확인 후 비영 반환 = 중단)를 보조로 사용. **보장하는 것 = 메인 스레드의 결정 시점(만료 시 `deadline` 확정)뿐**이다. 디스크 I/O 정지처럼 C 호출 안에서 멈춘 경우 스레드 자체는 끝나지 않을 수 있으나 데몬이므로 프로세스 종료를 막지 않는다. 결정 지연 = 스레드 스케줄·프레임 작성 시간(**미측정**).
- **core opener 와의 관계**: projection 용 `open_readonly` 는 `busy_timeout=5000` 을 설정하고 진행 핸들러 설치 이전에 읽기 검증을 수행한다(`connect.py:200-205`). 이 5초와 검증 시간은 **위 점검 스레드 마감 안**에 들어가며, 보조 핸들러가 아니라 메인 스레드 `join` 이 이를 제한한다. consumer 연결은 busy 대기를 점검용으로 짧게(`busy_timeout=1000`) 둔다.
- **계획 예산 vs 보장 상한**: 계획 예산 = `Σ min(70, 7 × ceil(크기MiB/16))`(크기 = 본체+WAL 의 `os.stat` 합, 점검 시작 시점 값). 현재 크기(consumer 10,473,472B · projection 13,221,888B + WAL 4,054,112B)에서의 산술은 **7초 + 14초 = 21초 «계획 예산(실측 0·16MiB 기준 임의)»**이다. 크기가 바뀌면 값도 바뀌고, 이 값은 틱 총 시간에 더해지는 **보장값이 아니다**. 보장하는 것은 위 «결정 시점» 뿐이며 그 상한도 계획 예산에 스케줄 지연을 더한 값이라 수치로 확정하지 않는다. 첫 점검의 `ms` 기록으로 기준 크기·계획 예산을 개정한다.
- 규칙 12: 로컬 파일 스캔이라 외부 호출이 아니므로 7초 룰을 직접 적용하지 않는다는 r17 해석은 유지(DA 수용).

# 5. M4 — 마커 대신 «깨끗한 종료 상태 파일» 계약 (r17 §6 «1회 규칙» 칸 대체)

| 파일 | `log_dir/pass-state.json`, 0600, 정규 파일(§3 와 같은 `O_NOFOLLOW\|O_NONBLOCK`+`fstat`·소유자·`st_nlink==1`), 크기 ≤256B |
| 스키마(닫힌, 추가 키 거부) | `{"v":1,"proj":"<16자 hex>","state":"running"\|"clean"}` — `proj` = 설정의 consumer DB·projection DB 경로 문자열을 정해진 순서로 이은 값의 sha256 앞 16자(경로 값은 저장하지 않음) |
| 점검 여부 | **`state=="clean"` 이고 `v`·`proj` 가 일치하며 스키마·권한·크기·소유자가 유효할 때만 점검을 생략.** 파일 없음·`running`·판독 오류·불일치·오래된 형식·잘못된 권한 = 전부 **점검 실행** |
| 기록 시점 | 점검 통과(또는 생략) 직후·`cli_main` 호출 직전에 `running` 기록 → `cli_main` 이 **정상 반환하거나 예외로 끝난 직후** `clean` 기록. SIGTERM·강제 종료로 자식이 끝나면 `running` 이 남아 다음 틱이 점검 |
| 기록 방식 | 같은 디렉터리 임시 파일 작성 → `fsync` 없이 `os.replace`(0600). 기록·판독 실패는 업무 동작을 바꾸지 않음(실패 = 다음 틱도 점검) |
| 의미 | 첫 배포 직후 첫 틱(파일 없음)과 **중단 뒤 첫 틱**에 자동으로 점검이 돈다 — Master 의 «재개 첫 틱 1회» 요구는 파일이 없는 첫 틱에서 충족되고, 이후 재개에서도 중단 흔적이 있으면 재점검. 수동 이동 절차 불필요(필요 시 파일 이름 변경으로 점검 강제 가능, 재개 절차의 선택 1줄) |
| 한계 | `clean` 은 «프로세스가 정상 종료했음»이지 DB 정상 증명이 아니다. 이 파일은 `quick_check` 결과를 대신하지 않는다 |

# 6. M5 — 호출 총마감 계약·pass 최악 시간 (r17 §5 «호출 총 마감»·«pass 마감» 대체)

r17 의 «read 루프에서 단조시계 확인»과 «120+70=190초 < 300» 을 삭제한다.

- **호출 총마감 계약(후속 단위 구현 시 인수 조건, 이번 단위에는 적용 안 함)**: 호출 하나에 시작 시각 기준 마감 `D` 를 두고, **블로킹 대기 하나하나(연결·요청 송신·헤더 대기·본문 수신 각 단계)** 에 `timeout = D − 현재 단조시계` 를 다시 설정하며 남은 시간이 0 이하이면 즉시 `timeout` 처리한다. `urllib.request.urlopen(timeout=…)` 하나만으로는 단계별 합이 `D` 를 넘을 수 있으므로, 구현은 ①단계별 잔여 시간 재설정 ②별도 타이머가 소켓을 닫는 방식 중 하나로 «시작부터 `D` 안에 반환 또는 `timeout` 예외»를 시험 가능한 형태로 보여야 한다. 이름 조회 등 소켓 밖 대기는 보장 밖으로 표기한다(F8).
- **pass 최악 시간은 미확정**. 구성 항: 수집 + 첫 refresh + Σ(consumer 발행 윈도우: 전체 core 처리 = `pipeline.py:71` 의 문서 분할에 따른 **여러 core semantic window**(`processing.py:91-` `compute`: 묶음 chat·번역/요약 chat·각 chat 직전 `/tokenize`) + 임베딩 배치 + 저장) + 기억 추출(최대 1건) + 두 번째 refresh + 보관 + 백업(`runtime.py:1002-1012`). 호출마다 상한이 있어도 호출 개수·윈도우 개수·core semantic window 개수가 미확정이므로 **현재 구조에서 pass 상한은 증명되지 않는다.**
- 「새 consumer 윈도우 시작 금지 시계」(r17 의 120초)는 **보장 상한이 아닌 잠정 제어 후보**로만 남긴다: 시계 만료 시 다음 consumer 윈도우를 시작하지 않고 기억 추출을 다음 pass 로 미루는 동작을 가정할 뿐, 이미 시작한 윈도우는 전체 core 처리·저장까지 완료돼야 하므로 pass 종료 시각은 이 시계로 한정되지 않는다. 확정하려면 core semantic window 단위 마감(core 변경)이 필요한지 별도 설계에서 판단.

# 7. M6 — 규칙 12 환산 (r17 §5 표의 «목표 시도당 상한» 칸 대체)

- 「8단위·56초」는 **계산 예시**로만 남긴다. 근거 부족: 요청량 기준은 `max(입력 토큰/2,000, 출력 문자/300)` 이며 `max_tokens=2048` 은 출력 문자 수를 정하지 않는다(토큰↔문자 환산은 모델·언어 의존, 미측정). `/tokenize` 는 **실제 전체 프롬프트**를 받으므로 항상 1단위가 아니다. v3 줄 단위 호출(`llm_enrichment.py:431-512`)에도 지시문·JSON·출력 예약이 붙는다.
- 표의 상한 칸은 «계산식 + 필요한 입력 값(미확보)»로 바꾼다: `시도당 상한 = min(고정비 + 7초 × ceil(요청량/기준량), 70초)`, 로컬 HTTP 고정비 0. 예: 요청량이 입력 2,000토큰 이하·출력 600자로 **실측되면** 14.0초.
- 기억 추출 chat 을 «쪼갤 수 없는 크기 아는 배치»로 분류하는 근거는 **미증명**이다. lineage 변경(`memory.py:1313-1318`)은 쪼개기의 비용 위험이지 분할 불가의 증명이 아니므로, 쪼개기 검토는 계측 뒤 단위로 남긴다.
- 문구 명시: **총마감은 재시도를 포함해 70초 이내**, **재시도는 첫 출력 전 실패에 한함**(이번 단위는 호출 내부 재시도를 도입하지 않음), **스트림을 도입한다면 첫 출력·청크 간 무진행 각 7초를 별도 조건으로 유지하고 같은 총마감을 적용**, **600/300초 기본값은 채택하지 않음**(DA 수용 유지).

# 9. m1 — R-5·재개 전 확인 표현 (r17 §7 대체)

- 수행하지 않은 점검은 **「재개 전 확인」이 아니라 「미확인 위험 고지」**로 쓴다: 기억 `pending` 배치 수·윈도우 `processing` 잔여는 운영 DB 열기가 필요해 이번에 읽지 않았다 → R-3 위험 고지에 «미확인 위험» 한 줄.
- R-5 개정 문장: 관찰 상한 T 도달 시 행위 = **«보고»**(trace 마지막 유효 줄 읽기 + Master 의 상황 보고). **실제 프로세스 종료·launchctl 변경은 별개 집행**이며, 재개 승인 문구에 「T 초과 시 정지 집행」이 **명시적으로 포함됐을 때만** Master 가 집행한다. T 의 대리 선정은 보고 시각을 정하는 것일 뿐 운영 종료 권한을 뜻하지 않는다. 잠정 T: pass 시작 5분에 진행 확인 보고, 15분 초과 시 «정지 여부 판단 요청» 보고(종료는 위 조건).
- 로그 줄이 남지 않는 중도 종료 틱도 실패 계수에 1틱으로 센다(r17 유지). **R-6**(재개 1회 = 계측·게이트 외 행위 변경 금지)도 유지.

# 10. N4 — 2종 점검의 제외 근거 표현 (r17 §6 «몇 종» 칸 대체)

- 제외 근거(중심): **정상 pass 경로가 profile-source DB 를 열지 않는다** — `run_once` 호출 순서에 해당 호출이 없고(`runtime.py:1002-1012`), `_install_profile`(`runtime.py:592`)은 초기화 경로(`:646`)에서 호출된다(DA N4 확인). 이어서 4번째 키(`PROFILE_SOURCE_KEY_ENV`, 기존 키와 달라야 함: `runtime.py:433-446`) 요구가 틱의 키 3개 계약·`_pass_child` 프로토콜 변경을 부른다는 비용을 적는다. 파일이 작고 오래됐다는 점은 근거로 쓰지 않는다.
- **3종 지시를 완료했다고 쓰지 않는다**: profile-source DB 점검은 **미수행·미확인**이며 별도 단위 후보다.
