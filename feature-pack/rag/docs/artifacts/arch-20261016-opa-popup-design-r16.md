# 3. Q1 — «행위 변경 없는 계측» 최소안
**가능/불가능부터:**
- **운영 자격·DB 접촉 0 으로 `op read` 동등 프로브: 불가.** `op read` 는 서비스 계정 토큰이 있어야 같은 경로(인증·왕복)를 탄다. 토큰 없이 부르면 데스크톱 연동·로그인 안내 경로로 가서 **다른 경로(팝업 후보 그 자체)** 이고, 가짜 토큰은 형식 검사에서 로컬로 끝나 왕복을 안 탈 수 있다(미확인 — 실행 금지라 확인 못 함). 프로브에 `op read` 모드를 만들려면 **테스트용 서비스 계정·테스트 볼트 신설(오빠 HIL·자격 신설)** 이 필요해 이번 판정에서는 **권하지 않는다**.
- **자격 신설 없이 가능한 것: 운영 틱 자신이 하는 읽기에 계측 필드만 추가.** 새 호출 0·새 접촉 0(틱이 이미 하는 `op read` 3개).
**계측 필드 최소안(전부 값 비출력·닫힌 스키마 · 코드 변경 = Nano+DA):**
| 필드 | 내용 | 가르는 것 |
|---|---|---|
| `keys[].name` | `NAMES` 의 이름 3종 중 하나(참조 문자열 아님) | 어느 키가 느린가(H3·H4) |
| `keys[].attempts[]` | 시도별 `{start_ms, end_ms, outcome}` — 틱 시작 기준 오프셋, outcome ∈ `ok / timeout / exec_error / nonzero_rc` | 겹침(H4)·7초 잘림 위치(H1) |
| `tick_total_s` | 틱 시작~기록 소요 | F2 의 추정을 실측으로 |
| `load1` | `os.getloadavg()[0]`(틱 시작 시) | H2 |
| `op_children` | 틱 시작 시 `op` 프로세스 수(수치만) | H4 · F7 |
- 실패 틱에도 위 필드를 **반드시** 기록한다(`TickError` 경로의 로그 줄에 합류). 기존 필드(`code`·`type`·`exit`·`status`·`ts`)는 불변.
- **한계(솔직히):** 상한에서 잘린 호출의 «끝났을 시간»은 계측으로도 모른다. 이 한계 때문에 §6 은 계측과 상한 개정을 같은 단위로 묶는다.

# 4. Q2 — 7초 룰 적용
## 4.1 요청량 판정
- 규칙 12 의 기준 요청량(입력 2,000 토큰 또는 출력 300자 중 큰 비율) 대비 `op read` 1회는 입력 = 참조 한 줄, 출력 = 64 hex 자 → **1 요청량 미만 = 1단위**. 키 3개는 **독립된 서브프로세스 3개**이고 키마다 시도 7.0·마감 14.0 이 따로 적용된다. 틱 벽시계 상한은 그중 최대 = 14.0(F2 가 실측 14.7). 따라서 «3요청량 한 덩어리»가 아니라 «1요청량 × 3 병렬»이다. (병렬이 서로 지연을 키우는지는 H4, 미확인.)
## 4.2 기동 고정비 — tick.py 가 규칙에서 빠뜨린 항
- 규칙 12 문구: «CLI 서브프로세스는 기동 고정비(잠정 3.5 s)를 따로 더하되 천장은 같다». tick.py 주석은 «7-second rule: per attempt, one retry…» 만 인용했고 `OP_ATTEMPT_TIMEOUT_S = 7.0` 에 고정비가 **더해지지 않았다**.
- **내 독해:** 1단위 CLI 호출의 시도당 상한 = 3.5 + 7.0 = **10.5s**, 재시도 포함 키당 총 마감 = **21.0s**(70초 천장 안). 이는 «상한을 늘리는 것»이 아니라 규칙이 CLI 에 정한 기본값으로 맞추는 것이다. 600/300초 값은 쓰지 않는다. **이 독해는 DA 심사 대상**이다(고정비 3.5s 는 규칙이 «잠정»이라 적었다 — 근거 실측은 미확인).
- 이 값으로도 F4 기준 과거 성공 틱의 **14/54(26%)** 가 10.5 를 넘고, 재시도 포함 21.0 은 **3/54(6%)** 만 넘는다(재시도는 새 프로세스라 단순 합산 해석 불가 — 대략치). F5 의 «30초를 다 쓰는 군집(멈춤)»은 이 값으로도 못 고친다. 그 군집이 오늘 재현됐는지는 **계측 뒤에만** 안다.
## 4.3 «상한을 늘리기 전에 쪼개기» 설계안
| 안 | 내용 | 판정 |
|---|---|---|
| (a) 키별 순차 | 병렬 3 → 순차 3 | **기각** — 벽시계가 최대 3배(키당 중앙값 7.4s 면 합 약 22s) |
| (b) 분산 틱 | 틱마다 키 하나씩 | **기각** — 한 틱이 세 키를 다 필요로 한다(`load_keys` 의 `STORE_KEYS_MUST_BE_DISTINCT` 검사 포함) |

- 결론: **지금은 쪼갤 안이 없다.** 기동 고정비 반영(§4.2)이 규칙 안에서 가능한 유일한 조정이고, (d)는 계측 결과를 본 뒤 재판정.
