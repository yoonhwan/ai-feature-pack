## receipt 경로 검사를 제거한 범위

`runtime.py:822`의 `_archive_receipts()`는 복원된 암호화 원장에서 receipt의 bundle ID·scope·record count·기존 path를 읽는다. `runtime.py:924`의 복원 경로는 이 결과로 기대 component 이름을 만들고, 임시 복원 component 집합과 정확히 비교한다. 실제 archive 검사는 `restored[name]`으로 수행한다. receipt의 기존 path를 읽을 파일 경로로 사용하지 않는다.

반면 운영 백업 생성과 명시 archive 조회는 여전히 `runtime.py:850`의 `_confirmed_archives()`를 사용한다. 그 경로에는 archive_root 내부·절대경로·regular file·symlink 거부 검사가 남아 있다. 이 분리를 코드에서 확인했다.

합성 백업 사본의 **암호화된 consumer 원장**에서 receipt.path를 project 밖의 존재하지 않는 경로로 바꿨다. manifest의 consumer hash도 갱신하여 초반 checksum 검사 이후의 연결 검증을 시험했다. 결과는 verify=True였으며 spy로 관찰한 archive 검증 경로 2개가 모두 `airag-restore-` 임시 디렉터리 아래였다. 조작된 원래 path는 열지 않았다. 따라서 이 PASS는 임의 경로 접근 허용을 의미하지 않는다.

scope·bundle ID·record count 조작은 아래 표와 같이 거부됐다. 이 negative probe들은 시험 키로 fixture DB를 수정한 것이며, 공격자가 키 없이 암호화된 원장을 수정할 수 있다고 주장하는 재현은 아니다.

## ciphertext_sha256의 실제 보장 범위

**receipt에 저장된 `ciphertext_sha256`와 복원 파일의 ciphertext hash를 직접 동등 비교하지 않는다.** 이 필드를 검사가 수행되는 보안 장벽으로 설명해서는 안 된다. 확인한 실제 경계는 다음과 같다.

1. operations는 백업 component 전체 파일의 SHA-256을 manifest/checkpoint 값과 비교한다.
2. archive 검증은 고정 archive key로 재개방하고 SQLCipher DB integrity, 기대 scope/engine, entry별 payload SHA, canonical payload/ID, 전체 records의 scoped bundle SHA를 검증한다.
3. runtime은 복호화 검증 결과의 전체 bundle ID와 record count를 restored ledger의 receipt와 비교한다.

receipt의 ciphertext hash만 `0` 64자로 바꾼 합성 세트는 verify=True였다. 반대로 manifest의 archive hash를 같은 값으로 바꾸면 `BACKUP_DIGEST_MISMATCH`, archive payload를 바꾸고 manifest 파일 hash를 새로 계산해도 `ARCHIVE_RECORD_DIGEST_MISMATCH`로 거부됐다.

추가로 구버전 방식의 SQLCipher database snapshot은 **논리 contents를 복사해도 복사본 ciphertext hash가 원래 receipt hash와 달라짐**을 실제로 확인했다. 따라서 구버전 snapshot과 원래 receipt의 물리적 hash 동등성을 공통 조건이라고 가정할 수 없다. 신규 archive 복사와 구버전 database snapshot은 같은 방식으로 bytes가 보존되는 것이 아니다.

이번 PASS는 위 파일 hash와 scoped logical bundle 검증에 대한 판단이다. receipt의 모든 메타데이터가 복원 파일과 동일하다는 보장은 포함하지 않는다. 이 검사 범위는 r2에도 존재했으며, 실제 payload·scope·key 위조가 통과하는 추가 결함은 이번 대조에서 확정하지 않았다.

## 재현 조건

양성 종료 확인은 r2 문서의 Python 블록을 그대로 실행한 뒤 `current.verify_backup(oldid)`를 다시 호출한다. 원본 archive 두 파일 모두의 이름을 `finally`로 복구 가능한 방식으로 변경하고 새 backup ID를 verify한다.

negative probes는 유지한 정상 backup 디렉터리를 별도 fixture 세트로 복사해서 수행했다. receipt 조작은 사본의 `consumer.bin`을 기존 시험 key로 열어 `airag_lifecycle_archive_queue.archive_receipt_json` 또는 `payload_json`을 변경한다. 그 후 consumer component의 manifest/checkpoint SHA를 다시 계산한다. 이렇게 하여 암호화 원장·archive 사이의 링크 검사까지 도달하도록 했다.

manifest 공격은 사본의 JSON component/checkpoint만 변경했다. archive payload 공격은 사본의 archive DB를 시험 archive key로 열어 `entries.payload`에 공백 byte를 추가하고 archive component SHA를 다시 계산했다. 코드/테스트 파일을 수정하지 않았다. 구버전 ciphertext 측정용 단일 snapshot은 bytes 비교를 위한 격리 probe이며, 완전한 archive component 세트의 연결 검증 증거로 계산하지 않았다.

운영 DB·Redis·실데이터·외부 endpoint에 접근하지 않았고 키 값을 출력하거나 문서에 기록하지 않았다. 기존 archive filename의 임시 변경은 pytest 합성 fixture에서만 수행하고 복구했다. 소스 수정·커밋·push·프로세스 kill은 수행하지 않았다.
