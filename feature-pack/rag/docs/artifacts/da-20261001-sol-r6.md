## 잠금·시각 신뢰 경계

1. **대기·해제:** 별도 프로세스가 보유한 flock을 실제 helper가 기다리는 것을 확인했다. 보유 프로세스는 stdin 해제 신호로 정상 종료(exit 0)했고, 그 뒤 호출은 완료됐다. malformed 로그, 의도 writer 예외, finalize writer 예외 뒤에도 새 fd의 nonblocking flock 획득이 성공했다. 파일이 남는 것은 잠금 누수가 아니다. with 블록의 handle close가 flock을 해제한다.
2. **교착:** gate의 verify가 사용하는 runtime 잠금은 flock 진입 전에 반환·해제된다. 내부 memory 작업의 runtime 잠금은 nonblocking이며, 현재 helper 호출 경로에 역순으로 blocking 획득하는 경로가 없다. 합성 runtime 잠금을 보유한 채 decide를 호출했을 때 즉시 BACKUP_VERIFICATION_FAILED로 중단하고 decision lock 누수도 없었다. 모든 외부 호출/운영 부하에서 교착이 불가능하다고 일반화하지 않는다.
3. **대기 시간:** helper의 flock에는 독립 timeout이 없다. notebook 결정 셀의 기본 subprocess timeout은 240초이고, subprocess.run이 timeout 시 자식을 종료하면 OS가 fd를 회수한다. 이 리뷰에서 강제 종료를 수행하지 않았다. 정상 7셀은 새 락과 완료 시각 검사 후에도 전부 통과했다. 시간 경계 재검사는 R6-M1의 별도 결함이다.
4. **시각 형식:** completed_at은 runtime의 verify 반환에서 오며 operations는 manifest를 읽어 fromisoformat과 aware time 검사를 먼저 수행한다. Z와 +09:00의 동등한 시각은 통과했다. naive/잘못된 시각은 BACKUP_VERIFICATION_FAILED, 미래 시각·6시간+1µs는 BACKUP_RECEIPT_STALE, 정확히 6시간은 통과했다. 형식 오류로 기억을 쓰는 경로는 확인되지 않았다.
5. **신뢰의 범위:** completed_at은 검증된 세트의 **plaintext manifest 메타데이터**다. component/checkpoint 해시 검사는 DB/파일 내용과 일치함을 확인하며 manifest 시각을 암호학적으로 인증하지 않는다. 합성 manifest의 completed_at과 영수증의 at/run을 모두 재표기하면 실제 48시간 전 snapshot으로 materialized가 됐다. 이는 r5가 명시한 **영수증만 재작성하는 범위**를 넘어 백업 manifest까지 수정하는 경우다. 이번 패치가 그 더 넓은 변조 범위까지 해결했다고 주장하지 않으며, 이를 새 blocker/major로 확대하지 않았다. 시간 조건이 검사 가능한 메타데이터에 의존한다는 신뢰 가정이 남는다. completed_at만으로 이번 실행의 생성 provenance까지 증명하는 것도 아니다.
