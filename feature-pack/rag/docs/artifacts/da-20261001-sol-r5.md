### R5-M1 — 두 결정 호출이 겹치면 성공한 다른 결정의 의도·결과 기록을 덮어쓴다

- 원인: JSON 파일의 읽기→의도 쓰기→코어 변경→마무리 쓰기 전체를 직렬화하지 않는다. atomic rename은 개별 파일 교체만 보호한다. runtime의 개별 코어 작업 잠금도 이 helper 시퀀스 밖에 있다.
- 재현: 정상 검증 백업과 동일 run에서 서로 다른 두 합성 후보를 승인한다. 호출 A를 첫 write 직전에 잠시 멈춘다(이미 기존 빈 로그를 읽고 자기 의도를 만들었다). 호출 B의 실제 helper·코어 승인을 끝낸다. A를 계속 실행한다. 이 순서는 실제 두 프로세스에서도 가능한 스케줄이다. synthetic seam은 A의 write 전 대기뿐이며 저장·승인·마무리는 실제 구현이다.
- 관찰: 두 호출 모두 materialized, log_complete=True, 코어 기억 2개. 최종 로그에는 A의 한 항목만 남고 B의 의도와 결과가 모두 사라졌다. summary도 approve:materialized=1만 보고한다. 예외나 실패한 파일 writer가 없어 경고도 없다.
- 의미: 이번 수정이 보장하려는 사용자 결정 provenance가 다시 누락된다. 단일 호출의 pending 보존만으로는 여러 writer의 전체 파일 교체를 보호할 수 없다.

## 신규 경계와 복구 대조

1. **6시간/실행 식별자:** 정상 영수증은 같은 run에서만 쓸 수 있다. 정확한 상한·상한 초과·미래 시각을 확인했다. run 값의 비어 있음과 동등성을 검사하며 UUID 문법을 검사하지 않는다. UI가 UUID를 생성하는 계약과 helper의 불투명 run token 비교를 구분했고, UUID 문법 자체는 결함으로 세지 않았다.
2. **의도/결과 불일치:** finalize 실패 후 summary에 verify:pending=1이 남는다. 같은 후보의 verify를 재실행하면 멱등적으로 materialized를 반환하며 기억 수는 1로 유지된다. 새 done 항목은 기록되지만 원래 pending 항목은 pending으로 남는다. 자동 reconciliation 기능은 없으며, 의도와 후속 성공 기록을 사람이 대조할 수 있는 수준의 복구다. 이를 완료 결과가 자동 복원됐다고 표현하지 않는다.
3. **재검증의 부작용·지연:** operations는 임시 디렉터리로 구성 파일을 복사하고 해시·DB 무결성·연결을 확인한다. 만료 refresh도 복원된 임시 원장에 적용한다. 운영 복원을 수행하지 않는다. 합성 세트의 독립 verify는 0.010초였으나 실제 세트 크기의 성능 보장은 아니다. 백업 셀은 300초·15초 heartbeat, 결정 셀은 notebook 기본 240초·heartbeat 없음이다. 큰 세트의 시간 초과를 실제로 재현하지 않았으므로 성능 결함으로 세지 않았다.
4. **만료 후보 UI/쓰기:** 두 상태 모두 본문·인용·proof가 비었고, UI는 3개 만료 후보를 placeholder로 렌더링했다. 본문 라벨은 출력하지 않았고 보류 선택은 빈 결정이었다. UI에서 stale 번호를 승인/검증 대상으로 고르는 입력 자체는 막지 않지만, 코어는 이를 SOURCE_CHANGED로 거절한다. 이는 기존 terminal rejection 계약이며 일반 승인 성공으로 잘못 판정하지 않았다.
