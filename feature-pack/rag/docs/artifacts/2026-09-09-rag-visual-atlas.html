세 겹의 표준화 결과물

① 원본 바이트(original_ref, 불변) · ② 표준 MD(사람이 읽는 뷰, 자체 해시/버전 보유) · ③ 구조화 표현 + 앵커 + 청크(검색 단위, provenance 보유) — 셋은 서로 연결되지만 별개의 산출물입니다. HybridChunker는 재-파싱한 MD 문자열이 아니라 DoclingDocument(구조화 표현)를 직접 입력으로 받습니다.

OCR · 비전 설명 · 임베딩 구분

OCR(이미지 속 가시 텍스트 인식) · 비전 설명(모델의 해석 캡션, 사실이 아닌 해석으로 별도 라벨) · 임베딩(검색용 벡터, 위 결과들로부터 생성)은 서로 다른 층이며 하나로 합쳐 표기하지 않습니다. 혼합 페이지(디지털+스캔)는 페이지/영역 단위 처리가 필요할 수 있으나, Docling의 정확한 기본 자동판별 알고리즘은 이번 조사에서 확인되지 않았습니다.

책임 경계 — 외부 배선 vs AI RAG CLI

신규/변경/삭제 감지, 파일 워처·폴링·스케줄·자동 폴더 탐색은 이 코어의 책임이 아니라 사용하는 프로젝트(소비자) 쪽 외부 배선입니다. AI RAG CLI는 add/update/delete/search/expand/fetch 같은 명시적 요청만 받아 표준화·청크·색인·불변 원본/이력 관리를 수행하고 결과를 반환하는 일반 처리기입니다. 내장 디렉터리 워처나 상시 감시 루프는 core 범위가 아닙니다. delete 요청은 원본 파일이 이미 사라진 뒤에도 등록된 소스를 식별해 검색에서 제외하고, 관리 이력·원본은 보존합니다(원격 파일 자체를 지우지 않음). 요청 정확성(충돌 판정, 원자적 발행/tombstone, 재현 가능한 조회 스냅숏)은 트리거 타이밍과 무관하게 core 안에서 보장됩니다.
