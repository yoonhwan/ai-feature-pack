# 4. 권고 1안 — 연달아 3단계 (N1 → N2 → N3)

## 4.1 순서와 이유
1. **N1(launchd 프로브) 먼저:** 뒤의 터미널 실행이 `op` 파일 캐시를 데워 N1 의 콜드 조건을 바꾸지 않도록 먼저 한다.
2. **N2(E1 평소)** 와 **N3(E1 + `taskpolicy -b`)** 를 이어서: N1 과 같은 몇 분 안이라 시간·부하 차이(L4)를 줄인다. N3 는 N2 직후라 파일 캐시 상태가 같다.

## 4.2 단계 간 이어 가기 규칙 (Master 가 만드는 한 줄 스크립트의 계약)
- 각 단계의 종료 코드로만 판단한다(출력 해석 없음): 프로브 종료 0(완료)일 때만 다음으로. 프로브 종료 1(결과 불완전)·3(등록 실패)·4(잔존 확인 필요)·2(시작 거부)·130/143/129(중단)이면 **남은 단계를 실행하지 않고** 그 사실을 화면에 표시하고 멈춘다. E1 종료 0 일 때만 N3.
- 어떤 단계도 자동 재시도 없음. Ctrl-C 는 현재 도구의 정리(각 도구 계약)가 끝난 뒤 남은 단계를 건너뛴다.
- 단계별 상한은 각 도구 그대로: 프로브 **최대 75초**, E1 **최대 75초**, E1(N3) **최대 75초** → 전체 최대 **225초 + 단계 사이 여유**(스크립트 자체 마감 240초). 정상 시 프로브 20~40초(P0 가 통과하면 P2·P1 포함), E1 각 수 초.
- Master 사전 점검(오빠 입력 전, 읽기 전용): 경로 실재(`test -f`)·`bash -n`·`taskpolicy` 실재·대화형 프롬프트 0·`!` 한 줄 규칙(60자 이내, `/tmp/h<N>` 한 줄).
- 결과 수집: 오빠 스크립트가 각 도구의 값 없는 요약만 화면에 보이고, Master 가 결과 파일 3개(프로브 `result.json`, E1 두 개)와 사후 TCC 조회(구간별 `DeveloperTool`·AppData 건수만)를 읽는다.

- **한 번의 3단계로 원인이 확정되지는 않는다.** «연관 라벨 + 다음 한 걸음»만 얻는다. 특히 Background 로 판명돼도 운영 plist 변경(ProcessType 제거 등)은 **별도 설계·DA·HIL** 이다.

# 5. 오빠 부담 0 으로 Master 가 지금 할 수 있는 읽기 전용 단계

1. **오빠 한 줄 스크립트 사전 점검** (§4.2 마지막 항목).
2. **`taskpolicy -b` 동등성 사전 확인(읽기 전용):** `man taskpolicy`(`-b` = `PRIO_DARWIN_BG` 로 `setpriority` 호출, 자식 상속)와 launchd `ProcessType=Background` 문서(launchd.plist(5))의 서술을 대조해 «같은 정책인가»를 문서 근거로 적어 둔다. 동등성이 문서로 확인되지 않으면 N3 결과는 «Background 우선순위 흉내와의 연관»으로만 읽는다(미확인 명시).
3. **사후 로그 대조 준비:** 위 세 구간의 `subsystem == "com.apple.TCC"` 조회를 같은 방식(7초 한도·원문 비저장)으로 준비 — 건수만 기록.
4. 전부 `op` 실행 0·토큰 열람 0.

# 6. 오빠께 드릴 질문 1개 (Master 가 사전 점검 뒤 올림 · 이 문서가 실제 승인을 대체하지 않음)

> **정정 한 줄:** 같은 `op --version` 이 오빠 터미널에서는 6번 모두 0.2초 안에 끝났고, 지난번 launchd 프로브에서는 7초를 넘겼습니다. 지금 보이는 차이 후보는 launchd 의 낮은 우선순위(Background) 설정 등이며 아직 확정이 아닙니다. 팝업과 타임아웃이 같은 원인인지는 여전히 모릅니다.
>
> **질문:** `! bash /tmp/h<N>` 한 줄을 1회 실행해 주세요(최대 4분). 기존에 검수된 도구를 **수정 없이** 순서대로 돌립니다: ① launchd 프로브(지난번과 같은 것) ② 터미널 `op --version` 6번 측정 ③ 같은 측정을 낮은 우선순위로.
> - **①에서 일어날 수 있는 일(지난번과 같음):** 임시 launchd 작업 등록·자동 내림 / `op --version` 이 통과하면 서비스 계정 토큰 파일을 읽어 계정 종류 조회(최대 3회)·버전 조회 1회·네트워크 도달 확인 1회(항목 값은 읽지도 저장하지도 않음) / `~/.config/op` 공유 상태 접촉 가능 / 1Password 팝업이 뜰 수 있고 개수 보장 불가 — 누르지 말 것(«허용 안 함»도 설정으로 저장될 수 있음) / 끝난 뒤 남을 수 있음.
> - **②③:** 서비스 계정 토큰 주입·토큰 파일 읽기·계정 조회 없음. `op` 가 내부적으로 네트워크나 기존 데몬에 접촉하는지는 미확인. 새 `op` 데몬이 생기면 임시 폴더를 지우지 않고 «남은 것 확인 필요»로 표시.
> - 중간에 문제가 생기면 남은 단계는 실행하지 않고 멈춥니다. Ctrl-C 로 언제든 멈출 수 있습니다(정리 후 종료). 기존 1Password 데몬은 어떤 단계도 종료하지 않습니다. consumer 는 계속 꺼 둡니다.

# 7. 후퇴안

- **후퇴안 A(토큰·계정 조회 없는 쪽만):** ②③ 만(최대 150초). 얻는 것: Background 흉내와의 연관(터미널 안), 잃는 것: launchd 쪽 같은 시간대 쌍과 재현 여부.
