## 2.2 시도 한도·종료 절차 (M1)
- **상한:** P1 = 실제 h 파일 실행 **최대 2회**. 1회째 = 최초 오빠 HIL. 2회째는 **호출 1 이 H0c 인 경우에만, 기술 원인을 Master 가 고친 뒤(또는 원인을 설명한 뒤), 새 오빠 HIL 1건**으로만 가능하다. 2회째 뒤에는 결과와 무관하게 **더 이상 없다**(3회째는 이 설계의 범위 밖 — 새 설계·DA·오빠 판정).
- **최대 호출 수:** 한 번의 실행 = `op --version` 최대 2회·P4 네트워크 확인 최대 2회(호출당 각 1). P1 전체 = 각 최대 **4회**. 호출당 시도 7.0초·재시도 0(7초 룰 불변). 호출당 75초 상한·chain 240초 미적용·새 합계 deadline 없음(r12 §2.4-6 그대로).
- **H0 뒤 종료 절차(최초 실행):** 호출 1 이 H0c 이거나 래퍼가 중단된 경우 → **기술 결과만 보고하고 멈춘다**: 어느 호출이 어디까지 실행됐는지, 각 호출의 rc·폴더 대응·실패한 검사(a~g 중 무엇)·**측정된 P4/P0 값(있으면 병기)**, 남은 프로세스(rc=4 면 정리 전 재시도 금지 — 남은 것 확인이 먼저). 자동 재실행 0. 재시도 여부는 오빠 새 HIL 1건(§2.2 상한 안에서)이며 그 요청에 「이미 소모된 시도 수」를 적는다.
- **호출 2 만 H0c/미시작/P4 비성공이면 재시도 사유가 아니다.** 호출 1 이 적격이면 그 관측은 이미 판정 단위를 채웠고, 호출 2 때문에 같은 쌍을 다시 재지 않는다(선택 편향 방지).
- **부적격 호출 1 의 측정값 병기 규칙(재시도 선택 편향 방지):** 1회째 호출 1 이 H0c 인데 측정값이 있었다면(예: P0 가 회수 확인된 timeout 이었으나 profile/폴더 검사에서 걸림) 보고와 재시도 요청에 그 값을 **그대로 병기**한다. 2회째 호출 1 이 적격 success 로 자격 충족이 되더라도 보고에 「1회째 부적격 호출 1: P0 timeout(분모 제외, 값 병기)」을 함께 적는다. 이 병기는 판정을 바꾸지 않고 읽는 사람이 선택 편향 여부를 직접 보게 한다.
## 2.3 판정 매트릭스 — 호출 1 4상태 × 호출 2 4상태, 전 16칸
**호출 1 상태:** A = 적격·P4 success·P0 success / B = 적격·P4 success·P0 회수 확인 timeout / C = 적격·P4 비성공(회수 확인 timeout 또는 network_error 등, P0 값은 병기) / D = 부적격(H0c).
**호출 2 상태:** a = 적격·P4 success(P0 success 또는 회수 확인 timeout) / b = 적격·P4 비성공 / c = 부적격(H0c) / d = 미시작(호출 1 rc≠0·잔존·신호·폴더 0/2+ 등으로 래퍼가 시작 안 함, 또는 호출 1 직후 래퍼 신호).
**후보 자격(호출 1 단독):** A → **충족**(위치 1 × 지정 안 함 적격 관측 누적 2/2 기한 안: r13 D2 호출 1 360ms + 이번 A). B → **불충족**(지정하지 않은 첫 작업에서도 기한 초과 관측). C → P4 가 회수 확인 timeout 이면 **불충족**, 그 밖의 비성공(network_error 등)이면 **성립 안 함(판정 보류)** — 어느 쪽이든 후보 없음·재측정 요구 없음. D → **성립 안 함(표본 없음)**.
**쌍 수준 표:** 호출 1 ∈ {A, B} 이고 호출 2 = a 일 때만 r12 §2.3 의 R1~R4 (A·a → P0 success 면 R1, timeout 이면 R2 / B·a → P0 success 면 R3, timeout 이면 R4). 그 밖의 칸은 H1 또는 H0 로 「해석 보류」+ 관측 병기.
| 호출 1 \ 호출 2 | **a** 적격·P4 success | **b** 적격·P4 비성공 | **c** H0c | **d** 미시작 |
|---|---|---|---|---|
| **A** (success/success) | 자격 **충족** · 쌍: **R1**(호출 2 P0 success) 또는 **R2**(timeout) · 시도 1 소모 · 종료 | 자격 **충족** · 쌍: H1 해석 보류(호출 2 P4 값 병기) · 시도 1 소모 · 종료 | 자격 **충족**(호출 1 은 삭제·재측정 안 함) · 쌍: H0 해석 보류 · 호출 2 의 실행·값 기록 · 종료 · 재시도 **없음** | 자격 **충족** · 쌍: 미완(해석 없음) · 시도 1 소모 · 종료 · 재시도 **없음**(단, 래퍼 신호·잔존이면 정리 확인 후 보고) |
| **B** (P4 success·P0 timeout) | 자격 **불충족** · 쌍: **R3**(호출 2 success) 또는 **R4**(timeout) · 종료 | 자격 **불충족** · 쌍: H1 해석 보류 · 종료 | 자격 **불충족** · 쌍: H0 해석 보류 · 호출 1 timeout 삭제 안 함 · 종료 · 재시도 **없음** | 자격 **불충족** · 쌍: 미완 · 종료 · 재시도 **없음** |
| **C** (P4 비성공) | 호출 2 가 a 이면 호출 1 이 P4 비성공이므로 쌍 판독은 **H1**(호출 2 가 a 인 경우 그 값 병기). 자격: timeout 이면 **불충족**, 그 밖이면 **판정 보류** · 종료 | 자격 동일(timeout→불충족 / 그 밖→보류) · 쌍: H1 · 종료 | 자격 동일 · 쌍: H0 · 종료 · 재시도 **없음** | 자격 동일 · 쌍: 미완 · 종료 · 재시도 **없음** |
| **D** (부적격) | 자격 **성립 안 함**(호출 1 표본 없음) · 쌍: H0 해석 보류 · 호출 2 값 병기 · **재시도 선택지**(§2.2: 1회째일 때만, 새 HIL 1건) | 자격 성립 안 함 · 쌍: H0 · 재시도 선택지(1회째일 때만) | 자격 성립 안 함 · 쌍: H0 · 재시도 선택지(1회째일 때만) | 자격 성립 안 함 · 쌍: 미완 · 재시도 선택지(1회째일 때만, **rc=4 면 정리·확인 후**) |
- **전 16칸 검산:** 행 4×열 4 = 16칸, 각 칸이 자격 결과(충족/불충족/보류/성립 안 함) 하나와 쌍 수준 결과(R1~R4/H1/H0/미완) 하나와 후속 하나(종료/재시도 선택지)를 가진다. **재시도 선택지는 D 행 4칸(호출 1 부적격)뿐**이고 그것도 1회째에 한정된다. 2회째 실행의 D 칸은 「성립 안 함·**종료**(상한 2회 소진)」이다.
- **우선순위(충돌 시):** ① 호출 1 의 적격/자격 판정 → ② 호출 2 와 쌍 수준 판독(r12 §2.3) → ③ 후속(종료/재시도). 쌍 수준 H0/H1 은 호출 1 의 자격 판정을 **바꾸지 못한다**.
- **호출 2 의 R2/R4(둘째의 적격 timeout)·H1·H0c 는 기록·병기만 하며 판정 규칙을 바꾸지 않는다**(r13 에서 수용된 원칙 유지).
- **신호·잔존:** 첫 호출 rc≠0(잔존 4·신호 129/130/143 포함)이면 둘째 미시작·그 코드를 보존하는 r12 §2.4-2~3 의 h 파일 계약을 **변경하지 않는다.** 래퍼 자신이 신호를 받은 경우도 같다(DA r12 인수 주의점 2개 그대로).
## 2.4 후보 자격 충족·불충족의 의미 (경계 유지)
- 충족은 「운영 plist `ProcessType` 변경 **설계**(설치 경로·되돌림·R-2 재설치와의 순서)를 시작할 자격」뿐이다. 운영 plist·runtime.json·설치본 변경, consumer 재개 승인, 원인 확정을 허가하지 않는다(r13 §2.4 경계 유지).
- 불충족·성립 안 함은 `ProcessType` 을 운영 변경 후보로 올리지 않고 판별을 끝내고 R-3·R-4 경로(오빠 판정)로 간다. 추가 측정 요구 없음.
## 2.5 오빠 고지·승인표 일치 (M1)
- **오빠 질문 1개:** `! bash /tmp/h<N>` 한 줄 실행(Master 가 `ft-hil.sh --add` 로 생성). 고지(r12 §2.4-6 유지 + 변경분): 순서 「지정 안 함 → Background」, **이번 한 번의 실행**에서 `op --version`·P4 네트워크 확인(my.1password.com 연결) **각 최대 2회**, **P1 전체로는 실행 최대 2회·각 최대 4회**(2회째는 기술 원인을 고친 뒤 새로 여쭤 봄), 서비스 계정 토큰 접촉 0 은 스크립트의 토큰 파일 읽기·`op` 전달·계정 조회 없음에 한정(`op` 내부 접촉 미확인), 호출당 75초 상한(직전 약 14초는 실측 참고이며 보장 아님)·chain 240초 감시 미적용·새 합계 deadline 없음, 팝업 가능성·누르지 말 것·consumer 계속 꺼 둠·Ctrl-C 로 중단 가능. 이전 3회(h67·h87·h88) 팝업은 모두 «없음»이나 부재의 보장은 아님.

# 3. §4.1·§4.2·§4.3 대체 — `op daemon` 서술 한정 (minor)
## 3.1 직접 읽은 사실 (읽기 전용 `ps`·소켓 stat · `op` 실행 0 · 환경·argv 값 출력 0)
- 현재 `op daemon` **26개**, 같은 사용자·부모 PID 1·상태 sleep·CPU 합 0.0. 시작 시각은 10-15 14:14 **1개** / 10-16 10:50~11:03 **7개** / 12:04~12:35 **7개** / 14:44~15:18 **11개**, 가장 늦은 시작 15:18:26. RSS 합계는 **표본 시각마다 다르다**(내 조회 약 101MB, DA 의 후속 표본 약 90.9MiB·앞선 표본 약 75.4MiB 보고) — 현재값은 프로브 당시 상태나 위험 부재의 보증이 아니다.
- Master 실측(발주 #2641): 26개 전부 PPID 1, 열린 유닉스 소켓 경로명이 `~/.config/op/op-daemon.sock` **한 개로 같음**(같은 inode 인지는 **미확인**), 소켓 mtime 10-16 15:18, 이 리포 mbox 에는 `op` 호출 기록 없음(출처 시각 대조 불가).
- **`s0.op_process_count` 의 정의(정정):** 프로브가 P4/P0 **전에** 읽는 `pgrep -x op` **전체 프로세스 수**이다(`probe.py:488`; `op daemon` 전용 아니며 다른 `op` 실행도 센다). 따라서 숫자 15·26 을 「데몬 수」로 읽지 않는다. 10-15 s0=2 인데 현재 생존하는 그 시기 시작 군집은 1개라 **당시 count 와 현재 생존 프로세스는 일대일이 아니다.**
- **한정된 관측(r13 의 해당 문장 대체):** ① s0 count 가 N4-A1(16:59) 이후 5개 폴더에서 26 으로 같고 현재 생존 프로세스의 시작 시각이 모두 프로브 이전이다 → **「후속 스냅샷·현재 생존 프로세스 기준 지속 증가 미관측」.** 각 `op` 실행이 새 프로세스를 만들지 않았는지·중간 생성/종료가 있었는지는 이 자료로 알 수 없다. ② 군집 시각의 **당시 생성 주체는 미확인**이다 — `consumer` 가 그 시점 disabled/loaded=false 였다는 스냅샷은 이전 군집 생성 시각의 consumer 실행 이력을 제외하지 못한다. ③ 소켓 mtime 15:18:26.667 과 가장 늦은 시작의 초 단위가 같다는 관측은 소켓을 갱신한 PID 의 귀속 증명이 아니다.
- r13 §4.1 의 「`op --version` 은 데몬 수를 늘리지 않았다」·「consumer 가 disabled 였으므로 consumer 틱이 만든 데몬이 아니다」 두 문장은 **삭제한다.** 「개수와 지연 사이 관측된 관계 없음」은 **「단독으로 결정적인 관계를 뒷받침하는 자료가 없다(표본 7건, 개수는 `op` 전체 프로세스 수)」** 범위로만 쓴다.
## 3.2 A03 처리 (r13 §4.2 우선순위 유지)
**원인 후보로 올리지 않고 «별건 기록 + 읽기 전용 메타데이터 관찰»로 둔다.** 승격 조건(관찰 우선순위 규칙, 임계 수치는 이 설계가 만들지 않음): 개수·자원 사용이 눈에 띄게 변하거나 재개 후 `op` 호출 지연이 개수 변화와 **동행**하는 관측이 생기면 검토 승격. 현재 CPU/RSS 를 프로브 당시 상태나 위험 부재 보증으로 쓰지 않는다. **공유 데몬 종료·신호·원인 확정은 계속 금지**한다.
## 3.3 읽기 전용 추가 수집 범위 (r13 §4.3 대체)
수집해도 되는 것: **시각**(군집 시작 시각·좌석 활동 시각)·**도구 종류**(예: 어느 도구가 그 시각에 `op` 를 부를 수 있는지의 일반 종류)·**선택한 프로세스의 메타데이터**(PID·시작 시각·상태·열린 유닉스 소켓의 **경로명·개수·inode 번호**).
수집하지 않는 것: **원문 mbox 본문·자격 증명·프로세스 argv·환경 값·소켓 내용**. 소켓에 연결하거나 읽지 않고, `op` 를 실행하지 않고, 데몬에 신호를 보내지 않는다. 같은 시각에 활동한 좌석은 **출처 후보일 뿐**이다. Master 가 이미 한 실측 결과(위)는 이 범위 안이다. 남은 항목: ① 26개 소켓이 **같은 inode** 인지(`stat`/`lsof` 의 inode 열, 내용 읽기 아님) ② 후속 프로브·P1 의 `s0` 시계열 유지(자동) ③ 실행 직후 `vm.swapusage`·memory free 를 같은 시각에 병기(연관 후보 열기용, 판정 아님).

# 4. 7초 룰 (변경 없음)
모든 측정은 단계당 7.0초·재시도 0 이고 상수를 키우지 않는다. 쌍 전체 재실행은 7초 룰과 별개이므로 §2.2 의 시도 상한으로 제한한다. 7초 밖 측정은 오빠 결정으로만 별도 상신한다.

# 5. note — 누적 라벨의 범위 (한 줄 유지)
r13 §2.2 의 7건 누적 라벨(「지정 여부와 연관된 관측」)은 **별도의 사후 집계**이며 **r10 N4 association 행이 성립했다는 뜻이 아니다**(N4 는 기존대로 해석 보류, D2 는 기존대로 R1). 원인·통계적 효과·지정 효과의 우세/배제 판정으로 전달하지 않는다. 팝업 «없음» 3회(h67·h87·h88)는 오빠 관찰 보고이며 부재의 보장이 아니다.

# 6. 미확인 (r13 유지 + 추가)
r13 §7·r12 §5 전부 유지. 추가: 26개 소켓 보유의 같은 inode 여부 · `s0` count 와 daemon 수의 대응(정의상 불일치 가능) · 중간 생성·종료된 `op` 프로세스 유무 · 군집별 생성 주체 · P1 1회째 호출 1 이 H0c 일 때의 기술 원인(발생 시).
