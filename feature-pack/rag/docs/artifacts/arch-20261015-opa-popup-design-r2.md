# 0. r2 요약 (먼저 읽기)

1. **r1 의 핵심 서사가 틀렸다 — 틱 로그를 시각까지 다시 집계해 정정한다 (§1).** op 키 읽기는 launchd 에서 «항상 막힌 게 아니라 **간헐적으로** 실패»했고, 타임아웃 231건은 **전부 재부팅(10-13 10:58) 이전**이며, 팝업 요청(10-13 11:44) 시각의 직전 틱은 **성공**이었다. 따라서 **«팝업»과 «타임아웃»은 별개 문제일 수 있다.** 해결 대상을 둘로 나눈다: **(문제 가) 팝업이 뜬다 · (문제 나) 키 읽기가 간헐 타임아웃.** 둘이 같은 원인이라는 증거는 없다.
2. DA r1 의 필수 수정 9항목 반영 표는 §9. 외부 호출 **7초 룰을 설계 안에서 확정**했고(프로브·`tick.py` 모두), `timeout=30` 수정은 **구현 범위에 포함**했다 («별도 기록만» 문구 삭제).
3. 프로브(1회 승인)는 **계정 조회 경로의 «후보 축소»만** 한다. 키 읽기 경로 검증은 **별도 승인·값 비출력 후속 단계(S2)** 로 분리했다. 모든 분기에서 **consumer 는 서버 18712·18703 복구 통보 + HELM 재개 절차 전까지 disabled 유지.**
4. ⑦(책임 프로세스 분리)는 **승인 제외·실험 후보.** 프로브에서 P3 를 뺐다. ⑤는 «전용 설정 경로 사용 후보»로 격하했다(격리·차단이 아님).
5. **즉시 진행해도 되는 것은 7초 룰 수정(구현 단계 I-1) 하나뿐**이다 — 원인과 무관하게 필요하고 틱 점유(팝업/지연 대기)를 줄인다. 나머지는 증거 뒤.

## 1.1 틱 로그 재집계 (이번에 시각 단위로 직접 재집계, 값 없는 필드 `ts/status/exit/code/type` 만)

해석 (사실에서 직접 나오는 범위만):
- **«op 가 launchd 에서 항상 막힌다» 는 틀렸다.** 막힘/통과가 **시간에 따라** 바뀌었다 (10-02 통과 → 10-12 낮 혼재 → 10-12 밤~10-13 아침 거의 전부 실패 → 10-13 10:43 이후 통과).
- 바뀐 계기는 **미확인**이다. 재부팅이 계기가 아니다(회복이 재부팅보다 먼저). 화면 켜짐/꺼짐(`pmset -g log` Display 이벤트 19개)과도 안 갈린다 — 타임아웃 222건이 화면 «켜짐» 상태였다. **후보 중 데이터로 기각된 것: 재부팅, 화면 상태.**
- **TCC `AppData` 팝업 요청 3건(10-13 11:44:00)은 틱 11:43:59(성공)과 같은 시각**이다 (master-progress.md:172 의 근거 + 이번 집계). 즉 **팝업 요청이 있어도 그 틱은 키를 읽는 데 성공했다.** 팝업은 «op 를 막는 원인»이 아니라 **op 실행의 곁가지(비동기 접근 시도)일 수 있다.** 단 타임아웃 기간(10-12~13 아침)에 팝업이 있었는지는 로그 보존 한계로 **미확인**(이번 `log show` 재조회도 0줄).
- ⇒ **서로 다른 두 문제로 취급한다:** (가) 팝업이 뜨는 것(오빠 불편) · (나) 키 읽기가 간헐적으로 30초 타임아웃(운영 신뢰성). 오빠 목표 «팝업이 영구히 안 뜨고 상시 안정 가동» 은 둘 다 닫아야 한다.

# 3. 외부 호출 7초 룰 확정 (DA B1)

기준: 시도당 상한 = 기준 요청량 1회 7초(CLI 서브프로세스는 기동 고정비 3.5초 잠정 가산) · 재시도 최대 1회(첫 출력 전 실패만) · 전체 마감 전파 · 어떤 값도 70초 천장 밖으로 나가지 않는다. 계정 조회·키 1개 읽기는 «분할 불가능한 크기 아는 배치»가 **아니다** → 70초 조건부 확장 근거 없음.

## 3.1 `tick.py` 의 op 호출 (구현 범위에 포함 — I-1)
| 항목 | 값 |
|---|---|
| 시도당 상한 | **10.5초** (= 7 + 3.5 기동 고정비) — 현행 `timeout=30` 대체 |
| 재시도 | 최대 **1회**. 대상 오류: `TimeoutExpired`(첫 stdout 출력 전) 만. `OSError`(스폰 실패)·`returncode≠0`(인증/형식 오류)은 **재시도 안 함**. 읽기(`op read`)는 멱등이라 안전 |
| 전체 마감 | 호출(키 1개)당 **21초** (= 10.5 × 2). 2차 시도의 timeout = `min(10.5, 21 − 경과)`, 남은 시간이 1초 미만이면 재시도 안 함 — 마감은 호출 단위로 전파 |
| 틱 전체 | 키 3개 병렬이라 최대 ≈21초 + 로컬 처리. 재시도는 각 호출 내부 순차이므로 한 호출당 동시 op 프로세스는 ≤1 (최대 동시 3 유지) |
| 이유 코드 | 기존 `OP_READ_UNAVAILABLE`·`OP_KEY_READ_OR_FORMAT_FAILED` 재사용 → **레지스트리 528 불변.** 재시도 횟수는 로그에 새 코드를 만들지 않는다 |
| 상수 | `OP_ATTEMPT_TIMEOUT_S = 10.5`, `OP_CALL_DEADLINE_S = 21.0` — 모듈 상수(주석 1줄: 출처 룰) |
| 시험 | (1) stub op 가 sleep 하여 `TimeoutExpired` → 시도 2회·`OP_READ_UNAVAILABLE`·type=TimeoutExpired (상수를 monkeypatch 로 0.2/0.4초로 줄여 시험 시간 단축) (2) rc≠0 → 시도 1회 (3) 스폰 불가(`OSError`) → 시도 1회 (4) 2차 시도 timeout ≤ 남은 마감 (5) 기존 `test_op_child_environment_is_an_allowlist` 불변 통과 |
| 위험 | 정상이어도 콜드 스타트가 10.5초를 넘으면 실패로 보일 수 있다 → 단계 S2 에서 정상 시 소요 분포 측정(성공 틱 57건의 pass 소요는 로그 `pass_elapsed_s` 로 이미 보임: 구현 DA 에서 확인). 이 위험이 확인되면 상수는 «룰에서 허용하는 크기비례 조정»이 아니라 **분할(호출 쪼개기)** 로 푼다 |
| 부작용 주의 | 재시도 1회는 팝업이 대기 중인 환경에서 op 요청을 키당 최대 2회로 늘린다 (복수 팝업 가능성). 이를 수용하는 것은 룰의 기본값이다 |

## 3.2 프로브의 외부 호출
- **단계별 단일 시도(재시도 0)**: 관측 순도를 위해 재시도를 쓰지 않는다 (룰 상한 «이하»).
- P4 도달성: **하나의 7초 마감**을 TCP 연결 + TLS 핸드셰이크에 **공유**한다(연결 후 남은 시간만 핸드셰이크에 사용). 단계별 개별 5초+α 금지.
- P0·P1·P2 (CLI): 시도당 10.5초.
- **외부 호출 마감과 구분되는 로컬 예산** (룰 대상 아님): launchd 작업 시작 대기 ≤10초 · 결과 대기 ≤ 외부 호출 합계 + 15초 · 정리 ≤15초 · 전체 하드 상한 **105초** (아래 §4.3 상한 표).

# 4. 증거 수집 프로브 (1회 승인) — 결론은 «후보 축소»로 제한 (DA M1·M2·M3·m2)

## 4.1 제한: 이 프로브가 말할 수 있는 것 / 없는 것
- 말할 수 있음: **계정 조회(`op user get --me`) 경로**에서 기본 경로와 전용 경로의 차이, op 기동 자체(`op --version`)의 지연, 도달성, 요청 시점의 TCC 요청 상관.
- **말할 수 없음:** 키 읽기(`op read`) 경로의 성공/실패, vault 접근, 3 병렬 동시성, 간헐 타임아웃의 원인. **프로브 성공 = «정상 가동» 아님**, 프로브가 통과해도 후속 S2 전에는 어떤 운영 판정도 내리지 않는다.
- 간헐 현상이라 **단일 시행의 «성공»은 «문제 없음»을 뜻하지 않는다**(§1.1). 판정은 «재현 여부를 본 후보 축소» 수준이다.

| P1 | 같은 호출 | 실제 HOME (= tick 조건) | 10.5초×1 | 기준선 재현? |
| P1b | P1 한 번 더 | 실제 HOME | 10.5초×1 | 간헐성(같은 조건 2회) — P1 이 `success` 이고 팝업 미관측일 때만 실행 |

- **중지 규칙:** 어느 단계든 `timeout`(또는 `observation_unknown` 중 팝업 가능성)이면 **후속 단계를 `skipped_prior_unresolved` 로 기록하고 중지**한다. 단 P4 는 독립이라 먼저 실행한다. (P0 가 타임아웃이면 P2·P1 은 실행하지 않는다 — 그 자체가 «자격 없이 op 기동에서 이미 막힘» 이라는 결과.)
- **단계 순서 근거:** 가장 덜 침습적인(P0) → 전용 경로(P2) → 기준선(P1). P2 를 P1 앞에 두는 이유: P1 이 팝업을 띄우면 이후 중지되므로, 비교가 필요한 두 값을 먼저 확보한다. 이 순서 효과(앞 단계가 공유 데몬/캐시를 바꿀 수 있음)는 결과 해석에 한계로 명시한다.

## 4.3 단계 상태 · 결과 스키마 (DA M2·m2)
- 단계 상태(유한): `success / auth_error / network_error / timeout / spawn_error / unsupported / observation_unknown / skipped_prior_unresolved`.
- 매핑(부모 프로세스가 메모리에서만 판정, 원문 저장 금지):
  - rc=0 이고 stdout JSON 파싱 가능하고 `type == "SERVICE_ACCOUNT"`(필드 이름은 합성 입력과 실제 실행 «전» 구현 DA 에서 검증) → `success`.
  - rc=0 이지만 파싱 불가/타입 불일치 → `unsupported`(출력 형식 미지원).
  - rc≠0 → stderr 를 **고정 부분문자열 허용목록**으로 분류: 인증 계열 → `auth_error`, 네트워크 계열 → `network_error`, 그 외 → `observation_unknown`. 분류 후 stderr 는 즉시 버린다.
  - `TimeoutExpired` → `timeout` (부분 출력 `e.stdout/e.stderr` 는 읽지 않고 폐기).
  - `OSError`(스폰 실패) → `spawn_error`.
- 단계 기록 필드(허용목록): `step, status, rc, elapsed_ms, started_utc_ms, ended_utc_ms, child_pid, account_type_confirmed(bool|null), tcc_observation`.
- `tcc_observation`(유한): `seen_attributed`(단계 시간창[시작−0.5초, 종료+2초] 안의 AppData 요청이 있고 PID/책임 주체로 귀속) / `seen_unattributed` / `none_logged_ok` / `unknown_log_unavailable`.
  - `none_logged_ok` 는 **양성 대조**가 있을 때만: 같은 시간 범위의 TCC 서브시스템 줄이 «다른 항목이라도» ≥1줄 있어야 한다. **0줄이면 `unknown_log_unavailable`** — 로그 0줄을 성공/미요청으로 바꾸지 않는다(이번 r2 작성 중 `log show` 가 0줄이었던 사실이 그 사례).
- 결과 파일: `schema_version`, 단계 배열, `complete: true`. **원자 기록**(임시 파일에 쓰고 rename). 읽는 쪽은 `complete != true` 또는 파일 부재를 `observation_unknown` 으로 읽는다.
- 오류 클래스·예외 이름은 유한 목록으로만, **원문 메시지·traceback·stdout/stderr 본문은 결과·로그·launchd 스트림 어디에도 쓰지 않는다**(§4.4).

## 4.4 약속의 정확한 문구와 값 경계 (DA M3)
**하는 약속:** 운영 consumer 의 **파일/DB 쓰기 0** — `com.airag.consumer` plist·`runtime.json`·`credential-source.json`·토큰 파일(`~/.config/krb/op-sa-token`, 읽기만)·운영 DB·`~/.local/share/airag/logs`·`~/Library/LaunchAgents` 에 쓰지 않는다.
**하지 않는 약속(명시 고지):** **공유 op 상태 접촉 가능** — 실제 HOME 의 P0/P1/P1b 는 `~/.config/op`(설정·소켓·데몬)·1Password 컨테이너 접근 시도·로컬 캐시에 접촉하거나 변경을 일으킬 수 있다(`op user get` 이 조회 명령이라도 CLI 로컬 상태 쓰기가 없다는 보장은 없다). 다른 도구/터미널의 op 사용과 간섭할 가능성이 있다. 이 접촉은 **승인 범위에 명시**한다.

값 경계:
- 토큰 흐름 = 기존 파일 → 부모 파이썬 메모리 → **필요한 op 자식의 env 만**(P2·P1·P1b; P0 은 토큰 없음). argv·plist·결과·traceback·원문 스트림에 쓰지 않는다. (부모 메모리에 원문이 존재하는 것은 불가피하다 — «child env 외 어디에도 없다» 는 주장은 철회.)
- launchd `StandardOutPath`/`StandardErrorPath` = `/dev/null`. 파이썬 최상위 핸들러는 예외 **클래스 이름(허용목록)** 만 결과에 남기고 메시지는 버린다. `TimeoutExpired` 부분 출력도 읽지 않는다.
- 공유 데몬은 **임의 종료하지 않는다.** 프로브가 직접 만든 자식(P0/P2/P1)만 타임아웃 시 종료한다.

## 4.5 스크립트 구조 · 정리 (DA M3) — `ft-hil.sh --add` 대상 계획
- **정리 핸들러를 가장 먼저 설치**: 셸 `trap cleanup EXIT INT TERM HUP` 을 어떤 파일/라벨 생성보다 앞에 둔다. `cleanup` 은 멱등이며, 상태 변수(`LABEL_LOADED`, `PROBE_DIR_CREATED`)가 참일 때만 해당 정리를 한다 — 부분 실패(bootstrap 만 성공, mkdir 만 성공)에서도 안전.
- **충돌 없는 전용 경로:** `PROBE_BASE=$HOME/.local/share/airag-probe` (운영 `airag` 디렉터리와 분리). 부모가 심링크면 거부(`test -L`), `mkdir -m 700 "$PROBE_BASE/$ID"`(이미 있으면 실패 = 원자적 충돌 검출). `ID=$(date +%Y%m%d-%H%M%S)-$$-$RANDOM`. 초 단위 충돌 불가.
- **임시 plist 는 `$PROBE_DIR/job.plist`** (LaunchAgents 에 두지 않는다). 라벨 `com.airag.probe-opa-$ID`. bootstrap 전에 `launchctl print gui/$UID/$LABEL` 이 «없음»임을 확인(기존 라벨 충돌 시 중단). 자동 재시작 키(`KeepAlive`, `StartInterval`) **없음**, `RunAtLoad` 한 번만.
- `cleanup`: ① `launchctl bootout gui/$UID/$LABEL`(자기 라벨만) ② 잔존 검증 `launchctl print` 가 실패해야 정상 — 실패하면 **«잔존 확인 필요»를 출력**(삭제 시도 반복 안 함) ③ `$PROBE_DIR/job.plist` 만 삭제, 결과 파일은 보존 ④ 프로브가 만든 파이썬/op 자식 잔존 여부를 `pgrep -f "$PROBE_DIR"` 로 **보고만**(공유 op 데몬은 대상 아님).
- **결과 대기 상한**: `wait_cap = 외부호출 합계(7 + 10.5×4 = 49s) + 15s = 64s`, 시작 대기 10초, 정리 15초 → 전체 하드 상한 **≈ 90초.** 상한 도달 시 결과를 `observation_unknown`(+ `timed_out_wait=true`)로 닫고 정리.
- **합성 토큰 시험(구현 DA 입력):** 스크립트에 `--selftest` 모드(운영 실행 경로와 분리). `PROBE_OP_BIN`·`PROBE_TOKEN_FILE`·`PROBE_LAUNCHCTL` 오버라이드는 `--selftest` 에서만 허용. 시나리오: (a) 정상 stub, (b) `sleep` 으로 타임아웃, (c) 실행 중 SIGINT, (d) 가짜 `launchctl` 이 bootout 실패, (e) stub 이 stderr 에 «토큰처럼 보이는 합성 문자열» 출력 → **결과·launchd 스트림·프로브 디렉터리 전체에서 합성 토큰·stdout/stderr 문자열 grep 0건**, (f) 부분 결과 파일(`complete` 없음) 처리. 검증 결과를 구현 DA 에 제출한다. 운영 op 실행은 Master HIL 이후에만.

## 5.1 ⑤ «전용 설정 경로 사용 후보» (DA M4)
정의 정정: **파일시스템 격리·차단이 아니다.** HOME/`OP_CONFIG_DIR` 은 경로 선택 힌트이며 같은 UID 프로세스의 접근 능력을 제한하지 않는다. 후보의 주장은 «op 가 앱 컨테이너/설정을 찾는 **기본 경로를 바꿨을 때** 요청/지연이 사라지는가» 뿐이다. 서비스 계정 모드에서 필수인 상태(지역/계정 선택·CLI 통합·캐시)는 **미확인**.
- 경로: 부모에서 받은 임의 `OP_CONFIG_DIR` 을 허용목록에 넣지 **않는다**(부모 값이 있어도 자식으로 전달 안 함 — 시험 추가). 검증된 **전용 절대경로** `<HOME>/.local/share/airag/op-home` 를 코드가 계산하고 자식 env 에 `HOME=<그 경로>`, `OP_CONFIG_DIR=<그 경로>/.config/op` 로 **직접 설정**한다.
- 경로 정책: `os.makedirs(mode=0o700)` 후 `lstat` — 디렉터리이고 심링크 아님, 소유 uid == euid, `mode & 0o077 == 0`, `realpath` == 기대 경로. 위반/생성 실패 → 기존 `OP_SERVICE_ACCOUNT_UNAVAILABLE`(코드 신규 0, 528 불변). 매 틱 삭제 금지·공유 데몬 종료 금지(비용 해법으로 쓰지 않는다).
- 검증 계획(S2 에 포함): 동일 경로 **반복**(콜드 1회 → 웜 ≥5회, 각 ≥60초 간격) · 실제 키 읽기 **3 병렬** 경로에서 호출당 마감(21초) 내 완료 비율 · 완료 뒤 잔존 op 프로세스/데몬 수·증가 여부 · 전용 경로 디스크 바이트 증가 · 일 요청량(최대 864 읽기/일, rate-limit 수치 **미확인**이므로 문서 확인 선행).
- 성공 기준을 사전 고정: 콜드 1 + 웜 5 + 3병렬 3라운드 전부 `success`, 호출당 21초 초과 0, 잔존 증가 없음. 하나라도 어기면 ⑤ 채택 보류.

> **«1Password 연결 상태를 점검하는 1회 스크립트(`! bash /tmp/h<N>`)를 실행해도 될까요?** 실제로 하는 일은 이렇습니다.
> ① 임시 점검 작업을 launchd 에 잠깐 등록했다가 끝나면 스스로 내립니다.
> ② **서비스 계정 토큰 파일(`~/.config/krb/op-sa-token`)을 읽어서** 1Password 에 계정 종류 조회를 최대 4번 요청합니다. 금고 안의 항목 값은 읽지 않고, 어떤 출력도 저장하지 않습니다.
> ③ 오빠 PC 에서 쓰는 1Password CLI 설정·백그라운드 프로그램(`~/.config/op`)을 건드릴 수 있어서, 다른 터미널의 1Password 사용과 잠깐 겹칠 수 있습니다.
> ④ **1Password 관련 macOS 팝업이 단계마다 최대 3번까지 뜰 수 있습니다. 누르지 마세요**(«허용 안 함»도 설정으로 저장될 수 있습니다). 스크립트가 끝나도 팝업이 남아 있을 수 있는데, 그대로 두고 저에게 알려 주세요.
> ⑤ **최대 약 90초**이며, 도중에 멈추려면 Ctrl-C (정리 후 종료됩니다).
> ⑥ 운영 consumer 는 **계속 꺼진 채로 둡니다.** 서버(18712·18703)가 복구됐다는 연락과 HELM 의 재개 절차가 있기 전에는 켜지 않습니다.»
>
> 같은 메시지에 한 줄 정정: «서비스 계정 방식은 이미 쓰는 중이었습니다 — 권장의 전제가 달랐습니다. 또 로그를 다시 보니 **키 읽기는 항상 막힌 게 아니라 간헐적으로 실패**했고, 마지막 팝업 요청 시각에는 오히려 성공 중이었습니다.»

별도 한 줄(결정 아님, 보고): 7초 룰 수정(I-1)은 오빠 승인 없이 Master 가 먼저 진행할 수 있습니다.
