# AI RAG 자료·대화·프로젝트 지식 운영 기획

2026-09-27 · 기획 v1.2 · 프로젝트 코드/문서 RAG 축 추가 · P08A-03 원장 경계 7차 코드 DA PASS

검토 이력: v1.0 2차 PASS → v1.1 3차 조건부 PASS → B4~B6 대응 후 4차 PASS. 최종 계약 blocker는 0건이며 P08A-02/03 구현 착수 가능 판정이다. 사용자 운영 정책 확정·실수집·운영 검증 완료를 뜻하지 않는다.

v1.2의 프로젝트 지식 축은 그 이후 사용자 요구로 추가한 설계다. v1.1 계약 PASS를 프로젝트 코드 색인·Serena 연동의 검증 결과로 확대하지 않는다.

목표는 **바뀌는 자료는 최신 상태로, 쌓이는 대화는 근거를 잃지 않고, 지금 필요한 기억만 가볍게** 제공하는 것이다. 완전무결한 운영을 이미 보장한다는 문서가 아니다. 동작·실패·재시작·권한 경계를 정하고, 개발 완료를 판정할 증거를 명시한 구현 기준안이다.

[나노 초안](data-lifecycle-draft.md), [Fable 5.1 DA 1차 검토](data-lifecycle-da-review.md), [개발 인덱스 PLAN](../PLAN.md)을 함께 보존한다. 현재 core 완료 기록을 새 소비자 기능의 구현 증거로 사용하지 않는다.

## 1. 전체 지도

```text
AI RAG 운영
├─ A. 상태가 바뀌는 자료
│  ├─ 문서·이미지·백과/wiki·DB 행/partition
│  ├─ 확정된 추가/변경/삭제/복원 이벤트
│  └─ 최신 검색 자료로 명시 발행
├─ B. 시간순으로 쌓이는 사건
│  ├─ 채팅·메시지·CS·에이전트 대화·도구 결과
│  ├─ 보안 정리 → JSONL 사건 기록 → 윈도우 문서 연속 생성
│  └─ 수정·삭제 반영 → Docling 구조 → 기존 RAG 청킹·검색
├─ C. 프로젝트 지식 — 자체 프로젝트·선택한 오픈소스
│  ├─ 설계 문서·소스코드·테스트코드·스크립트
│  ├─ 저장소/작업트리 snapshot → 구조·심볼별 청크 → 변경분 재색인
│  └─ AIRAG 근거 검색 ↔ Serena/LSP 정의·참조·호출 관계 확인
└─ 공통 읽기 계층
   ├─ 최근 N개 창 + 별도 예산의 중요 기억
   ├─ 대화·CS 전체 허용 이력의 기본 검색·원문 메시지 인용
   ├─ 검색 근거에서 기억·트러블슈팅 지원
   └─ 원본 보존 확인 후 오래된 활성 참조만 내리기
```

문서·이미지 역시 형식상 비정형일 수 있다. 여기서 A/B는 정형 여부가 아니라 **같은 대상을 갱신하는가 / 사건이 계속 늘어나는가**의 구분이다. 기술 구현 위치는 기존 `feature-pack/rag/` core와 분리된 **`feature-pack/rag-consumer/`**다. 현재 정규 JSONL 검증·대화 변환의 순수 입력 어댑터와 테스트를 구현했으며 저장·수집·검색 실행 계층은 아직 미구현이다.

### 1.1 기존 IBM Docling 경로를 공통 기반으로 재사용

기존 D-010/P03-01은 텍스트·Markdown·대화를 네이티브 `DoclingDocument`로 구성하고 실제 `HybridChunker`로 청킹하는 경로를 채택했다. D-012/P04는 Docling 기반 PDF·DOCX·XLSX 변환을 연결했다. HWP/HWPX·이미지는 각 어댑터 계약을 따른다. 이 완료 기록은 PLAN에 있으며 이번 문서 수정에서 런타임을 다시 실행한 것은 아니다.

대화·CS도 별도 검색 엔진을 만들지 않는다. **JSONL 윈도우 → 현재 유효 메시지의 DoclingDocument → 기존 HybridChunker → 기존 전처리·임베딩·BM25+vector 검색**으로 연결한다. JSONL 자체를 Docling의 네이티브 파일 형식 지원으로 가정하지 않는다. 소비자가 JSONL을 파싱하고 승인된 대화 입력 계약으로 전달하며, 구조를 Markdown으로 내보냈다가 재파싱해 청킹하지 않는다. 표준 Markdown은 사람이 읽는 파생 문서다. 기존 입력 계약으로 메시지 앵커를 전달하지 못하는 부분이 발견되면 별도 core 변경·회귀 범위를 먼저 등록한다.

## 2. 무엇을 누가 저장하는가 — DA B1 해제

| 저장 대상 | 기준 저장소·소유자 | 검색/수정 방식 |
|---|---|---|
| 수집 이벤트·outbox·offset·복원 epoch | 소비자 소유 별도 SQLCipher 원장 | 재수신·순서·권한·checkpoint의 정본. core 백업과 독립적으로 복구 |
| 봉인된 원본 로그 파일 | JSONL 직렬화 레코드를 보존하는 소비자 SQLCipher 세그먼트 파일 | 한 줄 한 사건인 UTF-8 JSONL이 논리 기록 형식. 운영 디스크에는 평문 JSONL을 추가 복제하지 않고 세그먼트마다 독립 SQLCipher DB에 줄 순서·내용을 보존한다. JSONL 파일 내보내기는 명시적 권한이 있는 별도 경로다. 키 수명주기는 소비자가 소유하고 core DB 키와 분리한다. 비밀 저장소의 key reference만 원장에 기록한다. 실제 키 보관·교체·복구 정책은 P08A-01에서 확정한다. 직접 만든 암호 포맷 없음. 영구 불변 보관과 무기한 보관은 다른 개념 |
| 현재 검색용 윈도우 문서(projection) | core의 일반 source | `session/<session>/window/<window>/view`; 안정 window ID와 원본 event/message ID 범위를 소비자 원장에 매핑. edit/delete overlay마다 같은 ID로 update/delete |
| 기억 후보 | 소비자 SQLCipher 후보/outbox | 미검증 후보는 일반 검색에 발행하지 않음 |
| 검색 허용된 기억 본문 | core의 별도 memory collection/source | `memory/<memory_id>`에 claim·scope·근거·상태를 직렬화. 일반 자료와 검색 목적을 분리 |
| 기억 상태·승인·의존성 원장 | 소비자 SQLCipher 원장 | reviewer·source versions·invalidation_epoch·core receipt를 관리. 외부 노출 여부의 권위 |
| 활성 컨텍스트 창 | 소비자의 bounded read view | 원본 복제가 아니라 청크/사건 참조와 제한된 발췌·요약. 원장의 ID로 재구성 |

원본 세그먼트는 일반 검색에 무차별 등록하지 않는다. core에 전달하는 것은 **마스킹·접근 범위·수정/삭제를 반영한 projection**이다. 후보를 발행할 때 기억 본문은 core에 두고 소비자 원장이 상태를 결정한다. 원장 검증이 끝나지 않은 core 결과는 응답으로 내보내지 않는다. 원장과 core 사이의 실패는 outbox·멱등 재전송·발행 상태 대조로 수렴시킨다.

## 3. A축 — 외부 추가·변경·삭제 조건

```text
외부 이벤트
├─ 파일/이미지
│  ├─ 쓰기·업로드 완료 + 안정 ID + 해시 확정 → add
│  ├─ 같은 ID의 바이트/메타 변경 → update
│  └─ 이름·경로만 변경 → ID 유지, 필요한 메타만 update
├─ 백과/wiki
│  ├─ 새 문서의 게시 revision → add
│  ├─ 같은 문서의 새 게시 revision → update
│  └─ 초안 저장/일시적 404 → 게시/삭제로 추정하지 않음
├─ 큰 DB
│  ├─ commit된 CDC insert/update/delete → 안정 PK 기준 요청
│  ├─ 초기 snapshot → watermark 이후 CDC와 연결
│  └─ rollback·누락된 구간 → 발행하지 않고 재대조
├─ 삭제/복원
│  ├─ 권위 있는 삭제 또는 승인된 완전 대조 → delete
│  ├─ 부분 목록·접근 불가·timeout → 관측, 삭제 아님
│  └─ tombstone 뒤 재등장 → 명시 restore 없이는 부활 금지
└─ 원본 불변·처리 방식 변경 → reindex
```

`source_version`은 외부 순서용이고 core `expected_revision`은 현재 source 상태의 CAS 토큰이다. 둘을 혼용하지 않는다. 동일 operation 재전송은 같은 request_id와 같은 payload를 쓴다. 여러 목적지로 나뉘면 하위 operation ID를 결정적으로 만든다. 충돌 시 최신 CAS를 무조건 다시 넣어 강행하지 않고 외부 현재 상태와 의도를 재대조한다.

안정 ID는 파일 경로가 아니다. DB 행은 DB incarnation/schema/table/PK를 구분하고, wiki는 문서 ID를 사용한다. 전체 큰 DB를 문서 하나로 재등록하는 방법은 기본안이 아니다.

### CDC 여러 행의 가시성 — DA M4의 구체 선택

현재 core의 원자 발행은 source 하나 기준이다. `add_batch/update_batch`가 DB transaction 전체의 원자성을 보장하지 않는다.

**초기 기준안:** 소비자에서 dataset read gate를 닫고 같은 commit 그룹의 모든 요청을 처리한 다음, receipt·projection 집합 대조가 끝나면 gate를 연다. 외부 응답 직전에도 gate/epoch를 재검사해 경합 중 결과가 새어나가지 않게 한다. 실패한 그룹이 남으면 해당 dataset은 `updating/unavailable`로 표시하며 부분 완료 자료를 정상 최신 상태로 제공하지 않는다. 이것은 검색 가용성을 일부 희생하는 정합성 선택이다. 고빈도/대량 CDC에서 실측해야 하며, 가용성 목표를 못 맞추면 partition snapshot 또는 core group-publication을 별도 범위로 다시 결정한다.

core group publish·임의 메타 필터·hard purge는 현재 구현으로 가정하지 않는다. 필요해지면 P08A-01에서 별도 core 작업과 P-06 회귀 게이트를 만들며, 조용히 범위를 늘리지 않는다.

### 4.1 JSONL → 윈도우 문서 → 기존 RAG 검색 (기본 기능)

```text
채팅·CS·에이전트 메시지 계속 도착
→ 한 사건 한 JSONL 레코드: 마스킹 후 암호화 저장·commit
→ 안정 ID의 윈도우 문서 W001, W002, W003… 생성
   ├─ 논리 파일: W001.jsonl, W002.jsonl…
   ├─ 현재 메시지 view: create/edit/delete/권한을 반영
   └─ DoclingDocument → HybridChunker → 청크 여러 개 → 기존 RAG 발행
      ├─ 기본: 대화·CS 히스토리 검색 → 원문 메시지와 당시 문맥
      ├─ 현재 입력: 최근 N개 윈도우 + 필요한 과거 검색 결과
      └─ 활용: 기억·결정·진행 상태 / 유사 장애·해결·재발 사례
W001이 최근 N개 밖으로 밀림
→ 현재 입력 참조만 퇴거; 유효한 검색 문서·청크는 계속 검색 가능
```

**N개 윈도우 문서를 모두 RAG에 넣는 것이 기본**이다. 이후 새 윈도우가 생기면 새 문서만 추가하므로 전체 검색 대상은 N개를 넘어 누적된다. N은 최근 활성 컨텍스트 제한이지 전체 색인 개수나 검색 결과 top-k가 아니다. 윈도우 문서 하나와 검색 청크 하나를 1:1로 강제하지 않는다. 기록 크기는 `window_max_events/window_max_tokens`, 활성 개수는 `active_window_count=N`, 검색 결과는 `retrieval_top_k`로 따로 정의한다. 대화/티켓 경계는 섞지 않으며 큰 메시지 분할 시 같은 message ID와 부분 범위를 보존한다.

JSONL 최소 사건 계약은 `schema_version, event_id, stream_id, producer_epoch, message_id, source_version, source_ordinal, event_type, occurred_at, ingested_at, access_scope`다. 세션/티켓은 안정 stream_id로 매핑하며 create/edit에는 role/content가 필요하다. delete/restore는 본문 없는 제어 사건이다. 수정·삭제는 대상 message ID와 새 버전을 갖는 별도 사건으로 남기고 raw 줄을 덮어쓰지 않는다. `tool_call_id/reply_to/attachment_ref`는 해당 사건에 포함한다. 현재 선택한 공개 세션 어댑터는 user/assistant만 허용하며 도구·CS 역할과 권한 사건은 별도 adapter 검증 전 거부한다. 중복 event ID는 멱등 재생, 중단된 마지막 줄은 검증 전 미확정 상태로 둔다. 불완전 JSONL 줄이나 저장 실패를 수신 성공으로 처리하지 않는다.

원본 저장 세그먼트와 검색 윈도우는 별도 ID로 관리한다. 저장 세그먼트 하나가 여러 작은 윈도우를 담을 수 있다. 윈도우 발행 시에는 참조하는 원본 범위를 봉인·내구성 확인한 뒤 outbox로 발행하며 필요하면 조기 봉인한다. 열린 윈도우는 사건 수·토큰·시간·명시 flush 중 먼저 도달한 경계에서 닫는다. 완료된 창 W001~Wk의 검색 성공은 열린 tail의 색인 성공을 뜻하지 않는다. `stored/index_pending/searchable/failed`와 마지막 색인 시각을 사용자에게 구분하고 flush/재시도로 전진시킨다. 채팅 기록의 저장 성공은 임베딩 제공자 장애와 분리한다.

**기본 히스토리 검색은 기억 추출·요약·사람의 기억 승인이 끝나기 전에도 제공한다.** 동일 core 검색 API/CLI를 활용하되 소비자 권한 facade를 경유하고 tenant/project/session/ticket/time 범위를 소비자에서 검증한다. core가 임의 메타 필터를 지원한다고 가정하지 않는다. 검색 결과에는 window ID·원본 message/event ID·역할·시각·revision·관련 구절·접근 가능한 앞뒤 문맥을 반환한다. 창을 가로지르는 질문/답변, 도구 호출/결과는 연결 참조로 문맥을 회수하며 전체 로그를 무조건 주입하지 않는다. 겹치는 청크는 원본 message ID/범위로 중복 제거한다.

대화·CS 전용 임베딩 공간을 무조건 분리하지 않는다. 기존 문서와 호환되는 처리 프로필·모델 공간에서 검색을 재사용하고, 비호환 프로필은 기존 공간 격리 규칙을 따른다. 통합 검색 시 출처/권한 범위를 유지하며 서로 다른 공간의 점수를 근거 없이 직접 비교하지 않는다.

### 4.2 저장 파일·검색 문서·청크·활성 창의 역할

- **파일 세그먼트:** 제안 기준 `200 events / 1 MiB / 30분 / 명시 checkpoint` 중 먼저 도달하면 봉인. 수신 ack는 30분을 기다리지 않고 개별 이벤트의 SQLCipher commit 뒤에 보낸다. 큰 단일 도구 결과는 같은 보안/내구성 정책의 분리 객체를 참조한다.
- **윈도우 문서:** 현재 유효한 대화 묶음을 담는 안정 ID의 source. 기본 제안 최대 40 events 또는 2,000 tokens. JSONL 원본 범위와 Docling 구조·읽기용 문서가 연결된다.
- **engine chunk:** 윈도우 문서를 포함한 기존 문서의 구조·청커·프로필에 따라 생기는 검색 단위. 파일/윈도우 하나에 여러 청크가 있을 수 있다.
- **활성 창:** 최신 맥락을 조립하는 단위. 제안 `N=4`, 창당 최대 40 events 또는 2,000 tokens, tail 합계 8,000 tokens.
- **상단 기억:** tail과 별도 예산 2,000 tokens. pin도 이 예산을 쓴다.
- **과거 근거:** 필요한 경우 2,000 tokens. 총 제안 예산은 12,000 tokens이고 시스템·현재 요청·도구·출력 예약분은 먼저 확보한다.

N과 숫자는 **개발 실험의 제안값**이며 운영 승인은 아니다. 임베딩 토크나이저가 아니라 실제 응답 모델에 넣는 표현과 wrapper를 센다. tokenizer 부재 시 정확 계수와 보수 추정을 구분하며, 정확 상한 모드에서는 계수 수단 없이 통과 처리하지 않는다. 청크가 예산보다 크면 범위를 명시한 발췌/요약과 원본 참조로 나타낸다. tool call/result 관계를 무음으로 끊지 않는다.

매 메시지마다 전체 대화 파일을 core update하지 않는다. `JSONL 기록 → 윈도우 닫기·원본 봉인 → 윈도우 문서 add → 기존 RAG 청킹·발행`이 기본이고, 과거 수정은 correction event와 영향 윈도우 문서의 새 revision으로 처리한다. 아직 색인되지 않은 tail은 소비자가 제한된 실시간 view로 제공하되 검색 완료 자료로 표시하지 않는다.

### 같은 메시지의 수정·삭제 순서

비교 기준은 producer incarnation/sequence와 source_version이다. ingested_at으로 최신 의미를 결정하지 않는다. tombstone보다 낮거나 같은 버전의 create/edit는 늦게 도착해도 projection·요약·기억을 되살리지 못한다. 비교 불가능한 순서는 격리 후 원천 재조회한다. 더 높은 버전의 create/edit가 와도 tombstone 해제는 **별도 승인된 restore 사건**이 필요하다. 권한 재부여는 내용 restore와 다른 사건이며 현재 데이터·근거를 다시 검사한다.

## 5. 중요 기억은 어디에 어떻게 올라가는가

**사용자 인터뷰 확정:** 결정·진행 상태·검증된 해결책은 자동 선정한다. 최신 원문 anchor·현재 권한·충돌 여부를 확인하고, 해결책은 성공 검증 근거가 있는 경우만 대상으로 한다. 자동 선정 상태는 rule_checked이며 사람 승인으로 표시하지 않는다. 장기 선호·지침 후보는 사용자 확인 후 반영하고 상위 지침 권한으로 자동 승격하지 않는다. 재오픈·원문 변경으로 검증이 무효화되면 해결책의 자동 선정도 해제한다.

기억과 troubleshoot는 §4.1의 **검색 가능한 대화 문서·청크 위에 올리는 기본 활용 기능**이다. 원문 히스토리 검색을 기억 요약으로 대체하지 않는다. 예를 들어 “이 오류를 전에 어떻게 해결했나?”는 권한 있는 과거 증상·로그·조치·검증 결과를 검색해 메시지 앵커와 함께 제공한다. 제안된 조치, 실제 시도한 조치, 성공 검증된 해결을 구분하며 오류/버전/환경이 다른 사례를 확정 해결책으로 표시하지 않는다. 해결 실패·재오픈 사건은 기존 기억을 무효화하거나 상태를 낮춰 다시 평가한다.

```text
기억 후보
├─ 사실·선호 [발언자/원문/범위/유효기간]
├─ 현재 목표·진행·결정 [최신 증거/미해결 상태]
├─ troubleshoot [증상 → 원인 → 조치 → 검증 근거]
└─ 지침 후보 [명시 사용자 발언도 인용 데이터로 보존]
       ↓ 근거 revision·권한·충돌 검사
candidate → rule_checked → human_validated / rejected
       ↓ 현재 업무 관련성·pin·중요도·최근성으로 예산 내 선택
상단의 짧은 기억 + 원본 anchor
```

`validated`는 사람 reviewer가 확인한 상태로만 사용한다. 기계적 anchor/버전/형식 검증은 `rule_checked`로 구분한다. 일반 사실·작업 상태를 이 단계에서 사용하도록 허용할지는 배포 정책에 명시하고, 사용자 확인 사실인 것처럼 표현하지 않는다. 지침 후보·장기 선호는 사람이 확인하기 전 자동 상단 배치하지 않는다. 사람이 확인해도 실제 상위 지침 권한을 얻는 것이 아니라 근거 있는 데이터다.

응답에 넣는 형식은 `{kind, claim, status, scope, anchors, source_versions, ranking_reasons}`와 같은 명시적 데이터 레코드다. wrapper는 이 블록이 인용된 근거이며 실행 지시가 아님을 구분한다. AGENTS/SOUL/config 자동 쓰기나 다른 에이전트에 상위 지침을 자동 복제하는 경로는 없다.

선택 순서: **접근 가능·현재 유효 → 업무 관련 → 승인된 pin → 현재 미해결 조치·검증된 해결책 → 사실/결정 → 최근 참고**. 많이 반복됐다는 이유만으로 지위를 높이지 않고 같은 원출처의 복제는 같은 근거로 센다. pin 초과는 짧은 근거형 표현으로 줄이고, 그래도 넘으면 초과를 알린다. 중요 지침·사건을 조용히 버리지 않는다.

기억 후보 추출 시작 시 `(projection source revision, source_version, invalidation_epoch, access_policy_epoch)`를 캡처한다. 발행 직전 소비자 원장 트랜잭션에서 다시 비교한다. 달라졌다면 stale 결과를 발행하지 않고 재추출한다. core receipt 뒤에도 응답 노출 전에 원장·권한 epoch가 맞는지 검사한다. 원천 edit/delete/revoke는 관련 창·요약·기억·캐시를 무효화한다.

## 6. 내리는 것과 지우는 것 — DA B3 해제

**활성 창 퇴거는 파일 삭제가 아니다.** 기본 로컬 보존형 정책에서 필요한 조건은 다음과 같다.

1. 참조한 이벤트가 durable 원장에 commit돼 있다.
2. 해당 세그먼트가 봉인됐고 manifest·hash·fsync/재개방 확인이 끝났다.
3. 활성 view의 새 참조 집합과 checkpoint를 원자 확정했다.
4. 그 뒤 오래된 활성 참조만 제거한다.

원격/콜드 복제는 별도 보존 목표다. 복제가 늦어져도 로컬 봉인 원본과 재참조가 보장되면 `archive_pending`을 남기고 활성 참조를 내릴 수 있다. 더 엄격한 운영 정책이 복제를 필수로 정하면 그 정책을 만족하기 전에는 퇴거하지 않는다. 로컬 디스크 하나만으로 재해 무손실을 보장한다고 주장하지 않는다.

창이 넘치면 현재 tail을 조기에 seal한다. **강제 seal도 디스크 오류를 해결하지는 않는다.** durable write가 실패하면 수집 성공으로 ack하지 않는다. 이는 사용자의 원래 채팅을 삭제하거나 거부한다는 뜻이 아니라, 소비자 수집 cursor를 전진시키지 않고 원천의 재전송/보존 원장에 의존한다는 뜻이다. 원천 보존도 보장되지 않으면 복구 가능하다고 주장하지 않고 운영 차단·경보로 남긴다.

요약 추출 실패는 `extraction_pending`으로 남기고 검증되지 않은 요약을 만들지 않는다. 원본 보존과 checkpoint가 확인되면 원본 참조로 내려놓고 추출을 재시도할 수 있다. N은 활성 맥락 상한이지 디스크 보존 기간이 아니다.

## 7. 권한·보존·백업 복원 — DA B2 해제

### 조회 경계

새 소비자/auth facade를 모든 검색·fetch·기억 조립·archive 접근의 진입점으로 둔다. core DB 키와 직접 호출은 내부 작업자에게만 제공한다. **collection/source_keys는 인증이 아니다.** 기본안은 tenant/access_scope별 collection, 강한 격리가 필요한 경우 별도 DB로 나누며 권한 검사는 facade가 수행한다. 임의로 많은 허용 ID를 100개 source_keys 필터에 밀어 넣는 방법은 쓰지 않는다.

권한 철회 시 먼저 read gate/정책 epoch를 갱신한다. 이후 물리 색인 정리가 늦더라도 응답 직전 epoch와 모든 근거의 현재 접근권한을 다시 검사해 노출을 막는다. 다근거 기억은 모든 근거에 접근 가능한 범위에서만 제공한다. 역순 grant/revoke가 오면 현재 원천 정책으로 재대조한다.

현재 답변용 과거 회수는 **현재 overlay와 권한이 반영된 archived projection**에서 한다. raw 역사 세그먼트, historical manifest replay, revision fetch는 별도의 명시적 감사 경로다. 삭제된 옛 내용을 자동으로 응답 에이전트에 넣는 우회로로 쓰지 않는다.

### 백업 복원 절차

현재 core `restore-backup`은 기존 DB를 덮어쓰지 않고 **새 경로**에 복원한다. 이후 소비자가 그 DB로 전환하면, 백업 뒤의 수정·삭제·철회가 빠질 수 있다. 모든 CAS 토큰이 반드시 stale해진다고 가정할 수 없다. source_id/state_version이 우연히 같을 수 있으므로 소비자 **DB incarnation/restore_epoch**로 이전 요청과 발행자를 분리한다.

```text
백업에서 새 DB 복원
→ 응답용 read gate 닫기 + 새 DB incarnation/restore_epoch
→ 소비자 원장의 backup checkpoint 레코드(applied offset/receipt) 대조
→ 외부 durable 원장 또는 권위 있는 snapshot으로 이후 사건 복구
→ create/edit/delete/restore/revoke 순서·tombstone 규칙 재적용
→ projection·memory·권한·원본/색인 정합성 재검증
→ 복구 watermark 확정 후 gate 열기
```

core `status`만으로 외부 CDC offset을 알아낼 수 없다. core는 별도 backup manifest를 생성하지 않는다. 소비자가 자신의 암호화 원장에 백업 식별자·applied offset·receipt 매핑의 checkpoint 레코드를 저장한다. 원장이 백업보다 최신이라는 보장도 확인하며, 없다면 권위 있는 원천 전체 대조가 끝날 때까지 읽기를 열지 않는다. 재적용 core request ID는 `(event_id, operation, projection_version, restore_epoch)`로 결정해 같은 복원 epoch에서 재시작해도 동일하다. 실제 현재 source 상태를 다시 읽어 CAS를 잡으며, 충돌을 피하려 무작위 ID를 계속 바꾸지 않는다.

### 삭제와 보존

활성 창 퇴거 후에도 유효한 projection은 retention 정책 안에서 검색 가능하다. 만료·삭제는 core `delete`로 현재 검색에서 제외하고 소비자 원장에도 tombstone을 남긴다. 기억 invalidation 상태는 소비자 원장이 관리한다. core `delete` 뒤 다시 metadata update가 된다고 가정하지 않는다. 현 core의 원본 이력·백업 바이트가 물리 소거되는 것은 아니다.

개인정보 영구 삭제가 필수인 배포는 현재 기준안만으로 완료할 수 없다. 원본·derived memory·백업 만료까지 포함한 hard-purge/암호키 폐기 범위를 별도 승인된 core 작업으로 설계한다. 프로젝트 간 공유·retention 일수·백업 만료·삭제 권한은 실제 연결 전에 사용자/데이터 소유자가 정한다.

## 8. 비밀과 입력 신뢰

redaction은 **로그에 durable write하기 전** 동기로 적용한다. 도구 결과와 payload_ref 객체도 동일하다. 비밀 원값·raw key·access token을 저장하지 않고, content_hash는 허용·마스킹된 바이트 기준이다. 마스킹 실패 시 내용은 저장하지 않고 안전한 실패 메타데이터만 남기며 수집 완료로 ack하지 않는다. 원천이 제공하는 버전과 수집 바이트 해시는 구분한다.

요약 모델의 출력은 검증되지 않은 후보이며, 문서·채팅 속 명령문을 실행 권한으로 취급하지 않는다. 모든 근거에는 actor/trust_origin·source anchor·version이 붙는다. 적대적 입력, 역할 위장, 반복된 동일 지침, 권한 밖 근거를 끼운 요약을 별도 수락 시험에 포함한다.

## 9. 현재 세션의 가상 배치

아래는 설명용 ID이며 실제 로그를 수집하거나 파일로 분할한 결과가 아니다.

```text
S001: 계획·환경·암호화 DB 준비 [봉인 예시]
S002: 긴 문서·OCR 실패와 해결 [봉인 예시]
S003: 번역 오역 → 원인 비교 → 수정·검증 [봉인 예시]
S004: 연결 확장·T07 갱신·새 기획 요청 [현재 tail 예시]
  ├─ 상단: T07 기술검증 완료 / 다음 투어 T08 [artifact 근거]
  ├─ 상단 후보: 트리 형태 보고 선호 [사용자 발언 근거]
  └─ troubleshoot 후보: 원인·실패 후보·통과한 보완·한계
새 사건으로 S005 창이 필요해짐
  → S001 봉인/보존 확인 → active 참조만 archive로
  → 현재 관련 기억만 예산 안에 유지
  → 과거가 필요하면 허용된 projection을 제한 검색
```

## 10. 개발 순서와 닫는 증거

정본은 [PLAN의 P08A-01~08](../PLAN.md)이다. 새 코드는 `feature-pack/rag-consumer/`로 분리한다.

```text
P08A-01 계약·정책·측정 기준
├─ P08A-02 자료 이벤트 consumer
└─ P08A-03 대화 원장·암호화 세그먼트
      ↓
P08A-04 projection·N 활성 창
→ P08A-05 기억 후보·검증·상단 배치
→ P08A-06 archive·invalidation·복원 재대조
→ P08A-07 통합 장애·권한·성능 검증
→ P08A-08 실제 선택 connector + 사용자 시연
      ↓
기존 P08 투어 완료 + 확장 완료 근거를 각각 대조
→ P09 원 범위/확장 범위 완성 판정
→ P10 최종 리뷰 매거진
```

합성 fixture 통과는 실제 connector 운영 완료가 아니다. 첫 자료/채팅 원천을 지정하고 읽기 범위·이벤트 형식·재전송 계약을 검증해야 한다. 실제 wiki·DB·CS 서비스 미지정 상태에서 해당 연동이 완료됐다고 표시하지 않는다. 기존 T08~T13 core 투어는 독립 진행 가능하며 확장 시험이 이를 대신하지 않는다.

### 최소 수락 실험 — 임계는 운영 승인 전 제안

- 고정된 합성 사건 5,000개/10개 세션. 중복10%, 수정·삭제5%, 늦은 도착5%, 큰 도구 결과와 재시작 포함. 실패 전후 수집 ack 사건 누락0, 중복 projection0.
- JSONL round-trip으로 message/event ID·줄 순서·역할·시각·tool 관계 보존을 확인한다. 중단된 마지막 줄, 중복, 윈도우 경계의 질문/답변·도구 쌍, 매우 긴 메시지를 포함한다.
- N=4에서 10개 윈도우 발행 후 최근 4개만 활성 입력에 넣어도 W001의 허용된 원문을 기존 RAG 검색으로 찾고 message ID까지 추적한다. 기억 추출을 비활성화해도 히스토리 검색이 된다. 청크 수와 윈도우 수가 같다는 전제는 두지 않는다.
- 동일 Docling/HybridChunker 기반 처리·기존 검색 계약을 문서와 대화·CS에 적용한 근거를 남긴다. 임베딩 실패 시 raw 보존·색인 상태 표시, 멱등 재시도 후 중복 문서 없는 searchable 전환을 검증한다.
- 이전 오류 해결 fixture에 증상·환경·실패 시도·성공 검증·재오픈을 포함한다. 원문 인용, 조치 상태 구분, 삭제/권한철회 후 히스토리·기억·troubleshoot 결과의 일관된 배제를 확인한다.
- 사건/권한/근거가 있는 고정20질의. tail-only를 기준선으로 비교하고 archive evidence recall@3 ≥0.9를 목표로 한다. 삭제·철회된 근거가 정답으로 남은 fixture는 먼저 갱신한다.
- 실제 agent 입력 표현의 토큰 상한 준수100%, 창 조립 p95≤500ms(모델 호출 제외), pin overflow·발췌/잘림은 모두 표시한다.
- 요약/추출은 사건당 토큰·호출 수·재시도 비용을 실측한다. 비용 상한은 사용할 모델과 사용자 정책을 정한 뒤 확정하며, 측정 전 저렴하다고 주장하지 않는다.
- 원본편집 중 추출, 후보발행 중 철회, delete보다 늦은 create, CDC 부분실패, seal 중단, archive 복제실패, 백업 후 삭제를 포함한 복원, outbox 재전송, raw 디스크오류를 각각 재현한다.
- 허용되지 않은 근거 노출0, stale 후보 신규발행0, 보존 미확인 퇴거0, 조용한 pin 유실0. 실제 모델 요약의 의미 정확도는 자동 타입 검증과 별도로 원문 대조한다.

## 11. 실제 연결 전에 확정할 운영 값

### 인터뷰 결론 — 첫 완료 범위

사용자는 **대화 검색·기억·운영까지**를 첫 완료 기준으로 선택했다. 선택한 실제 입력에서 근거가 있는 과거 대화 검색과 결정/해결책 기억, 작성일부터 90일 활성 만료 및 무기한 파일 아카이브, 명시 아카이브 조회, 환경변수 키 주입, 매일 한국시간03시 백업/누락1회 보충, 임시 복원·무결성·연결 검증, 검증 성공 후30일 만료 백업 정리를 함께 시연해야 완료다. 90일/30일 경계는 가상 시간 시험으로 검증할 수 있으나 이를 실제90일 운영 실적으로 표시하지 않는다.

자동 에이전트 컨텍스트 주입과 프로젝트 코드 RAG/Serena 연동은 후속 범위에 남긴다. 첫 단계에서 제외했다고 전체 계획에서 삭제하지 않는다. 아카이브 파일 묶음·인증 주체와 tenant 연결·응답 tokenizer/최종 컨텍스트 예산·배포 키 주입/복구 절차는 구현 전에 구체화할 설정이다. 주요 사용자 운영 선택은 위 인터뷰로 기록했으며, 기존 7차 코드 DA는 새 운영 정책 전체의 구현 완료나 검토를 대신하지 않는다.

**백업 검증 인터뷰 확정:** 매일 및 누락 보충 백업마다 별도 임시 경로로 복원해 암호화 DB 재개방·DB 무결성·원장 receipt/checkpoint·아카이브 manifest/hash와 근거 연결을 검증한다. 운영 경로를 덮어쓰지 않고 복원 시험의 수집·발행·스케줄러는 비활성화한다. 검증에는 외부 모델 호출이 필요하지 않다. 임시 공간 부족이나 연결 불일치도 검증 실패로 처리하며 검사를 축소한 채 성공으로 표시하지 않는다. 검증된 새 백업이 있어야만 30일 만료 백업 정리를 실행할 수 있다. 실제 예약·복원 시험은 아직 실행하지 않았다.

**복구용 백업 보존 인터뷰 확정:** 최근 30일의 백업 세트를 보관하고 새 백업 검증 성공 후 30일이 지난 AIRAG 소유 완료 백업을 자동 정리하도록 사용자가 선택했다. 이 실행 권한은 지정 프로젝트 백업 디렉터리의 만료된 복구용 백업에 한정하며 무기한 보관하는 주 아카이브·원천 데이터·키·다른 파일은 제외한다. 검증 실패 시 기존 백업을 유지하고 최소 한 개의 검증된 백업과 복원 사용 중인 세트를 보호한다. 보존 시계는 백업 완료 시각을 기준으로 한다. 현재 자동 정리 기능은 비활성이고 실제 파일 삭제는 수행하지 않았다.

**백업 시각 인터뷰 확정:** 매일 `Asia/Seoul 03:00`에 실행한다. 꺼져 있거나 실행되지 않아 일정이 밀렸으면 다음 실행 시 현재 상태를 1회 보충 백업하며 누락된 날짜 수만큼 반복 생성하지 않는다. 누락 판정은 마지막 시도가 아니라 검증된 성공 기록으로 하고, 같은 프로젝트의 동시 예약/보충 실행과 같은 일정의 중복 완료를 막는다. 실패를 성공으로 기록하지 않는다. 실제 예약 작업은 아직 없다.

**백업 경로 인터뷰 확정:** 기본 목적지는 `~/.local/share/airag/backups/<project-id>/`이다. 실행 사용자 홈을 기준으로 해석하고 project-id는 경로 이탈이 없는 단일 디렉터리 이름으로 검증한다. 프로젝트별 디렉터리를 분리하며 아직 실제 폴더나 예약 작업은 생성하지 않았다.

**백업 담당 인터뷰 확정:** AIRAG 운영 계층이 매일 사용자 지정 경로에 암호화 백업을 생성한다. 외부 복제와 키 보관·복구 책임은 사용자에게 있으며 백업에 키 값을 포함하지 않는다. 대상은 소비자 원장·발행 DB·아카이브 및 복원 manifest/checkpoint이며 각 구성요소가 일관된 백업 세트인지 검증한 뒤 완료로 공개한다. 스케줄러는 core 내부에 넣지 않는다. 목적지·시각/시간대·기동 누락 시 처리·백업 보존 개수는 후속 확정하며 자동 백업과 삭제는 아직 활성화하지 않았다.

**최신 키 접근 선택 — 1Password 직접 연동을 대체:** AIRAG는 실행자가 시작 시 주입한 환경변수에서 암호화 키를 읽는다. 에이전트나 1Password 앱/CLI를 runtime 필수 의존성으로 두지 않는다. 소비자/발행 DB/아카이브별 32-byte 키를 64자리 hex로 전달하는 환경변수 계약을 정했으며 실제 로더 구현은 아직 없다. 활성 저장소의 키가 없거나 형식이 잘못되면 파일 생성/열기 전에 실패하고 임의 키 생성·다른 저장소 키 재사용으로 폴백하지 않는다. 설정/argv/로그/환경 전체 출력에 값을 남기지 않고 관련 없는 자식 프로세스에는 전달하지 않는다. 키의 외부 보관·복구 책임과 백업은 후속 확정한다. 기존 투어 키에는 변경이 없다.

**키 보관 인터뷰 확정:** 소비자/발행 DB·아카이브 암호화 키의 보관 제공자는 1Password다. 실제 접근 방식, vault/item/field 참조, 기기 이동·복구·키 교체 계약은 후속 확정한다. 설정에는 비밀값 대신 항목 참조만 두며 키를 argv·로그·문서에 기록하지 않는다. 이번 선택으로 실제 1Password 항목을 만들거나 읽거나 기존 투어 키를 이동하지 않았다.

**공유 범위 인터뷰 확정:** 같은 프로젝트에서 동일 소유자의 명시적으로 등록된 세션끼리 대화 검색·기억을 공유하고 다른 프로젝트는 기본 차단한다. 원본 stream ID와 개별 접근 상태는 계속 보존한다. 아카이브도 같은 소유자/프로젝트 경계를 적용하며 별도 조회 요청이 있어야 읽는다. 이 선택은 새로운 세션 파일의 자동 탐색·수집 권한이 아니다. 현재 입력 허용 목록은 선택한 AI RAG 세션과 투어 자료로 유지한다. 인증된 소유자와 tenant 식별값의 연결은 구현 계약에서 추가 확정한다.

**아카이브 기한 인터뷰 확정:** 활성 영역에서 만료된 대화·기억의 파일 아카이브는 기한 없이 보관한다. 시간 경과만으로 purge하지 않으며 사용자 명시 요청 때만 정리한다. “정리”가 보존/재배치인지 영구 삭제인지 모호하면 먼저 구분한다. 아카이브 파일 묶음 단위와 키/백업 관리는 후속 확정 대상이다.

**최신 보존 선택 — 앞선 영구 삭제 요구를 대체:** 작성 후 90일이 된 대화와 이에 의존하는 기억은 자동 검색·현재 컨텍스트에서 함께 만료시킨다. 허용 범위에서 수집·마스킹한 대화·파생 기억·근거/수정/권한 상태를 별도 항목별 승인 없이 파일 아카이브로 보존한다. 평상시 검색이나 기억 회수에서 아카이브를 자동 조회하지 않고 사용자가 별도로 과거 아카이브 조회 작업을 요청할 때 현재 권한을 확인해 읽는다. 이 조회가 활성 기억 재등록을 뜻하지 않는다.

90일은 활성 이용 기간이며 영구 소거 기한이 아니다. P08A-09는 활성 영역 만료·암호화 파일 아카이브 전환·명시 조회를 개발한다. 파일/manifest의 보존 검증 전에는 활성 저장 참조를 물리적으로 해제하지 않되, 아카이브 장애가 있어도 만료된 내용의 일반 검색 노출은 막는다. 처음 들여올 때 이미 만료된 메시지는 승인된 입력 범위 안에서 archive-only로 처리한다. 아카이브 자체의 보존 기한·묶음 단위는 후속 선택 대상이며 자동 purge는 비활성이다. 원천 채팅 파일과 제외된 비밀/시스템 기록까지 복사·삭제한다는 뜻은 아니다.

**보존 시계 인터뷰 확정:** 각 메시지의 원래 작성 시각부터 90일을 계산한다. 재수집·본문 수정·요약 재생성이 원본 메시지의 만료 시각을 연장하지 않는다. 이미 만료된 과거 메시지는 새 일반 색인에 본문을 넣지 않으며, 작성 시각이 없거나 신뢰할 수 없으면 수집 시각으로 조용히 대체하지 않고 격리한다. 수정 사건의 occurred_at과 원래 메시지 작성 시각은 별도로 연결한다. 중요한 기억의 만료 예외는 다음 인터뷰 대상이다. AIRAG 보존 정책이 원천 채팅 파일 자체를 삭제할 권한을 뜻하지 않는다.

**보존 인터뷰 확정:** 사용자는 대화 기록을 90일 보관하는 것을 목표로 하고 만료 삭제 기능까지 개발 범위에 포함하도록 선택했다. 기존 “물리 삭제 미지원”은 현재 구현의 한계이며 앞으로의 범위 제외를 뜻하지 않는다. PLAN P08A-09에서 원장/세그먼트·core 원본/청크/벡터·파생 기억·캐시·백업의 삭제 및 복원 후 부활 방지를 함께 설계·검증한다. 90일의 기준 시각, 중요 기억 예외, 백업 만료 방식은 아직 미정이다. 자동 purge는 비활성 상태이고 기존 기록을 삭제할 권한을 이번 개발 범위 선택만으로 실행에 사용하지 않는다.

기획 기준안은 위와 같이 선택했지만 사용자가 승인했다고 쓰지 않는다. P08A-01에서 다음 값을 확정한다.

1. 첫 입력: 현재 에이전트 채팅 한 종류와 문서 connector 한 종류를 추천. 실제 읽기 경로·계정·권한 범위를 지정한다.
2. 세그먼트 임계, N=4·12,000 tokens, 비용·지연 목표를 사용할 환경에서 확정한다.
3. rule_checked 일반 사실의 사용 범위, 사람 확인이 필요한 선호/지침, pin 담당자를 정한다.
4. access_scope 분할·프로젝트 간 공유·CDC read-gate 가용성 요구를 정한다.
5. retention/복제 내구성·백업 만료·영구삭제 요구를 정한다. 현 core 미지원 조건이 필수면 범위를 별도 등록한다.

## 13. P08A-01 진행 — 검토 가능한 계약 초안

**사용자 인터뷰 확정:** 첫 사용 경험은 대화 기억(과거 대화 검색·결정·오류 해결 근거 회수)이다. 검색용 윈도우는 작업 단위 완료·명시 저장 또는 미색인 사건이 5분 경과했을 때 닫아 발행 요청한다. 새 메시지가 타이머를 계속 미루지 않으며 새 사건이 없으면 재발행하지 않는다. 앞 절의 30분 창 제안은 이 선택으로 대체한다. 원본 수신 commit은 이 타이머를 기다리지 않는다. 5분은 처리 시작 조건이며 모델 장애 상황에서도 검색 완료를 보장하는 SLA는 아니다. 나머지 운영값은 별도 인터뷰로 확정한다.

2026-09-27 사용자 “다음으로 진행”에 따라 계약 구체화를 시작했다. 정형 계약은 [p08a01-contract.json](p08a01-contract.json), 합성 입력은 [p08a01-synthetic-conversation.jsonl](p08a01-synthetic-conversation.jsonl)이다. 이후 사용자가 **현재 AI RAG 세션 이력 + 기존 투어 샘플 문서**를 선택했다. 정확한 입력 경로를 계약 허용 목록에 반영했으며 원본 내용의 수집·재색인은 시작하지 않았다.

입력 확인: 현재 세션 ID는 `01a083f2-359f-7de3-bc99-47ed799675ac`, 지정 rollout JSONL 첫 session_meta의 ID와 일치한다. 과거 시작 cwd는 cli-rag이므로 cwd 문자열로 현재 세션을 고르지 않는다. 이 파일 하나의 user/assistant 공개 메시지만 후보이며 reasoning·system/developer·압축요약·이중 기록을 제외한다. 도구 본문은 마스킹/짝 연결 검증 전 제외한다. 바이트 checkpoint와 파일 교체/축소 감지로 재시작하며 원본을 수정하지 않는다.

투어 문서는 개별 library-ko.txt 파일들이 디렉터리에 놓인 구조가 아니다. `tour.db`의 암호화 source/revision이 현재 원본이다. T03 생성 스크립트의 과거 5권/14일 상수를 재사용하면 T07의 7권/21일 갱신을 되돌리므로, 기존 읽기 전용 API로 지정된 17개 source의 현재 비삭제 head를 대조해야 한다. 사용자 선택은 이 원천 범위에 대한 것이며 저장 키·retention 등 미결 운영 정책까지 승인한 것으로 확대하지 않는다.

### 기존 core와 연결되는 실제 계약

Serena로 기존 `normalize._build_conversation`과 테스트를 확인했다. 입력은 `application/x-airag-conversation+json`의 `{"turns":[{"id":"...","role":"...","text":"..."}]}`다. 각 turn의 ID는 `conversation_turn` 앵커의 `turn_id`에, 위치는 `/turns/i/text`에 보존된다. 소비자 JSONL 사건을 현재 유효 메시지로 해석한 뒤 이 구조에 맞춰 전달한다.

core 앵커가 시각·권한·세션 메타를 자동 보존한다고 가정하지 않는다. 소비자가 `source/revision/turn_id/pointer/window_version`으로 원장에 연결해 응답 직전에 검증한다. 기존 source의 옛 ready가 처리 중 남더라도 삭제·편집·권한철회로 무효화된 내용은 소비자 응답 gate에서 먼저 막는다.

합성 JSONL 두 줄을 기존 어댑터에 전달해 DoclingDocument 생성과 메시지 ID·원문 pointer·본문 보존을 실행 확인했다. 이는 변환 접점의 확인이며 이벤트 소비자·윈도우 생성·임베딩·검색 완료 시험은 아니다.

### 이번 단계에서 정한 개발 실험값

- 창 최대 40사건/2,000토큰, 30분 또는 명시 flush. 최근 활성 4개, tail 8,000 + memory 2,000 + 과거 회수 2,000토큰. 정확 계수는 실제 응답 모델 tokenizer 선정 후 가능하다.
- 원본은 JSONL 논리 형식과 SQLCipher 암호화 저장. 원장 commit 이전 ack 금지, 연속 commit 구간까지만 cursor 이동.
- 첫 기본 검색 top-k=5, 품질 측정 recall@3은 별도 기준. 전체 색인은 N개로 자르지 않는다.
- 실험 중 자동 영구삭제·평문 로그 복제·외부 공유 없음. 운영 retention과 암호화 키 보관/교체/복구는 별도 확정한다.
- C01~C14로 중복·충돌·부분 줄·늦은 수정·이력 검색·권한·재오픈·저장실패·복원·rename·비밀값 처리의 입력 상황과 기대 결과를 기록했다. 사례를 기록한 것이 실행 통과를 뜻하지 않는다.

### 완료 전 남은 항목

1. 첫 실제 입력 선택·정확한 파일 경로는 확정. 지정 JSONL의 공개 메시지 매핑과 기존 암호화 DB의 17개 source/current head 읽기 계약 검증이 남았다.
2. 선택 환경에 맞는 개인정보 범위·retention·키 보관/교체/복구·모델/tokenizer·기억 승인 정책 확정.
3. v1.1 및 계약의 DA 개발 착수 검토는 4차 PASS로 완료. 사례의 실행 가능한 인수 시험 연결은 남았다.

### 3차 DA 대응 — B4~B6

- **B4 발행 대상:** 투어 DB는 기존 17개 source의 읽기 대조·검색 원천으로 유지하고 재발행하지 않는다. 새 윈도우·기억의 대상은 실행 디렉터리 아래 `p08a/projections.db`와 `airag-session-v1/airag-memory-v1` 컬렉션이다. 소비자 원장은 `p08a/consumer.db`다. 경로만 확정했으며 생성하지 않았다. 대상 DB별 별도 키가 제공되기 전 생성/발행을 거부한다. 첫 연결의 문서+대화 검색은 동일 core 엔진을 쓰는 두 DB의 구분된 결과 그룹이며 하나의 전역 순위나 원자 snapshot을 주장하지 않는다.
- **B5 접근 범위:** 양 입력에 project `airag-rag-transplant`와 각 session/tour stream scope를 고정했다. tenant ID는 `pending_user_value`로 남기고 미확정이면 실수집·검색을 거부한다. 입력이 보내온 scope를 신뢰하지 않고 인증된 주체에 대해 수집 전·검색 전·문맥 확장 전·최종 응답 전 검사한다. 필드/검사 위치 확정과 실제 사용자 권한 값의 승인은 별개다.
- **B6 프로필:** 기존 conversation.json에 등록된 `cb98ca939d44340d796e2eaa0388c66f1a2771f637739fdc3f1b94f84181633c`를 읽기 전용으로 확인하고 고정했다. 새 DB에 동일 descriptor로 등록한 fingerprint·대화 호환성이 확인돼야 발행한다. 이번 확인은 provider 호출·현재 모델 운영 품질 검증이 아니다.
- **B6 마스킹:** `airag-local-redaction-r1`을 고정했다. user_shell_command/environment_context 태그의 완전한 블록은 내용 대신 유형 placeholder로 바꾸고 주변 공개 발언과 message ID를 보존한다. 깨진/모호한 블록이나 마스킹 실패는 저장 전 거부한다. bearer·명명된 key/token/password/secret·개인키 PEM·URL 자격정보 규칙을 명시했으며, 모든 민감정보를 완벽하게 탐지한다고 주장하지 않는다. 실제 파서·규칙 구현과 인수 시험은 남아 있다.
- **비차단 정합:** compacted 레코드의 replacement history를 재수입하지 않고 원래 파일 checkpoint를 이어간다. 파일 신원/무결성 확인 → byte offset 재개 → ordinal·event ID 검사의 우선순위를 정했다. 시연 전 명시 flush와 searchable 확인을 요구하며 수정삭제 correction 시연은 합성 주입임을 표시한다.

기준선 질의는 P08A-07 실행 전에 H01~H20을 고정한다: 최근 대화 4, N개 밖 이력 4, 창 경계 문맥 4, 오류/해결/재오픈 4, 삭제/권한 음성 사례 4. 각 항목의 질의·기대 message ID·허용 범위·정답 revision을 함께 동결해야 실행 근거로 인정한다. 아직 질의와 정답 데이터의 작성/실행 완료를 뜻하지 않는다.

**4차 DA 마감:** B4~B6 및 비차단 6건의 반영을 확인해 구현 계약 기준 PASS를 받았다. 고정 프로필에는 LLM 전처리가 포함되므로 C07은 LLM·임베딩 각각의 실패와 재시도를 검증한다. C14는 마스킹 후 공백/placeholder만 남은 메시지의 사건·receipt를 보존하되 검색 turns에서 제외하고 청크 0개를 정상으로 판정한다. P08A-01은 운영값과 인수 시험이 남아 전체 완료로 닫지 않으며, 합성·격리된 P08A-02/03 구현은 착수할 수 있다.

이 문서와 HTML 매거진은 기획 산출물이다. 실제 자료 수집·아카이브 이동·메모리 주입·삭제 자동화가 실행됐다는 뜻이 아니다.

## 14. P08A-03 첫 구현 단위

새 소비자 패키지에 이벤트 계약 검증, 바이트 기준 JSONL 파싱, create-only 대화 직렬화를 구현했다. [검증 결과](p08a03-input-adapter-verification.json): 합성 입력·기존 Docling 앵커 연결을 포함해 70개 테스트 통과. 수정/삭제 사건은 파싱만 가능하고 적용하지 않는다. grant/revoke는 아직 거부한다. create-only 변환은 correction·중복·다른 scope 혼합을 거부해 기록을 잘못 신규 발행하지 않게 한다.

파서의 parsed_end_offset은 저장 checkpoint가 아니다. 마스킹·SQLCipher 원장·멱등 수신·durable commit/ack·세그먼트 봉인·윈도우 관리가 다음 구현 범위다. 실제 rollout 입력, 외부 모델, DB 생성은 실행하지 않았으며 독립 코드 DA는 아직 수행하지 않았다.

후속 구현: 순수 어댑터의 K1/K2를 수정했고 SQLCipher 원장·마스킹·멱등 receipt·checkpoint를 구현했다. 합성 소비자96+기존 정규화26=122개 테스트 통과([근거](p08a03-ledger-verification.json)). 첫 기록의 한계 목록은 당시 상태이며 현재는 native rollout 연결·파일 prefix 검증·correction/권한 reducer·봉인·윈도우·실제 RAG 발행이 남아 있다. 시험용 암호화 DB만 임시 경로에서 생성했다.

거부된 완전한 한 줄은 `skip_rejected_record`로 명시적 누락 결정을 기록할 수 있다. 정확한 digest·범위·사유·source binding을 확인하고 사유/해시/범위와 checkpoint만 한 트랜잭션으로 저장한다. 원문은 저장하지 않고 정상 수신 ack와 다른 SkipReceipt(accepted_events=0, coverage_gap=true)를 반환한다. 유효/미완성/여러 줄은 이 API로 건너뛸 수 없다. caller는 누락을 표시해야 하며 이를 완전한 이력이라고 보고하지 않는다.

마스킹 정책은 보수적으로 유지한다. 모호한 태그 산문은 여전히 거부될 수 있고 숫자 token 값도 자격정보일 가능성이 있어 치환한다. 이는 알려진 오탐 경계이며 명시적 누락 기록·정책 개정으로 처리한다. 사용자 문자 그대로의 placeholder는 공개 텍스트로 보존하고, 실제 redactor가 산출한 has_public_text 증거만 빈 검색 본문 판정에 쓴다. 정책 버전 변경은 기존 source를 제자리 재바인딩하지 않고 새 암호화 원장 세대에서 명시 재처리한다. 운영 키 교체/복구와 스키마 migration은 아직 구현하지 않았다.

7차 코드 DA는 위 5개 모듈의 구현 경계에 PASS(blocker 0)를 부여했다. DA가 소비자96개 테스트와 거부 기록 복구·placeholder 보존 사례를 독립 재현했다. 메인은 기존 정규화26개를 포함한122개 통과를 기록했다. 이 판정은 P08A-03 전체 완료나 §15 프로젝트 축의 검증을 뜻하지 않는다.

## 15. C축 — 프로젝트 문서·코드·테스트·스크립트 RAG (v1.2)

사용자 목표는 AIRAG를 여러 프로젝트에 연결 가능한 저수준 지식 엔진으로 만들고, 문서/코드의 넓은 의미 검색과 Serena/LSP의 정확한 심볼 탐색을 결합하는 것이다. 코드도 바뀌는 자료이지만 언어·심볼·의존성과 저장소 버전 경계가 있으므로 **별도 프로젝트 소비자 축**으로 관리한다. 사건 원장·멱등성·접근 범위·백업 재대조 등 P08A 공통 기반을 재사용하며 진행 중인 대화 원장 작업을 대체하지 않는다.

```text
선택한 저장소·worktree
├─ 문서: README·설계·운영·ADR → 제목/문단/표 단위
├─ 소스: 모듈·클래스·함수 → 언어/AST/심볼 단위
├─ 테스트: fixture·테스트 함수·기대 동작 → 구현과 연결
└─ 스크립트: 진입점·명령·설정 의존 → 실행하지 않고 읽기
      ↓ 권한·파일 선택·비밀 제외·snapshot 고정
원문/파일해시/버전/경로/행·심볼 anchor + 검색 청크
      ↓ 기존 AIRAG 저장·임베딩·키워드/의미 검색
질문: “재시도 멱등성은 어디서 보장하고 어떤 테스트가 있나?”
├─ RAG: 관련 설계·구현·테스트·스크립트 후보를 함께 찾기
├─ Serena/LSP: 정의·참조·호출자·현재 심볼 범위를 확인
└─ 답변: 같은 버전의 근거 + 확인된 관계 + 불확실한 관계 구분
      ↓ 파일 저장 / commit / rename / delete / branch 전환
변경된 파일·심볼과 영향 파생물만 재평가 → 새 snapshot 발행
```

### 저장소·파일·코드 버전 계약

- `repo_id`는 소비자 등록 시 부여하는 안정 ID다. 같은 URL의 fork·복수 worktree를 자동으로 같은 저장소 상태로 합치지 않는다. `worktree_id, snapshot_kind, base_commit, snapshot_id, relative_path, content_hash, language, parser_version, profile_key`를 기록한다.
- commit snapshot과 미커밋 working-tree snapshot을 구분한다. dirty 파일의 내용 해시·선택 파일 manifest로 실제 관측 상태를 고정하며 저장 중 바뀐 파일은 재읽기한다. 조회는 완료된 snapshot을 고르고, 다른 branch/commit의 청크를 현재 코드인 것처럼 섞지 않는다.
- 각 검색 결과는 원문 파일 hash·revision·행/문자/byte 범위·symbol ID(관측된 경우)를 가진다. 파서가 심볼을 모르면 만들어내지 않고 텍스트 경계 fallback을 표시한다. 긴 함수는 여러 청크로 나누되 부모 심볼·문맥 링크를 보존한다.
- 파일 source 변경은 기존 core CAS/멱등성으로 처리한다. 다파일 snapshot의 가시성은 소비자 manifest/read gate로 관리하며 core가 저장소 전체를 원자 발행한다고 가정하지 않는다. 등록/발행 중 실패하면 최신 상태를 미완료로 표시하고 마지막 검증 snapshot을 명시적으로 사용할 수 있게 한다.
- rename은 git/원천 근거로 신원을 대조한다. 불명확한 이동은 억지로 같은 파일로 합치지 않는다. 확정 삭제는 현재 snapshot에서 배제하고 파생 관계를 무효화한다. 부분 탐색·권한 오류를 삭제로 추측하지 않는다.

### 코드 청킹은 문서 청킹과 공통 저장 기반을 쓰되 구조를 보존

문서는 기존 Docling 구조·HybridChunker 경로를 재사용한다. 코드는 언어 parser/AST·Serena가 확인한 심볼을 청크 경계와 anchor의 근거로 삼는다. 코드 블록의 들여쓰기·주석·문자열·식별자와 원문 바이트를 보존하고, 일반 문서용 번역/의미 그룹 변환으로 실행 코드를 바꾸지 않는다. 검색용 설명·요약·번역은 별도 파생 필드로 표시한다.

현재 LLM 전처리 프로필을 코드에 그대로 적용해도 안전하다고 가정하지 않는다. P08B-03에서 코드 보존용 프로필과 tokenizer·parser fingerprint를 확정한다. Docling 코드 item/기존 core adapter로 원문·심볼 범위를 정확히 전달할 수 있는지 검증하고, 불가능하면 별도 core normalizer 작업과 회귀 게이트를 등록한다. “모든 언어 AST 지원”을 초기 완료 기준으로 삼지 않고 첫 언어와 미지원 fallback을 명시한다.

### 변화 감지·업데이트 주기

- 초기 등록: 승인된 tracked 파일과 명시 허용된 untracked 파일만 목록화 → 비밀/생성물/외부경로 제외 → snapshot 생성.
- 저장 이벤트: 외부 소비자 watcher가 변경을 모으고 쓰기 안정성·내용 hash 확인 뒤 영향 파일만 처리한다. debounce 시간은 사용 환경에서 정한다. core 내부에 watcher를 넣지 않는다.
- commit/branch 전환: 새 snapshot ID로 범위를 재대조한다. LSP가 옛 branch 상태면 완료로 처리하지 않고 갱신을 기다리거나 해당 관계를 미확인으로 반환한다.
- 중단/누락 복구: git diff·파일 manifest 정기 대조와 마지막 durable checkpoint로 수렴한다. mtime이나 watcher 전달 성공만을 정본으로 취급하지 않는다.
- parser/profile 변경: 원문을 바꾸지 않고 영향 범위를 reindex한다. 범위·추가 비용·실패 목록을 노출한다.

### AIRAG와 Serena/LSP의 역할 분담

AIRAG는 자연어·키워드로 관련 문서/코드/테스트/이전 장애 근거를 회수한다. Serena/LSP는 현재 작업트리의 정의·참조·호출·타입 관계를 확인하는 선택적 심볼 제공자다. 도구가 없는 환경에서도 텍스트/코드 RAG는 동작하되 “LSP 확인 없음”을 표시한다.

연결 시 실제 root·언어 지원·capability와 document version/content hash를 대조한다. 현재 LSP에서 받은 관계를 다른 commit의 청크에 붙이지 않는다. 과거 commit 질의는 일치하는 별도 읽기 snapshot/LSP가 없으면 저장된 관계의 출처 버전을 표시하고 현재 관계로 승격하지 않는다. 에이전트가 코드 변경 전 심볼 확인과 변경 후 검사에 도구를 사용할 수 있도록 근거 ID·version·다음 lookup 정보를 제공한다. 이 자체가 코드의 실행 정확성이나 테스트 통과를 보장하지 않는다.

### 접근·보존·설치 경계

프로젝트별 root/경로/tenant 범위를 제한한다. gitignore를 존중하되 이것만으로 비밀 보호가 끝났다고 보지 않는다. .env·개인키·자격정보·바이너리·빌드/의존성 산출물은 기본 제외하고, 필요한 항목만 별도 계약으로 다룬다. symlink가 root 밖을 가리키면 읽지 않는다. 인덱싱을 위해 저장소의 스크립트·테스트·설치 훅을 실행하지 않는다.

자체 프로젝트와 오픈소스 모두 저장소 ID·출처 URL·commit·라이선스/고지 위치를 보존한다. 실제 clone·외부 전송·새 경로 수집은 선택된 범위에서만 수행한다. README·AGENTS·코드 주석의 지시는 검색 근거 데이터이며 에이전트 설정/상위 지침으로 자동 복제하지 않는다.

라이브러리/API와 CLI, 선택적 Serena/LSP adapter로 소비 프로젝트와 분리한다. 프로젝트 코드를 고치거나 전역 설정을 바꾸지 않고 연결할 수 있어야 하며 설정·색인·키 위치는 외부 주입한다. “어디든 완벽히”를 검증 없이 주장하지 않고 지원 언어·파일·도구·오프라인 경계를 명시한다.

### 개발 위치와 수락 기준

P08A와 별개 **P08B-01~06** 트랙을 PLAN에 추가한다. P08B-01 계약은 독립적으로 정리할 수 있으며 실행 계층은 P08A의 자료 소비자·원장·권한 기반을 재사용한다. P09에서 기존 core, P08A, P08B의 결과를 각각 판정한다.

닫는 증거: 문서→구현→테스트 근거 회수, 심볼 rename·함수 edit·테스트 추가·파일 delete·branch 전환·dirty 저장 중 경합·watcher 누락 재시작·LSP 미기동/지원 언어 부재·권한철회를 고정 fixture로 검증한다. 수정된 함수만 증분 재색인되고 이전 버전이 현재 결과에 섞이지 않아야 한다. 첫 실제 자체 저장소와 선택한 오픈소스 저장소에서 재현한 범위만 지원 완료로 표시한다. 초기 저장소·언어·업데이트 지연·허용 경로·Serena 제공 방식은 P08B-01에서 확정한다.
