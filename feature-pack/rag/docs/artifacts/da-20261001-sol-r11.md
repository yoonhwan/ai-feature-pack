## Nano 편차 3건

### 1. native-raise의 INTERNAL_ERROR — 허용 가능한 코드 보정

실제 관찰은 `exit=40`, `code=INTERNAL_ERROR`, `type=RuntimeError`였다. `cli.py:146-152`의 기존 예외 처리에서 메시지 `inside`가 코드 형태가 아니므로 INTERNAL_ERROR로 바꾼다. 이 값은 정적 레지스트리에 선언돼 있어 `_result.error_fields`가 보존한다. CLI는 이번 diff에서 변경되지 않았다. 메시지나 native marker가 전달되는 것은 아니므로 `{RUNTIME_FAILED, INTERNAL_ERROR}` 단언의 완화는 비노출 보호를 약화하지 않는다. 승인 설계의 예외 코드 기대를 기존 CLI 동작에 맞춰 보정하면 된다.

### 2. fork 손자의 .airag-runtime.lock — 다음 tick 정상 실행까지 보장하지 않는다

독립 실제 tick 관찰:

```text
FORK_FIRST_EXIT 0
FORK_PARENT_RETURNED_BEFORE_MARKER true
FORK_SECOND_TICK_EXIT 40
FORK_SECOND_TICK_CODE PROJECT_BUSY
FORK_SECOND_TICK_NOT_SKIPPED true
FORK_FINITE_DESCENDANT_MARKER true
FORK_TICK_AFTER_DESCENDANT_EXIT 0
FORK_AFTER_DESCENDANT_STATUS ok
```

`runtime.py:472-489`의 `_lock`은 flock fd를 패스 동안 보유하며 fork/no-exec 손자가 같은 open file description을 상속한다. 부모/worker의 close만으로 손자의 사본이 닫히지 않는다. runtime.py는 이번 변경 범위에서 수정되지 않았다. 새 wrapper는 tick.lock을 부모에만 남겨 기존 wrapper 락의 손자 연장을 제거하지만, 프로젝트 락을 해제하는 변경은 하지 않았다.

따라서 **wrapper 완료와 다음 wrapper 락 획득은 성공하지만 다음 consumer 패스는 실패할 수 있다.** 손자 생존이 다음 StartInterval까지 이어지면 그 tick의 수집·발행·기억·백업 패스는 PROJECT_BUSY로 실패하고, 손자가 종료되면 후속 tick에서 복구된다. 무한 생존 손자라면 이 가용성 잔여도 계속될 수 있다. 실제 운영 컴포넌트에서 발생한다고 주장하지 않는다.

설계 I6/T-fork-descendant-no-delay의 `!= EXIT_SKIPPED`는 문자 그대로 충족된다. 그러나 ⑤2에 **runtime 프로젝트 락 상속으로 PROJECT_BUSY가 지속될 수 있음**을 명시해야 “다음 틱이 정상 실행된다”는 과대 해석을 막는다. 이는 알려진 손자 존속·기존 runtime 락의 범위이며 이번 소스 변경의 새 비노출 major로 세지 않는다. 향후 락 지원 범위를 넓히려면 별도 설계 판단이 필요하다.

### 3. 레지스트리 574→528 — 현재 결과는 일관되며 cardinality가 완전성 증명은 아니다

현재 생성기의 `current()`를 실행해 실제 frozen 목록과 equality, 미분류 0·수기 모순 0을 확인했다. 위험한 지정 환경변수명은 제거됐고 공개된 선언 코드는 보존된다. `reason` 필드/keyword의 도메인 상태와 code/reason_code·수기 reason의 구분, 동적 코드군의 RUNTIME_FAILED fallback은 승인된 정책이다. 숫자 528 자체로 모든 코드 의미가 증명되는 것은 아니며, R11-m3의 이름 해석은 별도 결함이다.

추가 관찰: `_pass_child`의 `from .tick import NAMES`는 설계의 stdlib+_result 목록보다 넓지만, 현재 tick은 순수 부모 경계이고 component 의존성을 당기지 않으므로 비노출 결함으로 세지 않았다.

## 신규 Minor

### R11-m1 — unhashable code가 strict frame 거부 대신 부모 내부 오류가 된다

- 위치: `_result.py:104-120`, 특히 `:116`; `tick.py:190-191,247-248`.
- `validate_frame`이 code 자료형을 검사하기 전에 frozenset membership을 수행한다. code가 list/dict이면 None 반환 대신 TypeError가 발생한다. `_run_component`는 ValueError만 잡으므로 부모의 일반 Exception 처리로 넘어간다.
- 실제 synthetic component가 `{"exit":0,"summary":{},"code":["MARKER_CODE"],"type":""}`를 쓴 결과: **tick exit 50 / code TypeError**. 설계상 기대는 **exit 40 / RUNTIME_OUTPUT_INVALID**다. MARKER_CODE는 출력/로그로 에코되지 않았다.
- 범위/심각도: **minor**, malformed 결과의 진단·exit 분류 계약 위반. fail-closed 비노출은 유지된다.
- 보정: membership 전에 code가 str인지 검사하고 부적합 타입이면 None을 반환한다. list/dict/null/수 등 code 타입과 실제 tick 매핑을 테스트한다. source는 수정하지 않았다.

### R11-m2 — stdin 검증은 64hex가 아니라 “길이 64 + fromhex 성공”이다

- 위치: `_pass_child.py:26-48`, 특히 `:39-42`.
- bytes.fromhex는 공백을 허용한다. `(a1/b2/c3)*31 + 공백 2개`는 길이 64이고 서로 다른 **31바이트**로 decode되며 `_read_keys`가 그대로 수락했다. 이는 설계의 64자 hex / 32바이트 키 bootstrap 계약과 맞지 않는다.
- 범위/심각도: **minor**. 정상 tick의 load_keys가 `_KEY.fullmatch`로 먼저 검사하므로 현재 부모 경로가 잘못된 키를 전송하는 재현은 아니다. 직접 자식 프로토콜 경계의 검증 누락이다.
- 보정: exact 64-hex fullmatch 또는 whitespace 없는 hex 검증과 decoded 길이 32를 적용한다. whitespace·tab/newline·짧은 decode의 종료코드 2/빈 결과 테스트를 추가한다. 기존 stdin 테스트에는 이 경우가 없다.

### R11-m3 — 생성기가 다른 모듈의 동일 이름 함수 바인딩을 합친다

- 위치: `tests/_regen_reason_codes.py:54-60,81-96,150-160`.
- `_name`은 owner/module을 버리고 짧은 함수명만 사용하며 build_bindings는 같은 이름의 code 인자 위치를 union한다. 실제 source에도 혼합 이름이 있다: `events._identifier(value, field)`와 `memory/lifecycle._identifier(value, code)`, `expansion._id(value, name)`와 `runtime._id(value, code)`, runtime의 check callback과 diagnostics.check(code).
- 독립 합성 두 파일에서 `reason.py`는 `_identifier(value, code)`, `data.py`는 `_identifier(value, field)`를 정의하고 후자가 `_identifier(value, "PATH")`를 호출했다. 생성기는 **PATH를 declaration/reason에 넣고**, closed-world **미분류 0·모순 0**으로 통과시켰다. 실제 호출의 두 번째 인자는 field다.
- 범위/심각도: **minor**, 공개 데이터 literal을 이유 코드로 오인할 수 있는 생성/진단 의미 결함. 현재 frozen 목록에서 PATH는 거부되고, 현재 source의 같은 파일에 정의된 직접 호출을 좁혀 대조했을 때 이 유형의 false declaration은 0이었다. 합성 재현을 현재 실제 비밀 누출로 표현하지 않는다.
- 보정: module/scope와 import alias를 반영한 callee identity로 바인딩하거나, 동일 이름의 다른 signature는 모호함으로 실패시켜 검토한다. 서로 다른 모듈의 같은 이름 code/field 함수와 receiver 이름 충돌을 회귀로 고정한다. 현재 528개는 본 검토 중 재생성/수정하지 않았다.

### R11-m4 — huge-raw 모드가 정제 대상 CLI StringIO를 키우지 않는다

- 위치: `tests/_tick_component.py:77-79`, `tests/test_tick.py`의 `test_raw_component_output_is_never_persisted_in_the_result_file`.
- 모드는 print와 sys.stderr.write로 약 5 MiB를 쓰는데, 해당 stream은 이미 /dev/null이다. CLI의 명시적 stdout/stderr 인자로 받은 StringIO와 다르다. 따라서 이 테스트는 큰 표준 스트림 폐기는 확인하지만, 설계가 요구한 큰 raw CLI stdout → 작은 정제 frame 경로를 확인하지 않는다.
- 범위/심각도: **minor**, 테스트 대상 차이. 구현의 build_frame/자식 쓰기 전 정제 자체는 올바른 방향이다.
- 보정: synthetic CLI stub이 실제 전달받은 stdout StringIO에 큰 비-JSON 문자열을 쓰도록 한다. 기존 standard-stream 부하 mode는 별도로 유지할 수 있다.
- 독립 보완 관찰: 임시 stub으로 실제 `_pass_child.child_main`의 cli.main을 대체해 **6,000,000바이트**의 raw StringIO 입력을 만들었다. 자식 exit 0, 파일 **65바이트**, validate_frame 통과, code RUNTIME_OUTPUT_INVALID, MARKER_ 부재였다. 이 probe는 repo 테스트 수정 없이 수행했고 실제 runtime/endpoint를 호출하지 않았다.
