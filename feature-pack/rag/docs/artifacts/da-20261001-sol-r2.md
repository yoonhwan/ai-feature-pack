## 검증 커서와 마이그레이션

`memory.py:478`의 `airag_memory_verification_cursor` 및 `memory.py:713`의 `_unverified_batch()`를 검토했다. 조회 후 cursor 쓰기는 `_transaction()`으로 실행되고, 모든 관련 extraction 진입점은 먼저 `initialize_memory()`를 수행한다. runtime lock 아래 직렬 호출하는 기존 계약에서 새 race나 영구 고착을 확정하지 않았다. 동시 다중 프로세스가 lock 없이 이 API를 호출하는 범위까지 검증한 것은 아니다.

합성 구스키마는 `2938a36`의 memory 모듈을 메모리 내 별도 Python 모듈로 로드해 생성했다. 파일이나 현재 모듈을 교체하지 않았다.

1. 구버전으로 unverified 후보 3개를 만들고 새 cursor 테이블이 없음을 확인했다.
2. 현재 `initialize_memory()`를 두 번 호출했다. 기존 후보 모든 column 값이 유지됐고 schema 초기화는 성공했다.
3. 첫 verifier 방문 뒤 SQLite DB를 새 connection으로 복사해 Lifecycle을 재생성했다. 방문 순서는 `legacy-solution-0 → legacy-solution-1 → legacy-solution-2 → legacy-solution-0`으로 유지됐다.
4. 외부 `BEGIN` 안에서 extraction/verifier를 실행하고 `ROLLBACK`했다. cursor 행은 호출 전 값으로 복귀했다.


### R2-M1 — 구버전의 검증된 archive 포함 백업을 새 runtime이 거부한다

- 심각도: **major**. Nano가 알린 가능성을 실제 합성 실행으로 확인했다.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/runtime.py:1266`–1269; 거부 경계 `feature-pack/rag-consumer/src/airag_consumer/operations.py:329`–332.
- 재현: `2938a36`의 runtime.py를 메모리 내 별도 모듈로 로드한다. 기존 `test_runtime.py` fixtures로 91일 된 메시지 하나를 수집하고 archive 묶음 1개를 포함한 구버전 백업을 만든다. 그 구버전 runtime으로 verify=True를 확인한다. 동일 config/keys/backup ID를 현재 runtime으로 검증한다.
- 관찰: 구버전 검증은 `True`; 현재 runtime은 `OperationsError: MISSING_DATABASE_KEY`. 같은 저장소에 현재 runtime으로 새 백업을 만드는 것은 성공한다.
- 근거: 구버전 manifest는 archive component를 `kind='database'`로 기록한다. 현재 verify는 consumer/projection key만 제공한다. operations는 과거 manifest의 database archive component에 필요한 key를 찾지 못해 거부한다. 신규 backup 형식의 정상 verify 경로와 다른 호환성 경계다.
- 영향과 한계: 구버전의 정상·검증된 archive 포함 복구 세트를 새 verify 경로로 재검증할 수 없다. 백업 파일이 삭제되거나 암호화 데이터가 손상되는 현상은 아니다. 구버전 runtime으로 같은 세트를 검증할 수 있으며 신규 백업은 정상이라 blocker로 올리지 않았다. archive가 없는 구버전 백업까지 실패한다고 일반화하지 않는다.
- 테스트 공백: r2 테스트는 모두 수정 후 형식으로 백업을 생성한다. 실제 구버전 manifest를 생산한 뒤 새 runtime으로 여는 경계를 포함하지 않는다.

### R2-M2 — 격리 복원 검증이 원래 archive 파일의 존재에 의존한다

- 심각도: **major**.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/runtime.py:918`–920; 호출된 `_confirmed_archives()`의 `runtime.py:841`–846.
- 재현: 수정 후 runtime으로 archive 두 묶음을 포함한 새 백업을 만들고 검증한다. pytest fixture의 원래 archive 파일 하나를 `.preserved-offline` 이름으로 이동하여 원래 경로에서 잠시 사용할 수 없게 한다. backup component/manifest는 변경하지 않는다. 그 backup ID를 다시 검증한 뒤 `finally`에서 원래 archive 파일 이름을 복구하고 다시 검증한다.
- 관찰: 원래 파일이 없을 때 `RuntimeError: UNTRUSTED_ARCHIVE_RECEIPT_PATH`; 파일 이름을 복구하면 같은 백업의 verify=True이다.
- 근거: `_restore_link_check()`가 restored ledger의 receipt를 `_confirmed_archives()`로 해석한다. 이 helper는 receipt의 원래 절대경로가 현재 운영 archive_root 아래에 있고 `is_file()`이어야 한다고 검사한다. 따라서 이미 backup component를 임시 경로로 복원한 이후에도 원래 source file의 존재가 필요하다. 오류는 복원된 archive 자체의 integrity 검사 이전에 발생한다.
- 영향과 한계: archive 원본이 unavailable인 상황에서, 해당 archive를 포함한 유지된 백업도 현재 격리 검증 경로로 검사하지 못한다. P08A-10의 격리 복원 검증에 불필요한 운영 파일 의존성이 관찰된다. 운영 파일이 존재하는 평상시 신규 백업/일일 실행은 성공하므로 major로 기록했다. 전체 저장소 손실이나 완전한 재배치 복구까지 실증한 것은 아니다.
- 테스트 공백: 현재 테스트는 백업 verify 동안 원래 archive 파일을 모두 유지한다.
