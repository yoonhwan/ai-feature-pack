### R8-M1 — 값 없는 출력 경계가 런타임 예외 메시지와 구성요소의 직접 출력을 막지 못한다

- 심각도: **major**.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/tick.py:171-176` (런타임 error.code 문자열 허용), `:207-214` (CLI 출력 객체만 교체), `:226-233` (외부 출력·로그). 관련 기존 CLI 경계 `cli.py:146-153`.

- 재현: 기존 fixture의 실제 합성 runtime을 서로 다른 유효한 대문자 hex 저장소 키 3개로 초기화한다. 실제 bridge publish 메서드만 합성 RuntimeError를 던지게 하며 그 메시지는 합성 저장소 키 1개다. tick→실제 CLI→실제 run_once→bridge의 오류 처리를 실행한다. CLI나 tick의 오류 반환 자체를 가짜로 만들지 않았다.
- 관찰: exit 40이며 **출력 JSON의 code 필드와 날짜별 tick 로그에 합성 키가 그대로 남았다.** 키 값은 판정서에 기재하지 않는다. 정상 error code의 문자 형태라는 사실은 값 비노출을 보장하지 않는다.
- 같은 출력 경계의 다른 우회: 실제 bridge publish가 stdout/stderr에 합성 본문·인용 marker를 print한 뒤 원래 작업을 계속하는 경우, tick은 exit 0·정상 숫자 요약을 반환하지만 두 marker가 프로세스 stdout/stderr에 남는다. CLI에 TextIO 인자를 주는 것은 구성요소의 sys.stdout/sys.stderr 출력까지 캡처하는 조치가 아니다. plist의 StandardOutPath/StandardErrorPath는 그 원시 스트림을 launchd 로그로 연결한다.
- 범위: 현재 실제 운영 bridge가 본문을 출력하거나 실제 운영 키를 예외로 던졌다고 주장하지 않는다. 발주의 예외 메시지·예상 밖 출력 비노출 계약을 합성 스텁 경계에서 검증한 결과다. 운영 데이터·운영 키는 미접촉이다. 산술 summary의 필드 whitelist 자체는 통과했다.
- 수정 방향: 임의 문자열을 코드 형태만으로 안전하다고 믿지 말고 알려진 값 없는 코드/타입으로 제한한다. in-process 구성요소의 원시 출력도 동일한 보호 경계에서 처리해야 한다. 구현 코드는 수정하지 않았다.

### R8-M2 — 날짜 로그의 심볼릭 링크를 따라 로그 디렉터리 밖 파일을 수정한다

- 심각도: **major**.
- 위치: `feature-pack/rag-consumer/src/airag_consumer/tick.py:122-126`; main의 로그 디렉터리/파일 생성 `:193-198`.
- 재현: 임시 log-dir의 현재 날짜 tick-YYYYMMDD.log를 별도 임시 텍스트 파일로 향하는 symlink로 만든다. 그 파일은 상한보다 작다. 실제 append_log를 호출한다.
- 관찰: 날짜 로그 symlink가 가리키는 **log-dir 밖 파일에 JSON 줄이 append**됐다. stat/open 모두 symlink를 따른다. 회전 전 크기 검사나 14일 prune glob은 이 쓰기를 제한하지 않는다.
- 의미: 로거가 선택한 디렉터리의 로그 파일만 쓰는 경계가 없다. 기존 runtime의 symlink 거부와 달리 새 로거가 외부 파일에 쓰는 우회 경로를 만든다. 실제 DB나 운영 파일 손상을 재현한 것은 아니며, 임시 텍스트 파일만 사용했다.
- 관련 사실: tick.lock도 일반 open으로 symlink/파일 타입을 검증하지 않는다. 이번 확정 재현은 날짜 로그의 외부 파일 수정이며, FIFO 대기나 lock symlink 공격까지 실행했다고 주장하지 않는다.
- 수정 방향: 로그와 잠금 파일의 안전한 일반 파일 열기·경로 정책을 결정하고 적용해야 한다. 날짜 이름/확장자만으로 쓰기 대상의 실제 파일을 보장할 수 없다.

## 통과한 동작·설계 경계

**키 로딩:** 기존 env 우선과 missing 항목만 op read하는 테스트가 통과했다. 64hex 검사·bytes 기준 중복 거부는 대소문자로 같은 키를 쓰는 경우도 잡는다. 부분 fetch 실패 exit 30 뒤 제공된 env dict와 os.environ이 모두 그대로였다. fetched는 전체 성공·세 키 distinct 검사 후 한 번 update된다. token/key는 자식 argv에 없고 reference만 있다. 가짜 op의 stderr 값도 출력되지 않았다. 실제 op 호출은 하지 않았다.

**겹침/해제:** 같은 log-dir의 tick.lock을 보유하면 exit 10이고 op를 호출하지 않는다. 비차단 flock은 정확하다. 키 로딩 실패와 실제 runtime 오류 뒤 다른 fd의 nonblocking flock 획득도 성공했다. Python 파일 context가 fd를 닫으며 subprocess는 lock fd를 전달하지 않는다. 락의 보호 범위는 키 로딩과 CLI 실행이고, 마지막 출력·append_log는 락 밖이다. 서로 다른 log-dir을 지정한 호출의 전역 직렬화는 이 wrapper lock의 범위가 아니다.

**권한:** 명시적으로 umask 022를 설정한 임시 probe에서 log-dir=0755, tick.lock=0644, 날짜 log=0644였다. private mode를 고정하지 않고 umask를 따른다. 실제 운영 부모 디렉터리의 권한은 금지 범위여서 확인하지 않았다. 그 부모가 private인지와 별개로 wrapper가 0700/0600을 강제한다고 표현할 수 없다.

**실제 run_once 요약:** collected의 accepted_count/gap_count/committed_native_offset/pending_bytes, published의 attempted/succeeded, memory의 attempts/candidate_count/materialized_count/awaiting_confirmation_count/unverified_count/conflict_count/rejected_count/batch_message_count/provider_called, archives 길이, backup의 due/created와 필드가 맞는다. int는 정확한 type 검사라 bool·문자열을 수치로 받아들이지 않는다. 본문/인용/경로 marker를 숫자 필드에 넣은 추가 probe도 출력 summary에서 제거했다. pass_elapsed_s는 CLI run-once 호출 범위의 경과시간이며 키 조회나 로그 쓰기 시간, 모델 단독 시간으로 해석하면 안 된다. provider_requests는 직렬 run_once의 출력 필드가 아니므로 새로 주장하지 않았다.

**보존/경로:** 14일보다 오래된 날짜의 tick-????????.log* 파일과 .1은 지워졌고, 다른 이름·비숫자 날짜의 파일은 보존됐다. unlink는 그 디렉터리의 glob 범위에 한정된다. append의 실제 대상 보호는 R8-M2로 실패한다. 날짜는 UTC다. template의 launchd.out.log/launchd.err.log는 이 cap/prune 대상이 아니므로 그 파일들의 자동 회전·보존까지 구현됐다고 판정하지 않았다.
