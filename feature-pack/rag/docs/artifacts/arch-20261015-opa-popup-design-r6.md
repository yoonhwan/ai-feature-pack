# 0. 요약 (먼저 읽기)

1. **관측:** 프로브 P0(`op --version`, 토큰을 자식에 주지 않음, launchd 작업)가 **이번 1회에서 7초 안에 끝나지 않았다.** 같은 launchd 작업의 python 자식 P4(네트워크 연결 확인)는 707 ms 에 끝났다. 이 1회 관측은 **키 읽기·계정 조회 «이전 단계»에서도 7초를 넘길 수 있다**는 것을 보일 뿐, **과거 키 읽기 타임아웃(231건)이 같은 원인이라는 증거는 아니다.**
2. **팝업에 대해:** 프로브가 끝난 뒤 셸에서 같은 시간대 TCC 로그를 읽어 보니 **AppData 요청은 관측되지 않았다**(DeveloperTool 조회 전용 요청 + 프롬프트 불허 기록만). 이는 «이번 사후 조회에서 안 보였다»이지 «팝업이 없었다»의 전면 증명이 아니며, 프로브 안의 원래 `unknown_log_unavailable` 의 하위 원인은 **미확정**이다(§3).
3. **관측 과제:** `op` 프로세스 2개는 둘 다 `op daemon` 이며 pid 파일 위치가 둘로 갈려 있다(§2). 이것이 정지와 관련 있는지는 **가설**이다.
4. **권고 1안 = E1 «오빠 터미널 조건별 관측표»**(§6): 오빠 터미널에서 `op --version`만 3조건 × 2회. **원인 확정표가 아니라 조건별 관측 + 연관 후보 표**이며, 결과를 원인으로 단정하지 않는다. 기존 프로브(`probe.py`·`probe.sh`) 0줄 변경, **신규 3파일**(`compare.py`·`compare.sh`·`tests/test_compare_opa.py`). 6회 실행기의 **전체 마감·부분 완료·종료 미확인 규칙**을 §6.3 에 둔다.
5. **오빠께 드릴 질문은 1개**(§8): 대조 측정 `! bash /tmp/h<N>` 1회 실행 승인. 고지 범위를 «할 수 없다고 말할 수 있는 것»으로만 좁혔다. 실제 질문은 구현·DA 뒤 Master 가 올리고, 이 문서나 DA 판정이 실제 `op` 실행 승인을 대체하지 않는다.
6. **r5 → r6 변경 7건 (설계 DA r5 지적 전부):**
   - **M1** 부모는 P0 앞에서 토큰 파일 읽기를 **시도**했다(결과로는 성공 여부·토큰 존재 불명). «토큰 파일은 한 번도 읽히지 않았다» 문장 폐기 → «자식에 토큰 미전달·인증 계정 명령 미실행»으로 구분(§1). E1 이 토큰 파일을 열지 않는다는 약속은 신규 시험으로 확인(§6.4).
   - **M2** TCC unknown 의 하위 원인을 «호출 실패»로 확정한 표현 폐기 — 네 갈래 모두 후보(§3).
   - **M3** E1 결과 해석을 «연관 후보 + 추가 실험 필요»로 제한, 소켓 소유자 서술을 가설로 내림, 결론 열거형 이름도 인과 중립으로 개명(§4·§6.3).
   - **M4** 오빠 고지의 «무토큰·무네트워크» 단정을 폐기하고 실제로 말할 수 있는 범위로 재작성, A 조건에서 **이름 기반으로 자격 증명 의심 변수도 제거**, «원시 값 공유» → «승인된 숫자·열거형 요약만»(§6.1·§8).
   - **M5** 6회 실행기에 **전체 하드 상한 75초 · 정리 예약 5초 · 시작 조건 · skipped 상태 · 불완전 우선 검사**를 추가, 합성 시험에 부분 완료 경로 추가(§6.3·§6.4).
   - **m1** I-1 = «소스 완료, 설치본 구버전»으로 정정(§10).
   - **m2** «정리 완전» 문구를 «실행 중 job/자식 부재와 증거 파일 보존»으로 분리, 신규 파일 **3개**로 정정(§1·§6.4).

# 3. TCC `unknown_log_unavailable` — 하위 원인은 미확정 (M2)

프로브 코드(probe.py:394-456)에서 같은 `unknown_log_unavailable` 한 값에 합쳐지는 경우:
1. 관측 예산 부족으로 `log show` 를 **시작하지 않음**(435-436, 441-442).
2. `log show` 실행 오류·시간 초과·비정상 rc(452-455).
3. 성공한 조회에서도 분류 가능한 타임스탬프 줄이 0개(412-413).
4. 자기 PID 귀속만 있고 service 줄이 없는 부분 관측(426-427).

- **어느 갈래였는지는 모른다.** 나중에 셸에서 같은 시간대를 읽어 로그가 나온 사실은 당시 프로브가 받은 stdout 을 복원하지 않는다(가시성·수집 시점·버퍼링·관측창 차이를 배제할 수 없다). 예산 부족(시작 안 함)은 «호출 실패»와도 다르다.
- **쓸 수 있는 문장:** «원래 unknown 의 하위 원인은 미확정이다. 사후 셸 조회에서는 같은 창에 AppData 요청이 관측되지 않았다. 이는 과거 팝업이 없었다는 전면 증명이 아니다.»
- 사후 조회 방식은 **프로브 수정 없이** 계속 쓴다(창 [시작−0.5초, 끝+2초], 7초 한도, 로그 원문 비저장). 관측 사유 필드(`observe_tcc` 사유 열거형) 추가는 **이번 라운드에서 구현하지 않는다**(§7 보강안으로만 남김).

# 6. 권고 1안 — E1 «오빠 터미널 조건별 관측표» 설계

## 6.1 측정 조건 3가지 × 2회 (순서 A,B,C,A,B,C)
| 조건 | 환경 | 읽는 법 |
|---|---|---|
| **A** 터미널 환경 | 현재 터미널 환경에서 **① `OP_` 로 시작하는 이름 전부 ② 이름에 `TOKEN`·`KEY`·`SECRET`·`PASSWORD`·`CREDENTIAL`·`AUTH` 가 들어간 이름 전부**(대소문자 무관, **이름만 보고 판단 · 값은 읽지 않음**)를 제거 | 기준선. 이름 패턴에 걸리지 않는 자격 관련 변수는 남을 수 있다 |
| **B** 터미널에서 만든 최소 환경 | `PATH·HOME·USER·LOGNAME·LANG·LC_ALL·LC_CTYPE·TMPDIR` 허용 목록만(probe.py:102 와 **이름 목록이 같다**). **값은 오빠 터미널의 값**이라 과거 launchd P0 의 값과 같다는 증거는 없다 | A 와 B 의 차이 = «환경 축 연관 후보»(시간·직전 실행 상태가 섞인 연관 관찰) |
| **C** B + 격리 설정 | B + `HOME`=새 임시 폴더(0700), `OP_CONFIG_DIR`=`<임시>/.config/op`(`TMPDIR` 는 유지) | B 와 C 의 차이 = «격리 설정 축 연관 후보». HOME·설정·데몬 접촉이 **동시에** 바뀌므로 특정 요인(예: TMPDIR/pid 파일 분열)을 가리키지 않는다 |

- 명령은 모두 절대 경로 `op --version` 하나(PATH 로 찾은 `op`, 프로브와 같은 해석). 이 스크립트는 **서비스 계정 토큰을 주입하지 않고, 토큰 파일을 읽지 않으며, 계정 조회·로그인 등 명시적 계정·네트워크 진단 명령을 실행하지 않는다.** 다만 **`op` CLI 가 내부적으로 네트워크나 공유 상태(데몬·소켓·`~/.config/op`)에 접촉하는지는 미확인**이다(§2.1).
- 각 실행: **시도 7.0초 · 재시도 0**(2회차는 재시도가 아니라 별도 라운드). 7초 밖은 관측하지 않는다.
- 종료 계약: r4 §4.6 «자식 프로세스 회수 계약» **그대로** — 시간 초과 시 직접 자식만 종료 → 유한 대기 2.0초 → 파이프 회수 ≤1.0초 → 확인 전 `reaped` 미기록. 공유 데몬·미식별 후손·광역 종료·프로세스 그룹 종료 금지. SIGINT/TERM/HUP 는 정리 후 명시 종료(130/143/129).
- 전후 읽기 전용 관측(값 비기록): `op` 프로세스 수(전·후, `pgrep -x op` 와 같은 방식) · `~/.config/op/op-daemon.sock` mtime 변화 여부(불리언) · A 에서 이름 패턴으로 제거한 변수 **개수**(이름은 기록하지 않음). **새 데몬이 생겼을 가능성**은 «프로세스 수 증가»로만 표시한다(단정 아님).
- **임시 폴더(C 용):** `~/.local/share/airag-probe/compare-<id>/`(0700). **전후 `op` 프로세스 수가 같을 때만** 스크립트가 지운다. **수가 늘었으면 지우지 않고** `leftover_check_required=true` 를 표시한다(데몬 정리·판단은 별도 HIL, 이 스크립트는 기존·새 `op` 프로세스를 종료하지 않는다).

## 6.2 기록 필드 (값 없음 · 승인된 숫자·열거형 요약만)
실행마다: `variant(A/B/C) · round(1..2) · status(success/timeout/spawn_error/bad_output/skipped_budget/skipped_after_unconfirmed/cancelled) · elapsed_ms(monotonic) · rc · reaped · child_exit_unconfirmed`. `success` = rc 0 이고 stdout 첫 줄이 버전 정규식 `^\d+\.\d+\.\d+` 에 맞음(내용 비기록, 맞음/아님 불리언만). 전체: `op_count_before/after · sock_mtime_changed · removed_name_count_A · leftover_check_required · complete · exit_class · conclusion`. **stdout/stderr·환경 값·토큰 내용은 어떤 파일·화면에도 쓰지 않는다.**

## 6.3 전체 마감·미완료 규칙과 결론 열거형 (M5)

**시간 상한(한 표):**
| 항목 | 값 |
|---|---|
| 전체 하드 상한(스크립트 시작 → 종료) | **75.0초** |
| 라운드 1회 최악 | 시도 7.0 + 종료 대기 2.0 + 파이프 회수 1.0 = **10.0초** |
| 시작 전 관측(프로세스 수·소켓 stat, 호출당 ≤1.0초) | ≤3.0초 |
| 정리 예약(마지막 관측·결과 기록·임시 폴더 처리) | **5.0초 예약**(어떤 라운드도 이 몫을 쓰지 못한다) |

| 1 | 취소 신호를 받음 | `cancelled_incomplete` | 해석하지 않음 |
