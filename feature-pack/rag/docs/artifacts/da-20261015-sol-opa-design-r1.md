## m1 — 일부 사실의 강도가 증거보다 세다 (minor)

근거: 설계:20,25,31–33,42 · 사실:63–72 · 진행:172.

앱 디렉터리 mtime은 갱신 정황이며 정확한 업데이트 이력을 증명하지 않는다. 소켓 mtime 한 번은 그 시점의 생성/변경 정황이며 «지금도 누군가 사용 중»의 증거가 아니다. Python mtime만으로 서명/정책 변화를 완전히 배제할 수도 없다. F5는 요청 주체 Python까지의 관측이고 op의 대상 컨테이너/책임 관계는 미확인이다. §1.1의 첫 문장은 서비스 계정 모드의 컨테이너 접근이 실증된 것으로 읽히지 않도록 «토큰 방식만으로 팝업 방지가 입증되지 않았다»로 낮춘다.

반면 «타임아웃과 팝업이 별개 사건일 수 있다»는 추론은 타당하다. 11:44 AUTHREQ만으로 이전 타임아웃을 설명할 수 없으며, 로그 부재가 이전 팝업 부재의 증거도 아니다. 225건의 시점별 원시 집계는 입력 facts에 직접 제시되지 않아 이 DA에서 독립 재현했다고 주장하지 않는다.

## m2 — 프로브 결과 스키마와 판정식이 일치하지 않는다 (minor)

근거: 설계:60,73,97,107–114.

출력 필드 목록에는 `SERVICE_ACCOUNT` bool·TCC 수집 성공 여부·단계 귀속이 없지만 채택 조건은 이를 사용한다. 단순 stdout 부분 문자열 검색은 계정 타입의 구조적 확인과 같지 않으며 err_class 분류 규칙도 없다. raw stderr를 분류명으로 복사하면 값 비출력 약속이 깨진다.

필수 수정: 결과 버전·단계별 실행/관측 상태·구조적으로 확인한 계정 타입·TCC 관측 가능 여부를 정의하고, 오류 클래스는 유한 허용목록으로 만든다. 출력 원문이나 예외 메시지는 결과에 넣지 않는다. result는 최종 완료 표시와 원자적 기록을 갖추어 부분 결과를 성공으로 읽지 않게 한다.

## 재심 입력과 범위

1. B1을 반영한 수정 설계와 M1/M2/M6의 원인 미확정·운영 재개 보류 분기.
2. M3의 값 경계·실패 시 정리가 구현된 실제 프로브 및 합성 입력 검증 결과. 운영 op 실행은 master의 HIL 이후에만.
3. ⑤의 상태 호환성·반복/동시성 검증 계획. ⑦은 별도 승인 전까지 실험 후보로 한정.

현재 판정은 설계 반송이다. 운영 consumer가 꺼져 있는 상태를 변경하거나 기존 사용자 정지 결정을 해제할 근거를 제공하지 않는다. 산출물 이외 파일 수정·커밋·push는 하지 않았다.
