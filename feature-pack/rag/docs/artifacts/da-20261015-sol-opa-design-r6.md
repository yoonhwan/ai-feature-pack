## 2. 독립 확인

실제 op 없이 순수 Python으로 설계의 집계표를 별도 모델링했다.

- fast/slow/mixed 27조합을 열거했다. r6:141–147 순서의 도달 수는 **19/1/1/2/1/1/2**로 문서와 일치한다.
- 취소 → 종료 미확인 → 미실행 → 실행 오류의 우선순위를 각 27조합에 적용한 **108개 단언이 통과**했다. 불완전 결과가 간헐/콜드 후보로 내려가지 않는 구조다.
- 최악 시간 합계는 **시작 전 3 + 6×10 + 정리 5 = 68초**다. 별도 시작 지연 모형에서 준비에 11초를 사용하면 마지막 회차를 시작하지 않고 5회 후 정리를 포함해 66초에 끝난다. 시도 시간을 7초보다 줄이지 않아도 75초 경계와 양립한다.

이는 **설계 모델의 정합성 확인**이다. 아직 구현되지 않은 compare.py/compare.sh의 런타임 마감·신호 처리·실제 자식 회수를 시험한 증거가 아니다. 구현 DA에서는 r6:155–164의 합성 시험과 실제 wrapper 경계를 확인하면 된다. 기존 P의 닫힌 회수 코드를 재심하거나 실제 op를 실행할 필요는 없다.

## m1 — 프로세스 수 일치는 새 데몬 부재의 증명이 아니다 (minor, 비차단)

근거: r6:111–112,129,162,178.

현재 보존 기준은 전후 op 개수가 같으면 C 폴더 삭제, 증가하면 보존이다. 다른 op가 동시에 종료하고 새 데몬이 생기면 개수가 같아도 구성원은 달라질 수 있다. 감소·관측 실패 때의 `leftover_check_required` 값과, 종료 미확인/취소 시 폴더 보존 우선순위도 명시가 덜 되어 있다.

이번 검토에서 실제 `--version`이 데몬을 생성하거나 이 교체가 발생하는 것을 관측하지 않았다. **외부 프로세스 변동과 데몬 생성이 겹쳐야 하는 조건부 문제**이며, 이 실사용 범위의 차단 사유로 올리지 않는다. 구현에서는 개수 일치를 부재 증명으로 표현하지 말고, 관측 실패·종료 미확인에는 보존/확인 필요를 우선시키는 보수적 처리를 권한다. 정밀 소유 확인을 하지 않는 경우 폴더를 보존하는 선택도 가능하다. 기존·새 공유 데몬을 정리하는 별도 기능은 요구하지 않는다.

## m2 — 합성 시험의 두 문구에 예외 대상을 명확히 한다 (minor, 비차단)

근거: r6:106,110,159,163,178.

첫째, «B/C에서 허용 목록 외 변수 0» 시험은 C에 설계상 필요한 `OP_CONFIG_DIR` 예외를 포함해야 한다. 둘째, «기존 op·새 op 프로세스를 종료하는 코드 경로 0»은 직접 띄운 측정 자식까지 포함하면 timeout 때 직접 자식만 종료한다는 계약과 충돌한다. 본문과 사람 고지의 취지는 **공유 데몬·비소유 op 종료 금지**로 읽힌다.

구현 인수 기준은 «B=허용 목록, C=B에서 HOME 교체 + OP_CONFIG_DIR 추가» 및 «공유 데몬/비소유 op 종료 금지, 이 실행이 소유한 측정 자식의 유한 회수는 허용»으로 구체화하면 된다. 설계의 주 계약을 바꾸는 문제는 아니므로 구현 착수를 막지 않는다.
