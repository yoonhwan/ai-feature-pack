## 새 경계 대조

1. **정상 결정·7셀:** 두 전체 실행 모두 정상 투어 7/7셀 완료, 기억 3·대기 0이다. 쓰기 셀의 Enter 게이트와 범위 밖 번호 재질문도 통과했다. 대기 없는 fresh 경로와 두 동시 결정의 2개 done 로그도 기존 checks가 통과했다.
2. **재검사 시각·형식:** 정확히 6시간은 통과하고 6시간+1µs는 BACKUP_RECEIPT_STALE다. Z와 +09:00의 동등한 aware 시각도 통과했다. helper의 직접 assert_fresh에 naive/잘못된 영수증 시각을 주면 각각 TypeError/ValueError로 실패한다. 실제 backup completed_at은 기존 operations의 ISO/aware 검증을 거친 값이다. clock도 기존 runtime의 aware time 계약을 전제로 한다.
3. **재검사 실패의 부작용:** 실제 두 번째 assert_fresh에서 형식 오류를 주입했을 때 결정 로그를 만들지 않았고 기억 변화가 0이며, 다른 fd의 nonblocking flock 획득이 성공했다. 두 번째 검사도 락 context의 예외 해제 경계를 따른다. 실제 verify의 completed_at은 사본에만 추가되며, 디스크 영수증 형식은 그대로다.
4. **finish/SELFTEST:** 기본 fail-fast는 첫 실패에서 SystemExit로 종료하고 finish까지 가지 않는 기존 계약이다. KEEP_GOING SELFTEST는 FAILED 1 of 1·exit 1이다. 직접 finish 혼합 결과(성공 1, 실패 2)는 FAILED 2 of 3·exit 1, 성공만 있으면 exit 0이다. finish 전 RuntimeError도 성공 요약 없이 exit 1이었다. 다음 minor는 finish 자체가 아니라 새 락 대기 시나리오의 자원 정리 경로다.
5. **이전 한계:** helper가 사용하는 completed_at은 plaintext manifest에서 검증 API가 반환하는 메타데이터이며 암호학적 시각 인증이 아니다. r6에 기록한 manifest까지 재작성하는 변조 범위·자동 pending reconciliation 부재·flock의 독립 timeout 부재는 이번 수정 대상이 아니고, 이번 PASS가 그 한계까지 해결됐다는 뜻은 아니다.

### R7-m1 — 락 대기 검증 중간 실패 시 잠금 보유 자식과 non-daemon waiter를 정리하지 않는다

- 심각도: **minor**.
- 위치: `.fable-team/bin/tour/verify_14_isolated.py:246` (잠금 보유 자식), `:268-277` (waiter 시작·중간 check·정상 해제). 특히 `:271-272`의 검사와 `:274-277`의 해제/join 사이에 try/finally가 없다.
- 재현: 지정 스크립트의 fixture 정의와 **실제 R6-M1 락 대기 블록**을 그대로 실행한다. actual gate 통과와 대기 상태를 확인하는 `decision is waiting, core untouched` check만 False로 주입해 기본 모드의 실제 check가 SystemExit를 내게 한다. 소스 파일은 수정하지 않았다. probe는 이 예외를 잡아 자원 상태를 관찰했다.
- 관찰: SystemExit 시점에 holder 자식은 실행 중, waiter는 살아 있는 non-daemon 스레드, 실제 flock도 여전히 보유 중이었다. 정상 해제 줄은 실행되지 않았다. Python 종료는 non-daemon 스레드를 기다리는데 그 스레드는 자식의 락을 기다리고, 자식은 부모가 보내지 못한 stdin 신호를 기다리는 경로가 된다.
- 의미: 기본 모드의 이 중간 check 실패나 같은 위치의 예외가 단순 실패 종료 대신 테스트 종료를 막을 수 있다. 정상 33 checks와 운영 helper에서는 발생한 것으로 주장하지 않는다. KEEP_GOING에서 단순 False는 계속 진행해 정상 해제 줄에 도달하므로 해당 경우와 구분한다.
- 한계/정리: probe가 자원 상태를 확인한 뒤 직접 정상 stdin 신호를 보내 holder exit 0과 waiter 종료를 확인했다. 실제 세션을 무한 대기로 남기거나 kill하지 않았다. 검증은 **실패 뒤 미정리 상태와 종료 의존 관계**를 확인한 것이며, 운영 프로세스 장애를 재현한 것은 아니다.
- 수정 방향: 새 락 대기 시나리오를 try/finally로 감싸 check·예외 경로에서도 자식에 해제 신호를 보내고 waiter를 join해야 한다. 수정 코드는 작성하지 않았다.
