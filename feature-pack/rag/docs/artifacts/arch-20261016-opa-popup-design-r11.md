# 0. 결론 (먼저 읽기)
1. **이번 조합(A1 timeout · B 빠름 · A2 빠름)은 r10 §4.6 표의 어느 행에도 가지 않는다 → 해석 보류.** 이중으로 보류다: ① 표의 적용 전제 «세 단계 모두 `P4=success`» 가 A1 에서 깨졌고(P4 도 7035ms timeout) ② 조합 자체가 «그 밖의 조합» 이다. A2 의 2449ms 는 success 로 읽고(표에 속도 구간이 없고 임계를 새로 만들지 않는다) 참고 수치로만 적는다.

4. **다음 판별 후보(전부 `op --version` 만·토큰 0):** 지금까지 «첫 launchd 작업 × 지정 여부» 4칸 중 한 칸(**첫 작업 + 지정 안 함**)이 한 번도 관측되지 않았다(§3). 그 칸을 채우는 가장 값싼 방법은 **같은 `chain --plan n4` 를 한 번 더**가 아니라 **기존 `probe.sh` 를 «지정 안 함 → Background» 순서로 직접 두 번** 호출하는 것(코드 변경 0, §4). `chain --plan n4` 재실행은 코드 변경 없이 가능하나 순서가 A-B-A 로 고정돼 있어 **순서 효과를 못 가른다.** 둘 다 오빠 실행(HIL)이 필요하고 이 설계는 실행을 승인하지 않는다.

# 4. 사전 판독 규칙 (결과가 오기 전에 고정)
## 4.1 D1(같은 chain 재실행)을 하게 될 경우
세 단계 모두 G4 통과·`P4=success` 일 때만 r10 §4.6 표를 읽는다. 아니면 «해석 보류»로 두고 단계별 `P4/P0` 상태만 보고한다. 이번 결과와 합쳐 A1 표본 2·B 표본 2·A2 표본 2 로 **횟수만 병기**하고 방향 단정은 하지 않는다.
## 4.2 D2(`probe.sh` 직접 2회, 순서 «지정 안 함 → Background»)를 하게 될 경우
전제: 각 호출이 종료코드 0, `result.json` 이 닫힌 스키마(`validate_result` 와 같은 기준), `profile.json` 유효·`process_type_set` 이 호출 인자와 `job.plist` 의 키 유무와 일치, P2/P1/P1b `skipped_not_applicable`, P0 가 success 또는 회수 확인된 timeout. **하나라도 아니면 판독하지 않는다.** 그 경우에만:
| 첫 호출(지정 안 함) | 둘째 호출(Background) | 읽는 법(관측 라벨·후보만) |
|---|---|---|
| P4 또는 P0 timeout | 무관(성공/timeout) | **첫 작업에서 지정하지 않아도 막힌 관측** — 첫 작업 효과(C1/C2) 쪽 연관. «ProcessType 지정 때문»이라는 설명은 이번 결과가 지지하지 않는다(판정은 아님). 운영 plist 변경 근거 없음 유지 |
| 둘 다 success | success | 이번 쌍에서 재현 안 됨 — 첫 작업이 «지정 안 함»일 때 빠르고 첫 Background 3/3 과 대비되는 **1건**. 표본 1건이라 «지정 연관» 단정 금지·«재현 안 됨은 해결이 아님» · 반복 필요 여부는 별도 판단 |
| 첫 success | 둘째 timeout | 해석 보류(조건 안 변동 또는 둘째 작업 효과 가능) · 같은 쌍 1회 더 필요 여부 별도 판단 |
| P4 가 success 가 아닌 단계가 있음 | | 해석 보류(P4 가 먼저) |
- 어느 경우에도 **원인 확정·운영 plist 변경·재개 승인을 내지 않는다.**

# 5. 운영 plist `ProcessType` 변경 후보 여부 (질문 3-a)
**근거 부족 — 후보를 만들지 않는다.** 이유(전부 관측): ① 같은 «Background» 안에서 성공(A2)과 실패(A1)가 갈렸다. ② 실패 3건 전부가 «첫 작업»이라 지정 여부와 겹쳐 있다(§3.1, 빈 칸 존재). ③ A1 은 `op` 비의존 단계(P4)까지 막혔다 → `ProcessType` 외 후보(일시 상태·첫 작업 상태)가 열려 있다. ④ 표본이 3개(조건별 1·2)다. ⑤ consumer 가 꺼져 있어 plist 만 바꿔도 즉시 효과를 관찰할 수 없다. **후보가 생기는 조건(참고):** 같은 판별에서 «지정하지 않은 작업은 반복해서 빠르고 Background 작업은 반복해서 막히는» 모양이 첫 작업 위치를 맞춘 상태로 재현될 때 — 그때에도 별도 설계·DA·오빠 판정을 거친다. 운영 plist·runtime.json·운영 DB 변경은 0.

# 6. consumer 재개 조건 R-3 에 이번 B·A2 가 기여하는 방식 (질문 3-b)
- R-3 원문(r10 §6): «launchd 컨텍스트 `op` 호출이 기한 안에 끝나는 관측 **또는** 오빠의 «막히는 상태로 재개해 위험 관찰» 명시 판정 — P0 한 번 success 는 실제 키 읽기 성공·팝업 방지와 같지 않다».
- **이번 기여:** `op --version` 이 launchd 작업에서 기한(7초) 안에 끝난 관측이 **2건**(B 581ms · A2 2449ms) 생겼고, 같은 실행에서 **기한을 넘긴 관측 1건**(A1, P4 포함)이 함께 있다. 따라서 R-3 의 앞쪽 가지(기한 안 완료 관측)를 **충족으로 읽지 않는다 — «성공 2·초과 1, 같은 실행 안에서 갈림»으로 병기하고 미충족 유지.**
- 성공 2건의 한계: ① `op --version` 은 서비스 계정 토큰을 읽지 않는다(P0 success≠키 읽기 성공≠팝업 방지). ② consumer 의 실제 호출은 틱마다(5분 간격) 키 읽기 명령이며 이번 구조와 다르다. ③ 성공 2건은 모두 «첫 작업이 아닌» 칸이라(§3.1) 틱의 조건과 같은지 미확인.
- R-1·R-2·R-4·R-5 는 이번 결과로 바뀌는 것이 없다. **이 설계는 enable/bootstrap/bootout/disable 어느 것도 집행·승인하지 않는다.** 오빠 판정 «막히는 상태로 재개해 위험 관찰»은 이 결과와 독립으로 가능하다는 r10 구조를 그대로 둔다(그때도 팝업 고지·범위 한정 고지·중단 후보 기존 HIL 경로).
