# AI RAG 데이터 생애주기 기획 초안

작성일: 2026-09-27. 상태: 검토용 제안. 이 문서는 수집·메모리 운영을 구현하거나 켜지 않는다. 현재 세션 로그를 수집하지 않았고, 원본·DB·설정·에이전트 지침을 변경하지 않았다. T07 투어 실행과 별개의 기획 초안이다.

## 1. 두 축의 이름과 책임

문서·이미지·백과사전도 엄밀히는 비정형 또는 반정형이다. 이번 설계에서는 형식보다 **변경되는 대상의 성격**을 기준으로 나눈다.

- **자료 축**: 안정된 대상 하나의 현재 내용이 교체·삭제·복원된다. 문서, 이미지, wiki 문서, DB 행·스냅숏이 해당한다.
- **이벤트 축**: 시간에 따라 사건이 늘고, 일부 과거 사건에 수정·삭제가 붙는다. 채팅, 메시지, CS, 에이전트 대화·도구 결과가 해당한다.

현재 계약: 소비자가 명시적으로 add/update/delete/restore/reindex를 요청하고 core가 저장·처리·검색한다. 워처, CDC, 스케줄, 이벤트 큐, 메모리 추출·순위·아카이브 운영은 아래의 **새 소비자 계층 제안**이다. 메모리 후보는 검색 가능한 근거 레코드이며, 에이전트의 상위 지침이나 실행 권한이 되지 않는다.

## 2. 자료 축: 외부에서 무엇이 트리거되는가

```text
자료 축 [기존 core + 외부 소비자 기획]
├─ 외부 변화 수신 [소비자 책임]
│  ├─ 문서·이미지: 업로드 완료 / 저장 확정 / 관리자의 삭제·복원
│  ├─ 백과·wiki: 문서 ID별 게시 revision / 철회 / 명시적 복원
│  ├─ 대형 DB: commit된 CDC insert/update/delete + durable offset
│  └─ 전체 대조: 일관된 snapshot·완전성 확인 후 차이 판정
├─ 요청 전 검사 [새 소비자 계층]
│  ├─ 안정된 대상 ID 확인: 경로 변경은 다른 자료로 취급하지 않음
│  ├─ 권한·버전·내용 fingerprint·삭제 근거 검증
│  ├─ 이벤트 ID + 요청 payload + CAS 토큰을 발송 전 보존
│  └─ 불완전 목록·접근 불가·404 한 번 → 관측만 기록, 삭제 금지
├─ 명시적 core 요청 [기존 계약]
│  ├─ add: 아직 없는 대상의 확정 콘텐츠
│  ├─ update: 동일 대상의 새 콘텐츠 또는 메타데이터
│  ├─ delete: 권위 있는 삭제 확인 → 검색 제외, 이력 보존
│  ├─ restore: 삭제된 대상에 대한 명시적 복원
│  └─ reindex: 같은 원본 + 변경된 처리 프로필 → 새 처리 세대
└─ 발행과 재시도 [기존 계약 + 소비자 checkpoint]
   ├─ 같은 이벤트 재전송 → 같은 request_id·payload로 결과 재생
   ├─ stale CAS / 같은 ID의 다른 payload → 충돌, 조용한 덮어쓰기 금지
   ├─ 처리 실패 → 이전 ready 유지, 실패와 원본 보존
   └─ 성공 → 새 색인 원자 발행 → 영수증 저장 → 이벤트 offset 확정
```

### 트리거 판정표

| 외부 조건 | 소비자 판정·core 요청 | 보호 조건 |
|---|---|---|
| 새 파일 업로드가 완료되고 크기·해시가 확정됨 | 안정된 파일 ID에 `add` | 쓰는 중인 파일·부분 업로드는 기다림 |
| 같은 문서 ID의 content version 증가 | 내용/메타 변화가 있으면 `update` | 외부 version 순서와 현재 CAS를 모두 확인 |
| 파일 이름·경로만 변경 | 동일 source_key 유지, 필요한 메타데이터 `update` | origin_uri는 신원이 아님 |
| 이미지 바이트 변경 | 새 원본 revision으로 `update` | OCR 결과만 달라진 경우와 구분 |
| OCR·청커·임베딩 프로필 변경 | 같은 원본에 `reindex` | 등록된 불변 profile, 모델 공간 격리 |
| wiki 새 게시 revision | 문서 ID별 `add` 또는 `update` | 초안 저장과 게시를 분리, 누락된 중간 revision 정책 명시 |
| DB commit된 행 insert/update/delete | PK와 DB incarnation 기반 source_key로 요청 | commit/LSN 등 원본 순서 보존, 트랜잭션 rollback은 미전달 |
| 큰 테이블 초기 snapshot 완료 | 행 또는 안정된 partition 단위 배치 `add` | CDC와 snapshot watermark를 연결해 누락·중복 방지 |
| 큰 DB의 한 transaction에 여러 행 변경 | 동일 commit 묶음으로 소비자 전달·추적 | 현재 core가 여러 source의 원자 발행을 보장한다고 주장하지 않음 |
| 관리자 삭제 이벤트 또는 완전 대조에서 삭제가 확정됨 | `delete` | 삭제 권한·대상·버전 검증. 대조 기반 삭제는 명시 승인된 정책 필요 |
| tombstone 자료가 다시 목록에 등장 | 자동 add/update 금지, 복원 판단 대기 | 명시적 `restore` 후 필요한 update |
| timeout / 권한 거부 / 부분 listing / 일시적 404 | 관측·재확인 | 사라짐은 곧 삭제가 아님 |
| 권한 범위 축소·외부 공유 철회 | 소비자에서 접근을 즉시 차단하고 권한 투영 갱신 | 내용 재색인 완료까지 민감정보를 계속 노출하지 않음 |

외부 event_id와 core request_id는 목적지가 포함된 안정적인 매핑으로 만들며, 재시도 시 바꾸지 않는다. 하나의 외부 사건이 여러 core 요청으로 나뉘면 하위 작업 ID를 결정적으로 만들고 각각의 영수증을 저장한다. 원본 source_version은 외부 순서 검사용이고, expected_revision은 core 현재 상태 전체를 보호하는 불투명 CAS 토큰이다. 둘은 서로 대체하지 않는다.

DB 자료 단위는 쿼리 요구로 선택한다. 행 단위는 부분 변경에 유리하고, partition 단위는 건수를 줄이지만 작은 변경도 partition 전체를 다시 처리한다. 전체 DB를 거대 문서 하나로 넣는 방식은 기본안에서 제외한다. 초대형 규모의 ANN이나 분산 트랜잭션은 현재 기능이 아니며 별도 검증이 필요하다.

## 3. 이벤트 축: 늘어나는 대화와 기억의 순환

```text
이벤트 축 [새 소비자 계층 기획]
├─ 입력 분류
│  ├─ 대화: 사용자·상담사·에이전트·시스템 이벤트
│  ├─ 도구: 호출·결과·실패·실행 증거
│  ├─ 업무: CS 티켓 상태·담당자·해결·재오픈
│  └─ 제어: 메시지 수정·삭제·권한 변경·동의 철회
├─ 원본 로그 [보존 기준점]
│  ├─ 안정된 event/message/session/thread ID + sequence
│  ├─ event_time·ingested_at 구분, 수정은 새 event revision
│  ├─ 일정 사건 수/바이트/시간마다 암호화 파일 세그먼트 봉인
│  └─ segment manifest·hash·checkpoint로 중복/누락/복구 확인
├─ 읽기 창 [N_active + 토큰 상한]
│  ├─ 최근 tail 창: 현재 진행 맥락을 최신 순으로 유지
│  ├─ 중요한 기억: 별도 예산으로 상단에 제한적으로 배치
│  ├─ 부족한 과거: 권한 필터를 적용해 아카이브에서 근거 검색
│  └─ 창 수나 토큰 초과 → 보존 확인된 오래된 창 참조만 퇴거
├─ 기억 후보 추출 [비동기, 실패해도 원본 유지]
│  ├─ 사실/선호: 확인된 내용, 유효 범위·기간
│  ├─ 진행/결정: 현재 목표·완료점·미해결 질문
│  ├─ troubleshoot: 증상 → 원인 → 조치 → 검증 증거
│  └─ 지침 후보: 사용자가 검토할 명시적 요구사항, 자동 권한 승격 금지
├─ 검증·순위·유효성
│  ├─ raw anchor·revision·발언 주체·추출 모델·신뢰 근거 기록
│  ├─ 사용자가 pin한 유효 기록 → 미해결 작업 → 관련 근거 순
│  ├─ 수정·삭제·반박 → 파생 기억 무효화 또는 새 version
│  └─ 중요도와 무관하게 권한 없는 근거는 제외
└─ 순환
   ├─ 원본 저장 → 후보 추출 → 검증 → 검색에 사용 가능
   ├─ 압축 요약·아카이브 확인 → checkpoint → 활성 참조 퇴거
   ├─ 다음 사건 수신 → 새 tail 창 → 필요한 기억 재선택
   └─ 영구 삭제는 별도 권한·보존 정책 없이는 실행하지 않음
```

### 세 가지 크기 단위는 별개다

| 단위 | 목적 | 제안 기본값·경계 |
|---|---|---|
| 로그 파일 세그먼트 | 원본의 내구성·보존·복구 | 200 events 또는 1 MiB 또는 30분 중 먼저 도달. 확정 시 봉인, 큰 단일 이벤트는 분리 객체+참조 |
| 엔진 청크 | 검색·출처·근거 확장 | 입력 구조와 불변 processing profile로 생성. 파일 개수나 대화 창 수와 같지 않음 |
| 활성 컨텍스트 창 | 다음 응답에 넣을 최근 맥락 | 창당 최대 40 events 또는 2,000 tokens, 기본 N_active=4·tail 합계 8,000 tokens |

모든 수치는 제안이며 사용자 승인된 설정이 아니다. raw 세그먼트는 의미적으로 append-only여도 개별 레코드를 평문 파일로 남기지 않는다. 신규 암호화 segment 포맷·키 관리·쓰기 내구성 검증이 필요하다. 기존 core는 수입된 원본·표준 표현·벡터를 SQLCipher 경계 안에 보관하며 평문 사이드카로 대체하지 않는다. 파일 세그먼트는 소비자 소유 원본, core는 그 확정 스냅숏을 명시 수입한다.

기본 수입 단위는 **열린 tail → 명시적 seal checkpoint → 불변 세그먼트 add**다. 매 메시지마다 전체 누적 로그를 update하지 않는다. 그 방식은 원본 revision이 폭증하고 누적 재처리량이 O(n²)로 커질 수 있다. 즉시 검색이 필요한 열린 tail은 소비자가 제한된 실시간 view로 제공하고, core에는 봉인된 세그먼트를 수입하는 방식을 먼저 검증한다. 과거 edit/delete는 correction event를 새 로그에 남기고 영향받은 검색 projection만 update/delete한다. 불변 raw archive와 현재 검색 projection은 별도 역할이며, raw에 남아 있다는 이유로 삭제된 메시지가 검색에 부활하면 안 된다.

여기서 core에 add하는 것은 봉인된 원본을 그대로 무차별 검색시키는 것이 아니라 **권한·마스킹·수정/삭제 overlay를 반영한 세그먼트별 검색 projection**이다. 원본 segment ID는 고정하고, projection의 source_key는 예를 들어 `session/<session_id>/segment/<segment_id>/view`로 둔다. 나중에 과거 메시지가 편집되면 원본 segment 파일을 덮어쓰지 않고 correction event를 별도 보존하며, 같은 projection source_key에 새 revision을 발행한다. 불변 원본 아카이브는 일반 검색 경로에 자동 등록하지 않는다. 이 source_key와 overlay 형식은 구현 전 확정할 제안이다.

기본 읽기 총예산 제안은 tail 8,000 + memory 2,000 + archive evidence 2,000 = 최대 12,000 tokens다. 시스템 지침·현재 사용자 입력·도구 결과·출력 예약분은 이와 별도로 먼저 확보한다. 가용 입력 예산이 작으면 총예산부터 줄이고 잘림 사유를 표시한다. 창 중간의 tool call/result 쌍은 무심코 자르지 않고 원본 anchor가 있는 묶음이나 요약으로 대체한다.

컨텍스트 예산은 DB의 전체 메타데이터나 임베딩용 텍스트가 아니라 **실제로 응답 에이전트에 주입하는 evidence 표현**(원문 또는 요약 + anchor 참조 + wrapper)을 대상으로 센다. 임베딩 토크나이저가 응답 모델 토크나이저와 같다고 가정하지 않는다. engine chunk 하나가 창 예산보다 크면 범위가 명시된 발췌·요약과 원본 참조를 쓰고 omitted/truncated를 표시한다. 일부를 조용히 누락한 뒤 전체라고 표현하지 않는다.

| 운영안 | N_active | tail / memory / archive tokens | 적합한 경우 |
|---|---:|---|---|
| 경량 | 2 | 4,000 / 1,000 / 1,000 | 짧은 고객 문의·작은 모델 |
| 기본 제안 | 4 | 8,000 / 2,000 / 2,000 | 일반 작업 세션 |
| 긴 문제 해결 | 8 | 16,000 / 4,000 / 4,000 | 장기 장애·많은 도구 결과. 실측 뒤 선택 |

N은 상한이지 정확히 N개를 채우라는 뜻이 아니다. 토큰 상한이 먼저 오면 창이 더 적다. 원본 전체에 대한 보존 기간·저장량 상한은 활성 창의 N과 독립적으로 결정한다.

### 이벤트 envelope 제안

공통 필드: schema_version, tenant/project, event_id, message_id, session_id, thread_id, producer_id, sequence, source_version, event_time, ingested_at, kind(create/edit/delete/close/reopen), actor_role, trust_origin, access_scope, pii_class, payload_ref, content_hash, supersedes_event_id. CS에는 ticket_id·status, 도구에는 call_id·result_of를 추가한다.

이 필드는 소비자 데이터 모델 제안으로, 현재 core API에 그대로 추가됐다는 뜻이 아니다. producer sequence는 그 producer 안에서만 순서가 확정된다. 늦게 온 사건은 원본 도착 순서를 뒤집어 쓰지 않고 별도 사건으로 수록하며, 시간순 view와 참조 관계를 다시 계산한다. 동일 event_id·동일 내용은 재생, 동일 ID·다른 내용은 충돌이다. 과거 메시지 수정은 새로운 revision으로 기록하고 해당 창·요약·기억을 재평가한다.

자격증명·raw DB key·access token은 로그 캡처 전에 제외하거나 마스킹한다. redaction metadata에는 마스킹한 필드·종류·정책 version을 남기되 비밀 원값이나 이를 쉽게 대조할 해시를 남기지 않는다. 여기서 ‘원본 로그’는 수집 정책을 통과한 사건의 보존 기준점이며 모든 비밀을 무조건 복제한다는 뜻이 아니다. 이미 비밀이 섞인 원천에 대한 정리는 이 초안으로 자동 실행하지 않는다.

### 중요 기억의 선정과 상단 배치

순서: 권한·유효성·원본 revision 검사 → 현재 작업 관련성 검사 → 승인된 pin → 미해결 조치·검증된 해결책 → 반복 사용된 사실·결정 → 최근 참고 정보. 점수식은 아직 확정하지 않고, 중요도·관련성·최근성·재사용·증거 강도를 기록해 비교 가능하게 한다. LLM의 자기 확신 수치만으로 높은 순위를 주지 않는다.

memory 레코드에는 ID, kind, claim, scope, source anchors, source revision/hash, evidence level, valid_from/to, status(candidate/validated/superseded/invalidated), reviewer, extraction profile, supersedes, ranking reasons를 둔다. 추출 실패는 재시도 상태로 남고 원본·아카이브는 보존한다. 모순되는 주장은 하나로 몰래 합치지 않고 충돌 후보로 노출한다.

pin도 memory 예산에 포함한다. pin된 레코드가 예산을 넘으면 중요 제어를 몰래 탈락시키지 않고 초과를 알린다. 우선 원본 anchor를 가진 짧은 표현으로 줄이고, 그래도 넘으면 사용자가 pin·범위를 조정하도록 요청한다. 이 레코드에 포함된 명령문은 실행 지침이 아닌 인용 데이터다. 실제 상위 지침은 별도 권위 경로로 전달되며, 메모리 추출로 AGENTS/SOUL/config를 바꾸거나 다른 에이전트에 지침을 자동 복제하지 않는다.

## 4. 아카이브 전환과 실패 처리

```text
사건 수신
  → durable raw 기록 + checksum 확인
  → 활성 창 갱신 + core 수입 큐 등록
  → 비동기 후보 추출·검증 [실패 시 raw와 실패상태 유지]
  → 창 용량 초과 후보 선정
  → 요약 산출물 저장 [원본 대체 아님]
  → archive 사본/참조 + raw hash/개수 확인
  → manifest 전환을 원자 확정 + checkpoint 기록
  → 활성 창 참조만 퇴거
  → 이후 제한된 archive 검색으로 재참조

원본 edit/delete/권한 철회
  → consumer 접근 차단·무효화 version 증가
  → 관련 창/요약/기억/검색 캐시를 invalidated로 표시
  → core 명시 update/delete + 재검증
  → 늦은 추출 결과는 옛 version이면 발행 거부
```

현재 요청의 ‘드롭’은 **활성 메모리에서 내리고 원본은 아카이브 보존**하는 것으로 해석한다. 파일·DB 레코드의 영구 삭제가 아니다. 아카이브 확정 전 크래시는 기존 활성 참조를 유지하고, 확정 후 재시작은 동일 전환 ID로 checkpoint를 재생한다. 단계 재실행은 중복 파일·중복 기억을 만들지 않아야 한다. 디스크 부족·아카이브 실패 시 조용히 원본을 버리지 않고 intake backpressure 또는 오류를 반환한다.

아카이브 검색은 source scope, tenant, access scope, time range, max_chunks, max_tokens, max_depth를 제한한다. 최신 사용용 검색과 historical 감사 검색을 분리하며, 편집·삭제·권한 철회된 과거 자료를 ‘기억 복구’라는 이유로 자동 재등장시키지 않는다. core의 과거 manifest 재현 기능만으로 현재 사용자 접근 권한을 보장할 수 없으므로 소비자가 모든 조회·원본 fetch 앞에서 권한을 확인해야 한다.

요약·후보 추출 실패를 데이터 유실이나 무한 활성 창 증가로 바꾸지 않는다. 원본과 아카이브 checkpoint가 확정됐다면 `extraction_pending`을 남기고, 검증되지 않은 요약 대신 원본 참조로 보존·재시도할 수 있다. 아직 보존을 확인하지 못했다면 퇴거하지 않고 입력 속도를 제한한다. 여러 근거를 합친 기억은 그 근거 모두에 접근 가능한 범위에서만 제공하며, 공개 근거와 제한 근거를 섞었다고 공개 기억으로 승격하지 않는다.

현재 core에 ACL·권한 철회 enforcement API가 있다는 뜻은 아니다. collection/source_key 필터는 검색 범위일 뿐 인증이나 권한 증명이 아니다. 위 tenant/access_scope 검증·철회 장벽·조회 차단은 새 consumer/auth 경계에서 구현할 제안이다.

법적 보존·개인정보 삭제 요구는 별도 retention 정책 대상으로 남긴다. tombstone·활성 참조 퇴거는 물리 삭제가 아니며 백업·외부 파일도 남을 수 있다. 영구 삭제 요청은 보존 의무·승인 범위·백업 만료·파생 기억 정리 범위를 확인한 뒤 별도 설계/승인을 받아야 한다. raw 불변성은 무조건 영구보관하라는 뜻이 아니다.

## 5. 현재 세션에 적용한 가상 예시

실제 채팅 파일 수·사건 수는 조사하지 않았다. 다음 ID와 창 배치는 설명용이며 저장 결과가 아니다.

```text
session: airag-tour-example
├─ segment S001 [가상 봉인]
│  └─ T00~T02 합의·환경·DB 준비 대화 → 원본 event anchor 유지
├─ segment S002 [가상 봉인]
│  └─ 긴 문서·OCR 문제와 해결 대화 → troubleshoot 후보
├─ segment S003 [가상 봉인]
│  └─ T05 고양이 번역 오류·수정·사용자 확인 → 검증 단계별 기록
├─ segment S004 [가상 현재 tail]
│  └─ T06 완료 설명·T07 요청·새 데이터 운영 기획 요청
├─ memory 상단 후보 [예산 안에서만]
│  ├─ 진행: T07 갱신·재생 검증 완료, 다음 투어 T08 [실행 artifact 대조]
│  ├─ 작업 범위: 실제 rag-transplant 워크트리 [이 세션 범위]
│  ├─ 선호 후보: 진행 보고를 트리로 표시 [사용자 발언 anchor]
│  └─ 해결 기록: 고양이 오역 보완 [기존 보고와 독립 실행 증거 구분]
└─ N_active 초과 시
   ├─ 오래된 창 원본·요약이 archive에 있음을 검증
   ├─ 상단 기억은 원본 anchor를 유지한 채 별도 예산으로 재선택
   └─ 가장 오래된 활성 창 참조 퇴거, 원본과 과거 증거는 보존
```

‘검증 492개 통과’ 같은 대화 속 완료 주장은 실제 테스트 artifact를 대조하기 전까지 ‘assistant가 보고한 사실’로만 보존한다. ‘트리로 보고’ 같은 사용자 요구도 범위·원문·승인 상태를 가진 선호 레코드이며 다른 세션의 시스템 지침으로 승격하지 않는다. 위 예시는 수집 없는 가상 배치이며 투어 실행 상태를 변경하지 않는다. 별도 메인 검토자의 최신 전달은 T07 검증 기록 보존 완료·다음 T08이다. 이 기획 작성자가 T07을 실행하거나 독립 재검증한 것은 아니다.

## 6. 역할과 모델 사용

| 책임자 | 맡는 일 | 모델 필요 여부 |
|---|---|---|
| 외부 connector/consumer | 워처·CDC·event ledger·순서·권한·CAS·checkpoint | 결정적 코드가 기본 |
| AI RAG core | 명시 수입·원본 revision·세대 처리·암호화 저장·검색·근거 반환 | 기존 불변 profile의 전처리/임베딩 |
| segment/window 관리자 | 로그 봉인·창 예산·archive 전환·내구성 | 결정적 코드 |
| 후보 추출 모델 | 요약·사실·문제 해결·선호 후보 생성 | 비용 작은 모델부터 실측, 출력은 미검증 후보 |
| 검증 계층 | anchor·revision·권한·모순·실행 증거 검증 | 규칙 우선, 필요 시 별도 의미 검증 모델 |
| 사용자/승인 담당 | pin·중요 선호·운영 정책·영구 삭제 승인 | 사람이 명시 결정 |
| 응답 에이전트 | 허용된 현재 창·근거를 읽고 답변 | 근거를 인용하고 도구 결과와 주장을 구분 |

‘나노 크루’는 이 초안을 작성하는 작은 기획 작업 단위다. nano라는 배포 모델이 준비됐거나 실행 중인 서비스가 생성됐다고 주장하지 않는다. 반복 메모리 추출의 모델 선택은 지연·비용·정확성 실측 후 확정한다.

## 7. 작은 구현 순서와 통과 조건

| 순서 | 최소 산출물 | 통과 조건 |
|---|---|---|
| M1 계약 확정 | 사건·신원·권한·revision·원본 저장 단위 | 재전송 결과 동일, ID 재사용 충돌, rename 신원 보존, stale CAS 차단 |
| M2 자료 consumer | 한 문서 connector와 명시 이벤트 큐 | add/update/delete/restore/reindex, 부분 목록 미삭제, 실패 중 옛 ready 유지 |
| M3 대화 log/window | 합성 채팅의 암호화 세그먼트·활성 창 | N/토큰 초과, 큰 도구 결과, 늦은 사건, edit/delete, 크래시·재시작 무손실 |
| M4 기억 후보 | anchor 있는 fact/troubleshoot/선호 후보 | 잘못된 근거·명령문 권한 승격 거부, 수정 후 stale 후보 발행 차단 |
| M5 아카이브 순환 | 확정 checkpoint·퇴거·제한된 과거 검색 | 복사 실패 시 보존, 두 번 실행해 중복 없음, 다른 권한 근거 비노출 |
| M6 운영 실측 | 비용·지연·원본/기억 크기·회수 품질 | pin overflow 명시, 삭제 후 비부활, retention 정책과 백업 범위 검토 |

추가 경합 검증: delete와 in-flight extract, restore와 이전 update, 같은 DB commit의 재전송, 최신 source와 오래된 summary, 권한 철회와 캐시 조회, 아카이브 확정 직후 크래시를 각각 재현한다. 하나의 자료에서 발생한 실패가 다른 세션의 창·기억을 지우지 않아야 한다.
