## M2 — 정리 핸들러를 추가했지만 중단·부분 성공·잔존 검증이 아직 안전하지 않다 (major)

근거: 설계:125–135,193.

`trap cleanup EXIT INT TERM HUP`만 선언하면 INT/TERM/HUP 처리 후 반드시 종료한다는 보장이 없다. cleanup이 반환하면 다음 셸 명령이 계속 실행될 수 있으므로 «Ctrl-C→정리 후 종료» 계약을 충족하지 못한다. LABEL_LOADED가 참일 때만 정리하는 정책도 bootstrap 성공 직후 플래그 기록 전에 중단되면 로드된 자기 작업을 놓칠 수 있다. 플래그만이 아니라 자기 고유 라벨의 실제 존재를 대조할 필요가 있다.

`pgrep -f "$PROBE_DIR"`는 `python .../$PROBE_DIR/...`는 찾을 수 있어도 **`op user get --me --format json` 자식 argv에는 그 디렉터리가 없으므로** op 잔존 검증이 되지 않는다. HOME/OP_CONFIG_DIR은 env이며 `pgrep -f`의 명령줄 일치 조건이 아니다. bootout 실패 뒤 Python/op가 살아 있어도 «잔존 없음»으로 오판할 수 있다. §4.3은 child_pid를 이미 기록하므로 직접 만든 프로세스의 식별/종료/재수거 계약을 이를 기준으로 설계해야 한다. 공유 데몬을 임의 종료하지 않는 경계는 적절하다.

필수 수정: signal별로 정리 후 명시적 종료하는 경로, bootstrap 부분 성공 시 자기 라벨 대조, 직접 생성한 PID/프로세스의 종료·재수거·잔존 상태를 정한다. launchctl 실패는 «없음»과 «조회/권한 오류»를 구분하고 미확인이면 잔존 확인 필요로 닫는다. 합성 시험에 bootstrap 성공 직후 중단과 bootout 실패 뒤 직접 op 잔존을 포함한다. 구현이 없는 현재 이를 실증 실패라고 부르는 것은 아니며, 실패 시 계약이 아직 불충분하다는 설계 지적이다.

## M4 — 집계 수치는 맞지만 키 읽기·TCC 인과·원인 기각 서술은 여전히 과하다 (major)

필수 수정: «degraded=키 확보 단계 정상 반환», «TCC 시각과 인접한 틱이 최종 degraded», «재부팅/화면 상태만으로 설명하는 단순 가설은 약화»로 고친다. op read 성공·TCC 귀속·회복 원인 확정은 필요한 추가 관측을 붙이기 전까지 미확정으로 둔다. 팝업과 타임아웃을 별도 문제로 관리한다는 방향은 타당하다.

## m2 — 사람에게 고지할 횟수/전체 마감 수치가 서로 다르고 근거가 없다 (minor)

근거: 설계:81–82,98–101,134,188–193.

실제 계정 조회는 최대 P2/P1/P1b **3회**인데 질문은 최대 4회라고 한다(4개 CLI 중 P0은 버전 조회). «단계마다 최대 3번 팝업»이라는 상한은 실행 횟수로 보장되지 않으며 이번 자료에 검증 근거가 없다. 전체 하드 상한도 105초와 약 90초 두 값이다. 신호 정리 계약은 M2가 닫히기 전까지 고지한 종료 보장이 아니다.

필수 수정: 계정 조회/버전 조회 횟수, 팝업은 복수 발생 가능하며 개수는 보장하지 않음, B1 수정 후 단일 전체 마감과 정리 실패 시 상태를 정확히 고지한다. 기존 정지 유지와 새 HIL 경계는 유지한다.

## m3 — 재시도 추가 뒤 일 호출량 상한을 갱신하지 않았다 (minor)

근거: 설계:69–76,168.

5분 틱 288회 × 키 3개는 기본 논리 읽기 864회/일이다. I-1은 키마다 1회 재시도를 추가하므로 **최대 CLI 시도는 1,728회/일**이다. 각 CLI 시도가 실제 서비스 API 요청을 몇 번 만드는지는 별도 미확인이다. 기존 «최대 864 읽기»만으로 rate-limit 여유를 판단하면 추가 시도 비용을 누락한다. 기본 논리 읽기·재시도 포함 CLI 시도·실제 과금/한도 요청을 구분해 S2 예산에 반영한다.

## 3. §8의 다섯 요청에 대한 답

| 요청 | 이번 DA 결과 |
|---|---|
| 1. 재시도/마감 전파·5개 시험·부분 출력 | **설계 B1/M3 반송**. 5개 시험은 미래 구현 계획이며 실행/통과했다고 주장하지 않는다. 부분 출력이 있는 timeout은 재시도하지 않는 합성 시험도 필요 |
| 2. 정리·합성 시험 a–f·원자 기록 | **M2 반송**. 원자 완료 표시 방향은 수용하나 실제 스크립트·시험 결과가 없는 현재 구현 PASS 대상은 아님 |
| 3. 실제 계정 JSON type | **미확인 유지**. op 실행 금지로 직접 확인하지 않았다. 공식 스키마/허용된 후속 실행 증거로 구현 DA에서 확인하되 P0/P4는 별도 판정해야 함 |
| 4. 분기 누락·P1b | **M1 반송**. 단계별 성공식과 TCC 중지/관측 불가 처리를 먼저 일치시킬 것 |
| 5. 로그 재집계 | **독립 재현 rc=0**: OP_READ_UNAVAILABLE 231 / 지정 재부팅 경계 이전 231 / degraded 64. 필드 제한과 시각/귀속 해석 한계는 §2/M4 |

재심 입력은 위 설계 결함을 고친 r3다. 이 판정은 I-1의 10.5초 구현이나 운영 프로브 실행을 승인하지 않는다. op 직접 실행 금지·서버 복구 전 disabled·HELM 재개 게이트는 그대로 유효하다.
