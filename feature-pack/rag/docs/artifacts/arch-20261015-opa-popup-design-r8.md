## 1.2 launchd 작업 정의 (읽기 전용)
- 프로브 `job.plist`: `ProcessType=Background` · `StandardOutPath/ErrorPath=/dev/null` · 환경 `PATH` 만 · `RunAtLoad`.
- 운영 `com.airag.consumer.plist`: `ProcessType=Background` · `StartInterval=300` · 환경 `PATH` 만. (`com.airag.ft-*` 두 작업에는 `ProcessType` 없음.)
- 반례 병기: 운영 consumer 가 같은 Background 설정으로 10-02(ok 6건)·10-13(연속 성공 구간)에는 성공했다(성공 틱이 실제 `op` 호출을 했는지는 상태 로그만으로 단정 못 함 — r4 §1.2). 과거 231건 실패는 밤 시간대가 많아 부하만으로는 설명되지 않는다. 따라서 Background 는 «단독 원인 후보»가 아니라 «다른 조건과 겹쳐야 하는 후보» 정도로만 둔다.

## 1.3 TCC 사후 조회 (읽기 전용, 7초 한도, 원문 비저장)
- 프로브 창(19:44:58~19:45:10): 타임스탬프 행 8 · `DeveloperTool` 행 2(요청 **1건**: 19:45:06.508, `syspolicyd`→`tccd`, 대상 = 부모 python PID 69892, «prompting 불허 → denied») · AppData 행 0. `op` 시작(00.4) 약 6.1초 뒤.
- E1 창(21:18:54~21:19:05): 타임스탬프 행 552 · `DeveloperTool` 0 · AppData 0.
- **행 수와 요청 건수는 다른 단위**이며, 조회된 창에서 AppData 가 관측되지 않았다는 사실을 팝업이 없었다는 보장으로 확대하지 않는다. 조회 대상이 `op` 가 아니라 부모 python 이므로 정지와의 인과는 미확인이다.

## 1.4 `taskpolicy`·launchd 문서 (로컬 man 페이지 직독)
- `taskpolicy -b`: `setpriority(PRIO_DARWIN_BG)` 후 프로그램 실행, **자식들이 정책을 상속**(`taskpolicy(8)`).
- launchd `ProcessType`: 값에 따라 자원 제한이 적용되고 Background 는 사용자 경험을 방해하지 않도록 제한(`launchd.plist(5)`). **문서에는 `taskpolicy -b` 와 launchd Background 가 완전히 같다는 명세가 없다.**
- DA 의 비제품 프로세스 확인: 보통 실행 시 `getpriority(PRIO_DARWIN_PROCESS)`=0/0, `taskpolicy -b` 실행 시 1/1(자식 포함). 종료 코드는 전달됨. 이는 launchd 와의 동등성이나 실제 N2 의 정책 상태를 측정한 증거가 아니다.
- **N3 의 적용 범위:** E1 의 python 전체 + 관측 보조 자식 + 측정 자식 + 새로 생기는 후손(데몬 포함). `op` 하나만의 정책을 바꾸는 실험이 아니다. 이미 있는 공유 `op` 데몬의 정책은 바꾸지 않는다.

## 1.5 판정에 쓰지 않는 것
7초 동안 `op` 가 기다린 대상 · 7초 이후 종료 시각 · 부분 stdout · 프로브 TCC 관측 unknown 의 하위 원인(r6 §3) · 터미널 N2 의 실제 정책 상태 — 모두 미확인.

# 4. 권고 1안 — 단계 게이트가 있는 연속 실행 (N1 → N2 → N3)

## 4.1 순서와 한계
1. N1 을 먼저 한다 — 뒤의 터미널 실행이 `op` 파일 캐시를 데워 N1 의 콜드 조건을 바꾸는 일을 피하기 위해서다(보장이 아니라 의도).
2. 이어서 N2, N3. 같은 몇 분 안에서 측정해 **시간 간격을 줄인다.** 위 3절의 한계 그대로이며, N3 와 N2 의 캐시 동일성은 보장하지 않는다.

## 4.2 게이트 입력 — 도구의 «닫힌 스키마 결과 JSON» 만 읽는다 (원 출력 해석 없음)
- 결과 파일 찾기: 도구 실행 **전후** 기본 폴더(`~/.local/share/airag-probe/`)의 항목 목록을 비교해 **새로 생긴 항목이 정확히 하나**(프로브: `<id>/result.json`, E1: `compare-<id>.result.json`)일 때만 그것을 쓴다. 0개·2개 이상·읽기 불가·JSON 불완전·필수 필드 누락/형 불일치는 모두 **후속 미실행**(값 없는 사유 열거형으로만 표시). stdout 의 «결과 파일:» 줄은 파싱하지 않는다.
- 읽는 필드는 값이 없는 수치·불리언·열거형만(r5 결과 스키마 `schema_version=1`, E1 `v=1`). 토큰·환경 값·로그 원문은 어떤 경우에도 읽지 않는다.

## 4.3 단계 게이트 표 (종료코드 AND 결과 JSON)
**공통:** 도구 종료코드가 0 이 아니면 **즉시 멈추고 저장한 코드를 그대로 전파**한다(프로브 1·2·3·4·130·143·129, E1 1·2·130·143·129; 신호 종료도 같은 값). 아래 표는 종료코드 0 인 경우에 **추가로** 통과해야 하는 조건이다.

| 게이트 | 통과 조건 (모두 참) | 하나라도 거짓이면 |
|---|---|---|
| **G1 (N1 → N2)** | `complete=true` · `aborted_class=null` · `timed_out_wait=false` · `conclusion≠observation_unknown` · **실제 실행된 단계**(status 가 `skipped_*` 가 아닌 단계)마다: `status∉{spawn_error, observation_unknown, unsupported}` AND `child_exit_unconfirmed=false` AND `descendants_may_hold_pipe=false` AND (`child_pid=null` OR `reaped=true`) | N2·N3 미실행, 사유 열거형 표시(예: `probe_incomplete`, `probe_step_error`, `probe_exit_unconfirmed`), 종료 5 |
| **G2 (N2 → N3)** | `complete=true` · `exit_class=ran_all` · `leftover_check_required=false` · `op_count_after = op_count_before` · `conclusion ∉ {inconclusive_error, cancelled_incomplete, incomplete_exit_unconfirmed, incomplete_missing_rounds}` · 여섯 라운드 모두 `status∈{success, timeout}` AND `child_exit_unconfirmed=false` AND `reaped=true` | N3 미실행, 사유 표시(예: `e1_leftover_check_required`, `e1_inconclusive_error`, `e1_incomplete`), 종료 5 |
| **G3 (N3 이후, 기록용)** | G2 와 같은 검사 | 종료 5 (후속 단계는 없음 — 표시와 종료 코드만) |
- **자동 오류로 취급하지 않는 것(이 실험의 관측 대상):** 프로브의 **회수 확인된 P0 timeout**(`status=timeout`·`reaped=true`)과 **TCC `unknown_log_unavailable`**, 프로브 P4 `network_error`·P2/P1 `auth_error`(관측 결과), 생략 단계(`skipped_*`)의 `reaped=false`(살아 있는 자식이 아님), E1 라운드의 `timeout`(회수 확인된 느린 측정).
- 프로브가 P0 에서 막혀 P2·P1·P1b 가 건너뛰어진 경우(`p0_blocked`)는 오류가 아니므로 N2 로 진행한다.
- G1~G3 의 판단 입력은 위 필드뿐이며, 판단 근거와 결과 해석은 별개다(게이트는 «다음 측정을 시작해도 안전한가»만 정한다).

## 4.5 새 연속 실행 스크립트는 «구현·검수 대상»이다 (M1)
- 스크립트는 임시 파일(Master 가 `ft-hil.sh --add` 로 `/tmp/h<N>` 생성)이지만 **새 제어 로직**이다. «기존 도구 무수정이므로 구현·DA 불필요» 입장을 **철회**한다.
- HIL 에 올리기 전에 ① 합성 시험(가짜 도구 3개·가짜 결과 JSON·실제 `op`/`launchctl`/`taskpolicy` 호출 0) 통과 ② **그 구체적 스크립트를 구현 DA 가 검수**(Master 소환) — 이 통과가 실제 `op` 실행 승인을 대체하지 않는다.
- 합성 시험(최소):
  1. **E1 개수 2→3, 종료 0·`leftover_check_required=true`** → N3 미실행 · 사유 `e1_leftover_check_required` · 종료 5.
  2. **E1 두 번째 `spawn_error`, 종료 0·`conclusion=inconclusive_error`** → N3 미실행.
  3. **프로브 완료 요약에 실행 단계 `spawn_error`(`cause_unconfirmed`), report 종료 0** → N2·N3 미실행.
  4. **프로브 P0 `timeout`(`reaped=true`)·`tcc=unknown_log_unavailable`·P2/P1/P1b `skipped_prior_unresolved`(`reaped=false`)** → **통과**하고 N2 진행(자동 오류 아님의 양성 대조).
  5. 프로브 `child_exit_unconfirmed=true`·`aborted_class≠null`·`timed_out_wait=true`·`complete=false` 각각 → 미실행.
  6. 결과 항목 새로 0개 / 2개 이상 / JSON 잘림 / 필수 필드 누락 / 형 불일치 → 미실행.
  7. 도구 종료코드 4·1·2·3·130·143·129 → 저장 코드 그대로 전파, 후속 미실행.
  8. 단계 사이 Ctrl-C(가짜 신호) → 남은 단계 미실행, 130 전파.
  9. 가짜 시계로 남은 시간 < 83초 → `skipped_budget`; 한 단계 77초 초과 → 그 도구에만 TERM·3초 대기·종료 6; 전체 240초 초과 불가.
  10. 값 비출력: 환경·stdout·토큰 대용 센티넬을 도구 출력에 넣어도 스크립트 출력·파일에 0.
  11. 어떤 경로에서도 기존/새 `op` 프로세스·프로세스 그룹에 신호를 보내는 코드 없음(정적 검사).
- Master 사전 점검(읽기 전용): 경로 실재(`test -f`)·`bash -n`·`/usr/sbin/taskpolicy` 실재·대화형 프롬프트 0·`!` 한 줄 규칙(60자 이내, `/tmp/h<N>`).

## 4.6 결과 해석표 — 관측 라벨만 (원인 확정 아님)
관측 라벨 세 개: **(a) 이번 launchd 재실행에서 P0 timeout 여부 · (b) 직후 터미널(N2) 결과 · (c) PRIO_DARWIN_BG 를 적용한 E1(N3)에서 결과 변화 여부.** 모든 행에 §3 의 한계(고정 순서·상태 변화·동시점 아님)와 §1.4 의 한계(`taskpolicy -b` 와 launchd Background 의 동등성 미확인)가 적용된다.

| (a) P0 | (b) N2 | (c) N3 | 읽는 법 |
|---|---|---|---|
| timeout | 모두 빠름 | 일부/전부 느림 | 이 순서에서 **PRIO_DARWIN_BG 적용과 결과 차이가 연관**된 관찰(연관 후보). 원인 확정 아님 |
| timeout | 모두 빠름 | 모두 빠름 | launchd 재실행에서는 재현, **해당 taskpolicy 구성에서는 재현되지 않음.** L1 을 배제하지 않고 L2·L5 를 확정하지도 않음 |
| 빠름(P2·P1 진행) | 모두 빠름 | 모두 빠름 | 이번 재실행에서 **재현되지 않음.** 간헐·콜드·시간대 등 후보는 열려 있음. 프로브 후속 결과(계정 종류 조회 등)가 함께 생김 |
| 빠름 | 모두 빠름 | 느림 | 터미널에서 정책 적용 시 느려진 관찰이나 launchd 재실행은 빨랐음 — 해석 보류, 같은 3단계 1회 더 필요 여부는 별도 판단 |
| timeout | 일부/전부 느림 | — | 터미널도 느린 관찰 — 시간대·머신 상태 후보 **포함** 해석 보류(N3 결과는 같은 방식으로 라벨링) |
| 게이트 중단(§4.3) | — | — | 해석하지 않음 · 사유부터 |
- **한 번의 3단계로 원인이 정해지지 않는다.** 얻는 것은 관측 라벨과 «다음 한 걸음 후보»(N4~N7 구현은 별도 설계·DA·HIL)이다. 운영 plist 의 `ProcessType` 변경은 어떤 결과든 **별도 설계·DA·오빠 판정** 뒤에만 한다.

# 6. 오빠께 드릴 질문 1개 (Master 가 §4.5 검수 뒤 올림 · 이 문서가 실제 승인을 대체하지 않음)

> **정정 한 줄:** 같은 `op --version` 이 오빠 터미널에서는 6번 모두 빠르게(약 0.03~0.22초, 모두 0.23초 미만) 끝났고, 지난번 launchd 프로브에서는 7초를 넘겼습니다. 차이가 어디서 나는지는 아직 모르고(launchd 의 낮은 우선순위 설정 등이 후보), 팝업과 타임아웃이 같은 원인인지도 모릅니다.
>
> **질문:** `! bash /tmp/h<N>` 한 줄을 1회 실행해 주세요(**최대 4분 = 240초**). 기존에 검수된 도구를 **수정 없이** 순서대로 돌립니다: ① launchd 프로브 ② 터미널 `op --version` 6번 측정 ③ 같은 측정을 낮은 우선순위(PRIO_DARWIN_BG)로. 앞 단계에서 이상(남은 것 확인 필요·불완전·실행 오류)이 확인되면 뒤 단계는 실행하지 않고 멈춥니다.
> - **① 프로브가 하는 일(순서대로, 앞의 둘은 `op --version` 결과와 무관하게 항상 일어남):** ⒜ 임시 launchd 작업 등록·자동 내림 ⒝ 네트워크 도달 확인 1회(my.1password.com 연결) ⒞ 프로브 본체가 **서비스 계정 토큰 파일 읽기를 시도**(값은 출력·저장하지 않음. 이번 점검이 읽기 성공 여부를 확인한 것은 아님) ⒟ `op --version` 1회(이때 토큰은 전달하지 않음) ⒠ **⒟ 가 통과하는 등 전이 조건이 맞을 때만** 토큰을 계정 종류 조회 명령에 전달(최대 3회). 항목 비밀 값을 조회하는 명령은 없습니다. 토큰 값은 프로브 본체와 그 조회 명령의 메모리에서만 쓰입니다. `~/.config/op` 공유 상태에 닿을 수 있고, 1Password 팝업이 뜰 수 있으며(개수 보장 불가) 누르지 말아 주세요(«허용 안 함»도 설정으로 저장될 수 있음). 팝업창을 부작용 없이 없애는 방법은 확인되지 않았으니 뜨면 Master 에게 알려 주세요. 끝난 뒤 남을 수 있는 것은 «남은 것 확인 필요»로 표시합니다.
> - **② 터미널 측정:** 서비스 계정 토큰 주입·토큰 파일 읽기·로그인·계정 조회 명령은 없습니다. `op` 가 내부적으로 네트워크나 기존 1Password 데몬·`~/.config/op` 에 접촉하는지는 모릅니다. 새 `op` 데몬이 생기면 임시 폴더를 지우지 않고 «남은 것 확인 필요»로 표시하고 멈춥니다.
> - **③ 낮은 우선순위 측정:** ②와 같은 일을, 측정 도구 전체(파이썬·보조 프로세스·측정 프로세스)와 그 후손에게 낮은 우선순위(PRIO_DARWIN_BG)를 걸어 실행합니다. 이 정책이 launchd 의 낮은 우선순위 설정과 같은지는 확인되지 않았습니다. 새 데몬이 생기면 그 데몬이 이 정책을 물려받은 채 남을 수 있습니다. 이미 떠 있는 1Password 데몬의 정책은 바꾸지 않고 종료하지도 않습니다.
> - Ctrl-C 로 언제든 멈출 수 있습니다(진행 중 도구가 정리 후 종료, 남은 단계는 건너뜀). consumer 는 계속 꺼 둡니다.
