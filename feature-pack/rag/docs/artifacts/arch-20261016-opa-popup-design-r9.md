# 0. 결론 (먼저 읽기)
1. **라벨 읽기:** (a) launchd P0 timeout **2회 재현**(7038 ms·7024 ms) · (b) 터미널 N2 전부 빠름(25~40 ms) · (c) `taskpolicy -b` N3 전부 빠름(95~157 ms) = r8 §4.6 **둘째 행.** 원인은 확정되지 않았다. N3 에서 7초 초과가 재현되지 않았다는 사실뿐이며, 후보를 약화·배제하지 않는다(`taskpolicy -b` ↔ launchd Background 동등성 미확인 그대로).
2. **새 관측(읽기 전용):** 두 launchd 창 모두 syspolicyd 가 프로브 부모(adhoc python)에 대해 `DeveloperTool` 조회를 하고 «prompting 불허 → denied» 가 났으며 터미널 창에는 없었다(n=2 : 0/2, 대상은 `op` 가 아님). 이는 후보 **L2(책임 프로세스)** 에 붙는 연관 증거일 뿐 원인이 아니다. 같은 로그에서 실행 평가(Gatekeeper)는 터미널 창에도 같은 속도로 있었으므로 «평가 유무»는 가르지 못한다.
3. **지금 가능한 것·불가한 것:** 읽기 전용(op 0)만으로 L1·L2 를 가르는 판별은 **없다**(§3). 가를 수 있는 다음 한 걸음은 «launchd 프로브에서 `ProcessType` 키 유무만 바꾼 A-B-A 쌍 비교(토큰 0 · P4+P0 만)» 이며 **프로브 코드 변경 + 구현 DA + 오빠 HIL(op --version 만 실행)** 이 필요하다(§4 N4). 운영 plist `ProcessType` 변경·I-2·S2 는 **지금 불가**, consumer 재개는 §5 조건 미충족.

# 2. r8 §4.6 해석표 적용 + 후보 갱신 (서열 없음 · 약화/배제/판명/우세 표기 없음)

## 2.1 라벨
| 라벨 | 값 |
|---|---|
| (a) launchd 재실행 P0 timeout 여부 | **timeout (2/2)** |
| (b) 직후 터미널 N2 | 모두 빠름 |
| (c) PRIO_DARWIN_BG 적용 E1(N3) 결과 변화 | **7초 초과 변화 없음(전부 success).** 별도 관찰: 지연 수치가 N2 의 약 4배(95~157 ms vs 25~40 ms) |
- 해당 행: «timeout / 모두 빠름 / 모두 빠름» — **launchd 재실행에서는 재현(2회째), 해당 taskpolicy 구성에서는 재현되지 않음. L1 을 배제하지 않고 L2·L5 를 확정하지도 않음.**
- **N3 수치 4배의 읽기:** (c) 의 «변화» 정의는 7초 초과 여부다. 4배 증가는 정책 연관 후보와 방향이 같으나 N2→N3 순서·캐시 상태·측정 오차와 분리되지 않고, 크기(약 0.1초 단위)가 7초 초과와 수십 배 차이다. 이 구성에서 PRIO_DARWIN_BG 만으로 7초 초과가 만들어지지 않았다는 관측으로만 쓴다.
- **«낮은 우선순위 후보가 N3 로 약해졌는가?»에 대한 답:** 표기 규칙상 «약화/배제» 라벨을 붙이지 않는다. L1 은 «`taskpolicy -b` 구성에서는 재현 안 됨 · 동등성 미확인 · 부하×낮은 우선순위 조합 미검증» 으로 열려 있다. 부하가 높았던 시점에 N1 이 있었고 N2·N3 도 같은 몇십 초 안에서 빨랐다는 점이 있으나(부하 미기록), 그것이 L1 을 뒤집는지 지지하는지는 이 자료로 가르지 못한다.

# 3. 읽기 전용(op 직접 실행 0)으로 가를 수 있는 것 — 솔직한 결론
| 판별 | 가르는 후보 | 가능 여부 |
|---|---|---|
| D1 launchd 창·터미널 창의 syspolicyd/tccd 계수 비교 | L2·L7 | **이번에 수행함**: DeveloperTool 요청만 launchd 에서 관측, GK 평가는 양쪽 같은 속도 → «평가 유무»는 가르지 못함, «responsible=adhoc python 의 DeveloperTool 조회»만 launchd 한정(n=2) |
| D2 운영 틱 이력의 시간 구조 | L4·L1 | **이번에 수행함**: 수 시간 덩어리 → 외부 상태 의존 «가능성»(부하·다른 사용자 기록 없어 가르지 못함) |
| D3 `op`·python 서명·속성 정적 확인 | L2·L7 | **이번에 수행함**: quarantine 있음, 터미널은 빠름 → 속성 단독 비충분 |
| D4 syspolicyd 가 `op` 를 평가하는 줄 확인 | L7 | **불가**: 대상 필드가 비공개(`<private>`), 정지 중 스냅샷은 `op` 실행이 필요 |
| D5 부하·정책 상태 기록 | L1·L4 | **다음 실행부터** 값 없는 수치(부하 3값)를 도구 결과에 넣어야 가능 — 코드 변경 |
- **결론: 읽기 전용만으로 L1·L2·L4·L7 을 가르는 판별은 더 없다.** 현재 자료는 «launchd 컨텍스트 + 지속 구간 구조(외부 상태 의존 가능)» 까지만 말한다.
- 읽기 전용으로 **하지 않는 것(비권고):** `spctl --assess`(syspolicyd 평가 캐시를 데워 이후 측정을 바꿀 수 있음), `op` 대상 `sample`/`log stream` 정지 중 관찰(`op` 실행 필요).
- **보존 권고(op 0, Master):** info/debug 로그는 보존이 짧다 — 앞으로 op 를 실행하는 단계가 있으면 **끝난 직후** 같은 계수(TCC 요청 건수·DeveloperTool·GK 평가 건수·XProtect 연결 건수)를 값 없이 기록해 둔다(원문 비저장·7초 한도).

# 4. 다음 증거 권고 — N4 (op --version 만, 토큰 0) · 코드 변경·구현 DA·오빠 HIL 필요
## 4.1 목적과 한계
L1 을 직접 가르는 **쌍 비교**: 같은 launchd 컨텍스트에서 `ProcessType` 키만 다르게 한 임시 작업으로 P4+P0 만 실행한다. r8 N4 의 구체화이며 **결과를 본 뒤 별도 설계·DA·HIL** 규칙에 따라 이 문서는 설계 요건까지만 적는다(구현·실행 승인 아님).

## 4.2 설계 요건 (프로브 소규모 변경)
1. 프로브에 두 플래그 추가: ⒜ `--process-type {background,none}`(기본 `background`=현행, `none`=`ProcessType` 키 없이 작업 생성) ⒝ `--p0-only`(P4·P0 만 실행하고 **토큰 파일 읽기·P2·P1·P1b 를 하지 않음**). 두 변경 모두 job.plist 생성부와 단계 선택부에 한정, 시험 추가.
2. 결과 JSON 에 값 없는 수치 추가: 각 P0 직전·직후 `vm.loadavg` 3값(float), 같은 작업 plist 의 `ProcessType` 유무(불리언). 환경·토큰·로그 원문 없음(r8 §4.2 닫힌 스키마 규칙 그대로).
3. 실행 순서 **A-B-A**(Background → none → Background), 단계 사이 간격 최소화. 각 `op --version` 은 시도당 7.0초·재시도 0(기존 계약). 연속 실행 스크립트는 r8 §4.3 게이트(종료코드 AND 결과 JSON)·§4.4 시간 한도 정본 방식을 재사용하고 **새 제어 로직이므로 합성 시험 + 구현 DA 필수**(r8 §4.5).
4. **오빠 고지가 r8 보다 줄어든다:** 토큰 파일을 읽지 않고 계정 조회 명령이 없으므로 «토큰 접촉 0»이다. 임시 launchd 작업 3개 등록·자동 내림, 네트워크 도달 확인(P4) 3회, `op --version` 3회. 팝업이 뜰 수 있으며(개수 보장 불가) 누르지 말 것·없애는 방법 미확인 — 기존 고지 유지.
5. 7초 룰: 모든 `op` 시도 7.0초·재시도 0 · 총 상한은 구현 때 마감 계산(작업당 단계 시작 조건·초과 감시·최종 마감을 r8 §4.4 와 같은 방식으로 한 곳에서 정의).

# 7. 7초 룰 — P0 timeout 2회 재현이 I-1 적용 틱에 미치는 영향 (상수를 키우지 않는다)
- **I-1 소스 기준(7.0/14.0):** launchd 에서 `op` 가 P0 와 같은 정지를 하면 한 키 읽기가 시도 7.0초 + 재시도 7.0초(첫 출력 전 timeout 에 한해) = **호출당 최대 14초**에서 `OP_READ_UNAVAILABLE`(exit 30)로 끝나고 틱은 보류된다. 3키 병렬이므로 틱의 `op` 점유는 약 14초가 상한이다(자식 회수 계약 그대로).
- **현재 운영 설치본(timeout=30):** 틱당 점유가 더 길었다(10-12~13 의 exit 30 231건이 그 모양). 재설치 전에는 I-1 효과가 운영에 없다.
- **성공 이력의 위험:** 과거 성공 틱의 `op` 호출이 7초 안이었는지는 모른다(§1.5). 따라서 I-1 적용 뒤 «정상인데 첫 시도 7초 초과로 실패»하는 틱이 생길 수 있다 — r4 §3 에 기록한 위험이며, 이번 결과(P0 자체가 launchd 에서 7초 초과 2/2)는 그 위험이 **현실일 수 있다**는 증거다. 그러나 상수를 키우는 것은 규칙 위반이다: 7초 밖 측정·상수 변경은 «오빠 결정»으로만 별도 상신한다(이 문서는 상신하지 않음).
- **영향의 성격:** 실패는 «데이터 손상·유실 없음 + 틱 보류» 이다(재시도 틱이 5분 뒤 다시 읽음). 따라서 7초 룰 때문에 생기는 손실은 «수집 지연»뿐이며, 그 지연이 p0 정지의 원인 해결 없이 줄지는 않는다.
- **분할·감소(상수 불변 선택지, 코드 변경 필요 → 이 문서가 권고하지 않음):** 호출 3→1 축소(③ 후보)는 정지가 launchd 컨텍스트 한정이면 효과가 없다. 후순위 유지.
