### D-001 — 범용 암호화 로컬 RAG 엔진 (사용자 결정, 2026-09-09)

가볍고 암호화된 로컬 SQLite 기반 RAG 엔진을 만들어 BYZ·KakaoBot 등 여러 프로젝트가
같은 계약으로 재사용한다. 승인 범위: 목적/책임 경계, SQLCipher+sqlite-vec, 원본
스냅숏 보존, 유형별 어댑터, 청크 연결과 제한된 확장, 상위 에이전트용 근거 반환.

핵심 불변조건(문서 통합 과정에서 누락되지 않도록 여기 보존):
- **원본 리비전 vs 파생 세대 분리**: 내용이 바뀌면 새 `source_revision`; 원본 바이트가
  같은데 청커/임베딩 profile만 바뀌면 새 원본 리비전이 아니라 같은 원본 위의 새
  파생 처리 세대다.
- **모델 공간 격리**: embedding space는 모델+리비전+차원+모달리티+전처리 fingerprint를
  함께 써서 격리한다 — 차원만 같다고 비교 가능하다고 보지 않는다.
- **요청 정확성**: idempotency key와 `expected_revision` 기반 충돌 감지, 원자적 발행
  (실패 시 이전 검색 가능 리비전이 그대로 유지, 절반만 발행된 상태 없음).
- **검색/확장 일관성**: 검색과 그 확장은 하나의 동일 스냅숏·동일 범위/필터를 공유하며,
  같은 요청이 재현될 때 동일한 청크 집합을 반환한다.
- **저장 암호화 경계**: 관리 원본, 표준 MD, 구조/앵커, 청크, 벡터, 이력 모두 SQLCipher
  저장 경계 안에 있다 — 평문 DB로 자동 폴백하지 않으며, 키는 명령행 인자/로그에
  노출하지 않는다.

**함의**: PLAN.md 전체의 기반 전제. 위 다섯 불변조건은 PLAN.md P-01/P-02/P-03/P-06의
완료 조건에도 반영된다.

### D-002 — 외부 배선 책임 경계 (사용자 결정, 2026-09-09, D-001의 내장 워처 계획을 대체)

신규/변경/삭제 감지, 파일시스템 워처, 폴링, 스케줄, 트리거 타이밍은 **소비 프로젝트**의
몫이다. core는 명시적 `add`/`update`/`delete`/`search`/`expand`/`fetch`/`manage` 요청만
처리하고 표준화된 결과/근거를 반환하는 일반 처리기다. core에 내장 디렉터리 워처·

검색 제외·이력 보존하며 외부 파일을 지우지 않는다. 재수입은 core가 요청 시 수행하는
작업이며 필요 판단은 소비자 몫이다.
**함의**: PLAN.md의 파이프라인·명령 어휘에서 `watch` 계열을 전부 제거.

### D-009 — 저장·입력 계약: 신원·CAS 토큰·멱등성·스테이징 모델 (아키텍트 설계, 아키텍트 구현 선택·실행 검토, 2026-09-09)

P-02 저장 기반의 핵심 불변조건. 예시로 설명한다: 컬렉션 `docs`의 소스 키 `faq.md`.

**신원**: 소스는 `(collection, source_key)` 튜플로 식별한다 — 변경 가능한 경로만으로
유도하지 않는다. `origin_uri`는 메타데이터일 뿐 신원이 아니다. 원본 바이트와
media_type은 SQLCipher 안에 있으며 평문 사이드카 blob이 없다.

**리비전 vs 세대 vs state_version**: `source_revisions.revision_id`는 불변 콘텐츠
식별자(내용이 바뀌면 새 리비전). `generations.generation_id`는 처리 세대(어댑터/청커/
임베딩 profile 조합) — 원본 바이트가 같아도 profile이 다르면 새 세대이지 새 리비전이
아니다(force_reprocess로 동일 바이트를 재처리해도 리비전은 그대로, 새 job/세대만
생긴다). `sources.state_version`은 **소스에 대한 모든 실질 변경**(콘텐츠 변경,
메타데이터 변경, delete, restore, publish)마다 증가하는 단조 카운터.

**revision_token(CAS 토큰)**: `base64("v1:<source_id>:<state_version>")` — **콘텐츠
해시가 아니라 불투명 compare-and-swap 토큰**이다. 모든 뮤테이션이 반환하고,
`update`/`delete`/`restore`/`stage_generation`이 `expected_revision`으로 돌려받아
서버측 `state_version`과 정확히 일치하는지 검증한다. **구체 예시**: `add`로
`faq.md`(내용 A)를 만들면 `source_id=42, state_version=1` → 토큰 T1. 같은 내용 A로
`update`를 재호출하면 no-op(리비전도 state_version도 그대로, 같은 T1 반환). 내용을
B로 `update`하면 `state_version=2`(새 리비전) → T2. `delete`하면 내용은 그대로인데
`state_version=3`(삭제도 실질 변경) → T3. `restore`하면 `state_version=4` → T4. **이
시점에 T2(삭제 이전 토큰)로 다시 뭔가를 하려 하면 내용이 B로 동일해도 거부된다** —
delete/restore 사이클을 겪은 토큰은 콘텐츠 불변과 무관하게 stale이다. 이것이
`expected_revision`이 콘텐츠 해시가 아니라 "현재 소스 상태 전체"를 인코딩해야 하는
이유다.

**멱등성**: 뮤테이션은 소비자 제공 `request_id` + 요청 페이로드(콘텐츠 바이트 포함,
경로 문자열만이 아님)의 지문(fingerprint)을 뮤테이션과 **같은 BEGIN IMMEDIATE
트랜잭션 안에서** 검사·기록한다(먼저 잠금 없이 검사하면 두 개의 동일 재시도가 둘 다
원장을 못 보고 이후 UNIQUE 충돌로 부딪힌다). 같은 `request_id`+같은 지문 → 저장된
결과를 그대로 재생(**CAS 재적용 없음** — 요청 형태 검증(`req.validate()`)은 재생
경로에서도 항상 실행된다, 건너뛰는 것은 `expected_revision` 대조뿐) — **이 재생
판정은 CAS 검증보다 먼저 일어난다**: 재시도 시점에 소스 상태가 더 진행돼 원래
`expected_revision`이 stale이 되어 있어도, 동일 재시도는 성공한다(재생된 결과가
원래 응답 그대로이지, 현재 상태를 건드리지 않는다). 같은 `request_id`+다른 지문 →
`IDEMPOTENCY_MISMATCH` 충돌.

**스테이징/발행 경계(P-03 인터페이스)**: `stage_generation`은 스테이징 **그 순간**의
`state_version`을 세대에 박아 넣는다(발행 시점에 호출자가 새로 제시하는 토큰이 아니다
— 그러면 호출자가 토큰만 새로 받아오면 이미 stale해진 세대를 발행할 수 있는 구멍이
생긴다). `publish_generation`은 세대가 여전히 'staged' 상태이고, 소스가 삭제되지
않았고, 세대의 리비전이 여전히 소스의 현재 head이고, 소스의 **현재** `state_version`이
스테이징 때 박아 넣은 값과 정확히 같을 때만 `ready_generation_id`를 옮긴다 — 그리고
**발행 자체가 `state_version`을 다시 1 증가시킨다**(그래야 같은 토큰으로 스테이징된
두 번째 세대가 첫 번째 발행 이후에도 여전히 "유효한" CAS로 보여 순서를 무시하고
발행되는 것을 막는다). 발행 실패는 이전에 발행된(ready) 세대의 콘텐츠를 그대로
검색 가능 상태로 남긴다 — 포인터를 건드리지 않는다.

**함의**: PLAN.md P-02 전체와 `feature-pack/rag/src/airag/db/schema.py`/`store.py`의
근거. Job 클레임(스테이징이 `job_id`로 job을 요청과 연결)은 대상 job이 해당
source/revision과 일치하고 `status='pending'`이며 아직 어떤 세대에도 연결(claim)되지
않았을 때만 허용 — 이미 완료/실행/실패한 job을 조용히 재배정하지 않는다.

<a id="d-010"></a>
### D-010 — P-03 임베딩·검색 구현 설계 (아키텍트 설계, 2026-09-09, P03A provider probe 근거)

정규화·청킹·임베딩공간·발행 가시성의 핵심 계약. 상세는
`artifacts/p03-embedding-search.json`.

- **정규화 표현**: 네이티브 `DoclingDocument`를 공통 구조 표현으로 채택 — MD를
  export한 뒤 그 MD를 재파싱해서 청킹하지 않는다(재파싱 금지는 [D-003](#d-003)
  그대로). 텍스트/Markdown/대화 입력은 P-03에서는 **경량 어댑터**(
  `DoclingDocument.add_text`/`add_heading`/`add_list_item` 등 docling-core 자체
  빌더 API)로 직접 구성한다 — 전체 `docling`(PDF 백엔드) 패키지는 설치하지 않고
  P-04로 미룬다. `docling-core[chunking]` extra(HybridChunker + 토크나이저)만
  설치. 그 위에서 실제 `HybridChunker`를 호출해 청킹한다.
- **processing profile 불변조건**: 정규화/청커/토크나이저 설정 + embedding space를
  함께 지문화(fingerprint)한 불변 profile. embedding space 신원 = provider
  protocol/model/revision/dimension/modality/document+query 전처리
  ([D-001](#d-001) 모델공간격리 그대로 구체화).
- **provider 설정**: LM Studio OpenAI-호환 `/v1/embeddings`, 모델
  `text-embedding-qwen3-embedding-0.6b`(P03A 실측 1024차원). query 템플릿은
  실제 개행 포함 `Instruct: <task>\nQuery: <query>`, document는 wrap 없음
  (P03A 실측: 래핑 유무가 코사인 값을 유의미하게 바꿈 — 고정 profile 필드로
  기록해야 하는 이유). **모델 리비전은 명시적 운영자 주장**이다 — 캐시된 GGUF
  파일 해시(P03A 증거)가 서버가 "지금 실제로 로드한" 가중치를 자동으로
  증명하지 않는다; 런타임 매핑을 검증할 수 없는 한 리비전은 설정값으로
  선언한다. 조용한 대체 모델/provider/차원/텍스트해시 폴백 금지.
- **FTS5 vs vec0 발행 가시성 — 비대칭 (ft-airag-arch-astra 2026-09-09 보충,
  atomic visibility 조건의 구체화이지 신규 요구 아님)**: vec0는 순수 거리
  계산이라 `active`/`collection` 같은 메타데이터 컬럼 + WHERE 필터로 안전하다
  (P03A에서 pre-filter가 top-k 이전에 정확히 적용됨을 실증). **FTS5는 다르다**
  — BM25는 인덱스 전역 통계(IDF 등)로 점수를 매기므로, staged/실패 청크를
  미리 넣고 쿼리 시 WHERE만 거는 방식은 **미발행 작업이 이미 발행된 콘텐츠의
  검색 순위를 오염시킨다.** 따라서 FTS5 행은 **발행(publish) 트랜잭션에서만**
  insert되고(해당 세대가 ready가 되는 순간), 이전 ready 세대의 FTS5 행은 **같은
  트랜잭션에서 삭제**된다 — WHERE 필터로 "숨기지" 않는다. 원문 청크
  텍스트/앵커는 `chunks`/정규화 산출물 테이블에 세대별로 영구 보존되고,
  FTS5는 "검색 가능한 현재 상태"만 반영하는 인덱스다. vec0의 `active` 플립,
  FTS5 insert/delete, `sources.ready_generation_id` 포인터 이동은 **모두 같은
  발행 트랜잭션** 안에서 원자적으로 함께 일어난다. 모델 호출·정규화·청킹은
  이 트랜잭션 **밖**에서 수행된다(D-009 stage/publish 경계 그대로 P-03에 확장).
- **내구성**: request → job → 캡처된 profile/revision을 저장 수락과 원자적으로
  연결한다([D-009](#d-009) 멱등성/CAS를 P-03 처리 파이프라인까지 확장) — 크래시
  후 재시도는 자신의 pending/completed job을 찾아야 하며 무관한 최신 job이나
  구 저장 영수증만으로 대체하지 않는다.

### D-011 — IAP·GCE GPU 모델과 LLM 전처리 (사용자 결정, 2026-09-09)

2026-09-09 개별 실측에서는 byz-llm(챗/전처리)과 byz-embed(1024차원 임베딩)의
별도 GPU 경로가 확인됐다. 최초 LLM 포트에서의 embedding 404 및 이후 광범위 부재
추정은 현재 결론이 아니다. [실측 근거](artifacts/gpu-provider-probe.json) 참고.
모델 가중치 revision은 아직 자동 증명되지 않았으며 vLLM 런타임 버전과 구분한다.

**구현 구체화(아키텍트, 2026-09-10)**:
- 처리 프로필은 LLM 설정, 두 프롬프트 버전, 의미 그룹/영어 처리 버전과 입력 윈도
  정책을 캡처한다. 이 전처리 fingerprint가 embedding space 신원에도 들어가므로
  원문 임베딩과 LLM 번역 임베딩, 다른 LLM revision을 같은 공간으로 섞지 않는다.
- 원문은 실제 HybridChunker로 최대 512토큰(임베딩 한도가 더 작으면 그 한도)의
  앵커 있는 입력 단위로 나누고, 문서 순서의 최대 4단위 윈도 안에서 LLM이 의미 그룹을
  정한다. 윈도 경계를 넘는 전역 의미 최적화는 구현하지 않았다. 그룹 ID의 완전·유일·
  연속 커버리지를 검증한 뒤 그룹별 태그/요약/영어 번역을 구해 실제 청크로 발행한다.
- 번역문이 임베딩 토큰 한도를 넘으면 별도 파생 텍스트를 HybridChunker로 나눈다.
  각 조각은 원문 그룹의 source_units/앵커와 전체 번역문, 실제 embedding_text를
  보존한다. 번역문의 위치를 원문의 정밀 위치로 가장하지 않는다. LLM 출력이 잘리거나
  구조가 틀리면 실패 처리하고 이전 ready 세대를 유지하며 원문 처리로 폴백하지 않는다.
- API는 저장된 job/profile/revision으로 실행하고, 실제 발행 후 토큰과 최종 응답을
  재현한다. 같은 요청의 동시 호출은 IN_PROGRESS, 만료 claim은 새 세대로 복구한다.
  종료된 실패도 저장된 오류를 재현하며 재처리는 새 요청으로 명시한다.
- query는 같은 LLM 설정의 영어 번역 후 임베딩하며 원문/번역/query provenance를
  manifest에 저장한다. BM25+cosine RRF는 같은 검색 스냅숏의 현재 ready/컬렉션/공간을
  사용한다. vec0 KNN의 동점 cutoff 제약 때문에 현재는 승인된 정확한 scalar cosine
  전수 비교(O(N))를 사용하고 chunk ID로 동점을 정한다.

**함의**: P-03의 코드 연결·오프라인 계약 검증에 이어, 사용자의 재로그인 후

### D-012 — P-04 문서 어댑터 계약 (아키텍트 구현 선택, 2026-09-10)

`documents_v1` normalizer를 명시적으로 등록한다. Docling 2.126.0의 실제 PDF/DOCX/XLSX
변환 결과를 HybridChunker에 직접 전달하며, HWP는 별도 hwplib 1.1.11(JVM), HWPX는
검증된 package spine/XML 경로를 사용한다. 문서 의존성은 `[documents]` extra이며
PDF/EasyOCR 모델과 HWP jar는 명시적으로 준비한 로컬 경로를 지정한다. 입력 처리 중
조용히 모델을 내려받거나 다른 OCR/비전 제공자로 폴백하지 않는다.

프로필은 어댑터 버전·의존성 버전·모델/라이브러리 해시와 옵션을 캡처한다. 원본은
SQLCipher 리비전에 보존하고 정규화 구조에는 관측된 앵커와 추출 메타데이터를 함께
저장한다. PDF는 실제 페이지 영역, DOCX는 package member/XML XPath, XLSX는 실제
시트·셀/시트 영역, HWP/HWPX는 섹션·문단·표 경로를 사용한다. 추출/OCR/비전 결과에
원문 바이트 오프셋을 발명하지 않는다. 원본 이미지와 임베디드 리소스 바이트도 보존한다.

OCR는 Tesseract/EasyOCR를 명시 선택한다. 한국어 문장형 시험 이미지에서 Tesseract
PSM 3 자동 분할의 오인식을 확인해 PSM을 프로필에 노출했고 기본값은 6(단일 텍스트
블록)이다. 복잡한 페이지에 보편적으로 최적인 설정이라는 뜻은 아니다. 인식된 공백은
그대로 보존하고 공백 포함/제외 오류율을 함께 기록한다. 비전은 캡처된 LLM의 실제
이미지 입력을 사용하며 설명을 `inferred`로 표시하고 검색 결과에도 추론 여부를 노출한다.

변환은 메모리 입력을 사용한다. Docling의 Tesseract PDF OCR는 mode 0600 임시 PNG를
사용하고 finally에서 정리하므로 이를 저장 암호화와 구분해 검증한다. standalone
이미지 OCR는 stdin/stdout, HWP는 JVM stdin/stdout을 사용한다. ZIP 확장·셀·페이지·
이미지 픽셀 수를 제한하고 불완전/손상 변환은 실패시켜 기존 ready를 유지한다.
DOCX의 자동 LibreOffice 렌더링은 비활성화한다. 수식은 값/캐시와 구분해 보존하며
재계산하지 않는다. 형식별 지원 한계와 실제 테스트 결과는 P-04 검증 산출물에 기록한다.

**함의**: PLAN P04-01~P04-09의 구현·검증 기준. 카테고리 완료 후 STOP_READY로 정지한다.

**P-04 마감(2026-09-10)**: 오프라인 326개, 실제 GPU 9개 사례, 설치 CLI 10개 명령과

EasyOCR 모델과 HWP jar의 실제 해시를 프로필에 캡처한다. 비전 프롬프트 버전과

<a id="d-013"></a>
### D-013 — P-05 스냅숏·연결·확장 계약 (아키텍트 구현 선택, 2026-09-10)

`search --expand`는 검색과 같은 읽기 트랜잭션에서 확장한다. 별도 `expand --manifest-id`는
그 검색의 eligible 소스/리비전/세대·state_version·graph version과 컬렉션/모델 공간/
source_key·MIME 필터가 현재와 같을 때만 실행한다. 달라지면 `STALE_SNAPSHOT`으로
재검색을 요구한다. 삭제 후 복구처럼 콘텐츠가 같아도 상태가 변한 경우를 포함한다.
과거 결과는 `fetch manifest`/`fetch expansion`으로 historical 재현하며 새 탐색과 구분한다.

v5 스키마에 세대 소유 구조 연결·참조 의도·관측 위치와 확장 manifest를 저장한다.
발행 트랜잭션에서 원문/청크/색인과 함께 생성하며 실패 시 함께 롤백한다. v4 데이터는
원본/정규화 구조/앵커만으로 backfill하고 모델을 호출하지 않는다. 예전 검색 manifest는
변경하지 않으며 새 스냅숏 정보가 없어 확장할 수 없으면 `LEGACY_MANIFEST`로 알린다.
새 그래프 크기 한도를 넘는 기존 세대는 graph unavailable로 기록하되 기존 검색/원본/
manifest 접근은 유지한다. 새 발행은 그래프 생성이 완료돼야 성공한다.

구조 연결은 청크 순서, 실제 Docling heading/container 경로, 표/페이지/시트/대화 턴
앵커에서 만든다. 같은 그룹의 모든 쌍을 저장하지 않고 순서상 인접 멤버를 연결한다.
parent/child는 실제 섹션 계층의 첫 직접 소속 청크를 진입점으로 삼으며 해당 텍스트가
하위 내용을 전부 포함한다는 뜻은 아니다. 반복 제목은 문자열이 아닌 실제 node ref로
구별하고 heading fragment는 문서 순서의 고유 slug로 정한다.

명시적 참조는 원문 Markdown 링크, `[[source:정확한_source_key]]`, 원본 대화 텍스트의
링크/reply_to 및 Docling이 보존한 hyperlink에서 추출한다. LLM 번역/요약에서 링크를
발명하지 않는다. URI와 fragment는 같은 스냅숏에서만 해석하고 모호함/누락/미지원 문법은
미해결 참조로 반환한다. 상대 링크는 source_key 경로 또는 저장된 origin URI 기준이며
외부 URL/파일을 열지 않는다. heading, `/texts/...` 같은 node ref, `page=`, `sheet=`,
`frame=`, `turn=` fragment를 지원하며 대상 영역의 첫 청크로 연결한다.

`similar`는 명시적 opt-in이다. 같은 스냅숏·모델 공간에 있는 실제 저장 벡터의 exact cosine
top-N으로 계산하고 거리/모델 공간 및 `inferred` 분류를 남긴다. 구조/명시적 참조를 먼저
방문하고 청크 ID 방문 집합으로 순환·중복을 막는다.

예산은 시드까지 포함한다. 기본 깊이 1, 20청크, 8,000토큰, 256KiB, 256개 조사 연결이다.
토큰/바이트는 `evidence` 전체(원문·번역·앵커·경로·미해결 참조)를 정렬 키/공백 없는
UTF-8 JSON으로 직렬화한 값을 센다. 검색 profile의 로컬 캐시 토크나이저와 revision을
사용하며 특수 토큰을 넣거나 잘라 세지 않는다. API wrapper/usage/scope 메타데이터는
이 예산의 대상이 아니며, 다른 상위 모델의 토큰 수를 보장하지 않는다. 로컬 토크나이저가
없으면 명시적으로 실패하며 확장 과정에서 다운로드/모델 호출을 하지 않는다.
깊이/개수/토큰/바이트/연결 예산에 걸리면 사유와 소모량을 반환하고 임의 요약은 하지 않는다.

**함의**: P05-01~P05-05 구현·검증 기준. 사용자 지시대로 P-05 카테고리 마감 후 STOP_READY.

**P-05 마감(2026-09-10)**: CommonMark 참조는 Marko 2.2.4의 source span을 사용하고
CRLF 정규화 위치를 원문 문자 위치로 되돌린다. 코드 블록/인라인 코드의 링크를 따르지
않고, 괄호가 있는 URL·참조 정의·escaped source-key 표기를 검증했다. URI 정규화에서
예약 문자와 사용자 정보의 의미를 합치지 않는다. 그래프 구조 깊이/연결/참조 수 제한에
걸린 기존 데이터는 검색 가능한 상태를 유지하되 확장 불가 원인을 명시한다.

전체 오프라인 360개, 실제 GPU를 쓰는 설치 CLI 12개 명령, 별도 synthetic CLI 검증을
통과했다. 실제 결과는 5개 청크에 next/references/similar 경로를 포함했고 근거 payload는
10,757토큰/48,950바이트였다. [완료 기록](artifacts/p05-completion.json)에 계약·실행
근거·지원 한계를 저장했다. 사용자 지시대로 P-05 마감 후 STOP_READY다.

영구 삭제를 승인했다는 뜻이 아니다.

아키텍트 기준안은 [data-lifecycle-plan.md](artifacts/data-lifecycle-plan.md)이며,
새 기능은 sibling `feature-pack/rag-consumer/`에 배치한다(아직 생성하지 않음).

범위와 확장 범위의 완료 근거를 각각 대조하고, P10 매거진에 최종 검증 범위를 반영한다.

설계 선택: 소비자 SQLCipher 이벤트/상태 원장과 봉인 로그, core projection·memory 본문,
독립 활성 읽기 창. 수정삭제와 권한철회를 반영한 projection만 일반 검색에 내보낸다.
raw 보존·checkpoint 후 활성 참조만 퇴거하고, 원격 복제는 별도 내구성 정책으로 관리한다.
복원은 새 DB incarnation/restore_epoch와 최신 외부 원장 대조 전에는 읽기를 열지 않는다.
지침 후보는 인용 데이터로 남기며 에이전트 설정이나 상위 지침으로 자동 승격하지 않는다.

첫 connector·허용 경로·N/토큰·기억 승인·공유·retention·백업/내구성·영구삭제 요구는
P08A-01에서 데이터 소유자와 확정한다. 숫자/운영 값은 아직 사용자 승인값이 아니다.
group publish·core 메타 ACL 필터·hard purge가 필요하면 별도 core 변경 작업과 P-06
회귀 게이트를 등록한다. fixture 통과와 실제 connector 운영 완료는 구분한다.

**2026-09-27 v1.1 사용자 보완:** 대화·CS·에이전트 이력을 한 사건 한 JSONL 레코드로
기록하고, 안정 ID의 윈도우 문서를 연속 생성해 기존 DoclingDocument/HybridChunker 및
RAG 처리·검색 경로에 넣는 것을 기본 기능으로 명시한다. JSONL은 논리 기록 형식이며
운영 저장은 소비자 SQLCipher 암호화를 유지한다. 평문 JSONL 내보내기는 별도 권한 경로다.
최근 N개는 활성 컨텍스트 한도이며 전체 색인 보존 개수가 아니다. 밀려난 창도 현재
권한·수정삭제·보존 정책 범위에서 검색된다. 원문 히스토리 검색은 기억 추출 없이도
동작해야 하며, 그 위에 근거 인용형 기억·트러블슈팅을 구현한다. 윈도우 문서 한 개는
여러 검색 청크가 될 수 있다. P08A-03/04/05/07/08의 필수 완료 조건에 반영한다.
기존 v1.0 DA PASS는 이 보완분의 재검토나 구현 완료를 뜻하지 않는다.

**2026-09-27 v1.1 검토 대응 완료:** 사용자 선택은 현재 AI RAG 세션 이력과 기존 투어
문서로 확정했다. 3차 DA의 B4~B6에 대해 별도 발행 DB/컬렉션, 입력별 scope와 미확정
거부 조건, 실제 등록된 대화 profile key와 redaction r1을 계약에 고정했고 4차 PASS를
받았다. 투어 DB는 읽기 전용이며 재발행하지 않고 두 DB 결과는 구분된 그룹으로 제시한다.
tenant 실제 값·키 제공/교체/복구·retention·응답 tokenizer 등 미결 정책은 임의 승인하지
않는다. 합성·격리된 P08A-02/03 구현은 착수 가능하지만 이 판정은 실수집/운영 완료가 아니다.

### D-015 — 프로젝트 문서·코드 RAG와 Serena/LSP 연결 (사용자 추가 요구, 2026-09-27)

자체 프로젝트와 선택한 오픈소스의 문서·소스·테스트·스크립트를 색인하고, 변경을

구현 완료를 뜻하지 않는다. 상세는 data-lifecycle-plan.md §15에 기록한다.

### 2026-09-27 보존 정책 인터뷰 — 90일과 만료 삭제 개발

사용자는 대화 기억 우선 경험에서 “90일 보관을 목표로 하고, 만료 삭제 기능까지 개발
범위에 포함”을 선택했다. 이를 P08A-09 필수 항목으로 추가한다. 보존 시계의 기준,
기억/pin 예외, 백업 만료, 물리 purge/암호키 소거 방법은 후속 확정 대상이다.
기존 core의 논리 삭제를 영구 소거로 간주하지 않는다. 현재 자동 purge는 비활성이고,
이번 선택은 삭제 기능 개발 범위에 대한 것이며 기존 자료 즉시 삭제는 실행하지 않는다.

후속 선택: 90일의 기준은 각 메시지의 원래 작성 시각이다. 재수집/편집 시 보존 시계를
재시작하지 않는다. 이미 만료된 과거 기록은 신규 일반 색인에서 제외하며 원천 채팅 파일
자체는 삭제하지 않는다. 중요한 기억과 백업의 처리 정책은 아직 미정이다.

**최신 선택으로 위 영구 삭제 범위를 대체:** 사용자는 원문과 기억을 함께 활성 영역에서
만료시키되 별도 보존 승인 없이 모두 파일 아카이브로 남기고, 별도 조회 작업 때만
확인하도록 요청했다. P08A-09를 활성 만료·아카이브 전환·명시 조회로 바꾼다.
90일은 활성 이용 기한이며 아카이브 영구 삭제 기한이 아니다. 원래 입력 권한·마스킹과
암호화 저장을 유지하고 원천 파일을 변경하지 않는다. 아카이브 자체의 보존 기한은
후속 선택 대상이다. 아직 runtime archive/자동 삭제는 활성화하지 않았다.

아카이브 기한 후속 확정: 기한 없이 보관하고 사용자가 정리를 요청할 때만 처리한다.
자동 purge는 하지 않으며 모호한 정리 요청을 영구 삭제로 해석하지 않는다.

공유 범위 후속 확정: 같은 프로젝트의 본인 세션끼리 공유하고 다른 프로젝트는 분리한다.
현재 권한이 있는 명시 등록 세션만 대상으로 하며 아카이브에도 같은 경계를 적용한다.
공유 정책 선택을 미등록 세션의 자동 수집이나 외부 사용자 공유 승인으로 확대하지 않는다.

키 제공자 후속 확정: 사용자는 1Password를 선택했다. 접근 방식·항목 참조·복구/교체는
미결이며 실제 항목 생성/조회나 기존 투어 키 이전은 수행하지 않았다.

최신 키 접근 선택으로 위 직접 연동을 대체: 에이전트 없이 실행되도록 시작 시
환경변수로 키를 주입한다. AIRAG의 1Password 직접 연동은 필수 범위에서 제외한다.
키 미제공/형식 오류는 저장소 생성·열기 전 거부하며 자동 키 생성·폴백은 하지 않는다.
키의 외부 보관/복구와 백업은 아직 미정이다. 실제 환경변수 설정이나 키 이전은 없다.

백업 담당 확정: AIRAG가 매일 지정 경로에 암호화 백업을 만들고 사용자가 외부 복제와
키 보관을 맡는다. 백업에는 키를 포함하지 않는다. 예약 실행은 core 밖의 운영 계층
책임이며 목적지·시각·백업 보존 정책은 후속 확정한다. 실제 예약 작업은 생성하지 않았다.

백업 기본 목적지 확정: `~/.local/share/airag/backups/<project-id>/`.
프로젝트별로 분리하며 실행 시 project-id의 경로 안전성을 검증한다. 실제 디렉터리는 아직 생성하지 않았다.

백업 시각 확정: 매일 한국시간 오전 3시(Asia/Seoul). 실행을 놓쳤으면 다음 실행에
현재 상태를 1회 보충한다. 누락 날짜별 반복 백업은 하지 않으며 성공 검증과 중복 방지를 적용한다.

복구용 백업 보존 확정: 최근 30일분을 보관하고 새 백업 검증 성공 후 오래된 백업을
자동 정리한다. 사용자 승인은 지정 프로젝트 백업 경로의 AIRAG 소유 만료 백업으로
한정한다. 주 아카이브·원천 데이터·키에는 적용하지 않으며 검증 실패 시 정리하지 않는다.
최소 한 개의 검증된 백업과 복원 사용 중 세트를 보호한다. 실제 자동 정리는 아직 비활성이다.

검증 수준 확정: 매일 새 백업을 격리 임시 경로로 복원하여 DB 무결성과 원장/아카이브
연결까지 검사한다. 운영 데이터는 덮어쓰지 않고 복원 시험에서 수집/발행을 하지 않는다.
공간 부족을 포함한 검증 실패는 새 백업 성공 처리와 오래된 백업 정리를 모두 막는다.

첫 완료 기준 확정: 대화 검색·기억·운영까지. 실제 선택 입력에서 과거 근거 회수,
결정/해결책 기억,90일 활성 만료와 파일 아카이브, 일일 암호화 백업·임시 복원 검증·
검증 성공 후30일 만료 백업 정리까지 확인해야 완료다. P08A-10을 운영 백업 작업으로
추가한다. 자동 에이전트 주입과 프로젝트 코드 RAG/Serena는 후속 범위에 유지한다.
