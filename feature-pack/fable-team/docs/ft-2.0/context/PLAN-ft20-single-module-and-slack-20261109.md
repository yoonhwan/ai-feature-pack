## 2.0.0 신규 구성과 레거시 격리 (사용자 방향 확정)

사용자 원문: «2.0.0은 기존 도구들 전부 이동 격리하고 히스코리 커밋한뒤 기존 도구는 코드만 참고해서 새로 구조와 파일을 새로 만들자. 안쓰는것들은 일일히 제거하는것보다 2.0에서 신규로 만드는게 빠르겠다.»

방향: 기존 도구 전체를 보존·격리한 뒤, 2.0의 팀 도구·상태 계약을 기준으로 새 구조와 파일을 만든다. 기존 코드는 기능과 검증 사례를 이해하는 참고 자료다. 구현 속도가 더 빠를지는 아직 측정한 사실이 아니다.

1. 먼저 소스·패키지·설치본·팀별 실행 진입점의 실제 범위를 조사해 기준 commit과 차이를 남긴다. 비밀값·개인 세션 로그·운영 상태를 도구 코드와 섞어 Git에 넣지 않는다.
2. 변경 전 기준을 Git에 보존한다. 격리용 checkout에서 기존 도구 이동을 별도 구조 commit으로 남겨 원래 경로와 새 보존 위치를 추적한다. 보존 위치와 정확한 파일 목록은 arch의 기존 조사에 맞춰 확정한다. 현재 운영 중인 설치본은 준비 과정에서 이동하지 않는다.
3. 2.0 활성 소스·파일 구조는 새로 작성한다. 격리된 1.x 도구는 실행·import·자동 fallback의 의존 대상으로 쓰지 않는다. 옛 도구를 전부 새 이름으로 복사하지 않고 필요한 동작을 공통 코어에 대응시켜 검증한다.
4. 기존 핵심 기능은 arch·DA·checker가 계승·통합·제외 근거를 대조한다. 누락을 막기 위한 대응 기록이며, 레거시 코드를 하나씩 삭제하는 작업을 완료 조건으로 삼지 않는다.
5. 진행 골·대기 요청·미확정 효과·결정·메모리·문서·원장·BTS·Git 근거는 별도의 상태/자료 이관 대상이다. 코드 재작성은 이들의 삭제·초기화·완료 처리를 뜻하지 않는다.
6. 전환 때는 기존 writer와 실행 진입점이 새 상태에 쓰지 못하도록 확인하고, 새 입력을 보존한 채 상태를 이관한다. 같은 골을 두 runtime이 동시에 실행하지 않는다. 되돌림도 전환 후 생긴 입력·결정·효과를 보존해야 한다.
7. 격리 실험 뒤 제품 구현·ft 랜딩·BYZ 설치/이관·설치본 checker의 골 접수→진행→문서/원장/BTS→Git/Issue→마감·재개 확인까지 완료한다. 신규 구조라는 이유로 기존 완료 관문을 생략하지 않는다.

기존 기획과의 관계: `PLAN-file-memory-tree-generalize-20261109.md` @ `97f84ede64`의 그룹 일반화·추적 가능한 근거·유한 읽기·진행 자료 보호는 이어받는다. 기존 도구의 경로를 유지하고 env만 바꾸는 단계2~6을 2.0 구현 방식으로 그대로 적용하지 않는다. 1.x에서 별도 승인된 작업의 범위는 바꾸지 않으며, 2.0의 새 경로·도구·이관 계약은 기존 PLAN과 대응해 갱신한다. `indices/`·기존 팀 루트 유지 같은 1.x 호환 제약이 새 2.0 구조에도 필수인지는 arch·DA가 구분한다.

현재는 방향의 확정과 기획 갱신이다. 앞서 사용자와 정한 풀스펙 HTML 확인·명시적 컨펌 뒤 제품 구현 관문은 유지한다. 이 문서 작성으로 실제 레거시 도구 이동·새 제품 구현·운영 전환이 수행된 것은 아니다.

### BYZ 배포·랜딩의 무유실 준비와 팀별 재개 관문

사용자 원문: «2.0 신규 구성은 절대 유실이 있으면 안된다. byz 배포 랜딩할때 각 팀장은 모두 활성 2.0 준비 마이그레이션. 대화 기록과 정지전 기록과 골카드 정렬 정리 필요. 아카이브를 뒤져서라도 정상화. 신규 2.0을 이해한상태에서 진행으로 작성.»

무유실은 전환의 필수 요구사항이며 현재 달성됐다는 선언이 아니다. 확인할 수 없는 원자료나 미해결 대조가 남으면 이관 완료로 처리하지 않는다. 사용자 컨펌 이후 실제 BYZ 배포·랜딩 준비에서 다음 순서를 적용한다.

1. **전 팀 준비 활성화:** planner가 모든 하네스 루트의 팀 목록과 책임 팀장을 확정한다. 현재 열린 세션만으로 팀 범위를 정하지 않는다. 정지·휴면 팀도 포함해 모든 팀장이 활성 상태에서 자기 팀의 2.0 준비를 담당한다. 원래 세션이 없으면 기록을 인계받은 후계 팀장을 명시하고 준비 확인을 받는다.
2. **정지 전 상태 보존:** 팀별 대화 원문·정지 전 기록·인계서·골·카드·미처리 쪽지·외부 대기·미확정 효과·결정·문서·원장·BTS·Git 참조를 원래 위치/ID/버전과 연결한다. Git에 없는 대화 원문도 별도 안전한 보존 위치와 무결성 근거를 남긴다. 요약본으로 원문을 대체하지 않고, 비밀값과 개인 기록을 공개 Git에 올리지 않는다.
3. **아카이브까지 회수·정렬:** 현행 파일과 정지 전 기록이 맞지 않으면 아카이브·이전 세대 인계·대화 이력·Git 이력에서 근거를 찾는다. 최초 요청→결정→작업→검증→남은 일의 연결을 복원하고 골·하위 골·카드·담당·상태·다음 행동을 정렬한다. 명시적 취소·대체도 원문 근거로 남긴다. 오래됐거나 아카이브에 있다는 이유로 완료/폐기하지 않는다.
4. **원본과 대상의 대응 대조:** 원본 항목마다 대상 경로/ID 또는 보존된 원문 참조를 연결한다. 개수·ID·원문 보존 hash뿐 아니라 열린 요청, 결정, 담당, 진행/대기/미확정 상태와 증거 참조의 의미도 대조한다. 읽기 실패·원본 소실·상충하는 기록·담당 미확정은 미해결 항목으로 기록하고 담당자를 둔다. 추측으로 채워 통과시키지 않는다.
5. **2.0 이해와 준비 확인:** 모든 팀장은 확정된 2.0 문서 버전, 공통 팀 도구·상태 정본, 사건 기반 진행/300초 확인, 작업 중 전달 보호, 문서·원장·BTS·Git 완료 관문을 확인한다. 자기 팀의 골·카드 대응표와 첫 재개 행동을 기록하고, 격리된 재개 점검 결과를 남긴다. 단순 «읽음»이나 세션 생존만으로 준비 완료가 되지 않는다.
6. **전환과 독립 확인:** 새 입력을 보존하고 구 writer/이중 실행을 차단한 뒤 전환한다. checker가 원본·대상·준비 기록을 대조하고 설치본의 실제 재개를 확인한다. 부분 갱신·누락·미확인이 있으면 해당 팀은 복구/보완 상태로 남기며 전체 BYZ 이관 완료를 선언하지 않는다. 되돌릴 때도 전환 뒤 접수·결정·효과를 잃지 않는다.

팀별 준비 원장에는 기존 체계를 사용해 팀/루트, 책임 팀장, 원본·아카이브 참조, 골·카드 대응, 미해결 대조, 2.0 문서 버전, 첫 재개 행동, checker 근거를 연결한다. 별도 경쟁 원장을 신설하지 않는다. 모든 팀의 준비 확인과 무유실 대조가 모여야 전체 BYZ 배포·마이그레이션 완료로 기록한다.

## 공통 모듈의 동작

### BYZ 특수팀의 기존 역할 확인

사용자 지적에 따라 이슈팀이 누락된 입력 설명을 대조했다. 옛 GOAL 원문11·PROPOSAL의 issue-manager 시작 노드 설명은 출처 이력으로 보존하되 현행 운영 정본으로 쓰지 않는다. planner arch275633 확인 후 `design/teams/planner/GUIDE-planner.md` @ `eb2d525a90`와 `main-team-governance.md` §2를 직접 대조했다. 현행은 issues의 분류안/추적/등록·배분 집행과 planner의 사용자 협의/분류 결정/팀 배정을 구분하며, 논의가 끝난 신규 기획은 planner가 직접 구현 배정한다.

| 팀·접점 | 확인한 기존 책임 | 2.0 설명에 반영할 경계 |
|---|---|---|
| 이슈팀 | 이슈 접수·모니터·재현 조사·분류/우선순위안·원장. 승인된 배분·추적·배분 코멘트·완료 검사·닫기 | 업무 관리의 특수팀이다. 신규 기획의 논의 완료 경로에서는 Issue 등록과 배분 기록을 맡고 planner가 구현 배정한다. |
| planner | 사람 협의·골/팀 구조·분류 결정·우선순위·예외·HIL·팀 배정 | 기존 이슈는 issues의 안을 사용자와 정렬하고 값을 회신한다. 논의 완료된 신규 기획은 직접 작업팀에 배정한다. 이미 주어진 사용자 승인을 무시하고 반복 확인하는 뜻은 아니다. |
| harness | 하네스/스킬 모니터·개선 접수·구현/검증 조직·패키지/머신 배포 | 하네스 개선의 직접 접수 경계를 유지하고 일반 업무 접수와 혼동하지 않는다. |
| 작업팀 | 맡은 골의 NW 작업·검증·문서/원장/BTS·Git 정본화 | 결과를 이슈팀의 완료 검사와 상위 골 판정에 연결한다. |
| Slack 접점 | 메시지의 업무 종류와 thread 연결·권한에 따라 목적지 식별 | 모든 메시지를 이슈팀 모델이 다시 해석하는 중계로 만들지 않는다. 기존 thread owner 직행은 옛 요구 기록은 있으나 현재 운영 정본은 미확인이다. 2.0의 binding 경로와 구분한다. |

이는 새 특수팀을 만드는 제안이 아니라 기존 BYZ 역할의 복원이다. 일반 코어는 동일하고 팀별 책임/권한/입력 정책이 다르다. GitHub Issue의 업무 원문·대외 추적 책임과 파일 기반 실행 상태의 책임도 구분해야 한다.

현재 운영 확인 범위: 루트 `.fable-team/seats-issues.json`은 master `byz-issues-master-sol#58`, arch `byz-issues-arch-claude#10`을 가리키며 이번 tmux 조회에서는 둘 다 없었다. 팀 폐지나 자동 라우팅 성공의 근거로 쓰지 않는다. planner arch275633은 현행 유휴 팀 종료/재개 규칙상 닫혀 있을 수 있음을 확인했다. 275629→275633으로 최신 역할을 확인했고 옛 «planner 발주0» 인용은 위 현행 경계로 정정했다. r1500에는275636으로 전달했다. 입력 라우팅의 실제 실행 검증과 thread owner 직행 정본은 아직 별도 확인 대상이다.

1. 입력 어댑터가 사람·부모팀·도구의 사건을 인증하고 목적 팀/골/주제를 찾는다.
2. 팀 모듈이 짧은 팀 잠금 안에서 중복키·owner 세대·revision·용량을 검사한다. 성공한 접수를 영속 기록한 뒤 업무 접수를 알린다. transport ACK와 업무 접수는 별개다.
3. 규칙만으로 처리 가능한 전이는 도구가 처리한다. 판단이 필요한 묶음만 역할 세션을 연다/재개한다. 잠금 안에서 모델·외부 API를 기다리지 않는다.
4. 팀장은 골·범위·완료 책임, arch는 작업 분해·배정 판단·NW 관리·통합·검증 설계와 진행, DA는 계약 반증, checker/tester는 구현자와 분리된 검증을 맡는다. 배정 전이의 집행은 공통 비모델 명령이 맡는다(arch275576 반영). 역할 검토 순서는 작업 계약에 맞추며 매 사건마다 모든 모델을 호출하지 않는다.
5. 작업 직전 실행권을 다시 검사한다. 응답·생존·실제 진척은 다른 값이다. 진척 사건은 무진행 시한을 갱신하며 300초 경과만으로 작업 종료나 재실행을 결정하지 않는다. 작업 중 보호와 외부 대기를 함께 검사한다.
6. 외부 효과 뒤 기록 전 중단은 UNCERTAIN으로 남긴다. 관측으로 확인하기 전 자동 재실행하지 않는다. 파일 잠금만으로 임의 외부 명령을 차단한다고 주장하지 않는다.
7. 검증 뒤 checker/tester가 실제 BTS 관측과 원자료를 남기고, arch가 아키텍처 정본을 실제 결과와 맞춘다. 공통 도구로 작업·랜딩 원장을 갱신하고 코드/실관측/문서/원장의 정합을 대조한다. 과정·판정·잔여·근거 파일/절/commit을 연결하며, 정본의 main 착지와 Git Issue 연결까지 확인한다. 기록 누락·불일치·부분 갱신이면 완료하지 않고 기록 보완으로 돌아간다. 여러 파일 쓰기를 자동으로 하나의 원자 트랜잭션이라고 가정하지 않는다.
8. 문서·원장·BTS 정합을 포함한 검증·판정·필요한 착지/설치 근거와 진행·대기·미확정 0을 같은 revision에서 검사한다. 새 골이 끼면 마감을 거부한다. 완료 이력을 기록하고 세션/좌석을 정리한다.
9. 부모팀은 자식 결과 사건을 같은 접수 절차로 받아 자기 골을 판정한다. 자식의 진행 중 대화 전체를 반복 수집하지 않는다. 새 골은 같은 팀 설정과 기록을 찾아 재개한다.

문서·원장·BTS는 사용자 정정으로 복원한 기존 핵심이다. 근거: `main-team-governance.md` §8(정본 main 착지와 Issue 파일#절@sha), `design/BTS-N-ROUND-LOOP-STANDARD.md`(arch 루프 소유, checker 실관측·raw), `context-management.md`(단계 전이·판정 수신·상태 변화·블록 때 원장 write-through). 최종 단계에서만 원장을 몰아 쓰지 않는다. BTS 증거는 대상에 맞는 실제 실행 관측이며, 모형 결과를 실 Slack/실 설치의 BTS로 바꾸어 부르지 않는다.

사용자 추가 정정: 문서·원장·BTS를 추가하며 기존 Git 표시를 대체하면 안 된다. 공통 모듈에 독립된 Git·Issue 라인을 유지한다. 파일 기록 → 로컬 검증 → 관련 산출 commit·원격 branch push → 통합 검증·main 착지 → 필요한 설치 검증 → 랜딩 원장/정본 반영과 Issue 파일#절@sha 연결 → 완료다. 작업 branch push와 main 착지, 소스 착지와 실설치, runtime heartbeat와 Git 완료 근거를 구분한다. 코드와 기록 착지가 별도 commit이어도 둘 다 추적하며 기록이 빠지면 완료하지 않는다. HTML에 Git·정본화 시퀀스를 추가했다.

대시보드는 정본에서 만드는 파생 화면이다. 역할별 좌석과 세대·세션·마지막 응답·진척·대기 이유를 표시하되 대시보드의 빈 자리만 보고 골 완료를 판단하지 않는다.

## Slack: 사용자 승인된 조사·실험·평가

### 반복 호출과 컨텍스트 재독의 금지 조건

사용자 추가 요구: 전체 대화/컨텍스트 재로드, 무분별한 LLM 분류기, 틱마다 팀에 보내는 상태 메시지로 세션 한도를 소모하지 않는다. 유휴·중복·무변화 사건은 비모델 도구에서 처리하며 이 사유의 모델 호출·세션 깨움은 0이어야 한다. 기존 binding과 상태로 목적지를 결정하고, 업무 판단이 필요한 새 입력만 해당 thread의 변경분·필요 근거와 함께 전달한다. 작업 중인 NW에는 무의미한 재촉이나 전체 컨텍스트를 주입하지 않는다.

실험은 실제 역할 세션의 요청 수, input/output/cache read/cache write, 컨텍스트 재독량, 불필요한 깨움, 지연과 업무 결과를 함께 측정한다. API 읽기 감소나 합성 prompt 비교만으로 운영 절감 판정을 내리지 않는다. 정상 새 업무의 판단·누락 복구가 막히지 않는지도 검사한다. 현재는 요구조건이며 실측 통과나 제품 구현 완료가 아니다.

### journal·JSONL의 유한 보관과 비모델 관리

사용자 추가 요구: 모든 journal·JSONL 파일은 용도에 맞는 유한 cap 안에서 회전한다. 읽기·절단·회전·정리는 스크립트만 수행하며 이를 위해 LLM을 호출하지 않는다. 현재 상태 조회는 최신 유효 상태본과 필요한 tail 범위로 제한한다. 최신 한 줄이 모든 진행 골·미처리 사건을 대신한다는 뜻은 아니다.

arch는 파일별 byte cap, 레코드 크기 상한, 필요한 경우 고정 segment 개수와 전체 상한을 정하고 근거를 제시한다. 단일 파일의 head 절단·교체와 고정 개수 segment 회전을 비교하되 운영 방식을 여러 개 덧붙이지 않는다. 동시 append, 절단 도중 crash, 부분 레코드, disk FULL에서도 접수한 사건과 최신 유효 상태를 잃지 않아야 한다. 열린 골·대기·미확정·복구 근거가 cap을 초과하면 미처리 자료를 버리지 않고 명시적 포화로 신규 접수를 제어한다.

완료 근거·결정 요약의 Git 보존은 기존 사용자 결정대로 유지한다. 회전 대상에서 필요한 근거를 보존한 사실을 확인한 뒤 오래된 상세 로그를 밀어낸다. Git 이력 증가 허용과 실행 journal·JSONL의 유한 상한은 별개다. 정확한 cap 숫자와 교체 방식은 아직 미결정이며 기획·반증·풀스펙 컨펌 뒤 구현한다.

사용자 추가 확정: Slack의 기획·시스템 실험·독립 검증·랜딩 결과를 **ft 2.0 업그레이드의 메인 축**으로 포함한다. Hermes는 참고 대상이며 새 코어의 실행 의존성으로 채택하지 않는다. 기존 Slack 봇/앱 자산을 재사용하거나 전용 신규 앱·봇을 추가해 토큰과 Socket으로 연결하는 선택은 모두 허용됐다. 구체 자산은 필요한 scope·workspace·채널·연결 소유권·기존 수신과의 충돌을 확인해 정한다. 재사용은 기존 gateway의 LLM 중계나 경쟁 Socket 연결까지 승인됐다는 뜻이 아니다. 비밀값은 문서·대화에 기록하지 않는다.

Slack 축의 완료는 단순 모형 통과가 아니라 확정 계약, 독립 checker, 실제 허용 채널의 양방향·thread 분리·복구 근거, ft 패키지 랜딩·설치본 대조, 로컬 doctor/개선 루프 연결까지다. 실제 신규 앱/토큰 제공 등 사용자의 손이 필요한 단계는 선택안과 필요한 행동이 구체화된 뒤 요청한다. 기존 기획 우선 순서와 2.0 제품 구현 전 풀스펙 컨펌 관문은 유지한다.

실제 FT 카드/tmux의 Pi 엔진, Opus 모델을 명시한 별도 나노를 요청했다(275542, master 확인275544). 조사만으로 끝내지 않고 격리 실험과 독립 Pi checker 평가까지 진행하도록 추가 전달했다(275545). 실제 개설·모델·진행 여부는 별도로 확인한다.

### 기존 로컬 Slack 연결을 이용하는 후보안 (사용자 검토 요청)

사용자 제안: Hermes와 byzmini 아이나가 로컬에 팀처럼 존재하고, Slack message/thread/channel ID 기반의 연결 풀로 양방향 통신하며 공통 팀 도구에 배정·전달하는 방식. 실제 프로그램 이름·프로세스·저장소·현재 입출력은 NW가 확인한다. 존재한다는 사용자 설명을 연결 재사용 가능성까지 검증된 것으로 확대하지 않는다.

- 연결 키 후보는 workspace/channel/root-thread이며 팀·골·주제·논리 컨텍스트·owner에 대응한다. message/event ID는 중복 접수와 회신 연결용으로 따로 사용한다. 연결 풀을 공유해도 thread의 모델 컨텍스트를 공유하지 않는다.
- 기존 gateway의 수신 사건을 비모델 어댑터가 공통 팀 도구에 접수하고, 필요한 업무만 역할 세션에 배정하며 출력 어댑터가 원래 thread에 응답하는 안을 우선 비교한다. 로컬 연결 관리가 매 메시지마다 별도 LLM 중계를 요구하지 않도록 한다.
- 기존 gateway 재사용과 별도 수신의 실재 근거·변경 범위·중복 소비 위험을 비교한다. 운영 gateway의 Socket 토큰으로 경쟁 연결하지 않는다. 기존 ft 실행도구를 새 코어에 묶는 것과 외부 통신 접점을 사용하는 것은 별도 검토한다.
