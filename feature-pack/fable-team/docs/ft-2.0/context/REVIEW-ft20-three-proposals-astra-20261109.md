## 메인의 첫 비교: 실행 전 설계 반례

### Fable 안

1. 디스크 상한·만료 경계: §5는 Git 무한·접수 정책 없음, 살아 있는 좌석 events는 회전하지 않는 보완을 제안한다. 긴 작업/입력 폭주로 유한 디스크가 차면 접수 성공과 기록 보존을 동시에 유지할 수 없다. 사용자 요구인 쌓이지 않는 보존 계약도 미완이다. 총량 상한·미접수 응답·재시도 세대와 미처리 보호를 명시하기 전 이 항목은 통과할 수 없다.
2. owner·효과 경합: A가 binding 검사 통과 → A 멈춤 → 라우터가 A 사망 판정·claim 삭제 → B claim → A 재개·외부 효과 실행. running 전/완료 후 검사만으로 A의 in-flight 효과는 취소되지 않는다. O_EXCL 카드 승자 1회도 이 순서를 검증하지 않는다. 구효과가 해소될 때까지 후계 효과를 막거나 상대 시스템의 fencing/멱등 계약이 필요하다. 단순 kill은 외부 효과 완료 여부를 알려주지 않는다.
3. 되돌림·서로 다른 정본의 마감: 플래그를 돌리고 양쪽에 사건을 남기는 것만으로 전환 뒤 완료/미확정을 옛 큐가 중복 집행하지 않음을 보장하지 못한다. Git 관측 sha도 runtime accepted/unknown·Slack 입력의 일관된 snapshot이 아니다. 전환 뒤 최신 상태의 역변환과 마감/새 접수 경합을 같은 revision 또는 재검증 계약으로 정해야 한다.

### DA 안

1. 유한 보관과 옛 입력: producer watermark·퇴역 세대 보관은 좋은 출발이지만 생산자 재설치와 세대 삭제 시 오래된 입력을 새 골로 재수락하는 경계를 시험해야 한다. 만료 키 재시도에 예전 결과를 돌려줄 수 없는 경우의 응답(명시 만료/거절)도 명세해야 한다. 무제한 dedupe 원장이 생기면 유한 상한 실패다.
2. 권한 강제: §4는 임의 Bash 외부 쓰기가 허용되면 owner 효과 계약 불성립을 명시했다. 실제 실행 어댑터·도구 권한으로 막을 수 있는지 aifp-ft 확인 전에는 보호 통과 판정을 할 수 없다. 같은 위험은 Astra 안에도 있다.
3. 전체 JSON 교체 비용·접수 포화: 1MiB 상태를 4개 프로세스가 각300회 갱신할 때 지연·총 bytes와 root/팀 FULL 경계를 측정해야 한다. 데이터 무결성이 통과해도 성능 목표를 넘으면 후보를 수정한다. 현재는 미측정이며 이미 실패했다고 판단하지 않는다.

### 현재 Astra 자기 반증

1. journal+snapshot+manifest는 단일 JSON보다 복구 상태와 crash 지점이 많다. 같은 규모에서 읽기/쓰기 이점이 입증되지 않으면 단순함 기준에서 이 부분을 버린다.
2. team lock의 owner 검사는 외부 효과 fencing이 아니다. 실행 어댑터 통제와 미확정 후계 차단이 실제로 연결되지 않으면 통과하지 못한다.
3. 접수 키·완료 결과의 만료 세대 정책과 용량 상한은 아직 숫자·상태 전이 표가 부족하다. 작동하는 보존 계약을 보완하기 전 실험 구현자가 임의로 채우면 안 된다.

현재 추천은 **DA의 팀별 원자 JSON 후보를 먼저 최소 실험**하는 것이다. 이유는 세 안 중 동일 팀의 접수·owner·결과를 한 상태 교체로 다루어 복구 경계가 가장 적기 때문이다. 비용·권한 통제·보존 반례 통과 전 승자 또는 최종안은 아니다. Fable의 파생 대시보드와 일회성 작업자는 비교할 구조 선택이며 근거 없이 승계 전부를 제거하지 않는다. 혼합 변경은 새 버전으로 재검증한다.

## 다음 단계에서 만들 실험의 경계

공통 사례를 충족하도록 각 안을 몰래 보완하지 않는다. 원안에 빈 계약이 있으면 «명세 미완»으로 분류한다. 원안 시험과 수정 후보 시험의 결과를 섞지 않는다.
