# ft 2.0.0 전환 목표

상태: 리서치·설계 검토·격리 실험 단계. 2.0.0 랜딩·실환경 마이그레이션 완료가 아니다.

## 구현 시작 전 사용자 확인 게이트

사용자 확정(2026-11-09): 기획·시뮬레이션·반증을 완성하고 하네스 시스템 풀스펙 HTML을 공개한다. HTML에서 ft 랜딩·BYZ ft 설치 후 팀의 전체 운영을 사용자가 완전히 이해한 뒤 명시적으로 컨펌해야 제품 구현을 시작한다.
컨펌 전 범위는 설계·문서·리서치·격리된 기획 검증 실험이다. 제품 코드 구현·운영 설정 변경·실제 배포/설치/마이그레이션은 시작하지 않는다. HTML의 설치 후 흐름은 예상 운영이며 실제 적용 완료와 구분한다.
이후 순서는 사용자 컨펌 → 제품 구현·검증 → ft 2.0 랜딩 → 실제 ft/BYZ 설치·마이그레이션 → 설치본 checker 검증이다. 전체 골의 완료 범위는 그대로 유지한다.
게이트 정본: `design/harness/research/ft-2.0/GATE-ft20-full-spec-before-implementation-20261109.md`. 사용자 원문과 질문 답변은 `/tmp/ft-2.0/INTERVIEW-ft20-decision-20261109.md`.

HTML 공개 규칙: 업데이트마다 파일을 다시 열어 사용자가 변경을 바로 볼 수 있게 한다(사용자 직접 지시).

## 목표

ft/BYZ의 검증된 기반과 레거시의 강점을 계승하여, 파일 기반 골·메모리·역할 상태·작업 전달·모니터링·마감이 일관되게 이어지는 ft 2.0.0을 완성한다.

최소 planner 팀과 작업팀으로 파일 기반 하네스와 중앙 프로시저를 실험한다. arch·DA·checker가 기존 기획, 동작 반례, 실험 근거를 검토한다. 사용자와 대안을 선택하고 운영법을 결정한 뒤 2.0.0을 랜딩한다. 랜딩 후에도 ft/BYZ 실제 환경의 폴더·파일·팀 설정을 마이그레이션하고 checker의 동작 검증까지 완료한다.

## 설계 원칙과 사용자 지시

### 2.0.0 루트 지침: 작고 완전한 일반화

인터뷰 확정(2026-11-09): 완료 근거·결정 요약은 Git에 보존하며 Git 이력 증가는 허용한다. 상세 로그만 용량 상한으로 회전한다. 진행·대기·미확정·현재 복구 기록은 보호한다. 보존 용량 숫자는 아직 미확정이다. 질문·사용자 원문은 `/tmp/ft-2.0/INTERVIEW-ft20-decision-20261109.md`에 기록한다.

세션 수명은 실험으로 결정한다: planner·작업팀 모두 판단 묶음마다 재개하는 후보와, planner 팀장은 유지하고 작업팀만 묶음별 재개하는 후보를 비교한다. 앞선 일회성 선택만으로 확정하지 않는다. 재개 안전성과 실제 컨텍스트·토큰·캐시·지연 근거를 비교하고, 비용 미측정은0으로 쓰지 않는다.

사용자가 원하는 강력함은 크기와 장치 수가 아니라 일반화에 기반한 작고 컴팩트하며 완전한 구조다. 이를 2.0.0의 루트 시스템 지침으로 삼는다.

- 문제마다 스크립트·크론·훅·예외를 덧붙이는 1.x식 누적을 반복하지 않는다.
- 공통 상태·작업 전달·메모리·감시·복구·마감의 일관된 모델을 먼저 정하고 검증한다.
- 운영·관리도 같은 모델과 공통 도구로 처리한다. 새 기능이나 수정은 공통 모델에 통합하며 중복 경로를 계속 남기지 않는다.
- 단순함은 기능 누락을 뜻하지 않는다. 필요한 동작과 실패·재개·종료 조건까지 완결된 최소 구조를 지향한다.
- 설계 선택과 변경 때 구성 요소·상태 정본·상주 작업·예외 경로·모델 호출과 컨텍스트 읽기 비용을 함께 비교한다.
- 유지보수의 목적은 검증된 공통 모델과 컴팩트함을 유지하는 것이다. 장치를 추가하는 것만으로 결함을 덮지 않는다.

사용자 원문 요지: «가장 강력한 건 일반화를 기반으로 한 작고 컴팩트하지만 완전한 시스템», «누더기로 추가하는 게 아닌 전체 일반화 그 완성 모델을 검증하고 유지하고 컴팩트를 유지».

### 협업과 검토 방식

- 최신 사용자 결정: 현재 Astra 세션이 메인을 맡아 Fable·DA·현재 Astra의 독립 기획 3개를 수합하고 오케스트레이션한다. 완료된 같은 레포 조사와 정정 근거를 모두 제공하고, 각자 완결된 안을 작성한 뒤 교차 반증·동일 시뮬레이션으로 비교한다. aifp-ft master는 일반화·현재 구현·설치 상태 확인을 지원한다.
- 비교 절차와 공통 입력: `/tmp/ft-2.0/three-proposals-brief.md`. 세 원안과 비교 결과를 공개하고 사용자와 선택한 뒤 확정본을 공개한다. 현재 세션의 안도 같은 기준으로 검증하며 자동으로 정답 취급하지 않는다.

- 사용자와 현재 Astra 세션이 설계 정렬·대안 비교·선택·오케스트레이션의 중심을 맡는다. 각 역할의 독립 근거를 합치되 사용자 제안, 우리 초안, 외부 저장소 어느 것도 정답으로 가정하지 않는다.
- 협업 구성: 하네스 arch(Fable)의 기획, DA(Astra)의 반박, Pi 나노의 분석·실행, tester/checker의 독립 검증, 실제 프로젝트 담당 `aifp-ft-master-pi#1`의 맥락과 구현 경로를 연결한다.
- 실제 프로젝트 담당은 파일·기존 구현·설치·운영 맥락과 적용 제약을 제공한다. 아직 선택하지 않은 설계를 먼저 제품에 적용하지 않는다. 구현 책임과 발주 범위는 사용자 선택과 역할 합의 뒤 구체화한다.

- 사용자 설명은 검토 입력이다. 그대로 최종 답으로 확정하지 않는다. 리서치·arch·DA·checker 의견과 실험 결과를 반영해 사용자와 선택·결정한다.
- 기존 기획에 매칭하여 유지·변경·대체 지점을 남긴다. 중복 기획을 양산하지 않는다.
- 더 단순하고 검증 가능한 구조라면 큰 전환도 비교한다. 기존 설계를 유지하는 것 자체가 목표가 아니다.
- OMO와 gajaecode 저장소의 메모리, 하네스 작업 전달, 모니터링, 관리 방식을 분석한다. 정확한 저장소와 commit을 먼저 확인한다.
- 리서치 정본: OMO는 `https://github.com/code-yeongyu/oh-my-openagent`의 `511dc35e22a7c4e2cebb8f0c5bab74b8660dc430`, gajae-code는 사용자가 지정한 `https://github.com/Yeachan-Heo/gajae-code`의 `b4127889c4a849133f868cbf8f4d5a65126baec4`를 최초 비교 기준으로 고정한다.
- Slack 통신도 조사한다. 수신·명령 분류·팀/세션 라우팅·thread 연결·ACK·중복 방지·재시도·rate limit·결과 회신·재시작 복구·권한 경계를 코드와 문서로 추적한다. 구현이 없는 항목은 없다고 기록한다. 실제 Slack 전송이나 비밀 조회는 조사에 포함하지 않는다.
- 나노 분석 작업을 분담한다. 각 분석은 코드·문서 근거, 장점·한계, 가져올 요소·가져오지 않을 요소를 남긴다.
- 사용자 확정: 새로 여는 나노는 모두 Pi다. 실제 FT 카드와 tmux 좌석으로 발주하며 도구 하위 에이전트나 다른 모델 좌석으로 대체하지 않는다.
- 최신 검토 방향: 중앙화를 전제로 두지 않고 arch와 DA가 각각 하네스 루트 일반화 아이디어를 제시한다. 두 원안과 리서치·실험 근거를 비교해 사용자와 선택한다.
- 반복 상태 수집과 기록은 비모델 경로를 우선한다. 중앙 팀장도 작은 실행 결과에서 필요한 결정만 하고 프로시저를 전달한다.
- 호출 수와 실제 토큰·컨텍스트·캐시 비용을 구분한다. 미측정은 0으로 쓰지 않는다.
- 단계별 검토는 텍스트 시퀀스로 먼저 사용자에게 제시한다. 사용자가 보완·완료한 뒤 runtime.html에 반영한다.

## 검증할 핵심

1. 골 파일에 따른 팀 투입, 역할별 진행, 완료 증거, 종료와 새 골 재개.
2. 세대와 구분되는 역할 식별, 현재 세션 소유권, 다중 나노 관리와 증류.
3. 실제 작업 사건에 기반한 상태·진행 시각과 LLM 없는 대시보드 갱신.
4. 디바운스·깨움 예산·중복 방지·확인 응답·외부 대기의 구분.
5. 중앙 프로시저의 장애·재시작·중복 기동·낡은 상태·일부 팀 지연 대응.
6. 미처리 작업과 최신 복구 상태를 보존하면서 히스토리·인덱스·읽기량을 유한하게 관리하는 방식.
7. 최소 팀에서 검증한 운영법을 하위 팀들과 planner 상위 트리로 확장하는 방식.
8. 기존 사건 기반 방식보다 나빠지는 경우까지 포함한 비용·지연·복구 비교.
