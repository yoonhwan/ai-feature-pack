# ft 좌석 호출 간격 운영 규칙

## 정책 (오빠 지시 — 이건 유지한다)
**tick 간격은 300초를 넘기지 않는다. 운영값 280초.**
| 대상 | 값 |
|---|---|
| `FT_TICK_MASTER_INTERVAL` | 280 |
| `FT_TICK_GOAL_INTERVAL` | 280 |
| `FT_TICK_MASTER_MIN_GAP` | 240 |

## 이 규칙이 말하지 않는 것 (DA 반례 수용)
- **"300초를 넘기면 매 호출이 전체 컨텍스트를 재작성한다" 는 거짓이다.** 프롬프트 캐시는 **5분(300s)과 1시간(1h) 두 등급**을 지원한다. 실측 `#53` JSONL 1009행은 앞선 고유응답과 **704초** 차이에도 `read=156,587 / write=1,067` 로 1h 캐시 hit 를 기록했다
- 응답 간격은 **요청 간격의 직접 계측이 아니다.** jsonl timestamp 로 TTL 초과를 판정할 수 없다
- **`cache hit < 95%` 는 TTL 초과의 진단 지표가 아니다.** 신규 prefix·컨텍스트 변경·초기 write 로도 hit 가 내려간다
- 280초는 **운영 설정**이지 모든 모델 요청 간격이나 캐시 hit 을 보장하는 값이 아니다

## 실측 수치 (정정)
| 항목 | 잘못 적었던 값 | 정정 |
|---|---|---|
| 응답당 cache_read (311 기준) | **130,221** (40,498,768/311) |
| 응답당 cache_read (synthetic 52 제외, 259 기준) | **156,366** |
| 280s 일 환산 | 21.6M | **재현 불가 — 산식 철회** |
| 900s 일 환산 | 90.0M | **재현 불가 — 산식 철회** |
| "417% 악화" | 확정 | **철회.** 조건부 산술이며 실측 아님 |

비용 환산 예시: 가상 입력 121k 에서 **cache-read 부분만** `121,000 × 0.05 = 6,050`(6.05k)이다. 이는 **총비용이 아니고** 폐기한 실측값을 가정한 산술이다.

정확한 비용 비교는 **실제 모델 요청 수 · 입출력 · 5m/1h 캐시 등급별 write 를 분리 집계**해야 한다. jsonl 행 수나 응답 수로 대체할 수 없다.

## 왜 280초인가 (정책 근거만 남긴다)
- 캐시 등급 중 **5분(300s)** 이 짧은 쪽이다. tick 주기를 그보다 짧게 두면 5분 등급이 만료될 여지를 줄인다
- 다만 1시간 등급이 살아 있으면 300초를 넘겨도 hit 된다. 즉 **280초는 보수적 기본값**이고, 300초 초과가 곧 낭비라는 뜻은 아니다
- 오빠 지시는 "300을 넘기지 않게" 이므로 그 상한을 지킨다

## 확인 방법
```bash
# 설정값
python3 -c "import plistlib,os;print(plistlib.load(open(os.path.expanduser('~/Library/LaunchAgents/com.byz.ft-tick.plist'),'rb'))['EnvironmentVariables'])"
```
비용·캐시 판정은 jsonl usage 의 `cache_read_input_tokens` · `cache_creation.ephemeral_5m_input_tokens` · `ephemeral_1h_input_tokens` 를 **요청 단위로 분리**해 집계한다.
