# mbox 무의미 읽기 억제

## 정책
1. **할 일이 없으면 좌석을 깨우지 않는다** — `FT_TICK_HASWORK_GATE=1` 통과가 발사 전제
2. **동일 내용 반복 `recv` 를 억제한다**
3. **새 발주·긴급 정정이 도착하면 재수신은 허용한다** — pending 을 0 으로 만드는 것이 목적이 아니다

## 이 규칙이 말하지 않는 것 (DA 반례 수용)
- **"peek 161 : recv 3,021 = 19배이므로 대부분 빈 읽기" 는 판정 불가다.** 원시 로그·명령 실행 구분·좌석별 시간범위·각 recv 시점의 pending 결과가 없다. 산술 비율만 맞다
- **사전 알림으로 pending 을 이미 아는 recv 도 있다.** 그건 낭비가 아니다
- **`tool_use` + `tool_result` 2행 ≠ 모델 요청 2회.** 비용은 실제 모델 요청 수·입출력·캐시 등급으로 계산한다
- **`peek` 도 모델 왕복이다.** 모델이 별도 도구로 peek 를 호출하고 결과를 읽은 뒤 recv 를 또 호출하면 왕복이 추가된다. pending=0 이어도 peek 자체가 왕복이다. 그래서 모델이 아니라 **비모델 gate 에서 판정**해야 한다
- **`pending 0` ≠ 미완료 카드 0.** mbox 가 비어도 카드·골이 남아 있을 수 있다

## 그래서 어떻게 해야 하나 (DA 권고)
- **모델 왕복을 늘리지 않는 자리에서 검사한다**: 기존 `haswork_gate` 같은 **비모델 wake gate** 가 이미 pending 을 판정한다. 모델이 peek 를 별도 호출하지 않게 그 gate 에 맡긴다
- 또는 **pending 값을 검사해 >0 일 때만 recv** 하는 한 도구 실행을 쓴다. peek 와 recv 를 셸 논리연산자로 잇는 방식은 쓰지 않는다 — 그 연산자는 pending 이 아니라 **종료코드**를 보므로 `pending=0` 이어도 recv 가 실행된다
- 억제 대상은 **동일 내용 반복 recv** 이고, 새 발주·긴급 정정 수신은 막지 않는다

## 확인
```bash
# pending 을 변수로 받아 0 이면 recv 0 — 한 실행 안에서 조건 분기
n=$(bash .fable-team/comm/mbox.sh peek "<좌석>" | sed -n 's/.*pending=\([0-9]*\).*/\1/p')
[ "${n:-0}" -gt 0 ] && bash .fable-team/comm/mbox.sh recv "<좌석>"
```
- `peek` 결과 예: `pending=0 scanned=1 lineage=0` — 종료코드는 0 이므로 `&&` 로는 막을 수 없다. **`pending` 값을 변수로 받아 판정**한다
