1. **§1-B:31/33/34/36 and §3-B:83 — queue identity and lifecycle owner are incomplete.** Q-3 requires queue row ↔ Issue number 1:1, while Q-6 admits direct human input before issue-manager assigns a number. The queue has no provisional admission state or duplicate reconciliation key when the same work also arrives as an existing Issue. Q-4 says only the head row activates, with an immediate-work exception, but neither Q-1 nor step ⑦ specifies who writes activation, suspension, resumption and clear, or preserves P3's main-owner verification → manager result → planner BOARD acknowledgment before the next admission. **Why:** a queue notification can be mistaken for authority to start, or a new head starts before completion reconciliation. **Correct value:** define planner as queue-state writer, distinguish pending Issue registration from admitted rows, acknowledge assignment/acceptance, and explicitly carry P3's activation/emergency-suspension/resumption and clear-ack contracts. The main orchestrator retains Issue completion verification; the queue closes only from its verified completion report and reconciliation event. Declare the duplicate-input reconciliation owner.
2. **§2-B:56 / §3-A:68 / §3-B:78 / L-1:85 — raw patch equivalence is not the actual close gate contract.** The proposal allows many commits to be squashed but requires raw `git cherry` “+ 0”. The live ft-nano-cherry-gate.sh 59–77 additionally accepts non-equivalent patches when merge-tree shows no non-design delta, and 85–110 handles landed-then-superseded content; documentation-only exceptions also exist. A two-commit worker squashed into one integration commit can have both individual patch IDs marked “+” even when all intended content is present. **Why:** normal squash intake can be permanently blocked by the proposed evidence criterion, or a recorded ledger row can be treated as proof unsupported by content. **Correct value:** require the existing gate's accepted result with mode/reason and immutable worker tip/result SHA, using raw +0 as one successful case. For squash, verify target content or the existing content-landed guard and the result commit's target reachability; a new markdown ledger is an audit record, not a replacement for that gate. Do not weaken gate failures to make an audit row sufficient.
3. **§3-B:81 — S10 prevention lacks a binding between inspected tree and pushed commit.** Step ⑤ computes a merge-tree on target advancement but says only “diff 0 against moved main commits” and then push. It does not require the produced commit's tree to equal that merge-tree or abort when the fetched target is not an ancestor of the candidate, although §3-A:70 explicitly requires abort. Whole-tree diff zero against main would reject legitimate feature changes; path preservation can also require explicit decisions where both teams intentionally changed one path. **Why:** the same S10 mistake—inspect a correct merge tree, create/push a commit carrying the feat tree instead—still satisfies the written sequence. **Correct value:** record fetched target SHA, integration SHA, rc/conflict status and expected merge-tree OID; materialize the candidate with that tree, verify candidate tree equality and target ancestry with fail-closed commands, inspect deletion/changed-main-path deltas with resolved overlap decisions, and push normally only that candidate. Verify exact remote SHA and re-enter inspection on target movement/non-fast-forward rejection. No force push.
4. **§3-B:80–82 — gates are bound to the pre-target-merge tip, not necessarily the pushed artifact.** Step ④ completes tests/3-bubble/DA at the integration tip; step ⑤ may then introduce new main changes and a different merge commit before push. **Why:** a conflict-free merge can still change behavior, and the candidate is no longer the tested single-set HEAD required by single_set_testing §§1/3. **Correct value:** target synchronization/merge construction precedes the final artifact gate, or any candidate change returns to the appropriate difference/regression and final-set gates with evidence bound to its exact SHA. Preserve source-to-target evidence and run required local verification before push. A historical baseline-difference allowance does not itself waive current required local gates.
