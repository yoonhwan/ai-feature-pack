직접 반례: 팀이 ‘닫힘·증거’를 보내고 issues master가 요청을 읽었지만 행을 커밋하기 전에 승계하거나 중단합니다. 요청은 이미 읽힌 것으로 보이고 원장은 여전히 진행입니다. 후계의 승계 보고는 SETS만 읽어 진행으로 반복합니다(47–48행). 설계에는 미반영 요청을 회수하거나 송신자가 완료 여부를 확인해 보이는 미반영으로 표시할 경로가 없습니다. 읽기 전 부재로 요청이 큐에 오래 남는 경우에도 원장 뷰는 동일하며 부재/대기를 표시하지 않습니다. 전송 성공이나 READ는 행 반영 성공과 다릅니다.

조회도 54행에서 issue-manager 작업 트리가 존재하면 그 파일을 우선합니다. 그 파일이 오래됐고 새 issues master의 정본만 갱신됐을 때 파일 존재만으로 오래된 상태를 정상 표처럼 출력할 수 있습니다. 원장 위치와 적용 버전을 확정하지 않으면 새 반영이 이루어져도 소비자 화면이 뒤처질 수 있습니다.

최소 교정: 단일 기록자는 유지하고, 상태 요청에 고정 id/mbox seq 및 기대 전 상태를 붙이며 송신 측의 미완료 요청을 영속 기록하세요. issues master가 행 갱신·커밋 뒤 ‘적용 id·세트·새 상태·원장 commit’으로 회신하고, 회신 전에는 요청 상태를 pending으로 드러내야 합니다. 부재/승계 시 후계가 미반영 요청과 마지막 적용 id를 대조하고 동일 요청 재처리는 중복 효과 없이 처리하도록 정하세요. 처리 시간 경계와 재알림은 정본에 한 가지 절차로 고정하면 됩니다. 새로운 분산 큐 서비스를 요구하지 않습니다.

닫힘은 사건을 만족하는 증거 확인과 원장 반영을 구분하고, 같은 id에 대한 완료 회신이 있어야 송신자가 닫힘 반영 완료로 판단해야 합니다. Issue 일괄 close가 별도 집행이면 그 성공/실패를 세트 닫는 사건과 대조해 표시해야 하며, 행 갱신만으로 실제 close까지 완료됐다고 취급하면 안 됩니다. 조회 경로는 단일 정본을 고정하거나 회신된 적용 commit과 소비자가 읽는 버전을 대조해 stale/미반영을 보이게 하세요.

교정 수락: 문서 절차 또는 가짜 로컬 기록으로 부재·READ 후 반영 전 중단·반영 후 회신 전 중단·재요청·오래된 우선 경로를 대조합니다. 상태가 오래된 경우 pending/stale이 보이고, 승계가 같은 요청을 회수해 완료 회신까지 추적하는지 확인해야 합니다. 기존 69행의 표 형식/건수 시험만으로는 이 계약을 확인하지 못합니다.

## §4 HOLD-S2 — 커밋은 있어도 발주 식별자는 절대경로뿐

35행은 로컬 발주자 브랜치에 커밋하고 절대경로로 읽게 합니다. 커밋 자체는 /tmp보다 분명히 낫습니다. 워크트리를 정리해도 브랜치가 남으면 Git에 내용이 살아 있으며, 그 브랜치/commit에서 git show로 복원할 수 있습니다. 따라서 워크트리 정리만으로 Git 객체까지 즉시 유실된다고 주장하지 않습니다.

그러나 27,35,41행의 원장/mbox 계약은 문서 경로와 seq뿐입니다. 발주 commit/보존 ref를 명시하지 않아 수신자는 절대경로가 없어진 뒤 어떤 버전을 복원해야 하는지 확정할 수 없습니다. 경로가 같은 다른 개정본을 읽는 경우도 구분하지 못합니다. --check는 실경로 부재를 오류로 잡을 뿐 복구 경로는 제공하지 않습니다(55행).

다른 머신은 발주자의 절대경로를 공유하지 않고, 미push 로컬 커밋 객체도 갖지 않습니다. 따라서 ‘브랜치 커밋 + 절대경로’만으로 머신 독립을 달성하지 않습니다. 브랜치를 삭제하면 아직 객체가 남아 있을 수 있으나 보존 ref가 없는 커밋은 장기 보존이 보장되지 않습니다. 이는 발주가 지정한 위험 분석이며 삭제 실행을 요구하거나 승인하는 것이 아닙니다.

최소 교정: 발주 식별자를 ‘리포 식별 + commit SHA + 리포 상대경로 + 필요 시 절 앵커’로 고정하고 절대경로는 동일 머신의 편의 힌트로만 두세요. 수신자는 git show <sha>:<path> 또는 검증된 복원 파일로 읽고 사용한 버전을 회신해야 합니다. 랜딩 전에는 발주 commit을 보호하는 ref를 유지하며, 정본 도달/보존 위치 확인 전 워크트리·브랜치 정리를 발주 보존 완료로 취급하지 않아야 합니다. 기존 삭제 HIL을 이 규칙이 대신하지는 않습니다.

원격 수신을 지원한다면 발주 전 해당 commit이 수신 머신에서 읽을 수 있도록 승인된 원격 ref/복제 경로를 정하고 객체 가용성 확인을 게이트로 두세요. 아직 로컬만 지원한다면 ‘동일 머신 Git 객체를 가진 좌석까지’라고 현재 수락 범위를 명시하고 머신 독립은 후속 단위로 남기는 것이 최소입니다. 자동 push나 특정 새 배포 방식을 이 DA가 임의로 승인하지 않습니다.

교정 수락: 절대경로가 없는 가짜 수신 환경에서 고정 SHA/상대경로로 정확 본문을 복원하고, 같은 경로의 이후 변경을 잘못 읽지 않아야 합니다. 객체가 없는 원격 환경은 정상 읽기로 취급하지 않고 명시적 오류/미전달을 표시해야 합니다. 보호 ref와 정본 도달 조건은 문서로 확인할 수 있습니다.
