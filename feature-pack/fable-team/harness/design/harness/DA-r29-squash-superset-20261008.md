## §2 질문 1 — HOLD-SQ1: PR 중간 blob 존재는 최종 랜딩의 충분조건이 아님

안:25–28의 state=MERGED, mergeCommit=S, PR head H 확인은 그 PR의 병합 사실을 증명합니다. 그러나 H의 역사에 나노 blob이 한번 있었다는 사실은 그 내용이 squash 결과/main에 들어왔다는 뜻이 아닙니다.

직접 반례(같은 경로·파일 mode를 유지한 Git 모델):

| 시점 | 코드 P | 문서 D |
| --- | --- | --- |
| 공통 base C | P0 | D0 |
| PR 중간 B | 나노 tip P1 | D1 |
| PR head H | P 변경을 되돌려 P0 | D1 |
| squash S, main | P0 | D1 |

PR은 문서 D의 실제 diff가 있으므로 병합 가능한 비어 있지 않은 PR입니다. state=MERGED와 S 일치가 모두 참이고, merge-base(H,main)..H에는 새 blob P1을 쓴 B가 있습니다. NANO tip은 P1이므로 제시한 ②로 통과하지만 main에는 P1이 한번도 랜딩되지 않았습니다. 새 gate가 요구한 ‘실제로 main에 없는데 PASS’가 됩니다. CI 통과/리뷰가 P의 보존인지 제거 승인인지 알려주지는 않습니다.

기존 gate는 분기 후 FEAT **실제 역사**에서 존재했던 내용의 후속 대체를 인정합니다(ft-nano-cherry-gate.sh:82–108). 새 안은 main이 받기 전에 사라진 내용까지 그 증거로 바꾸므로 같은 정의의 단순 구간 확대가 아닙니다. ‘나노를 의도적으로 폐기한 것’이면 명시 폐기 증거/기존 사람 override로 처리할 수 있지만 자동 content_landed 사유로 통과시키면 안 됩니다.

최소 교정: 중간 blob의 존재와 최종 반영/승인된 대체 증거를 구분해야 합니다. head/squash 최종 트리에서 정확 내용이 없는 코드 경로는 분기 후 실제 main 역사의 증거 또는 별도의 검증된 내용 보존/폐기 판정 없이 자동 PASS시키지 않는 보수 정책이 필요합니다. 리팩터 의미 동치는 Git blob만으로 자동 증명되지 않으며 현재 사례에 대한 사람 근거와 일반 gate 조건을 구분하세요. 경로의 mode/type도 기존 gate처럼 함께 비교해야 합니다.

안:34의 시험에 ‘PR 중간 P1→head에서 P0로 revert, D1만 squash’와 ‘PR head의 해당 코드가 제거됨’을 추가해 REJECT를 확인해야 합니다. GitHub state/mergeCommit 오류 시험만으로 이 반례는 막히지 않습니다.

## §3 질문 2 — HOLD-SQ2: design 경로 전체와 실제 문서는 다름

안:27은 모든 design/ 경로를 WARN으로 낮춥니다. 이 repo에는 실행 대상 DDL인 design/rag/sql/*.sql와 Bash/Python 실행 자료도 있습니다(예: 설계가 직접 언급한 design/cfo/harness/ft-tick-cfo.sh). 경로 접두사만으로 ‘문서만 미랜딩’이라고 판단하면 이들 코드도 예외가 됩니다.

혼합 커밋의 일반 코드 P는 이미 main 역사에 있되 후속 리팩터로 tip과 달라 merge-tree 충돌/delta로 superseded 경로를 타고, 같은 커밋의 design/rag/sql/신규.sql은 main/채택 PR에 없는 모델을 생각할 수 있습니다. 기존 superseded 검사는 혼합 커밋이 건드린 모든 경로를 검사해 그 SQL 부재를 막습니다(ft-nano-cherry-gate.sh:83–109). 제안한 design 전체 skip은 SQL 미랜딩을 WARN으로 바꾸고 P만으로 PASS시킬 수 있습니다. 기존 design-only WARN 예외 자체를 재심사하는 것이 아니라 이번 혼합 경로 검사 완화의 직접 누출입니다.

최소 교정: 새 혼합 커밋 완화는 검증된 문서 경로/파일 종류에만 적용하고, design 아래 SQL·실행 스크립트·제품이 소비하는 코드/설정은 원래 내용 증거 검사에 남겨야 합니다. 분류 불명은 REJECT 또는 명시 사람 판정으로 처리하세요. 모든 경로를 NUL-safe로 완독한 뒤 코드 하나라도 남으면 그 경로 전부의 증거를 확인하고, WARN 건수만으로 코드 목록이 비었다고 추정하면 안 됩니다.

시험은 혼합 순수 Markdown 미랜딩의 WARN 통과와 혼합 design SQL/스크립트 미랜딩의 REJECT를 분리해야 합니다. 정리/branch 삭제를 요구하거나 승인하지 않으며 원본 브랜치 보존은 기존 운영 규칙대로 유지합니다.

### SQ1 닫힘 — 자동 ‘랜딩 증명’을 명시 예외로 전환

안:23–30은 PR 중간 blob만으로 자동 통과하는 충분조건을 철회합니다. PR의 실제 MERGED/mergeCommit/FEAT 구간 관계를 확인하고, mode/type/blob을 함께 비교하며 되돌림·경로 제거·PR에도 없음은 전용 플래그로도 거부합니다. 기존 P1→P0 revert 후 문서만 squash 반례가 §4의 시험 ③, 제거가 ④로 고정되었습니다.

최종 경로가 base와 다르지만 나노 tip과도 다른 것은 ‘기계가 의미 보존을 증명했다’가 아니라 사람이 사유를 명시해야 하는 칸입니다. 전용 --squashed-pr와 reason, 경로별 증거 표, 원장 1행·ERROR로 이 예외를 드러내며 플래그 없이는 기존 거부를 유지합니다. 따라서 기존 자동 거짓 통과 원인을 해소한 것으로 수락합니다.

이 경로는 전체/부분 의미 삭제를 Git이 자동 검증하는 보장이 아닙니다. S!=base라는 조건만으로 partial revert나 다른 기능 대체가 내용 보존이라고 단정할 수 없고, 변경된 경로의 의미 보존/폐기를 표명하는 책임은 명시 사유의 소유자에게 남습니다. 출력 사유를 일반 content_landed 자동 증명과 구분하고, 판정·사유를 남기지 못하면 통과하면 안 됩니다. PR 조회/객체/경로 분류·원장 저장 오류도 정상 예외 통과로 흡수하지 않아야 합니다.

### SQ2 닫힘 — 혼합 design 코드 예외 제거

안:31은 새 혼합 커밋 WARN을 design 아래 명시한 문서 종류로 제한하고 SQL·Bash·Python·JSON/YAML/TOML·기타/무확장자는 코드 증거 칸에 남깁니다. NUL-safe 완독·mode/type 비교를 유지하고 §4 시험 ⑧이 Markdown WARN과 실제 SQL/스크립트 미랜딩 REJECT를 분리하므로 기존 반례를 차단합니다.

구현은 이 분류가 실제 superseded/PR 검사 대상에서만 문서를 제외하도록 하고, 코드 하나라도 남았으면 그 경로 전부의 증거를 확인해야 합니다. 경로 읽기 실패나 목록 상한으로 미검사 코드를 0개로 오인해서는 안 됩니다. 원본 브랜치 보존·실제 사람 override는 기존 규칙을 유지하며, 이 설계가 branch/worktree 삭제를 승인하는 것은 아닙니다.
