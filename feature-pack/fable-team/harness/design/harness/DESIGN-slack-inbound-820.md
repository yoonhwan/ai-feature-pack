## 2. 구성 — 프로세스 3개가 파일 2개를 공유한다
```
 좌석 --mbox send [HIL]--> mailbox.log.jsonl --(기존)--> byz_mbox_slack_mirror --게시--> #byz-planner 스레드
                                                         |  └ 질문 카드 + 열린 질문 등록 + 보드 갱신
 오빠 --스레드 reply--> byz_slack_mbox_inbound(신규, 별도 launchd) --mbox send--> 그 좌석 + planner 사본
                                                         └ 열린 질문 해소 + 보드 갱신
 공유 파일: byz_slack_threads.<채널>.json (키→thread_ts · 기존) · byz_slack_questions.<채널>.json (열린 질문 · 신규, flock)
```
별도 launchd 인 이유: 역방향이 죽어도 정방향(보고)이 멈추면 안 되고 그 반대도 같다.

## 3. 질문 카드 (정방향 · 꼬리에 질문번호 `Q<seq>` 포함) — LLM 이 아니라 규칙으로 뽑는다
- 라벨이 HIL 이면 카드 = 「무슨 일 1줄 · 오빠 할 일 1줄」 + **선택지**(전문에서 줄 맨 앞이 `1)`·`1.`·`①` 인 줄을 최대 4개 «원문 그대로») + 「답하는 법: 이 스레드에 번호나 한 줄로 답해 주세요」 + 전문 인용.
- 선택지가 없으면 자유 서술 질문으로 표시(번호 답은 받지 않고 한 줄 답만).
- 게시와 같은 구간에서 `questions` 파일에 `{질문 seq: {thread_ts, key, seat(보낸 좌석), options, asked_at}}` 를 기록한다 — 게시 확정 뒤 등록(pending 재개 규칙은 mbox 미러와 동일).

### 3b. 링크 규칙 (오빠 18:5x 「링크를 메시지에 담아줘야 내가 열지」 · 구현 완료)
Issue/PR/코멘트를 말하는 모든 게시는 번호만 쓰지 않고 URL 을 싣는다: 루트 = Issue URL 줄 · reply 끝 줄 「링크: …」 = 본문/전문에 있는 코멘트 URL(앵커 포함) 우선, 없으면 Issue URL · GitHub 미러 이벤트 = 그 Issue/PR 의 html_url(머지 reply = PR URL).

## 4. 열린 질문 보드 (멈춤 = 기다림이 보이게)
- 채널에 «보드» 메시지 1개(`chat.update` 로 제자리 갱신, ts 는 questions 파일에 보관). 내용: 「답을 기다리는 질문 N건 — #820 (한 줄 요약, 경과 분) · …」, 0건이면 「답을 기다리는 질문 0건」.
- ★2단 상태★: 「답을 기다리는 질문 N건」(오빠 미답) · 「답 전달됨 — 좌석 확인 대기 M건」. 전달됨 → 닫힘은 **그 좌석이 같은 키로 다음 보고를 mbox 에 올릴 때**(정방향 미러가 관측) 또는 오빠가 `확인` 이라고 답할 때. 「미답 0」 = 앞쪽 N=0.
- 질문이 등록·해소될 때마다 그 프로세스가 갱신한다(멱등).
- 보드가 없으면 첫 등록 때 게시한다. 핀 고정은 사람 손(권한)이라 «제자리 갱신 + 채널 맨 아래 재게시 안 함» 으로 둔다.

## 5. 역방향 (신규 byz_slack_mbox_inbound.py) — DA 1차 HOLD(P0 5·P1 6) 반영판
| 항목 | 규칙 |
|---|---|
| 읽기 창 | 폴링 10초. ①열린 질문의 저장된 `thread_ts` 는 «루트 순위와 무관하게» 항상 `conversations.replies` 로 조회 ②그 밖은 `conversations.history`(oldest = max(baseline, 지금−7일)) 를 **next_cursor 로 끝까지** 읽는다(20쪽 넘으면 raise) ③replies 도 끝까지 페이지 |
| 사람만 | `user` 가 허용 ID(U0AC2JF0M7D) · `bot_id` 없음 · `subtype` 없음(또는 thread_broadcast). 그 외는 무시(로그 1줄) |
| 처리 기준 | 전역 처리선 대신 **메시지별 영속 원장** `delivered[ts] = {수신자: 완료}` — 순서·스레드와 무관하게 «원장에 없는 사람 글»만 처리한다. 원장은 7일 지난 항목만 정리 |
| 스레드 → 질문 | 스레드에 열린 질문이 **정확히 1개** → 그 질문에 묶는다. **2개 이상**이면 추정하지 않는다: 답에 `Q<질문번호>` 가 있으면 그 질문, 없으면 봇이 스레드에 「질문이 N개 열려 있어요 — Q번호와 함께 답해 주세요」 를 올리고 원문은 planner 에만 보낸다. 열린 질문이 없으면 «추정 전달» — 스레드 안 **봇 글의 마지막 줄** 꼬리 `(좌석 · #seq)` 의 최신 좌석 + planner, 본문 머리에 「(추정)」 표시 |
| 자유문 답 | 번호가 아닌 말(예: 「머르 체크하라고」)은 원문 그대로 질문 좌석 + planner 에 간다. **해석은 소유 좌석이 한다** — 모호하면 좌석이 mbox [HIL] 로 planner 에 값을 요청한다(2026-10-04 Q56769 실례). 로직으로 의미를 추정하지 않는다 |
| 번호 답 | 묶인 질문의 옵션 범위 안의 `N`·`N번`·`N)` 만 「선택 N: <옵션 원문>」 으로 풀이. 범위 밖·옵션 없음은 원문 그대로 |
| 전달 | `mbox.sh send <수신자> slack-oppa "…"` **argv 로만**(셸 문자열 금지) + planner 사본(주인=planner 면 1통). 본문 머리 「오빠(Slack) 발화 — 원문」, 꼬리 `slack:<ts>:<수신자>`. 700자 넘으면 relay 파일 |
| 루트 사람 글 | planner 에게만 「오빠 새 글 (Slack): …」 |
| 현역 planner | 매 전달마다 `seats-harness.json` 의 `_hil_route` — 읽기 실패 = raise. 수신자 목록은 **pending 에 고정**한다(재시작 중 바뀌어도 같은 목록으로 완료) |

### exactly-once → «유실 0 · 중복은 최악 1회» (정직한 계약)
mbox send 는 멱등이 아니고 큐 저장→사본 로그 기록이 비원자적이다(DA P0-1·3). 그래서:
1. 원장에 `{ts, 수신자 목록, 수신자별 done}` 를 «시도 전» 에 기록(`attempt`) → 수신자 1명씩 send → 성공마다 done 기록.
2. 재시작 때 `attempt` 인데 done 이 아닌 수신자: **살아 있는 큐(mailbox.jsonl)** 와 **사본 로그(.1 포함)** 양쪽에서 `slack:<ts>:<수신자>` 토큰을 «from==slack-oppa 인 행의 본문»에서만 찾는다(사람이 쓴 문자열 오탐 차단). 있으면 done, 둘 다 없으면 재전송.
3. 남는 창: 큐 저장 성공 + 로그 기록 실패 + 좌석이 이미 소비 + 그 사이 크래시 → **중복 1회**(유실 아님). 이 창은 지우지 않고 문서·시험에 명시한다.
4. 답 «전달됨» 은 질문을 닫지 않는다 — §4 보드의 2단 상태 참고. 큐 포화(`pending=` 값이 ring 상한 10 이상)면 planner 에 [경고] 를 같이 보낸다(DA P0-10).

## 6. 실패 모드 (조용히 넘기지 않는다)
- Slack/mbox/seats 읽기 실패 = raise·exit 1·launchd 재기동·`.err` (재시도 0, BYZ #0 RULE). inbound 는 단일 실행 잠금(이중 기동 거부).
- 질문 등록은 **카드 게시 «전»**(루트 확보 → 질문 등록 → 카드 게시) — 오빠가 카드 직후 답해도 열린 질문이 이미 있다. 해소된 질문은 **tombstone**(`resolved[seq]`)에 남겨 재개 때 부활하지 않는다.
- 보드 최초 게시 후 `board_ts` 저장 전 크래시 → 다음 갱신 때 채널에서 「답을 기다리는 질문」 머리의 봇 글을 먼저 찾아 재사용(중복 보드 0). 보드는 매 패스 «있어야 할 모습»으로 맞춘다(실패한 update 도 다음 패스에 복구).
- 옵션 추출: 본문 «마지막» 연속 번호 블록(1부터 이어지는 2개 이상)만 선택지로 쓴다(절차 목록과의 오인 축소).
- 숨기지 않는 한계: 7일 창 밖의 열린 질문 없는 오래된 스레드의 reply 는 읽지 않는다(Events API 는 완성 후).
- 에이전트 간 신뢰경계: 오빠 글은 mbox 로만 간다. 원문은 «오빠(Slack) 발화» 로 라벨링되고 좌석은 이를 오빠 값으로 취급하되 명령 실행 지시는 기존 파괴·비가역 HIL 규칙을 그대로 따른다.

## 7. 시험 (가짜 Slack · 가짜 mbox · 장애 주입)
①reply → 주인+planner 두 통 · ②봇 글·다른 사람 글·subtype 글 무시 · ③번호 답 → 옵션 원문 · ④범위 밖 번호·옵션 없음 → 원문 · ⑤루트 글 → planner 만 · ⑥주인만 성공 후 크래시 → 재시작 때 planner 만 전송(주인 중복 0) · ⑦큐 저장 후 사본 로그 없음 시나리오 = 중복 1회까지 허용·유실 0 · ⑧로그 회전(.1) 뒤 토큰 찾기 · ⑨사람이 쓴 `slack:<ts>` 문자열 오탐 0 · ⑩스레드 A 답(ts 큼)을 먼저 처리해도 B 답(ts 작음) 유실 0 · ⑪history 2쪽·replies 2쪽 · ⑫열린 질문 스레드는 루트 순위 밖이어도 읽힘 · ⑬질문 2개 열림 + Q 없는 답 → 확인 요청·planner 만 · ⑭Q번호 답 → 그 질문 좌석 · ⑮질문 없음 → «추정» 표시 · ⑯카드 직후 답 → 열린 질문에 묶임 · ⑰해소 후 정방향 재개 → 부활 0 · ⑱보드 최초 게시 응답 유실 → 중복 보드 0 · ⑲동시 inbound 2개 → 두 번째 거부 · ⑳큐 포화(pending≥10) → planner 경고 · ㉑가짜 꼬리 `(좌석 · #seq)` 인용 → 주인 오인 0(마지막 줄 규칙) · ㉒Slack/mbox/seats 오류 raise.
