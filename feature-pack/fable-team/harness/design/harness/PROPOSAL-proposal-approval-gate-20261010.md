> 내부 하네스, 내부 스킬스를 모니터하고 요청을 사용자에게 받아 해당 부분 바로 확인 검토하고. 실제 하네스와 스킬스를 업그레이드하고 레포에 커밋 푸시하며 전 환경에 물리적 컴퓨팅 환경에도 설치하도록 배포 발행(슬랙) 수신해 반영되 업그레이드.
> 하네스 스킬 관리 오케는 메인오케들과 위성오케들에게 개선요청을 직접받아 등록관리하고 사용자와 협의해 개선하는 축도 필요함.
> 메인 하네스를 유니크하게 머신들에 완전히 독립 배분해 운용하는것.

골의 어느 축: 개선요청 접수·협의(오빠 「컨펌 전 Issue·코드 0」 규칙을 선언에서 강제로) + 업그레이드(하네스 도구·훅).

## 결론
(r1) 제안서를 처음부터 GitHub Issue(`proposal` 라벨)로 열고, 그 Issue 본문에 판단에 필요한 내용을 전부 싣고, 오빠 승인을 그 Issue 의 `approved` 라벨로 남기는 흐름으로 바꾸는 것을 추천해요. 나노 띄우기는 승인 라벨이 없으면 막혀요. A안의 «증거 3개»는 Issue 하나로 흡수돼요. 질의응답·추가 의견은 그 Issue 코멘트에 모으고, 이미 구현된 loom 7건은 사후 Issue 로 열어 한 건씩 유지·수정·되돌림을 여쭤요.

(r0) loom 제안서가 오빠 확인 없이 구현된 것은 사람이 규칙을 어겨서만이 아니에요. 나노 띄우기·Issue 등록·인터뷰 세 곳 모두 «오빠가 본 승인»을 검사하지 않아서 통과됐어요. 승인 증거 3개(제안서 머리줄 · 슬랙 발행 기록 · planner 판정 원장의 인터뷰 줄과 슬랙 링크)가 서로 맞지 않으면 그 세 곳에서 막도록 바꾸는 것을 추천해요.

## 오빠가 결정할 것
(r1) A안과 Issue 우선안의 관계를 고르시면 돼요. 추천은 ①흡수(Issue 가 정본 · 게이트는 Issue 만 검사)예요. ②보강은 A안 증거 3개에 Issue 라벨을 더하고(증거 4개), ③은 A안을 그대로 두고 Issue 는 지금처럼 승인 뒤에 열어요.

(r0 · 판정 816 으로 A안 결정됨) 게이트 범위를 고르시면 돼요. 추천은 A안(세 곳 강제 + 컨펌 기록 없는 2건의 진행 카드 4장은 오빠가 원문을 볼 때까지 멈춤)이에요. B안은 세 곳 강제만 하고 진행 카드는 그대로 두고, C안은 나노 띄우기·Issue 등록 두 곳만 강제해요.

## 되돌림
검사 도구 1개와 훅 1개를 빼고, 바뀐 래퍼 2개를 `.bak` 으로 되돌리면 지금 흐름으로 돌아가요. 이미 등록된 Issue·카드는 건드리지 않아요.

**Issue 본문 템플릿 (필수 칸 · 링크만 0 · 이 Issue 하나로 판단 가능해야 함)**: 숨은 표식 `<!-- byz-proposal-id: <팀>/<slug> -->` · `## 결론` · `## 오빠가 정할 것`(질문 1 + 선택지 2~3 · 추천 먼저) · `## 배경` · `## 제안` · `## 되돌림` · `## 근거`(커밋 sha · 경로:줄) · `## 부록`(길면 `<details>` 접기 · 선택). 필수 칸이 비면 열기 도구가 Issue 를 만들지 않고, 게이트도 REJECT 해요.

**spawn 게이트가 Issue 에서 확인하는 것 (읽기 전용 `gh` · 7초 + 재시도 1회 · 실패 = REJECT)**: 라벨 `proposal`+`approved`(+`rejected` 없음) · 작성자 byz-tank · 필수 칸 · 라벨을 단 사람(ⓐ오빠 계정이면 OK · ⓑbyz-tank 이면 `승인 — 판정 N` 코멘트 + 판정 원장 N 줄에 이 Issue 링크).

| | ①흡수 (추천) | ②보강 | ③A안 유지 |
|---|---|---|---|
| 정본 | GitHub Issue 1개 | Issue + md 머리줄 + 슬랙 장부 + 판정 원장 | md 머리줄 + 슬랙 장부 + 판정 원장 |
| 머신 독립(골 원문 3줄째) | 됨 — Issue 는 어디서나 읽혀요 | 안 됨 — 슬랙 장부는 이 머신 파일 | 안 됨 |
| 승인 전 GitHub 흔적 | 있음 | 있음 | 없음 |

**지금 A안 나노(DA 보류 3건 수정 중 · 설치 0)를 어디까지 살리나 (①일 때)**: 그대로 = spawn 배선 · 카드 lint `- 제안서:` 줄(값 = `#M` 또는 `없음 — 사유`) · 인터뷰 훅(필요 링크만 Issue 링크로) · 시험 틀. 바꿈 = `ft-proposal-gate.sh` 검사 내용(Issue 기준) · `ft-proposal-register.sh` → 승인 단계 도구(라벨+코멘트 · Issue 생성 0). 뺌 = Tank `create` 게이트(Issue 를 여는 것이 흐름의 시작이 됨) · 슬랙 장부·md 머리줄 검사(정보로만 남음).

**질의응답·오빠 추가 의견 (놓침 0)**: 자리는 그 제안 Issue 코멘트 하나예요(슬랙은 알림 전용).
- 인터뷰를 할 때마다 planner 가 Tank 로 `[인터뷰 판정 N]` 코멘트를 남겨요(질문 원문 · 오빠 답 원문 · 추가 의견 원문). 승인 판정(ⓑ)은 이 코멘트가 있어야 인정돼요.
- 오빠가 GitHub 에 직접 쓴 코멘트 가운데, 그 뒤 Tank 답이 없는 것은 «답 안 한 의견»이에요. 팀 master 틱 도구 `ft-proposal-inbox.sh` 가 그런 Issue 를 찾아 `needs-reply` 라벨을 달고 목록을 보고해요.
- `needs-reply` 가 붙은 Issue 는 spawn 게이트가 막아요(의견을 반영하기 전 구현 0). 반영하면 md rN → Issue 본문 갱신 → `rN 반영: <의견 링크>` 코멘트 → 라벨을 떼요.

**이미 구현된 loom 제안서 7건 질의**:
- 7건 모두 Tank 가 Issue 로 사후 등록해요(라벨 `proposal` + `사후등록`). 본문은 템플릿 + `## 지금 상태(사실)` 칸이에요: 구현된 카드 · 랜딩 sha · 관련 Issue · 컨펌 기록 유무(745 = 채택했지만 원문 미제시 · 520·548·552 = 기록 0). 사실 칸은 loom arch 가 채워요(판정 809 변환 작업 재사용).
- planner 가 한 번에 한 건씩 물어요(판정 805 순서). 선택지는 유지 / 수정(rN 요청) / 되돌림이고, 건마다 loom arch 추천을 먼저 둬요.
- 결과 처리: 유지 → `approved` + 판정 코멘트 · 수정 → `needs-reply` + rN · 되돌림 → loom master 되돌림 계획 카드(파괴 작업은 HIL). 멈춘 진행 카드 4장은 그 Issue 가 `approved` 가 될 때 다시 움직여요.

**진행 중인 것**: 컨펌 대기 제안서(R74 r1 등)는 설치 때 Issue 로 열어요. 이미 승인된 제안서(판정 812·816)는 Issue + `approved` + 판정 코멘트로 기록해요. loom 진행 카드 4장 멈춤은 그대로예요. Issue·라벨 이벤트로 도는 GitHub Actions 는 0개라 Actions 비용은 늘지 않아요(실측).

## 2. 제안 (A안)

**승인 증거 = 3개가 같은 것을 가리킬 때만 «오빠가 본 승인»으로 인정해요.**

| # | 증거 | 어디에 |
|---|---|---|
| ① | 제안서 머리줄 `- 상태: 승인 — 판정 N` | 제안서 파일 |
| ② | 그 제안서의 슬랙 발행 기록이 `done` (스레드 ts · 발행본 hash) | `~/.hermes/state/byz_proposal_publish.json` |
| ③ | planner 판정 원장에 `N 오빠 인터뷰(…)` 줄이 있고, 그 줄에 ②의 슬랙 스레드 링크가 들어 있어요 | `design/planner/VERDICTS-planner-*.md` |

검사 도구는 `ft-proposal-gate.sh <제안서.md>` 1개예요. 결과는 `OK 판정 N 스레드 <ts>` 또는 `REJECT <빠진 증거>` 이고, 아래 세 곳이 이 도구를 불러요.

1. **나노 띄우기**: 모든 새 카드에 `- 제안서:` 줄을 의무로 둬요(값 = 제안서 경로 또는 `없음 — <사유>`). 카드 검사기가 이 줄이 없는 카드를 막아요. 경로가 있으면 spawn 전에 게이트를 통과해야 해요. 제안서를 «쓰는» 카드(`proposal-<slug>`)는 면제예요.
2. **Issue 등록**: Tank 래퍼 `create` 본문에 `PROPOSAL-*.md` 인용이 있으면 게이트를 통과해야 해요(`ft-proposal-register.sh` 도 같은 도구를 써요).
3. **인터뷰**: `AskUserQuestion` 앞에 훅을 둬요. 질문·선택지에 「제안서」 또는 `PROPOSAL-` 이 있는데 `slack.com/archives/` 링크가 없으면 막아요. 오빠가 원문 스레드를 열 수 있어야 인터뷰가 떠요.

**이미 구현된 건 (A안)**:
- 7건은 R76(«승인 — 판정 N» 기록 발행)으로 슬랙에 올려 오빠가 원문을 보게 해요.
- 컨펌 기록이 0인 2건(rag-document-read · loom-rag-embed-scope)의 진행 카드 4장은 오빠가 원문을 본 판정이 생길 때까지 멈춰요. 4장은 `loom-api-r3d-document-get` · `loom-1016-1a` · `loom-1016-1b` · `loom-1020-5a` 예요.
