> 골 원문(GOAL-harness.md 복붙):
> 내부 하네스, 내부 스킬스를 모니터하고 요청을 사용자에게 받아 해당 부분 바로 확인 검토하고. 실제 하네스와 스킬스를 업그레이드하고 레포에 커밋 푸시하며 전 환경에 물리적 컴퓨팅 환경에도 설치하도록 배포 발행(슬랙) 수신해 반영되 업그레이드.
> 하네스 스킬 관리 오케는 메인오케들과 위성오케들에게 개선요청을 직접받아 등록관리하고 사용자와 협의해 개선하는 축도 필요함.
> 메인 하네스를 유니크하게 머신들에 완전히 독립 배분해 운용하는것.
> 정말 많은 양의 이슈와 테스트, 그리고 큰 병렬적인 메인 플랜(메인 기획)을 얼마나 잘 수행해내느냐에 핵심이 달려 있는 거예요. 지금 이 골(Goal)들은 그 세부 항목들을 다 잘 처리해서, 결국엔 그 루트인 큰일을 얼마나 별개로 쪼개서 동시에 아주 잘 해결하느냐에 달려 있는 거죠. 이게 기획에 반영되어야 해요.
> 골의 축: 표 A(모니터·오빠 요청 → Issue → 검토) · 표 B(오케 개선요청 접수·협의) · 원문 7(많은 이슈를 쪼개 동시에) — 닫는 증거 = DA APPROVE(조각 간 충돌만) + 오빠 「맞다」. 건드리는 정본은 확정된 P1~P10·MERGED — **오빠 새 지시가 앞 확정값을 바꾸는 자리는 «정정 후보»로 표시하고 오빠 질문으로 올린다**(arch 가 임의로 뒤집지 않는다).

## 할 일 (문서 1장 · `SPEC-github-issue-driven-20261006.md` · ≤200줄 · 구현 0)
1. **입력 경로 4종 → Issue 일원화**: ①오빠 임의 기획 세션(임시 마스터·실험 후 정리본을 issue-manager 에 넘김) ②세션 에이전트 직접 등록 ③오빠가 GitHub 에서 직접 등록(버그) ④사내 멤버 GitHub 버그 확인 요청(신규 입력). 경로마다 «누가·어떤 템플릿·어떤 라벨로 등록 → 누가 접수 검사»를 한 표로. P1 Issue 체계·P3 §1·P5 큐 입력·P10 와 연결.
2. **issue-manager 완주 범위**: 오빠 「아무도 아무것도 안 해도 0」 = 시험·완성·정본화 문서·워크트리/브랜치 정리까지 매니저가 끝낸다. **P10 확정값(루프 책임·정렬=사건만·시간 트리거 0·size:small 만 직접·메인 Issue close=소유 오케)과 부딪히는 자리**, **브랜치 삭제 HIL 규칙(오빠 확정 유지)과 부딪히는 자리**를 «정정 후보»로 표시한다 — 「아무도 안 해도」가 사건 없이 도는 자율 구동인지는 오빠 질문으로.
3. **Issue 생애 1줄기**: 등록 → 접수 검사 → 분류·우선순위 → 배분/직접 → 시험 → 완성 → 정본화 문서 → 워크트리·브랜치 정리(삭제는 HIL 유지 · 보존/정리 후보 목록만) → close. P8 단계 10~12·P7 시험 묶음과 어디서 이어지나.
4. **원문 7 기여**: 많은 Issue 를 쪼개 동시에 — 병렬 상한·큐·랜딩 수렴과 이 조각이 충돌하지 않는지 1표.
5. **충돌 표 + 오빠 질문 ≤3**(추천 첫째) · 구현 후보 목록(지금 0) · 머리 1줄 「핵심 한 줄 기여」 + 건드리는 정본 · 전제 조각 두 줄 · [사실]/[제안]/[추측] 표기. 팀 구성에 tester·checker·bts·poller 칸 유지.
