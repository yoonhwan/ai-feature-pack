## §3 HOLD-M1 — 원격 게시 성공과 로컬 상태 사이의 불확정 구간

근거: 설계 69행은 chat.postMessage 뒤 파일 업로드를 수행하고, 70행은 PDF 실패 시 ts와 pdf:null을 저장해 다음 실행에서 PDF만 재시도합니다. 정상 응답을 받은 뿌리 글 뒤 PDF API가 명확히 실패하고 상태 저장까지 성공한 경우에는 이 규칙으로 재게시를 막을 수 있습니다.

그러나 재사용 api_call은 HTTP 응답 읽기/JSON 파싱 오류를 MirrorError로 바꿉니다(mirror_lib.py:44–58). post는 그 응답의 ts를 받아야 반환합니다(:79–83). 따라서 기존 설계와 기존 코드만으로 다음 반례가 성립합니다.

1. 날짜 D의 상태 항목이 없는 상태에서 chat.postMessage를 호출합니다.
2. Slack은 뿌리 글을 생성했지만 응답 연결이 끊기거나 응답이 정상 JSON으로 전달되지 않습니다.
3. api_call은 MirrorError를 내고 post는 ts를 돌려주지 않습니다. 설계 70행의 pdf:null 상태를 쓸 ts가 없습니다.
4. 다음 실행은 D의 상태가 없으므로 뿌리 글을 다시 게시합니다. 같은 날짜 뿌리 글 두 개가 됩니다.

이는 임의의 새 운영 모드가 아니라 재사용 API의 이미 명시된 네트워크 오류 경로이며, 발주의 재게시 0 조건에 직접 해당합니다. 설계 92행의 최종 상태 기록 순서 또한 원격 성공 직후 로컬 기록 실패를 해결하지 않습니다. 원격 성공과 로컬 저장을 원자적으로 묶을 수 있다고 가정하면 안 됩니다.

고칠 곳: 설계 §5(69–70행), §8 실행 순서(92행), §9 게시 시험(105행), publish 카드의 상태 계약. 뿌리 글 호출 전 영속적인 발행 의도를 남기고, 성공 ts는 PDF 단계 전에 영속화하도록 계약을 명시하세요. 응답 유실/ts 저장 실패 시에는 원격 식별자로 기존 글을 확인·복구하거나, 불명 상태를 ERROR로 남겨 자동 뿌리 재게시를 금지하는 등 한 가지 복구 정책을 고정해야 합니다. pdf:null은 건너뜀 대상이 아니라 기존 ts로 PDF를 재시도하는 미완료 상태라는 우선순위도 명시하세요.

교정 수락 시험: 가짜 Slack이 글 생성 후 응답을 유실한 경우, 뿌리 성공 뒤 상태 기록 실패, 정상 ts 영속화 뒤 PDF 실패를 각각 주입하고 다음 실행의 뿌리 게시 추가 횟수가 0인지 확인합니다. 불명 상태를 차단하는 정책이면 오류와 복구 필요성이 보이는지도 확인합니다. 실제 Slack 시험은 이 DA에서 요청하지 않습니다.
