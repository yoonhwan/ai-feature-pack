## 2. 원인

1. `keeper_report.notify` 는 그 팀 `seats-<팀>.json` 의 `_master` 한 곳만 본다. 빈칸이면 `rc = "_master 없음"` 으로 실패한다. 다른 받는 곳이 없다.
2. 실패하면 `state["sent"]` 열쇠를 쓰지 않는다. `keeper_settle.alert` 도 «전송 실패 = 지문 미소비» 라 `alerts` 지문을 쓰지 않는다. 그래서 같은 [긴급] 을 다음 바퀴에 또 시도하고 `판정 불가` 줄을 또 찍는다.
4. 7초를 넘겨 rc None 이 된 보내기를 «실패» 로 본다. 적재는 이미 끝났는데 지문을 쓰지 않고 재시도해서 같은 글이 2통 들어간다.
5. 명부 자리를 `seats-<팀>.json` 한 꼴로만 찾는다. v65 는 `seats.json` 이라 팀장이 있어도 «_master 없음» 이 된다(오늘 360줄).
3. 보내기는 통마다 7초 + 재시도 1(최대 14초)이고 바퀴 안 통 수에 상한이 없다. 받는 좌석이 바쁘면 한 팀이 바퀴(60초 상한)를 다 쓴다.

### 3.1 도착 확인의 경계 (r3 · DA#11 반례 반영)

반례: send 시작 01:10:16.100 → 적재 01:10:16.200 → 장부 `ts` 는 초 단위 01:10:16. «send 시작 뒤 줄» 로 고르면 시작보다 이른 값으로 보여 실제 도착을 버린다. 초로 잘라 `>` 로 비교해도 같은 초는 빠진다. `>=` 로 바꾸면 같은 초에 먼저 있던 같은 글을 이번 도착으로 센다. 그래서 시각을 버리고 seq 로 가른다.

| # | 규칙 |
|---|---|
| 7-1 | 경계 잡기: send 를 부르기 바로 전에 장부 끝 200줄을 읽는다. 그중 정수 seq 의 최댓값이 경계다. seq 없는 줄은 건너뛴다 |
| 7-2 | 경계는 통마다 따로 잡는다. 바퀴 시작에 한 번 잡지 않는다(한 바퀴 3통이 같은 본문 첫 줄일 수 있다) |
| 7-3 | 판정: send 뒤 장부 끝 200줄을 다시 읽는다. seq 가 경계보다 큰 줄만 본다. 그중 from · to · 본문 첫 줄이 같은 줄이 1개 이상이면 도착이다 |
| 7-4 | 경계를 못 잡음(장부 없음 · 못 읽음 · 끝 200줄에 seq 줄 0): send 는 그대로 한다. rc 0 이면 성공이다. rc ≠ 0 또는 초과면 실패 지문 + `판정 불가 … 도착 판독 불가` 1줄이다 |
| 7-5 | 창 밖: send 뒤 읽은 200줄의 가장 작은 seq 가 경계 + 1 보다 크고 맞는 줄이 0 이면 그 사이 줄을 못 본 것이다. «없음» 이 아니라 `도착 판독 불가` 로 적는다(실패 지문은 같음) |
| 7-6 | rc 0 인 send 는 장부를 읽지 않는다(경계 읽기 1회만 든다) |

- seq 를 고른 까닭: 장부의 seq 는 적재 때 붙고 줄 순서대로 커진다(§1 실측 · 거꾸로 간 곳 0). byte offset 은 장부가 잘리거나 보관본으로 넘어가면 틀어진다(BYZ comm 폴더에 `mailbox.archive-<날짜>.jsonl` 이 있다).
- 드는 값: 통마다 장부 끝 200줄 읽기 1회(파일 끝에서 읽음 · 바퀴 3통 상한이라 바퀴당 3회까지).
- 남는 경계: 7초 안에 장부가 200줄 넘게 늘면 7-5 로 `도착 판독 불가` 가 된다. 그 글은 실패 지문으로 다음 날 1회 다시 간다(같은 글 2통이 될 수 있다 · 실측 사례 0).
- p2 설계(`DESIGN-p2-launch-failed-no-park-rest-20261116.md`)의 «실패하면 다음 바퀴 재시도» 문장은 이 카드가 착지하면 «그날 1회» 로 읽는다. 인수 때 두 문서를 같이 본다.

- 3번은 팀장 기준(5347 «실패도 하루 1회 지문 · 같은 지문 재시도 0»)을 그대로 따랐다. 치르는 값: 받는 좌석이 잠깐 바빠서 실패한 [긴급] 도 그날은 다시 가지 않는다. 그 판정은 keeper 로그와 `undelivered` 장부에 남고 다음 날 1회 다시 간다. DA 에게 묻는다(Q1).
- 팀장을 다시 세우면(`_master` 채움) 그 팀의 실패 지문을 지우지 않는다. 다음 날 1회 재시도가 새 팀장에게 간다. 바로 받게 하려면 사람이 `state["sent"]` 의 그 팀 `fail|` 값을 지운다(운영 손 · 문서 1줄).
- `full_alert` 의 받는 곳(팀 + harness 두 곳)은 손대지 않는다.
- 8번 함수의 자리 = `adapters/pi/launch_roster.py`(이미 명부 경로를 만드는 곳 · 55줄). 같은 한 꼴 찾기가 남은 곳(이 카드 밖 · 후속 1장): `core/execution.py` 133 · `tools/goal_close.py` 44 · `adapters/pi/full_alert.py` 34 · `adapters/pi/launch_plan.py` 80 · `adapters/slack/channels.py` 52 · 58 · `adapters/slack/wiring.py` 222 · 1.x `ft-team-tidy`(harness 몫).
- 7번으로 «7초 초과 = 실패» 가 줄어든다. 그래도 남는 진짜 실패(적재 전 실패)는 3번대로 그날 1회다.
