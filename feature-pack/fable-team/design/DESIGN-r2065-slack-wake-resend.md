## 2. 원인

1. `wiring.wake()`(52~61줄)는 send 를 1회 부른다. 실패하면 wire 장부에 rc 줄 1개를 쓰고 끝난다. 다시 보내는 곳이 없다.
2. 실패 뒤 하는 일은 `alert(reason="깨움 실패")` 1통이다(87~88줄 → 136줄). 이 알림도 같은 `wake()` 로 같은 좌석에 간다. 좌석이 막혀 있으면 같이 실패한다(00:34:43 rc 3).
3. 다시 깨우는 길은 수신기 재기동 때의 `recovered()`(90~109줄)뿐이다. 그것도 «알림이 아닌 wake 줄이 1개라도 있으면 깨움 0» 이다(93줄). rc 를 보지 않으므로 실패한 wake 도 «넘긴 글» 로 센다.
4. rc ≠ 0 일 때 send 의 출력을 기록하지 않는다. 시간 초과만 `why` 칸이 있다. rc 3 은 왜 거부됐는지 남지 않는다.
5. `landed()`(63~76줄)는 장부 끝 200줄에서 본문 첫 줄만 맞춘다. 받는 곳도 seq 도 보지 않는다. 다시 보내면 첫 줄이 같으므로 앞 시도의 줄과 새 시도의 줄을 가르지 못한다(행 E 의 DA 반례와 같은 꼴).

## 3. 고침

| # | 자리 | 규칙 |
|---|---|---|
| 1 | 다시 보낼 글 | 그 command 의 «알림이 아닌» wake 줄 중 마지막 줄이 rc ≠ 0 이고 적재가 «있음» 이 아닌 것. 알림 wake(`[Slack] 알림 …`)는 다시 보내지 않는다 |
| 2 | 언제 | 유휴 회차(`receive.pass_idle`)에서 본다. 한 유휴 회차에 1통까지. 같은 command 는 앞 시도에서 60초가 지난 뒤에만 다시 보낸다 |
| 3 | 몇 번 | 처음 시도를 넣어 3회까지. 3회째도 실패하면 그 command 는 멈춘다(4회째 0) |
| 4 | 본문 | `recovered()` 와 같은 길로 다시 만든다: route 장부의 그 command dispatched 행 + `router.context(key)` → `deliver()`. 본문 첫 줄은 그대로 두고 끝에 `재전송 <n>/3` 1줄을 붙인다 |
| 5 | 보내기 전 늦은 적재 확인 | 앞 시도의 경계(6번) 뒤에 그 글이 장부에 있으면 보내지 않는다. wake 줄 `rc 0 · why 늦은 적재 확인` 1줄을 쓰고 끝낸다 |
| 6 | 적재 판독 | 행 E 설계 r3 §3.1 과 같은 규칙이다. send 바로 전에 장부 끝 200줄의 최대 seq 를 경계로 잡아 wake 줄에 `seq0` 칸으로 적는다. 판정은 seq 가 경계보다 큰 줄 가운데 «받는 곳 · 본문 첫 줄» 이 같은 줄이다. 시각은 쓰지 않는다. 경계를 못 잡으면 `적재 판정 불가` 다 |
| 7 | 실패 사유 기록 | rc ≠ 0 이면 send 출력(stdout + stderr)의 마지막 줄 앞 160자를 wake 줄 `out` 칸에 적는다. 시간 초과면 그때까지 잡힌 출력을 적는다 |
| 8 | 3회 실패 뒤 | `[긴급] Slack 글 깨움 3회 실패 · thread <ts> · command <command> · 받는 곳 <좌석> · 마지막 rc <값> <out>` 을 harness `_master` 에게 1통. command 마다 1회다(wire 장부 `alert` 줄 `why 깨움 3회 실패` 로 dedup). 받는 곳 찾기는 행 E 규칙 8 의 명부 함수를 쓴다. 이 1통도 실패하면 `listen.log` 1줄만 남긴다(재시도 0) |
| 9 | `recovered()` | 93줄 조건을 «알림이 아닌 wake 줄 중 rc 0 이거나 적재 있음인 줄이 있으면 깨움 0» 으로 바꾼다. 재기동 때도 1~3번 셈을 잇는다(시도 수 = wire 장부의 그 command 비알림 wake 줄 수) |
| 10 | 기억 | 다시 보낼 후보는 수신기 메모리의 표 1개에 둔다(`wake()` 가 실패할 때 넣고 성공 · 멈춤 때 뺀다). 재기동 때 wire 장부를 1회 읽어 다시 채운다. 유휴 회차마다 wire 장부를 읽지 않는다 |

- 2번은 `pass_idle` 의 지금 약속 «모델 호출 · 좌석 깨움 · 기록 증가 0»(167줄 주석 · r1938 stat 서명 건너뜀)을 바꾼다. 후보 표가 비어 있으면 지금과 같다(읽기 · 쓰기 · 깨움 0). 후보가 있을 때만 깨움 1통과 wire 줄 1개가 생긴다. DA 에게 묻는다(Q1).
- 유휴 회차는 Slack 소켓 읽기 사이 1초마다 온다(`socket.py` 133~139줄). 재전송 1통은 그 읽기를 25초까지 막는다. 처음 깨움도 지금 같은 값을 치른다. 그래서 회차당 1통 · 60초 간격으로 묶었다.
- 5번이 필요한 까닭: 25초에 잘린 send 는 자식 프로세스가 뒤늦게 적재를 끝낼 수 있다. 그때 다시 보내면 같은 글이 2통 된다.
- 치르는 값: 장부 창(200줄)을 넘겨 `적재 판정 불가` 가 되면 다시 보낸다. 같은 글이 2통 될 수 있다. 오빠 글을 놓치는 쪽보다 낫다고 봤다. 끝줄 `재전송 <n>/3` 과 command 로 desk 가 같은 글임을 안다(Q3).
- rc 3(가드 거부)도 1번에 든다. 거부 사유가 그대로면 3회 모두 실패하고 8번 [긴급] 으로 간다. 7번 `out` 칸이 생긴 뒤 사유를 보고 갈래를 나눌지 정한다(Q2).
- 실패 뒤의 `[Slack] 알림 깨움 실패`(87~88줄)는 그대로 둔다. 처음 실패 1회에만 간다. 재전송 실패 때는 보내지 않는다(같은 좌석에 같은 실패를 겹치지 않는다).
