## 2. 원인

1. `wiring.wake()`(52~61줄)는 send 를 1회 부른다. 실패하면 wire 장부에 rc 줄 1개를 쓰고 끝난다. 다시 보내는 곳이 없다.
2. 실패 뒤 하는 일은 `alert(reason="깨움 실패")` 1통이다(87~88줄 → 136줄). 이 알림도 같은 `wake()` 로 같은 좌석에 간다. 좌석이 막혀 있으면 같이 실패한다(00:34:43 rc 3).
3. 다시 깨우는 길은 수신기 재기동 때의 `recovered()`(90~109줄)뿐이다. 그것도 «알림이 아닌 wake 줄이 1개라도 있으면 깨움 0» 이다(93줄). rc 를 보지 않으므로 실패한 wake 도 «넘긴 글» 로 센다.
4. rc ≠ 0 일 때 send 의 출력을 기록하지 않는다. 시간 초과만 `why` 칸이 있다. rc 3 은 왜 거부됐는지 남지 않는다.
5. `landed()`(63~76줄)는 장부 끝 200줄에서 본문 첫 줄만 맞춘다. 받는 곳도 seq 도 보지 않는다. 다시 보내면 첫 줄이 같으므로 앞 시도의 줄과 새 시도의 줄을 가르지 못한다(행 E 의 DA 반례와 같은 꼴).

## 8. 회귀 고침 pG2 (2026-11-16 · aifp-ft-arch-pi#19 · 원문 = `.fable-team/state/team-main/aifp-ft/orders/DESIGN-pG2-slack-wake-restore-boundary-20261116.md`)

3번 고침(위 §3) 그대로 2.0.66 으로 설치한 뒤, 수신기 재기동에서 이 판이 만든 것이 아닌 옛 실패 줄이 다시 나갔다. BYZ `wire.jsonl` 실측 = 재기동 03:48:01 뒤 36줄(wake rc 0 18 · rc 3 적재 없음 3 · issue 15) · 후보 18 command 의 마지막 깨움 줄은 11-13 12:24 ~ 11-16 01:06 · 그 줄들에 `seq0`·`landed` 칸이 없다 = 모두 이 고침 앞 판이 쓴 줄이다.

원인 2개.

1. §3 10번 «재기동 때 wire 장부 1회 읽어 다시 채운다» 에 «어느 줄까지가 이 판의 줄인가» 경계가 없었다. `_restore` 는 파일 전체의 마지막 비알림 wake 줄을 본다. 그래서 55시간 전 실패도 후보가 된다.
2. 재전송이 `deliver()` 를 타는데 `deliver()` 는 «새 업무» 면 `record_issue()` 를 부른다. issues 입구에서 그 command 가 이미 비워졌으면 `lookup` 이 None 이라 새 접수가 된다(실측 issue 15줄).

### G12 재기동 복원 경계

`_restore` 가 후보로 넣는 command = G1 조건(위 §3 1·3번) **그리고** 그 마지막 비알림 깨움 줄이 둘을 모두 채운다.

- (가) 줄에 `seq0` 칸이 있다(값이 null 이어도 칸이 있으면 참). 이 판이 쓴 줄이라는 표식이다. 칸이 없는 줄은 §3 5번(늦은 적재 확인)의 경계가 없으므로 다시 보내지 않는다.
- (나) `0 ≤ 기동 시각 − 그 줄 at ≤ RESTORE_WINDOW`. `RESTORE_WINDOW = 600`(초) · 기동 시각 = `Wiring.__init__` 의 `self.now()` 1회. `at` 을 못 읽으면 창 밖이고, `at` 이 기동 시각보다 뒤여도 창 밖이다.
- 뺀 것이 1건 이상이면 `listen.log` 1줄 = `[재전송] 복원 제외 <N>건 · 경계 칸 없음 <a> · 창 밖 <b>`. 건별 줄 0 · wire 쓰기 0 · [긴급] 0 · 깨움 0.
- 600초의 근거 = 살아 있는 수신기에서 후보 1개가 끝나는 195초(send 상한 25초 × 3 + 간격 60초 × 2)의 3배다. 재기동이 걸리는 시간의 분포를 재서 정한 값이 아니다(알려진 한계).

### G13 재전송은 issues 입구에 쓰지 않는다

`_resend` 가 부르는 `deliver()` 는 `record_issue()` 를 부르지 않는다(`deliver(..., resend=True)`). 처음 `deliver()` 는 `wake()` 앞에서 이미 불렀다. 처음 깨움 길과 `recovered()` 길은 그대로다. 조건 = `kind == route.NEW and not resend` 일 때만 `record_issue()`.

### 알려진 한계 (pG2)

- `RESTORE_WINDOW` 600초는 계산 값이다. 재기동에 걸리는 시간의 분포를 재지 않았다.
- 수신기가 10분 넘게 죽어 있으면 그 앞 실패는 다시 보내지 않는다. 처음 실패 때의 desk 알림(§3 마지막 줄)과 «복원 제외» 줄만 남는다.
- 창 안에서 이미 응대한 command 는 가려내지 못한다. 장부에 «응대 끝» 표식이 없다(실측 = 다시 나간 18 command 의 receive 최신 상태 settled 0).
- 늦은 적재 확인 직후에 앞 시도의 자식 프로세스가 적재하는 경합은 막지 못한다(exactly-once 보증 아님).
