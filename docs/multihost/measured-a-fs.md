## 1. 항목별 표

### 1-1. 파일 `os.replace` (tmp 쓰기+fsync → replace) — 1000회

| 명령 | 결과 수치 | 판정 |
|---|---|---|
| `write(tmp, 4KB+fsync)` → `os.replace(tmp, target)` ×1000, 관찰자 30,068회 샘플 | missing 0 · empty 0 · torn 0 · 예외 0 · 회당 2,954 µs(fsync 포함) | **가정 확인** — 교체는 원자적으로 보인다. 관찰자는 «이전 내용» 또는 «새 내용»만 봤다 |

### 1-2. `link()` — 200회 + link→rename 발행 1000회

| 명령 | 결과 수치 | 판정 |
|---|---|---|
| `os.link(tmp, existing_target)` ×200 | EEXIST 200 / 성공 0 / 기타오류 0 | **가정 확인(단, 제약)** — `link` 는 «없는 이름 만들기»만 원자적이다. **덮어쓰기 불가** → 「link 로 교체」는 성립하지 않고 `link`+`rename` 2단이 필요 |
| `write(tmp,fsync)` → `link(tmp,new)` → `replace(new,target)` → `unlink(tmp)` ×1000, 관찰자 69,851 샘플 | missing 0 · empty 0 · torn 0 · 예외 0 | **가정 확인** |

### 1-3. 디렉터리 단위 rename — 200회 + swap 1000회

| 명령 | 결과 수치 | 판정 |
|---|---|---|
| `os.replace(src_dir, non_empty_target_dir)` ×200 (src=파일 5개) | ENOTEMPTY 200 / 성공 0 / 기타 0 | **가정 부분 반증** — 디렉터리 rename 자체는 원자적이지만 **«비어 있지 않은 대상 위로의 교체»는 APFS 가 거부**한다. 디렉터리를 «덮어쓰는» 원자 교체는 이 FS 에 없다 |
| 실제 swap: `rename(target→trash)` → `rename(new→target)` ×1000 (관찰자 106,486 + 누락 226,949 = 333,435 관측) | target 부재 관측 **226,949 (68.1%)** · 파일 수 ≠5 관측 **34 / 106,486 샘플 (0.03%)** | **가정 반증** — 2단 swap 은 창이 «거의 항상» 보인다(68%). 게다가 5개 중 4개만 보인 목록이 관측됨 = **readdir 스냅샷도 원자적이지 않다** |
| (집중 재확인) 같은 swap 1000회 · 관찰자 52,449 샘플 | 부재 22,462 · 파일수 5 → 52,448 · **파일수 4 → 1** | 부분 목록 1건 재현 — 1/52,449 (0.002%). 두 실행을 합치면 **부분 목록 35건 / 158,935 샘플 ≈ 0.02%**. 희귀하지만 0 아님 |

⇒ 디렉터리 «1회 rename» 으로 바꾸는 설계(§3.1 보관함 디렉터리 단위)는 **새 이름으로만** 성립한다.
«같은 이름 유지 + 내용 교체»가 필요한 자리는 심링크 교체(`symlink`+`replace`)나 파일 단위 `os.replace` 로 내려가야 한다.

### 1-4. 디렉터리 fsync — 가부와 비용 (각 300회 중앙값)

| 명령 | 결과 수치 | 판정 |
|---|---|---|
| `fd=os.open(dir,O_RDONLY)`; `os.fsync(fd)` | 성공 (errno 없음) | **가정 확인** — APFS 에서 디렉터리 fsync 호출 가능 |
| 같은 fd 에 `fcntl(F_FULLFSYNC)` | 성공 | 호출 가능(비용은 아래) |
| 디렉터리 fsync 만 | median **22.9 µs** · p95 71 µs · mean 27.5 µs | **가정 확인** — 싸다. 파일 1건당 붙여도 부담 없음(≈ +0.02 ms) |
| 파일 fsync 만(256B) | median 698.9 µs · p95 2,250 µs · mean 1,061 µs | — |
| 파일 fsync + 디렉터리 fsync | median 367.6 µs · p95 2,531 µs · mean 715 µs | **주의** — 파일 fsync 단독보다 «작게» 나왔다. 회차 간 분산이 커서(디스크 배경 flush) **중앙값 크기 비교는 믿지 말 것**, 자릿수만 읽는다 |
| 파일 `F_FULLFSYNC` 만 | median **7,702 µs** · p95 **50,130 µs** · mean 15,976 µs | **비싸다** — 파일 1건당 7.7 ms, 꼬리 50 ms. 대량 이관·재작성 경로에 걸면 안 된다 |

⇒ durabilty 를 «프로세스 종료»까지로 잡는 한(§3.6) 디렉터리 fsync 는 값싼 보험(23 µs)이다.
`F_FULLFSYNC` 는 전원 차단 급에서만 의미가 있고, 그건 이번 실측 범위 밖이며 비용이 3자릿수 크다.

### 1-5. 동시 `recv` 이중 소비 — 100 라운드 × 2프로세스

방법: 격리 `FT_MBOX_DIR` 에 행 1개를 심고, **실제** `feature-pack/fable-team/skill/scripts/ft-mbox.py recv <me> --all` 을 2프로세스로 게이트 동기화 후 동시 실행. 두 출력에 같은 seq 가 나오면 «이중 소비».

| 명령 | 결과 수치 | 판정 |
|---|---|---|
| `ft-mbox.py recv nano-probe --all` ×2 동시 ×100 라운드 | **이중 소비 15 / 100 = 15.0%** · 단일 소비 85 · **행 유실 0** | **가정 반증** — 원자성 약속(§111) 중 «중복 0» 은 동시 recv 에서 성립하지 않는다. 대신 «유실 0» 은 지켜진다(둘 다 읽고 둘 다 소비 → 행은 그대로 사라짐) |

원인(코드 확인, `ft-mbox.py` L585–615): `recv` 는 **읽기 잠금**과 **소비 잠금**을 따로 잡는다 —
`_rows_for()` 로 읽고(락 해제) → 출력 → `_consume()` 으로 다시 잠근다. 그 사이가 열린 창이다.
⇒ 같은 발주가 두 좌석/두 프로세스에 «각각» 도착할 수 있다(15%).
계약을 지키려면 **읽기와 소비를 한 잠금 안에서**(읽은 seq 를 그 자리에서 제거하고 반환) 해야 한다.

### 1-6. JSONL 재작성 + SIGKILL — 500행 파일, 밴드별 100회

두 구현을 비교: **비원자**(현행 `_save` 와 같은 꼴 = `open(path,'w')` 후 줄마다 write) vs **원자**(같은 내용을 `.tmp` 에 다 쓰고 fsync → `os.replace`). 킬 시점은 자식이 남기는 단계 표식(`armed`→`truncated`/`pre-replace`→`done`/`post-replace`)으로 맞췄다(창 실측: 비원자 6.2 ms, 원자 9.6 ms).

| 구현 · 킬 밴드 | 결과 수치 | 판정 |
|---|---|---|
| 비원자 · 창 안 균등(0~3.7 ms) | torn 51 / 100 · 보존행 median 168 (min 0, max 487, 총 500) | **가정 반증** — truncate 후 쓰기 중 종료 = **다른 좌석 행이 사라진다** |
| 비원자 · `truncated` 직후(0~300 µs) | torn **100 / 100** · 보존행 median **58** (min 1, max 408) | **가정 반증** — 이 밴드는 «항상» 잃는다. 최악 408행 소실 |
| 원자 · 창 안 균등(0~9.6 ms) | torn **0 / 100** — old 전량 보존 30 · new 전량 70 | **가정 확인** |
| 원자 · `os.replace` 직전·직후(0~400 µs, pre-replace 도달 후 킬) | torn **0 / 100** — new 전량 99 · old 전량 1 | **가정 확인** — 대체 직전/직후 어느 쪽에서 죽어도 파일은 «이전 완본» 또는 «새 완본», 부분 상태 0 |

⇒ DESIGN §N1 이 이미 적은 `existing_save_fault_unrelated_B_lost=True` 는 **실측으로 재현**됐다(비원자 100%).
`.tmp` 완성 + `os.replace` 로 바꾸면 200/200 라운드에서 부분 상태가 0 이다.

## 3. 설계에 바로 걸리는 것 (근거 있는 것만)

1. **`_save` 는 `.tmp`+`os.replace` 로 바꿔야 한다** — 현행 truncate 재작성은 킬 한 번에 다른 좌석 행을 지운다(실측 100%). 우편함 잠금 안에서 `.tmp` 완성 → replace.
2. **`recv` 는 읽기·소비를 한 잠금으로 합쳐야 한다** — 지금은 15% 확률로 같은 행을 두 프로세스가 읽는다. 2단이면 F3(«같은 좌석 recv 2개 동시 → 각 mid 한 쪽만»)이 성립하지 않는다.
3. **디렉터리 «같은 이름 교체» 를 전제하지 말 것** — APFS 는 비어 있지 않은 디렉터리 위로 rename 을 거부한다. 보관함/처분 이동은 «새 이름으로 1회 rename» 이면 원자적이지만, 고정 경로를 유지해야 하는 자리는 심링크 교체나 파일 단위 replace 로 내려야 한다. 2단 swap 은 68% 확률로 부재 창을 노출한다.
4. **디렉터리 fsync 는 값싼 보험(23 µs)** — 프로세스 종료 내구성 계약(§3.6)에 굳이 필요하진 않지만 붙여도 비용이 사실상 0 이다. `F_FULLFSYNC`(7.7 ms / p95 50 ms)는 대량 경로에 넣지 말 것.

## 4. 원자료

- 스크립트 stdout 전문: `/tmp/a-fs-full.txt` (실행 로그, 이 표의 모든 수치 출처)
- 동시 recv 라운드별 상세(어느 프로세스가 잡았나·잔여 바이트): 실행 시 `--keep` 으로 남는 `WORK_DIR` 아래 `recv/details.tsv`
