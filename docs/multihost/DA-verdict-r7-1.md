L번호는 이 커밋의 설계 문서 1-based 줄이다. 헌장·r7·직전 r6-1 판정을 대조했고 운영 UX 문서는 계획 계약 L26–27만 확인했다. 제품 소스와 헌장은 r6 기준 이후 불변이다.

수용한 전제는 유지한다: 장애 범위는 프로세스 종료, UNKNOWN은 사람 처분, evict 미처리분 자동 이관 없음, 새 세대 쌍의 큐 커밋 순서. 기존 R2의 target 검사와 R3의 evict 완료 전 차단은 국소적으로 해소됐다. 아래는 새 isolate 및 R4 재계획/수명의 경계다.

질문 1: PASS — 단일 모드 불변 L16, tmuxc 명령 단위 원격 실행 §7, 전/후 비교 P2 L298. 이전 PASS 유지.

질문 3: HOLD — 로컬 경로 범위 L64, JSONL 사전 격리 L87, target live/host 상태/evict phase 검사 L225는 기존 반례에 대응한다. 하지만 새 isolate가 원격에서 허브로 link한다는 L269는 구현 가능한 원자 연산이 아니며, JSONL 삭제 중단의 보존 계약도 빠졌다(N1).

N1 — 격리의 위치와 원자 단위를 분리해야 한다. L269는 새 호스트와 옛 호스트 각각의 mailbox.jsonl 행을 그 호스트 mailbox.lock 안에서 «허브 quarantine에 link → JSONL에서 삭제»하고, 원격은 K2 inbox isolate로 실행한다고 한다. 원격 디스크와 허브 디스크 사이에는 hard link를 만들 수 없다. 이 설계는 공유 파일시스템 대신 호스트 로컬 파일과 SSH를 택했다. 원격이 본문을 stdout으로 보내고 바로 삭제하는 것으로 바꾸면, 응답 단절 때 허브에 저장되지 않은 행을 잃는다. 허브 저장 확인을 기다리면 잠금 안 네트워크 금지(L133)와 저장 확인 프로토콜이 다시 필요하다. K2 isolate 동사가 표 L232에 추가됐다는 사실만으로 이 경계가 해결되지는 않는다.
가장 작은 선택은 원격 행을 그 원격의 로컬 격리 파일로 옮기고 허브에는 잔재 목록만 보여 주는 것이다. 이는 수용한 «자동 이관 없음»과 맞는다. 중앙 보관을 꼭 원한다면 단절 시 어느 쪽이 원본을 보유하고 언제 삭제 가능한지를 별도로 정의해야 한다. 이번 판정은 중앙 전송 기능을 요구하지 않는다.
또 허브 로컬 격리도 JSONL 한 행은 파일 하나가 아니므로 삭제 시 나머지 행 전체를 재작성한다. 현재 `_save`는 open("w") 후 행을 쓰며(ft-mbox.py L309–313), 프로세스가 truncate 뒤 중단되면 격리 대상 A를 quarantine에 먼저 보관했어도 다른 좌석의 B는 잃는다. 새 isolate가 기존 헬퍼를 쓰면 이 반례가 생긴다. hosts/seats만이 아니라 isolate의 JSONL 게시도 mailbox.lock 아래 임시 파일 완성→원자 교체로 정하고, unrelated 행 보존을 검사해야 한다. «link 먼저»만으로는 A 외의 행까지 안전하다는 결론이 나오지 않는다. F13은 원격 격리 위치 및 JSONL 재작성 중단도 포함해야 한다.

질문 4: PASS — target 신규 mid와 기존 DUP를 분리한 L225, K2 isolate/list 표 L232 및 P1 L297의 기존 키/동사/실제 포워딩 요청 검증은 설계 수준에서 유지한다. isolate의 데이터 이동 문제는 N1이며 이를 해결하려고 K1의 revoked 차단을 우회해서는 안 된다.

질문 5: HOLD — evict phase/원자 교체/재실행/EVICT_INCOMPLETE(L265–268)는 r6의 부분 evict를 완료로 오인하는 반례에 대응한다. 그러나 계획 파일에 고정한 new_mid가 재계획에서는 바뀌고(N2), 고정한 같은 mid도 완료 묘비보다 오래 재실행할 수 있다(N3).

N2 — enqueue 후 중단과 LATE_CHANGED를 결합하면 다시 두 통이다. L270의 순서대로 P1 계획은 late=false, new_mid=n1을 고정 → 실행이 n1 enqueue 성공 직후 disposed 이동 전에 종료 → 뒤늦은 원 배달 성공으로 원본 quarantine 항목에 .late가 생김(L98) → P1 재실행은 LATE_CHANGED로 멈추고 문서대로 재계획 → P2는 이때 새 new_mid=n2를 생성 → 실행이 n2도 enqueue한다. 원본은 아직 미처분이므로 ALREADY가 아니고 n1과 n2가 달라 DUP도 아니다. 이는 임의의 두 번째 메시지를 보내라는 요구가 아니라, 문서가 지시한 오류 복구/재계획 경로를 따른 반례다. 운영 UX L27도 상태 변화 시 재계획을 지시할 뿐 기존 실행의 전송 ID를 보존하지 않는다.
고정 단위는 계획 파일 한 장을 넘어 원본 mid의 진행 중 처분이어야 한다. 첫 side effect 전에 원본 처분과 new_mid를 연결해 기록하고, 늦은 정보 때문에 승인을 다시 받아도 이미 시작한 처분의 ID/전송 결과를 잃지 않아야 한다. 이미 enqueue됐으면 재계획이 같은 전송을 마무리하거나 미확인 상태를 명시해야 하며, 다른 new_mid를 자동 생성해 같은 복구라고 취급하면 안 된다. N2는 F20의 «enqueue 후 종료→같은 계획 재실행»과 «계획 뒤 late 발생→LATE_CHANGED»를 따로 시험하면 놓친다.

N3 — 같은 h 계획도 무기한 재실행할 수 있다는 근거는 없다. n1 enqueue 성공 뒤 원본 quarantine→disposed 전에 종료 → 원본 quarantine은 시간 청소되지 않아 남음(L73) → 14일 뒤 n1의 허브 routed-done과 수신 consumed 묘비는 청소됨 → 같은 계획 재실행은 원본 disposed가 없어 ALREADY가 아니고, n1의 완료 기록도 없어 DUP가 아니다 → n1이 새 outbound에 다시 들어가 새 7일 기한을 얻는다. 그러면 동일 n1이 다시 소비된다. L83의 기한은 삭제된 첫 outbound 인스턴스에 대한 것이지 무기한 남은 처분 계획의 재실행 기한이 아니다. L270과 운영 UX L27의 «같은 h 두 번이면 한 번» 주장은 이 창까지 덮지 못한다.
허용 가능한 최소 선택은 처분 재실행에도 최초 커밋 기준의 불변 기한을 두고, 기한 밖 미확인은 새 전송 없이 사람에게 반환하는 것이다. 또는 원본 처분이 끝날 때까지 필요한 n1 완료 영수증을 보존해도 된다. 무조건적인 영구 로그나 자동 이관을 다시 요구하지 않는다. 어느 선택인지 명시하고 청소기/계획 계약과 맞춰야 한다. 기존 h 실행기가 더 짧은 유효기간을 강제한다면 그 계약을 명시적으로 연결해도 된다.

.late 게시 메모: L98의 현재 canonical 위치 검색은 r6의 quarantine 재생성 문제를 막는 방향이다. 구현에서는 표시가 먼저 생긴 뒤 quarantine→disposed로 이동하는 경우에도 기존 .late가 정본에 연결되고, 이동 직후 중단/ALREADY 재개에서 잃지 않아야 한다. 이 메모는 별도의 새 HOLD를 추가하는 것이 아니라 F20의 «표식 보존»을 실제로 확인할 지점이다.

질문 6: PASS — 허브 단절의 원격 로컬 수신/스풀 L100, 단일 호스트 후퇴 L275·288은 이전 PASS 유지. 프로세스 종료/사람 처분 전제를 되돌리지 않는다.

질문 7: HOLD — 기존 P0/P1/P2/P6의 판단은 각각 L296–298·303 유지. 새 닫는 증거는 N1의 원격/허브 서로 다른 파일시스템 격리와 JSONL 재작성 중단 시 다른 행 보존, N2의 enqueue 후 종료→late 추가→강제 재계획, N3의 14일 완료 청소 뒤 같은 계획 재실행이다. P3 L299의 F13/F19/F20을 단독 성공 사례로만 시험하면 부족하다. EVICT_INCOMPLETE 동안의 새 mid를 quarantine으로 끝내는 L225·267은 기존 R2/R3 요구를 해소한다.

검증 증거: N2/N3는 파일/네트워크 쓰기 없는 메모리 사양 모델이다. 결과는 `late_changed_replan_resend_count=2`, `late_same_plan_mid_is_new_to_dedup=True`였다. 실제 `_save` 함수만 AST로 추출해 open/write를 메모리 스텁으로 바꾸고 truncate 직후 fault를 주입했을 때 `existing_save_fault_unrelated_B_lost=True`였다. 이는 기존 헬퍼를 isolate에 재사용하면 생기는 위험의 증거이며 미구현 isolate가 이미 그 헬퍼를 호출한다는 주장은 아니다. 원격 hard link의 불가능성과 SSH 응답 단절 경계는 정적 설계 검토이며 실제 원격/파일시스템 시험을 하지 않았다.

도구·범위: Serena 문서 검색은 성공했다. ft-mbox.py의 find_symbol/find_referencing_symbols는 `path is ignored`로 거절돼 해당 코드 심볼 범위는 `serena unavailable, grep-based`다. `_save` 정의/참조는 앞서 대조한 실제 소스와 AST로 확인했고, 제품 소스·헌장은 r6 기준 커밋 이후 불변을 git diff로 확인했다. Serena 복구 후 참조 범위 재검증 대상으로 남긴다. 제품 Redis·DOM에 시험 데이터를 쓰지 않았으며 제품 우편함은 발주 수신/최종 회신에만 사용했다. 이번 쓰기는 판정문 한 파일이며 커밋·원격 접속·설치·실제 프로세스 종료·시간 변경 0이다.

checker 확인 대상: isolate의 로컬 격리 위치와 JSONL 원자 교체, 재계획을 넘어서 유지되는 원본 처분/new_mid 연결, 처분 재실행 기한 또는 완료 영수증 청소 조건, 기존 .late의 정본 이동/중단 복구를 확인한다. 수용된 r6 구조를 되돌리지 않고 이 새 경계만 닫을 수 있다.
